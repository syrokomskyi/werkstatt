# Site Kernel Handoff Agent Guide

This file applies to `packages/os/site-kernel-handoff`. Follow the root `AGENTS.md` and `packages/AGENTS.md` first.

## Scope

- This package owns the RFC-0221 internal site handoff surface.
- It validates thin handoff bundles, compares ecosystem versions, diffs consumed capabilities, and owns the forward migrator registry.
- It must not change `client.export`; that external full-fork deliverable remains owned by `@warpgogol/site-kernel-deploy`.
- It owns the Notausgang emergency export and validation commands (`notausgang.export`, `notausgang.validate`).

## Implementation Rules

- Keep migrators forward-only. Never add downgrade migrators.
- Migrators operate on the authored set only, never on generated output.
- Treat `handoff-lock.json` and `handoff-manifest.json` schemas as owned by `@warpgogol/ontology`; import their types/schemas instead of duplicating shapes locally.
- Register only implemented commands. `handoff.pack` is a thin bundle writer. `handoff.absorb` builds the catch-up report, refuses downgrades, then materializes (apply migrators → inject authored set → delegate regen). It never writes when `--report-only` is passed, and it refuses red-tier bundles unless `--force` is given.
- `handoff.absorb` must regenerate derived artifacts by delegating to `build.prepare` / `build.check` — never by copying generated files out of the bundle, and never by `git merge`.
- `handoff.pack` emits a golden `validation/` pack (routes, sitemap hash, llms hashes, scores) from the build output via `validation-pack.ts`; `handoff.absorb --regen` rebuilds it and diffs against the golden one. Keep the captured significant properties in sync with the public outputs (`isGeneratedPublicArtifact`) and the passport scores schema; add new properties to both `buildValidationPack` and `diffValidationPacks`.
- The authored partition (`authored-set.ts`) is Compass-complete: code is classified by `createCompassInventoryEntries`, non-code data by the RFC-0081 generated marker + path rules. When extending it, derive authored-vs-derived from the Compass inventory and the marker; do not invent a parallel classification. Generated public outputs (sitemap/robots/feed/llms/ai/pseo) are matched by filename in `isGeneratedPublicArtifact` — keep it in sync with the `build.prepare` public generators.
- `BOOTSTRAP_CONFIG` (`package.json`, `astro.config.mjs`, `postcss.config.cjs`) is force-included even though these files carry the RFC-0081 generated marker. They are template-synced (RFC-0137), not regenerated by `build.prepare`, so a brand-new app cannot `pnpm install` or build without them. Do not move them to an exclusion rule.
- `tools/kernel.config.ts` and `tools/modules/` are classified by Compass as authored but **should not travel in the bundle** — `kernel.config.ts` references app-local modules that don't exist until `kernel.wire` generates them. These are already excluded by Compass's generated-marker path (the marker is absent, but the file is under `tools/kernel.config.ts` which is not in `PACK_ROOTS` or `ROOT_CONFIG`). If the partition ever picks them up, add an explicit exclusion.
- `handoff.absorb` detects derived-file edits before materializing: if any manifest derived entry has a hash mismatch (edited after packing), it raises a decision record and refuses without `--force`. This check is in `derived-edits.ts` / `reportDerivedEdits`. Bundles currently pack only authored entries (no `derived` kind), so the path is wired but not exercised in the current pack format; it activates if future packs carry derived snapshot entries.
- Keep every relative import in package source on the on-disk `.ts` extension, per RFC-0092.
- **Non-fatal warnings use `logger.warn`, not `logger.info`.** When a catch block logs a non-fatal failure (e.g., baseline failure, push failure, derived-edit detection), use `logger.warn` to distinguish it from informational output. See `sternsystem-sync.ts`, `handoff-absorb.ts`, `mission-materialization-commands.ts` for existing examples.
- **Do not call `logger.success()` with the same text as the `summary` field.** The kernel CLI runner automatically prints the `summary` from `KernelCommandResult` — a `logger.success()` call with the same message produces duplicate output. Use `logger.info()` for intermediate progress updates and let `summary` handle the final result line.
- **Wrap `JSON.parse` in try/catch when reading evidence or manifest files.** Bare `JSON.parse` on file contents produces an unreadable `SyntaxError` when the file is corrupted or truncated. Always wrap with a try/catch that throws a descriptive error including the file name and context (e.g. `[leitstand.propagate] Axiom evidence malformed: evidence-metadata.json is not valid JSON for mission '<id>'.`). See `leitstand-commands.ts` propagate gate (RFC-0629) for the pattern.
- **`commitAndPushBordbuch` must commit `bordbuch/status.generated.yaml` alongside `bordbuch/events.ndjson`.** The generated status file is produced during mission lifecycle steps; if it is not committed, the cache clone stays dirty and the next `mission.validate` emits a warning. Always `git add` both files in the same commit.
- **`commitBordbuchProjections` is non-throwing (RFC-0702).** All `gitExecWithRetry` calls are wrapped in try/catch. Git failures return `{ committed: false, error: "..." }` instead of throwing. `runBordbuchCommit` logs `logger.warn` when `committed === false && error` is set. This ensures `bordbuch.commit` pipeline step never crashes `build.prepare` or `mission.validate`.
- **`mission.validate` distribution reuse path calls `commitBordbuchProjections` for cleanup (RFC-0702).** The reuse path skips `build.prepare`, so `bordbuch.commit` does not run. Without a cleanup call, dirty bordbuch files from a previous run stay in the cache clone. The cleanup call is non-fatal (try/catch) and does not block the reuse path.
- **`mission.close` must commit `.materialization-state.json` to the cache clone after writing it.** The state file is written as the final step of close (RFC-0597); if it is not committed, the cache clone stays dirty. Always `git add .materialization-state.json && git commit` after writing the state file.
- **Never commit cache state files or `.gitignore` updates to the cache clone when the cache key depends on `cacheCloneHead`.** Committing changes the cache clone HEAD, which invalidates the cache key on the next materialization. Cache state files (e.g. `.cache/materialization-state.json` from RFC-0659) must live inside gitignored directories (e.g. `.cache/`). The `.gitignore` update that excludes the cache directory is written but NOT committed — `sternsystem.validate` checks for dirty files, but the `.gitignore` itself is not tracked if `.cache/` is already gitignored at a higher level. See `writeArtifactCacheState` in `mission-materialize.ts` for the pattern.
- **`mission.materialize` must preserve operator-filled `.env` files across re-materialization.** Before `atomicMoveDir(stagingDir, workpieceDir, { replace: true })`, read `.env`, `.env.main`, `.env.alt` from the old workpiece. After the move, restore the preserved content (with `PUBLIC_IMAGE_PROVIDER=build-portable` override). Without this, secrets (`CLOUDFLARE_API_TOKEN`, `R2_ACCESS_KEY_ID`, etc.) are lost every time a mission is re-materialized. See the preservation block in `mission-materialize.ts` before the `atomicMoveDir` call.
- **R2 S3-compatible credentials cannot be created via Cloudflare API.** The `CLOUDFLARE_API_TOKEN` uses a different auth scheme and cannot be used for S3 access. R2 Access Key ID / Secret Access Key pairs must be created manually in Cloudflare Dashboard → R2 → Manage R2 API Tokens. Agents MUST NOT attempt to create R2 S3 credentials programmatically — direct the operator to `docs/engineering/r2-evidence-setup.md` instead. Scope tokens to the `axiom-evidence` bucket only (least-privilege).
- **`executeKernelCommand` returns `{ exitCode, data, summary }` and does NOT throw on non-zero exit codes.** When wrapping kernel commands in retry or error-handling logic, check `result.exitCode` on the returned result object — do not use try/catch to detect non-zero exits. Only unexpected internal errors (e.g. command not found, module load failure) throw. See `runMissionCheckWithResilience` in `leitstand-commands.ts` (RFC-0668) for the pattern: `const result = await executeKernelCommand(...); const exitCode = result.exitCode ?? 0;`.
- **ADR-0025: Long-running commands MUST emit periodic progress output.** Commands that may run for more than 10 seconds MUST emit at least one `logger.info()` line per 30 seconds of silence. This is a code-review convention, not a runtime check. The `evidence.sync` command in `src/evidence/evidence-sync.ts` is the first adopter — it uses a `setInterval` heartbeat (30s) during the R2 upload loop. When adding new long-running commands (external API calls, large file operations, R2/S3 uploads), include a similar heartbeat pattern: log start with file count, set interval timer, clear in `finally` block, log completion.

## Leitstand (RFC-0358 / RFC-0379 / RFC-0608 / RFC-0627 / RFC-0628 / RFC-0666)

- The Leitstand deploys published releases via adapter plugins. The adapter enum is `cloudflare-workers | netlify | null`. `cloudflare-pages` and `vercel` are removed (forward-only).
- The channel model defines `dev` (development), `alt` (staging), and `main` (production) channels in `deployment.channels` (RFC-0627). Each channel has `workerName` and `url`.
- `resolveAdapter` throws for any adapter name without a concrete implementation. Do not add fallback-to-null behavior.
- `leitstand.dev-deploy` (RFC-0628) deploys the active mission's workpiece to the `dev` channel. It takes `--system` (not `--release`), resolves `currentMission` from the registry, runs `methodologies.validate` pre-flight (fail fast on invalid `systems/methodologies.md` before build+deploy cycle; non-fatal if command not registered), builds the workpiece via `pnpm build`, captures the workpiece HEAD sha, deploys to dev via the adapter, purges CDN cache, runs the Axiom verification gate via `mission.check --external-preview --base-url=<dev-url> --commit-sha=<sha> --no-report` (the `--no-report` flag suppresses `report.html` generation in `mission.check` because `axiom.report` is auto-invoked separately in the next step). RFC-0668: the `mission.check` call is wrapped with a 15-minute per-attempt timeout (`MISSION_CHECK_TIMEOUT_MS = 15 * 60 * 1000`) and one-time retry on infrastructure errors (exit code 2 or any non-0/non-1); content violations (exit 1) are not retried; `--max-duration` is passed to `mission.check` matching the outer timeout; worst-case total is 30 minutes with retry. RFC-0634: before build, writes a preliminary `build-identity.json` to `workpiece/public/.well-known/` so Astro's static copy includes it; after build, removes the preliminary from `dist/client/.well-known/` before computing `distTreeHash` via `fingerprintTree`, writes the final `build-identity.json` with real hashes to `dist/client/.well-known/`, and cleans up the preliminary from `public/.well-known/`. The commit SHA is passed directly to `mission.check` which embeds it in `evidence-metadata.json` — no post-processing of evidence files. RFC-0633: after `mission.check` completes, `leitstand.dev-deploy` auto-invokes `axiom.report --mission=<id>` (best-effort, non-blocking — failures emit `logger.warn` and the pipeline continues) to generate an HTML triage report at `missions/{mission}/evidence/axiom/report.html`. RFC-0652: after `axiom.report`, `leitstand.dev-deploy` auto-invokes `evidence.sync --mission=<id>` (best-effort, non-blocking — failures emit `logger.warn` and the pipeline continues) to archive Axiom evidence to R2. The `--skip-evidence-sync` flag skips this step. The output includes `evidenceSynced` (boolean) and `evidenceSyncError` (string | null) fields. RFC-0653: implements build-skip cache — skips `pnpm build` when `commitSha` + `platformVersion` + `platformSemanticHash` match `missions/<missionId>/.dev-deploy-build-cache.json` and `dist/` exists. The `--force-build` flag bypasses the cache. The output includes `buildSkipped` (boolean). It does NOT write to the registry or bordbuch — dev deploys are ephemeral. The Axiom gate result (pass/fail/not-run) is included in the command output. RFC-0689: `leitstand.dev-deploy` automatically clears the Axiom browser evidence cache (`missions/{mission}/evidence/axiom/.cache/`) before `mission.check` to ensure fresh Playwright captures from the current deploy. When `pnpm build` fails, it runs `behavior.snapshot.validate` separately to check for SNAP-01 diagnostics; if detected, it auto-regenerates the snapshot via `behavior.snapshot.generate` and re-runs the build. When the build is skipped (RFC-0653), it still checks for stale snapshots and regenerates if SNAP-01 is detected. The shared `autoRegenerateSnapshotOnSnap01` helper in `src/mission/snapshot-auto-regen.ts` is reused by both `leitstand.dev-deploy` and `mission.validate` (RFC-0615). RFC-0698: after `pnpm build` completes (including `build.post`) and before computing `distTreeHash`, `leitstand.dev-deploy` auto-commits the workpiece via `mission.git.commit` (through `executeKernelCommand`) to capture generated artifacts. The `commitSha` is re-read from workpiece HEAD after the auto-commit so `build-identity.json` and Axiom evidence reference the post-commit HEAD. If `mission.git.commit` fails, the deploy aborts with a fatal error. The auto-commit is idempotent — no commit is created if the workpiece is clean. The build-skip cache (RFC-0653) is written after the auto-commit with the post-commit `commitSha` to prevent cache invalidation from the auto-commit itself.
- `leitstand.propagate` deploys a `published` release with verified Axiom evidence to the `alt` channel (RFC-0628). The `--channel` flag is removed; passing it throws with a message directing to `leitstand.promote`. Before deployment, it verifies that `missions/{missionId}/evidence/axiom/evidence-metadata.json` exists with `missionId` and `commitSha` matching the release manifest, and that `study-run.json` contains no high/critical findings. RFC-0665: the gate is now per-methodology — `evidence-metadata.json` must contain a `methodologies[]` array (pre-RFC-0665 evidence is rejected), and each methodology declares its own `blockOn` severity levels. Findings are matched by `methodologyId` (or extension predicate fallback) and checked against the methodology's `blockOn` set. RFC-0634: propagate also fetches `build-identity.json` from the dev channel URL and verifies `missionId`, `commitSha`, `distTreeHash`, and `siteContentHash` against the release manifest before deploying to alt. On success, the release state transitions from `published` to `alt-deployed`. **RFC-0667 boundary pattern**: `leitstand.propagate` reads `auditId` (not `missionId`) from `evidence-metadata.json` and compares it to the release's `missionId` only when `auditId` is present (`if (metadata.auditId && metadata.auditId !== missionId)`). When `auditId` is absent, the check is skipped — the RFC-0665 methodologies gate provides primary validation. The `evidence-fetch.ts` and `evidence-sync.ts` modules define local `EvidenceMetadata` interfaces with optional `auditId` (not `missionId`), matching the external Axiom format. Agents MUST NOT use `missionId` as a JSON key in `evidence-metadata.json` — only `auditId`.
- `leitstand.promote` (RFC-0608) promotes a verified `alt-deployed` release to the `main` channel. It requires release state `alt-deployed`, fetches `/.well-known/build-identity.json` from the alt URL, verifies `releaseId`/`distTreeHash`/`behaviorSnapshotHash`/`siteContentHash` against the release manifest, runs live health checks against the alt deployment, then deploys to main via the adapter. On success, the release state transitions to `promoted`.
- `leitstand.rollback` auto-detects the channel from the current release state (RFC-0628): `promoted` → `main`, `alt-deployed` → `alt`. The `--channel` flag is removed; passing it throws. After rollback, the release state auto-steps one step back in the deployment chain: `promoted` → `alt-deployed`, `alt-deployed` → `published`. The state transition is non-fatal if the release manifest is missing.
- Preflight checks verify: release manifest exists, channel is configured, convention `.env.alt`/`.env.main` file existence (info-level), dist directory is present.
- Health verification uses `@warpgogol/fingerprint` `hashHtml` to compute per-route content hashes from the behavior snapshot and compare them against live responses. Probe selection is deterministic (home, legal, sitemap, then remaining routes alphabetically, max 10 probes). Content mismatches always produce `unhealthy` verdict; only pure network failures produce `unknown`.
- `deployment.lastPropagated` is per-channel with `releaseId`, `at`, `healthy`, `state`, `operationId`, and `leaseExpiresAt`. Only Leitstand command handlers write this field.
- `leitstand.status` shows all three channels (dev, alt, main) by default; `--channel` filters to one (RFC-0627).
- `leitstand.rollback` auto-detects the channel from the release state (RFC-0628). The `--channel` flag is removed.
- RFC-0666: Secret resolution uses convention-based `.env.alt`/`.env.main` paths, not `secretsFile` env-var indirection. `leitstand.dev-deploy` reads `<workpiece>/.env.alt`; `leitstand.propagate` reads `<release>/.env.alt`; `leitstand.promote` reads `<release>/.env.main`; `leitstand.rollback` reads `<release>/.env.<channel>`. `release.prepare` copies `.env.alt`/`.env.main` from the workpiece to the release directory. If the convention file does not exist, the adapter falls back to `filterEnv(process.env)`. `sternsystem.validate` rejects registries with `secretsFile` fields. RFC-0700: when `--release` is set, `leitstand.dev-deploy` reads `<release>/.env.alt` instead of `<workpiece>/.env.alt`.
- RFC-0700: `leitstand.dev-deploy` accepts an optional `--release <id>` flag that deploys an existing release's pre-built dist to the dev channel without requiring an open mission. When `--release` is set: deploy from `releases/<id>/dist/`, skip build, skip Axiom checks, skip auto-commit, run CDN purge and health check. The release's `systemId` in `release.yaml` must match `--system`. Wrangler binary is resolved from workspace root `node_modules/.bin/` (release dir has no `node_modules/`). The result includes `releaseDeployed: <id>` and `buildSkipped: true`. Without `--release`, the command behaves exactly as before (requires open mission, builds from workpiece).
- `DeploymentAdapter` interface declares `getLimits(): DeploymentLimits` (RFC-0587). Each adapter declares its own size limits: `cloudflare-workers` returns 20 GiB total / 25 MiB per-file; `null` returns `Infinity`. `runPreflight` passes the adapter to `checkDistSize` — no hardcoded limits in `leitstand-commands.ts`.
- `filterEnv` and `sourceDotenv` are exported from `cloudflare-workers.ts` and re-exported from `adapters/index.ts` for reuse by future adapters (RFC-0587).
- `artifact.store.put` creates a `tar.gz` archive using the `tar` npm package and stores `distArtifactHash` as the archive hash (RFC-0587). It is idempotent: re-running for the same `releaseId` removes any existing manifest before writing the new one. The old tar.gz archive is not removed (content-addressed).
- `release.publish` automatically stores the dist artifact via `storeArtifactCore` (lock-free helper extracted from `runArtifactStorePut`) before transitioning the release to `published` (RFC-0596). The standalone `artifact.store.put` command remains available for manual use. `storeArtifactCore` is called directly (not `runArtifactStorePut`) to avoid lock conflict — `release.publish` already holds `release:${releaseId}` and `system:${systemId}` locks. The artifact is stored BEFORE the state transition, eliminating the partial failure window where a release could be `published` without an artifact. `release.validate` checks that published releases have a non-null `artifact` field.
- `artifactStoreRehydrate` extracts the tar.gz archive to the output directory using `tar` (RFC-0587). Throws if the archive is missing.
- `collectRoutes` in `behavior.snapshot.capture` reads `_redirects` and excludes routes matching 301/308 redirect source patterns from the behavior snapshot (RFC-0588). `parseRedirectRules` is reused from `@warpgogol/share/redirects`. 410 Gone handling is deferred to RFC-0589. RFC-0592: wildcard matching in `isRouteRedirected` fixed so `/de/*` matches `/de` (directory root without trailing slash), not just `/de/anything`. RFC-0595: meta-refresh redirect stubs are detected via `isHtmlRedirectPage` (from `@warpgogol/share/semantic`) and included in the snapshot with `contentHash: null` and `redirectTarget` (parsed via `extractRedirectTarget` from `@warpgogol/share/redirects`). The `RouteFact` type is owned by `@warpgogol/ontology/operations` — do not duplicate it locally.
- Health verification in `cloudflare-workers.ts` checks redirect routes (`contentHash === null`) by fetching with `redirect: "manual"` and verifying HTTP 307/308 status + `Location` header. If `redirectTarget` is known, the `Location` header must match it exactly. Non-redirect routes continue to use `hashHtml` comparison (RFC-0595).
- `wrangler deploy` in the cloudflare-workers adapter retries up to 2 times (3 total attempts) with 30s and 60s delays on transient Cloudflare API errors (502, 503, 504, 522, Gateway Timeout, malformed response). Non-retryable errors (auth, 4xx, syntax, build errors) fail immediately. The retry is internal to the adapter via `runWranglerDeployWithRetry` and transparent to callers. `leitstand.promote` benefits transitively because it calls `adapter.propagate` (RFC-0623).
- RFC-0624: `leitstand.propagate`, `leitstand.promote`, and `leitstand.rollback` purge CDN cache by URL after deploy/rollback succeeds. Purge sends `POST /zones/{zoneId}/purge_cache` with behavior snapshot route URLs + `/.well-known/build-identity.json`, batched max 30 per call. A fixed 6s delay follows purge before health checks (propagate and promote only; rollback has no health check). Purge failures are non-blocking warnings for propagate, promote, and rollback. `CLOUDFLARE_ZONE_ID` is read from the existing secretsFile env; missing zone ID skips purge with warning. `skippedPurgeResult` returns `success: false` (not `success: true`) — any code that checks `purgeResult.success` treats a skip as failure. RFC-0649 relies on this: `leitstand.dev-deploy` treats `purgeResult.success === false` as fatal, so missing env vars are fatal for dev deploys. `purgeResult` is recorded in per-channel `lastPropagated` and displayed by `leitstand.status`. Purge logic is at the command level (`leitstand-commands.ts`), not in the adapter. RFC-0649: `leitstand.dev-deploy` purge failure is **fatal** — the pipeline stops before the Axiom gate. RFC-0657: after purge, `leitstand.dev-deploy` fetches `build-identity.json` from the CDN URL and verifies `distTreeHash` against the local build-identity (freshness check) with retry — up to 5 attempts: first immediate, then retries with exponential backoff (3s, 6s, 12s, 24s). The fixed 6s sleep after purge is removed; the first freshness attempt is immediate. Freshness mismatch on all 5 attempts is fatal — Axiom gate is not run. For `null` adapter, purge and freshness check are skipped entirely (no CDN to invalidate).
- When replacing or renaming a Leitstand command handler, update both `leitstand.module.ts` (lazy registration) and `leitstand/index.ts` (barrel exports + synchronous `register()`). The barrel imports/exports handler functions directly and has its own duplicate `register()` function — a stale barrel causes `SyntaxError: does not provide an export named '<oldHandler>'` at module load time.
- After adding or changing command registrations in `leitstand.module.ts` (or any `*.module.ts` in this package), run `pnpm exec site-kernel run command.manifest.generate` to regenerate `docs/command-manifest.generated.yaml`. `rfc.validate` uses the manifest as a source of truth for live command existence (RFC-CMD-02). A stale manifest causes false-positive violations for commands from lazy-loaded modules.
- **Test fixtures for leitstand commands MUST include all three channels** (`dev`, `alt`, `main`) in `deployment.channels`. The `fleetRegistrySchema` Zod validator requires all three; omitting any channel causes a `ZodError` at registry parse time. See `leitstand-0628-dev-deploy.test.ts` for the canonical fixture pattern.

## Testing patterns for kernel commands

- **Mock `readMissionManifest` in tests** — `readMissionManifest` calls `missionManifestSchema.parse` (Zod), which requires all manifest fields (`operationId`, `systemId`, `state`, etc.). When testing commands that call `readMissionManifest`, mock `../mission/mission-io.ts` via `vi.mock` and return partial manifests from a `vi.hoisted` Map. This bypasses Zod validation and lets tests focus on the command logic, not manifest schema completeness. See `release-state-validate.test.ts` for the pattern.
- **`readReleaseManifest` uses a regex parser, not YAML** — `readReleaseManifest` parses `release.yaml` with `line.match(/^(\w+):\s*(.*)$/)`, capturing the raw value string. When writing test release manifests, use unquoted string values (e.g. `state: published`, not `state: "published"`) — quotes become part of the captured value and cause comparison failures. Null values should be written as `null` (the string).
- **Bordbuch test entries require all `bordbuchEntrySchema` fields** — `readBordbuch` runs `bordbuchEntrySchema.parse` on each NDJSON line. Test entries must include `schemaVersion: "1.0.0"`, `actor`, `summary`, and `previousHash` (null for the first entry) in addition to the fields under test. Missing fields cause `ZodError` at parse time, and `readBordbuch` returns an empty array, making bordbuch checks emit `warn` instead of the expected `pass`/`fail`. Also mock `resolveCachePath` from `../sternsystem/registry-io.ts` to return a path within the temp workspace's `systems/<id>` directory, so `resolveBordbuchPath` can find the test `events.ndjson` file.
- **Use `setTimeout` stub, not `vi.useFakeTimers()`, for retry/sleep tests** — `vi.useFakeTimers()` freezes all timers including those used by internal async operations (fetch mocks, execSync, fingerprintTree), causing test timeouts. When testing retry logic that uses `sleep()` (e.g. `verifyFreshness` retry loop), stub `setTimeout` via `vi.stubGlobal("setTimeout", vi.fn((cb) => { cb(); return 0; }))` to make `sleep` a no-op without interfering with other async operations. See `leitstand-0649-freshness.test.ts` `skipSleep()` helper for the pattern.
- **`executeKernelCommand` mocks MUST return `ok: true`** — `leitstand.dev-deploy` pre-flight calls `executeKernelCommand` for `methodologies.validate` and checks `!validateResult.ok || validateResult.exitCode !== 0`. Mocks that omit `ok: true` fail the pre-flight before reaching purge/freshness logic, producing misleading "methodologies.validate failed" errors instead of the expected test behavior. Always include `ok: true` in every `executeKernelCommand` mock return path. See `leitstand-0649-freshness.test.ts`, `leitstand-0628-dev-deploy.test.ts`, `rfc-0652-leitstand-dev-deploy-evidence-sync.test.ts` for the pattern.

## Notausgang (RFC-0359 / RFC-0380)

- `notausgang.export` produces a self-contained site package with dist, site content, Bordbuch, pin, behavior snapshots, and a YAML manifest.
- `notausgang.validate` performs **deep integrity verification** (RFC-0380), not shallow existence checks:
  - Parses and schema-validates `notausgang-manifest.yaml` using `notausgangManifestSchema` from `@warpgogol/ontology/operations`.
  - Re-computes `dist/` (byte mode), `site/` (semantic mode), `bordbuch/events.ndjson` (semantic mode), `behavior-snapshots/` (semantic mode), and `artifact-manifest.yaml` (byte mode) hashes via `@warpgogol/fingerprint`.
  - Validates Bordbuch NDJSON line-by-line: each line must be valid JSON with `eventId`, `type`, `timestamp`, `systemId` fields, and `systemId` must match the manifest.
  - Validates `system.pin.yaml` content: `systemId` and `platformVersion` must match the manifest.
  - Rejects legacy JSON artifacts (`notausgang-manifest.json`, `artifact-manifest.json`, `system.pin.json`) — forward-only, no JSON fallback.
  - Scans for secrets with refined patterns, excluding safe locations (`bordbuch/`, `system.pin.yaml`, `.hash` files).
  - Returns `CheckStatus` enum (`"valid" | "invalid" | "missing"`) per artifact and a `violations` array with `{ rule, message, file? }` shape (no `severity` field).
- All hashing must use `@warpgogol/fingerprint` (DNA-53). Do not use `crypto.createHash` directly — `fingerprint.usage.lint` enforces this invariant.
- Export artifacts are YAML-only per RFC-0376, except Bordbuch NDJSON which remains NDJSON.

## Evidence (RFC-0651)

- `evidence.sync` uploads all evidence artifacts from `missions/{mission}/evidence/axiom/` to Cloudflare R2 under `{systemId}/{missionId}/{runTimestamp}/` key prefix. Uses `@aws-sdk/client-s3` with R2's S3-compatible endpoint. Reads `runTimestamp` from `evidence-metadata.json` (or `--run-timestamp` flag). Supports `--dry-run` (reports what would be uploaded without R2 API calls). Failure modes: `MISSING_ENV` (R2 env vars not set), `NOT_FOUND` (evidence directory missing), `INVALID_EVIDENCE` (evidence-metadata.json missing or invalid), `R2_UPLOAD_ERROR` (PutObject API error).
- `evidence.fetch` downloads a historical evidence run from R2 to a local directory, or lists available runs via `ListObjectsV2`. Uses `--run-timestamp` to select a run, `--output-dir` for download location, `--no-raw` to skip `raw/` artifacts, `--list` to list available runs. In `--list` mode, downloads `evidence-metadata.json` per run to extract `commitSha`. Failure modes: `MISSING_ENV`, `NOT_FOUND`, `R2_LIST_ERROR`.
- Environment variables: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` (documented in `.env.example`).
- R2 bucket prerequisite: the operator must have created the `axiom-evidence` R2 bucket (RFC-0650 rollout).
- Agents MUST NOT invoke `evidence.sync` automatically after `mission.check` — sync is invoked by `mission.close` (mandatory) and `leitstand.dev-deploy` (best-effort) per RFC-0652. Agents MAY invoke `evidence.sync` manually when explicitly asked by the operator.
- Agents MUST NOT create R2 API tokens automatically — token creation is a manual operator action in the Cloudflare dashboard.
- Agents MUST NOT hardcode R2 credentials in source files — credentials are read from environment variables only.
- Iceberg REST catalog support is deferred to a future RFC — `ListObjectsV2` is the primary listing mechanism.

## Bordbuch git synchronization (RFC-0477)

All four commands that mutate `bordbuch/events.ndjson` (`mission.open`, `mission.close`, `mission.abort`, `sternsystem.sync`) commit and push the bordbuch file to the system's git origin after appending their entry. The shared helper `commitAndPushBordbuch` in `bordbuch-io.ts` stages only `bordbuch/events.ndjson` (not `git add -A`). Push failures are non-fatal — the bordbuch entry is committed locally; the next `sternsystem.sync` or manual `git push` will catch up.

- `mission.close` refuses to close a mission with null `reconciledAt` — this is a hard guard, not a warning.
- `mission.close` mandates `evidence.sync --mission=<id>` to R2 before writing `close-report.json` (RFC-0652). If `evidence/axiom/evidence-metadata.json` exists, the sync is invoked via `executeKernelCommand`. If sync fails, `mission.close` throws `EVIDENCE_SYNC_FAILED` and the mission remains open. The `--skip-evidence-sync` flag is an escape hatch for offline close only — it appends a `mission-close-evidence-skipped` Bordbuch entry for auditability.
- `mission.close` writes `evidence/close-report.json` with git, mirror, and reconcile status blocks.
- `mission.close` stops any running dev/preview server for the workpiece via `astro dev stop` before transitioning to closed (ADR-0010). Best-effort — if no server is running, the stop silently succeeds.
- `mission.cleanup` removes `evidence/axiom/` based on `--evidence-retention-days` (default: 30). It reads `runTimestamp` from `evidence-metadata.json` and removes the directory if the evidence is older than the retention period. Non-Axiom evidence (`close-report.json`, `workpiece.git-bundle`) is always preserved. Set `--evidence-retention-days 0` to preserve all evidence (RFC-0652).
- `release.prepare` requires `state: closed` — open missions are refused with a message directing to `mission.close` first (RFC-0590). The workflow is: `mission.close` → `release.prepare` on the closed mission.
- `sternsystem.status --id <id>` is a read-only command showing HEAD SHA, origin SHA, mirror SHA, dirty files, last 6 bordbuch events, and last reconciledAt. Use `--all` for all systems.

## Bordbuch repair (RFC-0583)

`bordbuch.repair` is an on-demand disaster-recovery command that detects `orphan-mission-close` violations, inserts missing `mission-open` events with auto-derived or operator-supplied metadata, recomputes the hash chain and event-id sequence, and writes the repaired bordbuch atomically. It amends RFC-0355 §3.4 (append-only invariant) as a meta-level tool — the only command permitted to rewrite the bordbuch file, and only when `bordbuch.validate` reports `orphan-mission-close` violations.

- **Flags:** `--system` (required), `--dry-run` (show planned repairs without writing), `--mission` (repair only the specified mission id), `--metadata` (JSON with `occurredAt`, `summary`, `actor` overrides).
- **Idempotent:** running on an already-valid bordbuch is a no-op (exits 0 with `insertedEvents: 0`).
- **Unrepairable violations** (`duplicate-mission-id`, `sensitive-payload`, `hash-mismatch`, `hash-chain-gap`) cause non-zero exit without writing.
- **Does not auto-commit** — the operator must commit the repaired bordbuch in the cache clone manually.
- **Not in any pipeline** — operator-only, never automated. Agents MUST NOT run `bordbuch.repair` proactively — only when `bordbuch.validate` reports `orphan-mission-close` violations.
- Uses RFC-0362 lock primitives (`system:<id>` and `bordbuch:<id>` lock scopes) to prevent concurrent repair or append operations.

## Bordbuch integrity protection (RFC-0658)

Three defense-in-depth measures protect `bordbuch/events.ndjson` from accidental deletion and corruption in the cache clone:

1. **Pre-commit hook** — `mission.materialize` installs a pre-commit hook at `<cache-clone>/.git/hooks/pre-commit` that rejects any commit staging a deletion of `bordbuch/events.ndjson` (`diff-filter=D`). The hook is installed transparently during every materialization. Non-git cache clones skip hook installation silently. `git commit --no-verify` bypasses the hook — agents MUST NOT use `--no-verify` (see RFC-0658 implementation notes).

2. **`bordbuch.validate` in `build.prepare`** — The full `SITES_BUILD_PREPARE_PIPELINE` includes `bordbuch.validate` between `bordbuch.generate` and `bordbuch.commit`. This catches hash-chain corruption, lifecycle pairing violations, and sensitive payloads before the build proceeds. NOT in `SITES_BUILD_PREPARE_DEV_PIPELINE` (dev pipeline excludes bordbuch steps).

3. **`mission.close` bordbuch validation** — Before appending the close event, `mission.close` calls `validateBordbuch` and throws on any violations. This is defense-in-depth for the distribution-reuse skip path (RFC-0635) where `mission.validate` skips `build.prepare` (and thus `bordbuch.validate`). The `MissionCloseData` interface includes `bordbuchValidation: { violations, checked }`.

- **Hook scope:** The pre-commit hook is installed in the cache clone only. Workpiece clones do not inherit it (git clone does not copy hooks). The `build.prepare` and `mission.close` validation steps cover workpiece paths.
- **`bordbuch.repair` is not blocked** by the pre-commit hook — it rewrites `events.ndjson` but does not delete it (`diff-filter=D` only triggers on deletion).

## Bordbuch projection auto-commit (RFC-0626, RFC-0646)

`bordbuch.commit` is an internal pipeline step that auto-commits dirty bordbuch projection files in the cache clone after `bordbuch.generate` runs in `build.prepare`. It eliminates the mission workflow friction where uncommitted bordbuch projections in the cache clone blocked `mission.close` and `release.prepare`.

- **Pipeline step:** registered in `SITES_BUILD_PREPARE_PIPELINE` after `bordbuch.generate` and before `passport.key.ensure`. NOT in `SITES_BUILD_PREPARE_DEV_PIPELINE`.
- **Selective staging:** only stages the three bordbuch projection paths (`bordbuch/status.generated.yaml`, `public/.well-known/bordbuch.json`, `public/.well-known/bordbuch/index.html`). Never `git add -A`.
- **Idempotent:** second run is a no-op when no bordbuch files are dirty.
- **No locks:** pipeline runs sequentially — `bordbuch.generate` has already released locks by the time `bordbuch.commit` runs.
- **Commit message:** `chore: bordbuch projections from build.prepare`.
- **Non-mission `build.prepare`:** when `resolveCachePath` fails (no cache clone), the command is a no-op.
- **Retry resilience (RFC-0646):** `bordbuch.commit` retries transient git failures (lock contention, timeout) up to 2 times with 12s and 60s backoff before failing the pipeline step. All `gitExec` calls in `commitBordbuchProjections` use `gitExecWithRetry` from `werkstatt/git-exec.ts`. Non-transient errors (missing repo, permissions) throw immediately without retry.

## Werkstatt side-effect auto-commit (RFC-0580)

All 6 mission lifecycle commands (`mission.open`, `mission.close`, `mission.abort`, `mission.materialize`, `mission.migrate`, `mission.reconcile`) auto-commit werkstatt-level side-effect files to the monorepo working tree after updating them. The shared helper `commitWerkstattSideEffects` in `werkstatt/werkstatt-commit.ts` stages only specific file paths (never `git add -A`), is idempotent (skips when no staged changes), and throws on commit failure. The helper does NOT push — werkstatt monorepo push is a separate operator-controlled operation.

- `mission.open`, `mission.close`, `mission.abort` commit `systems/registry.yaml` + `missions/<id>/mission.yaml`.
- `mission.materialize` commits `missions/<id>/mission.yaml` + `pnpm-lock.yaml`.
- `mission.migrate` commits `missions/<id>/mission.yaml`.
- `mission.reconcile` commits `missions/<id>/mission.yaml`.
- Commit message format: `werkstatt: <command> <missionId>`.
- The shared `gitExec` utility lives in `werkstatt/git-exec.ts` with an `allowNonZero` option for git commands that use non-zero exit codes as signals (e.g. `git diff --cached --quiet`).

## Mission materialization optimization (RFC-0597)

`mission.materialize` and `mission.close` use a split pipeline and materialization state file to optimize dev-mode materialization speed.

- **Pipeline split:** `mission.materialize` runs `build.prepare.dev` (codegen-only, ~38 steps) instead of `build.prepare.full` (all steps including media transcoding). `mission.validate` and `release.prepare` continue to use `build.prepare.full` for production validation.
- **State file:** `mission.close` writes `systems-cache/<id>/.materialization-state.json` (outside git) as the final step of a successful close. It records the cache clone HEAD hash, timestamp, and mission ID. `mission.materialize` reads this file and skips preflight if the cache clone HEAD is unchanged since the last close.
- **Preflight skip precedence:** `--skip-preflight` flag (operator override) always skips preflight and does not consult the state file. The state-file-based skip is automatic and only applies when the flag is not set. Both paths append a `preflight-skipped` bordbuch entry with distinct reason metadata.
- **Media cache warming:** `mission.materialize` copies `.cache/video/` and `.cache/video-live/` from the cache clone to the workpiece after data-path copy. `mission.close` copies them back from the workpiece to the cache clone as the final step. This avoids re-encoding unchanged video sources across missions.
- **`mission.reconcile` does NOT write the state file or copy `.cache/`** — it only transfers commits via git merge. The state file reflects "last successful close", not "last reconcile".
- **`--json` output:** `mission.materialize` gains `preflightSkipped`, `preflightSkipReason`, `pipelineUsed`, `mediaCacheWarmed`, and `mediaCacheSources` fields.
- **Compass audit baseline (RFC-0617):** `mission.materialize` automatically runs `compass.audit.baseline --workpiece <path>` after codegen and git commit to seed the audit ledger for workpiece files. This prevents `compass.audit.validate --strict` (in `build.post`) from failing on unbaselined files during `release.prepare`. Baseline failures are non-fatal — a warning is logged but materialization succeeds.
- **Artifact cache (RFC-0659):** `mission.materialize` maintains a workpiece artifact cache at `systems-cache/<id>/.cache/materialization/<cacheKey>/`. The cache key is `byteHash(cacheCloneHead + "|" + platformVersion + "|" + platformSemanticHash)`. On cache hit (key matches state file + cache dir exists), the workpiece is restored from cache and `build.prepare.dev` is skipped entirely. The `--force` flag bypasses cache read and forces full materialization (cache is refreshed). The state file lives at `.cache/materialization-state.json` (inside gitignored `.cache/`) — it is NOT committed to the cache clone (committing would change HEAD and invalidate the cache key). The `.gitignore` in the cache clone is updated to include `.cache/` (also not committed). Stale state (cache dir missing) falls through to full materialization and deletes the stale state file. The `--json` output includes `artifactCacheHit`, `artifactCacheKey`, and `artifactCacheSkipped` fields.

## Validation gates (RFC-0593)

- `mission.open` runs `bordbuch.validate` as a pre-flight gate before lock acquisition. If violations exist, `mission.open` refuses to open a new mission and directs the operator to run `bordbuch.repair` first. No side effects (directories, manifests, registry updates) are created on validation failure.
- `mission.close` runs `mission.validate` after the `reconciledAt` check, before `acquireLock`. Validation runs outside the lock scope to avoid holding registry/system/mission locks for 2+ minutes during the build. State is re-checked inside the locks before transition — if another process aborted the mission between validation and lock acquisition, `mission.close` exits with a state error.
- **Invariant chain:** `reconciledAt !== null` implies `materializedAt !== null` via the validate → reconcile → close flow. `mission.reconcile` requires `evidence/validation-report.json` (created by `mission.validate`, which requires `materializedAt`). No exception path is needed for non-materialized missions.
- **TOCTOU limitation:** `preflightBordbuch` in `mission.open` runs without holding any lock. `bordbuch.repair` (operator-only, uses its own lock scopes) could change the bordbuch concurrently. Low risk — the failed attempt exits with code 1 before any side effects, and the next `mission.open` will pass.
- **`--force` bypass flag is NOT provided.** Validation gates are hard gates, not warnings. Bypassing validation requires a code change, not a flag.

## Mission git workpiece and Layer C protection (RFC-0480)

- **Edits-only-through-missions invariant:** All site edits go through mission workpieces. `sternsystem.sync` is push-only (pull/both removed). `sternsystem.validate` detects external edits via Bordbuch-vs-git-log consistency check. Systems with detected external edits should be demoted to `paused` status, which blocks `mission.materialize`.
- **Workpiece git repository (RFC-0568):** `mission.materialize` clones the cache clone into the workpiece (shared git object database) and commits only data-path files (`STERNSYSTEM_DATA_PATHS` + `system.pin.json`). Boilerplate files remain untracked. Operators use `mission.git.commit` to commit edits. `mission.reconcile` transfers commits via `git merge --no-ff` to the cache clone (idempotent via `preReconcileSha`). Non-git cache clones fall back to `git init` with data-only staging.
- **Non-data-path file removal after clone:** When removing non-data-path files from the workpiece after `git clone`, the keep-path check must use prefix matching in addition to exact matching. `STERNSYSTEM_DATA_PATHS` contains nested paths like `src/content`, but `fs.readdir` returns top-level entries like `src`. Without checking `kp.startsWith(`${entry.name}/`)`, parent directories of data paths are incorrectly removed, deleting data-path files along with non-data-path files.
- **Git bundle audit trail:** `mission.close` and `mission.abort` create `evidence/workpiece.git-bundle` before state transition. Workpiece and distribution are preserved on disk after close/abort for `mission.preview` (side-by-side comparison). `mission.cleanup` is the explicit cleanup command (`--mission <id>` or `--older-than <Nd>`); it preserves evidence bundles.
- **`mission.preview`:** Blocking dev server (`astro dev` or `astro preview --production`) with `--port` flag. Works for open, closed, and aborted missions. Runs `content.ref-index.generate` before server start to ensure the content reference index is fresh (ADR-0007). Auto-stops any existing dev server on the port before starting (via `astro dev stop`).
- **In-process codegen calls from mission handlers:** When calling codegen functions (e.g. `runContentRefIndexGenerate`) from mission command handlers, pass a synthetic `DiscoveredSiteWorkspace` pointing to the workpiece directory. Do NOT use the `--site` flag or registry-based site resolution — `currentMission` is cleared for closed/aborted missions, causing resolution failures. See `mission-preview.ts` for the pattern.
- **Pre-commit content validation (RFC-0594):** `mission.git.commit` runs targeted content validators based on changed file paths before committing. The `VALIDATOR_MAPPINGS` table maps content directory prefixes to validators: `src/content/business-profile/` → `pbp.content.validate`, `src/content/pages/` → `semantic.drift.validate`, `src/content/faq/` → `faq.validate`. Validators are invoked via `executeKernelCommand` with `siteName: manifest.systemId`. If any validator fails, the commit is refused with exit code 1 and `preCommitValidation` data block — staged changes remain in the git index (not unstaged). Unregistered validators are skipped with a warning. No validators run when no content files are changed.
- **Layer C protection:** Declarative C-contract in `packages/ontology/src/external-surfaces/` (url-schema.yaml, jsonld-types.yaml, sitemap-shape.yaml). `surface.contract.validate` checks generated surfaces against the contract. `release.prepare` blocks on C-surface regression without `breaksC: true` in the mission's RFC. `release.publish` requires successful reconcile.
- **Extracted guards (RFC-0520):** The C-surface regression check in `release.prepare` is delegated to `evaluateCSurfaceGate` (pure function in `src/release/c-surface-guard.ts`). The Bordbuch-vs-git-log check in `sternsystem.validate` is delegated to `evaluateExternalEditGate` (pure function in `src/sternsystem/external-edit-guard.ts`). Shared `GuardResult` types live in `src/guards.ts`. I/O helpers: `src/release/breaks-c-helper.ts` (`checkBreaksCDeclaration`), `src/sternsystem/external-edit-collector.ts` (`collectExternalEditInputs`).

## Reconcile dirty cache clone guard, untracked file investigation, and releaseId tracking (RFC-0522, RFC-0568, RFC-0644)

- **Workpiece auto-commit before reconcile (RFC-0644):** `mission.reconcile` auto-commits all uncommitted changes in the workpiece git repository via `commitWorkpieceIfDirty` (in `mission-git-commit.ts`) before starting `git fetch` + `git merge` into the cache clone. The helper uses `git add -A` + `git commit --no-verify -m "workpiece: auto-commit before reconcile <missionId>"`. It is idempotent — a clean workpiece produces no commit. The call replaces the former `isWorkpieceDirty` blocking guard. The `MissionReconcileData` output includes `workpieceAutoCommitted: boolean` and `workpieceCommitSha: string | null` fields. The `--no-verify` flag skips pre-commit hooks intentionally — workpieces are clones where hooks are not copied by `git clone`, and the validation gate at `mission.validate` ensures content was already validated before reconcile.
- **Dirty cache clone guard in `mission.reconcile`:** Before merging, `mission.reconcile` checks the cache clone (`mirrors[0].path`) for uncommitted changes via `isWorkpieceDirty`. If dirty, it investigates untracked file origins via `investigateUntrackedFiles` (cross-references Bordbuch `mission-open` entries for time ranges and matches against boilerplate file patterns), writes `evidence/untracked-files-report.json` with the analysis, and throws an error listing the files with their likely origin (`previous-mission`, `direct-commit`, or `unknown`). The guard is placed inside the `existsSync(gitDir)` check to avoid errors on non-git cache clones (copyDir fallback).
- **Merge-based reconcile (RFC-0568):** `mission.reconcile` uses `git fetch` + `git merge --no-ff` to transfer workpiece commits into the cache clone. The workpiece branch name is determined dynamically (not hardcoded). Conflicts are resolved in the workpiece (not the cache clone) — the operator commits fixes via `mission.git.commit` and re-runs reconcile (idempotent via `preReconcileSha` reset). The old `git format-patch` + `git am` patch-based mechanism and its 3-way fallback / auto-resolve code are removed (forward-only).
- **Bordbuch delete-modify conflict auto-resolution (RFC-0584, RFC-0614):** `mission.reconcile` auto-resolves bordbuch delete-modify conflicts by keeping the cache clone version (`--ours`) when all conflicted paths are bordbuch paths — i.e. under `bordbuch/` or matching `public/.well-known/bordbuch*`. The `git checkout --ours` and `git add` commands use the `conflictedPaths` array dynamically, ensuring only actually-conflicted paths are resolved (robust against partial bordbuch artifact sets). Non-bordbuch or mixed conflicts abort the merge and throw the existing error. The result includes `autoResolvedPaths` in the `--json` output and `reconciliation-report.json` evidence file.
- **Push retry (RFC-0568):** After merge, `mission.reconcile` pushes to origin with 3 retry attempts and exponential backoff (1s, 2s, 4s). If all attempts fail, the push is non-fatal — the merge commit is in the cache clone locally and the workpiece is preserved on disk until `mission.cleanup`.
- **`releaseId` in `release.prepare`:** After successful release preparation, `release.prepare` writes the `releaseId` to the mission manifest via `writeMissionManifest` (Zod-validated). This associates the mission with its release.
- **`releaseId` precedence in `mission.close`:** The `--release` CLI flag overrides the manifest `releaseId`. Precedence: flag → manifest → null. If `releaseId` is null, `mission.close` adds a `missing-release-id` warning to `close-report.json`'s `warnings` array.
- **Dirty cache clone warning in `mission.validate`:** `mission.validate` warns if the cache clone has uncommitted files — reconcile will fail until resolved. The warning is placed inside the `existsSync(.git)` check to avoid errors on non-git cache clones.
- **`isWorkpieceDirty` return type:** Extended with `files: string[]` field listing the dirty file paths from `git status --porcelain`. Uses `execSync` directly (not the trimming `git()` helper) to preserve leading spaces in porcelain output.
- **Test helpers that swallow errors:** When using helpers like `gitExpectFail` that catch all errors and return empty strings, add a comment explaining the specific expected failure mode (e.g. "merge commands that fail with conflicts, exit code 1"). This prevents masking unexpected git failures as silent successes.
- **RFC-0615: dist cleanup before astro build:** `mission.validate` removes the workpiece `dist/` directory before running `pnpm exec astro build` to prevent stale build artifacts from causing false positives or masking real errors.
- **RFC-0635: distribution reuse in `mission.validate`:** `mission.validate` checks `distribution/build-input-hash.json` before running the build cycle. If the hash matches the current workpiece state and `distribution/dist/` exists, the entire build cycle is skipped and `distribution/dist/` is copied to `workpiece/dist/` if missing. `--force` bypasses this check. The `MissionValidateData` interface includes `distributionReused`, `buildInputHash`, and `fullBuildRan` fields to indicate the reuse path. `mission.validate` is `cacheable: false`.
- **RFC-0635: `build.check` in `mission.build`:** `mission.build` now runs `build.check` between `build.prepare` and `astro build` so that reused distributions have passed all content validators. `build-input-hash.json` is only written when all phases (including `build.check`) succeed.
- **RFC-0615: behavior snapshot auto-regeneration on SNAP-01:** `mission.validate` uses `executeKernelPipeline` (not `runPipelinePhase`) for `build.post` so it can inspect step-level diagnostics. If `behavior.snapshot.validate` fails with SNAP-01 diagnostics and the workpiece was clean before `build.post` ran, `mission.validate` automatically: (1) runs `behavior.snapshot.generate`, (2) runs `mission.git.commit` with message `chore: auto-regenerate behavior snapshot`, (3) re-runs `build.post`. If re-validation passes, the overall validation succeeds. If the workpiece was dirty, auto-regeneration is skipped (the operator must commit first). Non-SNAP-01 failures never trigger auto-regeneration.

## Preflight content quality gate (RFC-0517)

- `mission.materialize` runs a two-level preflight gate after `atomicMoveDir` and before the git commit step. The gate validates the workpiece content using author-time validators from `MISSION_PREFLIGHT_CRITICAL` and `MISSION_PREFLIGHT_WARNING` pipeline constants (exported from `@warpgogol/site-kernel-checks`).
- **Critical validators** (`content-types.validate`, `schema.drift.validate`, `cosmic.catalog.validate`, `biome.contract.validate`) block materialization on failure. The workpiece is preserved on disk (no `git init`) and `evidence/preflight-report.json` is written with failure details.
- **Warning validators** (`content.filename.validate`, `naming.content.lint`, `mirroring.validate`, `semantic.drift.validate`, `content.links.validate`, `content.references.validate`, `pbp.content.validate`) do not block — failures are logged and written to the report.
- **`--skip-preflight` flag:** Bypasses the gate, writes `evidence/preflight-report.json` with `skipped: true`, and appends a `preflight-skipped` Bordbuch entry with `writerRole: "mission"`.
- **`--report-only` flag:** Returns early with version comparison report only (existing behavior). No staging, no preflight.
- `evidence/preflight-report.json` is written for every materialization attempt (pass, fail, or skipped).

## Sternsystem registration (RFC-0354, RFC-0532)

- `sternsystem.register` is the single entry point for creating a new Sternsystem. It performs the full onboarding-to-mission bridge in one invocation:
  1. Adds an entry to `systems/registry.yaml` with `id`, `cosmicStar`, `mirrors` (RFC-0574), `pinnedPlatform`, `status: registered`, `registeredAt`, `deployment` config, and optional `owner` (VC subject id, RFC-0561).
  2. Creates the pin file `mirrors[0].path/system.pin.json` by delegating to `sternsystem.pin`.
  3. Creates initial content stubs: `mirrors[0].path/content/system.md` with identity and i18n blocks derived from the brief.
  4. Automatically opens the first mission (`<system-id>-m000001`) by calling `mission.open`.
  5. Triggers `mission.materialize` to produce the first Werkstück from the pinned data.
- **`--amend` flag:** Updates the pin file, opens an amend mission, and triggers materialization. Does not create a new registry entry. `--amend-id` specifies the amend batch number. `--owner` can be used with `--amend` to backfill or update the `owner` field on an existing entry (RFC-0561).
- **Atomic rollback:** If any step fails, the command cleans up partial state in reverse order: abort mission → remove content stubs → remove pin file → remove registry entry → remove system directory.
- **Noop case:** If the system-id already exists without `--amend`, the command fails with an explicit error. With `--amend`, it fails if the system-id does not exist.
- The `onboard` skill orchestrates the full pipeline: brief validation → `onboarding.synthesize` → AI synthesis → `sternsystem.register` → handoff.

## Branch convention (RFC-0648)

- All Sternsystem cache clones (mirrors[0]) and bare mirror repos (mirrors[1]) MUST use `main` as their default branch, not `master`. Enforced by `sternsystem.validate` (`branch-convention` rule).
- When creating new Sternsystem bare repos, use `git init --bare -b main` (or `git init -b main` for non-bare repos) to ensure compliance from creation.
- Agents MUST NOT rename branches automatically. Branch renaming (`git branch -m master main`) is a manual operator action that affects all mirrors simultaneously. Agents MAY recommend the rename commands but MUST NOT execute them without explicit operator approval.
- The fallback branch name in `sternsystem.status` and `mission.close` is `"main"` — if `git symbolic-ref HEAD` fails (detached HEAD), the code falls back to `"main"`.
- `mission.materialize` uses `git init -b main` for the non-git cache clone fallback to ensure workpieces start on `main`.

## Identity model (RFC-0558)

- **`identity/` module:** `identity-module.ts` registers 4 commands: `identity.bootstrap`, `identity.credential.issue`, `identity.credential.verify`, `identity.credential.revoke`. Shared I/O helpers in `identity/identity-io.ts`.
- **`werkstatt.identity.json`:** Workspace-level config file storing operator name, public key, auth mode (`permissive` or `enforced`), issued credentials, and revocation list. Created by `identity.bootstrap`, committed to git.
- **`PASSPORT_SIGNING_KEY` env var:** 32-byte Ed25519 private key as hex. Set after `identity.bootstrap` prints it to stdout. Required for `identity.credential.issue`.
- **`actor` field semantics:** `mission.open`, `mission.close`, `mission.abort`, and `mission.reconcile` accept `--actor-from-auth` flag to read actor identity from `WERKSTATT_ACTOR_ID` env var set by Studio Gate auth middleware. The `--actor` CLI flag is a fallback. Precedence: `--actor-from-auth` > `--actor` > `"unknown"` default. If `--actor-from-auth` is set but env vars are missing, the command throws an `actor-required` error. The `actor` value is a VC subject id (did:web) when authenticated via Studio Gate, or `"unknown"` for direct CLI usage.
- **Env-var propagation contract (RFC-0560):** Studio Gate sets `WERKSTATT_ACTOR_ID` (VC subject id), `WERKSTATT_ACTOR_SITE` (site id), and `WERKSTATT_ACTOR_SCOPES` (comma-separated scope list) in the child process environment before dispatching site-kernel commands. These env vars are the auth context propagation mechanism — agents MUST NOT read actor identity from LLM-provided values when `--actor-from-auth` is set.
- **Signed commits (RFC-0560):** `mission.git.commit` signs commits with Ed25519 when `PASSPORT_SIGNING_KEY` env var is set. Signed commits include `Werkstatt-Actor` and `Werkstatt-Signature` trailers added via `git commit --amend`. When the key is not set, commits are unsigned with `signed: false` and a stderr warning. The actor id for signing is taken from the mission manifest's `openedBy` field. Existing Bordbuch entries with `actor: "agent"` remain valid — no migration required.
- **Credential types:** `SiteOwnershipCredential` (operator → site ownership) and `ActorDelegationCredential` (operator → agent delegation, with expiry and scopes).
- **Canonicalization:** Identity credential subjects are canonicalized via sorted-key JSON (`identityCredentialBytes` in `@warpgogol/passport/identity-sign`). This is separate from `credentialBytes` in `sign.ts` (which handles build provenance `CredentialSubjectDigest`).

## Deploy (RFC-0566)

- **`deploy/` module:** `deploy.module.ts` registers 6 commands: `deploy.artifact.build`, `deploy.artifact.verify`, `deploy.atomic.swap`, `deploy.atomic.rollback`, `deploy.artifact.gc`, `deploy.status`. Shared utilities in `deploy/deploy-utils.ts`.
- **Artifact store:** Platform artifacts live at `.werkstatt/artifacts/platform/<sha-256>/` with `dist/` and `manifest.json`. The `current` and `previous` symlinks point to artifact directories. The filesystem is the only state source — no database or registry file.
- **`deploy.artifact.build`:** Runs `turbo run build`, copies `packages/*/dist/` trees into a staging directory, computes SHA-256 content hash via `@warpgogol/fingerprint` `byteHash`, writes `manifest.json` (hash, file list, git SHA, build time, build host), and signs it with Ed25519 via `@warpgogol/site-kernel-integrity` `signJsonPayload`. Flags: `--skip-build` (use existing dist), `--skip-sign` (unsigned manifest). Requires `SIGNING_PRIVATE_KEY` env var for signing (skipped silently if absent).
- **`deploy.artifact.verify`:** Recomputes content hash of `dist/` directory, compares against `manifest.json` hash, and verifies Ed25519 signature via `verifyJsonSignature` if `SIGNING_PUBLIC_KEY` env var is set. Returns `{ verified, hash, expectedHash, signatureVerified }`.
- **`deploy.atomic.swap`:** Verifies artifact hash first (aborts on mismatch), then atomically swaps `current` symlink via `rename(2)`. Updates `previous` symlink to old `current` target. First deploy creates `current` only (no `previous`). Flag: `--hash` (required).
- **`deploy.atomic.rollback`:** Reads `previous` symlink target, verifies artifact hash, atomically swaps `current` back. Returns `no-previous-artifact` error code (exit 1) if no `previous` symlink exists.
- **`deploy.artifact.gc`:** Scans artifact directories, never deletes artifacts referenced by `current` or `previous` symlinks, retains last 5 by default (configurable via `--retain N`). Flags: `--dry-run` (report only), `--retain N`.
- **`deploy.status`:** Read-only command reporting `currentHash`, `previousHash`, `currentGitSha`, `deployedAt` from symlinks and manifest.
- **Coexistence with Leitstand:** This module adds a complementary symlink-swap deployment path for local platform deployments. The Leitstand (DNA-49) continues to manage Cloudflare Workers deployments via adapter plugins.
- **Two-phase commit:** `TwoPhaseCommitResult` and `WorkshopDeployStatus` types are defined in `types.ts` as stubs for Phase 4 multi-workshop atomic deploys. No logic is implemented in the pilot.

## Three-phase build pipeline (RFC-0356, RFC-0357)

- **All distribution-producing commands must run the full three-phase build pipeline:** `build.prepare` → `astro build` → `build.post`, unconditionally and in that order. Each phase must succeed — a failure in any phase aborts the build and the distribution is not signed.
- **`build.post` is non-negotiable:** it runs `text.normalize.apply` (RFC-0235 egress text normalizer that replaces em dashes, curly quotes, special spaces, and other AI-authorship typographic signals), `passport.emit`, `dist.sitemap.images.generate`, `video.dist.prune`, and `dist.generated-marker.strip`. Without `build.post`, the dist output is raw Astro output — unnormalized and unsigned.
- **Affected commands:** `mission.build`, `mission.validate` (after the `astro build` step), and `release.prepare` (fresh build path, not the reuse path).
- **`mission.build` also writes `build-input-hash.json`** so `release.prepare` can reuse the distribution when the build input hash matches (content tree hash + platform version + platform semantic hash).
- **Never call `execSync("pnpm exec astro build")` directly** without wrapping it in the full pipeline. The pipeline runner (`executeKernelPipeline`) resolves the site workspace (including mission workpieces) and invokes all registered commands in the pipeline.

## Release commands (RFC-0357 / RFC-0585)

- **`release.prepare`:** Runs the full three-phase build pipeline (`build.prepare` → `astro build` → `build.post`) on the mission workpiece, or reuses `missions/<id>/distribution/dist` when its `build-input-hash.json` matches the current build input. Captures production and readable behavior snapshots from the build output via `behavior.snapshot.capture`, runs `behavior.snapshot.diff` between them, and computes `distTreeHash`, `siteContentHash`, `behaviorSnapshotHash`, and `readableSnapshotHash` via `@warpgogol/fingerprint` — never `sha256:pending`. If the snapshot diff fails, the prepare aborts with a non-zero exit code.
- **`release.publish`:** Refuses to publish any release whose `distTreeHash` is `sha256:pending` or missing, or whose `dist/` directory does not exist. The guard is fail-hard from the first run — no opt-in, no grace period.
- **Forward-only:** Existing releases with `sha256:pending` hashes must be deleted manually by the operator before running the new `release.prepare`. No migration path is provided.
- **RFC-0655: release.state.validate** — Validates release pipeline consistency across five checkpoints: (1) `mission-yaml-release-id-exists` — release directory exists when `mission.yaml` declares a `releaseId`; (2) `close-report-release-id-consistent` — `close-report.json` `releaseId` matches `mission.yaml`; (3) `release-state-progressed` — release is not stuck in `prepared` state (orphaned); (4) `bordbuch-release-id-consistent` — latest `mission-close` bordbuch entry `releaseId` matches `mission.yaml` (null is acceptable — close before `release.prepare`); (5) `registry-last-release-consistent` — `systems/registry.yaml` `lastRelease` matches the promoted release. Supports `--mission`, `--release`, and `--system` flags. Returns `ReleaseStateCheck[]` with `pass`/`warn`/`fail`/`skip` status per check.
- **RFC-0655: CloseReport.releaseId** — `mission.close` now includes `releaseId` in `CloseReport` and passes it as a top-level option to `appendBordbuchEntry`. `release.prepare` syncs `releaseId` to `close-report.json` after writing the mission manifest, ensuring consistency between `mission.yaml` and `close-report.json`.

## Evidence preservation (RFC-0650)

Axiom evidence from `mission.check` is preserved as an append-only archive in Cloudflare R2 (S3-compatible object storage) with timestamped keys. This RFC establishes DNA-59 (Evidence preservation).

- **R2 bucket:** `axiom-evidence` (single shared bucket, created by operator).
- **Key structure:** `{systemId}/{missionId}/{runTimestamp}/{filename}`
- **Timestamp format:** `YYYY-MM-DDTHH-MM-SS-mmmZ` (ISO 8601 UTC with colons and dots replaced by hyphens, milliseconds included). Filesystem-safe and lexicographically sortable.
- **`evidence-metadata.json`:** Now includes `runTimestamp` field (always present, written by `mission.check`). The `--run-timestamp` flag allows explicit timestamp specification (used by `evidence.sync` in RFC-0651 to ensure key consistency). When not provided, `mission.check` auto-generates from `new Date().toISOString()` with `[:.]` replaced by `-`.
- **R2 lifecycle rules:**

  | Prefix pattern | Transition | After | Rationale |
  | --- | --- | --- | --- |
  | `*/raw/*` | Standard → Infrequent Access | 7 days | Raw artifacts (screenshots, axe JSON) rarely accessed after first week. |
  | `*/raw/*` | Infrequent Access → delete | 365 days | After 1 year, raw screenshots have no forensic value. |
  | `*` (all other objects) | No transition | — | Structured JSON and report.html are small (~19 MB total) and retained indefinitely. |

- **R2 Data Catalog:** Managed Apache Iceberg table `axiom_evidence_runs` on the `axiom-evidence` bucket. Schema:

  | Column              | Type      | Description                                   |
  | ------------------- | --------- | --------------------------------------------- |
  | `system_id`         | string    | Sternsystem ID                                |
  | `mission_id`        | string    | Mission ID                                    |
  | `run_timestamp`     | timestamp | Run timestamp (ISO 8601 UTC)                  |
  | `commit_sha`        | string    | Git commit SHA from evidence-metadata.json    |
  | `findings_count`    | int       | Total findings from study-run.json            |
  | `errors_count`      | int       | Error-level findings                          |
  | `warnings_count`    | int       | Warning-level findings                        |
  | `closure_satisfied` | boolean   | Whether staged-capsule.json indicates closure |
  | `r2_key_prefix`     | string    | R2 key prefix for this run                    |

  The Iceberg table is written by `evidence.sync` (RFC-0651), not by this RFC. Partitioned by `system_id`.

- **Operator-only setup:** R2 bucket creation, Data Catalog enablement, and lifecycle rule configuration are **manual operator actions**. Agents MUST NOT run `wrangler r2 bucket create`, `wrangler r2 bucket catalog enable`, or `wrangler r2 bucket lifecycle` without explicit operator approval.
- **`evidence.sync` and `evidence.fetch`** are defined in RFC-0651, not this RFC. Integration into `mission.close` and `leitstand.dev-deploy` is defined in RFC-0652.
- **Local evidence remains ephemeral** (latest run only). R2 is the durable history.

## Test conventions

- **Await async operations before sync assertions:** When testing sync functions that inspect file state (e.g. `isWorkpieceDirty`, `existsSync`), always `await fs.writeFile()` or other async I/O before calling the sync function. Using `.then()` without awaiting creates a race condition — the assertion may execute before the file is written, causing flaky test failures.
- **Adapter-internal behavior tests go in the adapter test file:** When a command test (e.g. `leitstand-0608-promote.test.ts`) mocks an adapter via `vi.mock`, tests about the adapter's internal behavior (e.g. health check route probe URL construction) must go in the adapter's own test file (e.g. `cloudflare-workers.test.ts`), not the command's test file. The mock prevents the real adapter code from executing, so the behavior under test never runs.
- **Extract shared test setup to `src/tests/helpers/`:** When 2+ test files in `src/tests/` duplicate workspace setup logic (git init, registry, system, mission scaffolding), extract the shared helpers to `src/tests/helpers/materialize-fixture.ts` and import from both. This avoids the Duplicated Code smell and keeps test setup consistent across materialization test files.
- **Test bordbuch entries must conform to `bordbuchEntrySchema`:** When writing bordbuch entries in test fixtures, include all required fields: `schemaVersion: "1.0.0"`, `status` (enum: `done` | `failed` | `waiting` | `escalated`), `releaseId` (nullable string), `occurredAt` (ISO datetime with milliseconds), and `missionId` (nullable string). The `hash` field must be `sha256:`-prefixed (not bare hex), computed via `computeEntryHash` which uses sorted-key `JSON.stringify(entry, Object.keys(entry).sort())`. Tests that hardcode hashes will fail — always compute the hash using the same sorted-key method or import `computeEntryHash` directly.
- **`runMissionClose` tests must provide a `logger` mock with `warn`:** The `KernelRuntimeContext` passed to `runMissionClose` in tests must include `logger: { info: () => {}, warn: () => {}, error: () => {}, success: () => {} }`. The `warn` method is required for the `skipEvidenceSync` path (`mission-close.ts:404`). Without it, the test fails with `TypeError: Cannot read properties of undefined (reading 'warn')`.
