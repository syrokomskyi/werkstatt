## Visual Control System (RFC-0233)

A federated **`visual` domain** over the RFC-0203 Diagnostic model that catches **positional / contextual** visual defects the isolated section schemas cannot — e.g. a `background: { kind: fade, noEndFade: true, endOpacity: 1 }` that fades into the page bottom edge is correct only while its section is **last**; append a section after it and the fade lands mid-page (the 2026-06-23 nicaragua bug).

- **Tiers.** Tier 1 (implemented) = deterministic invariants over authored content in page context. Tier 2 (rendered-DOM/regression) and Tier 3 (LLM perceptual) are designed in RFC-0233 and **deferred**.
- **Gating policy — by severity-class.** `deterministic` rules (`VIS-BG-01/02`, `VIS-BG-04`) gate the build as `error`. `heuristic`/`perceptual` rules (`VIS-BG-03`) default to `warning` and only gate when a site escalates them in `src/content/system.md` frontmatter: `visual: { gate: { "VIS-BG-03": error } }`.
- **Adding a visual rule.** (1) Register the id in `src/diagnostics/rules.ts` with `{ domain: "visual", tier, severityClass }`. (2) Add a pure check in `src/visual/rules.ts` emitting a `Diagnostic` with `file`/`line` + `fixHint`. (3) Done — no pipeline wiring: it already runs inside `visual.contract.validate` (build.check + app.qa.validate) and shows up in `visual.rules.list`.
- **Where it runs.** `visual.contract.validate` is a step in the `build.check` pipeline and in the `app.qa.validate` deterministic subset.

## Rules

- All functions accept `(input: KernelCommandInput, context: KernelRuntimeContext)` — standard kernel signatures.
- **RFC-0203: report findings as canonical `Diagnostic[]`.** Every result builder in `result-helpers.ts` emits the canonical `CheckResult` (`{ command, status, diagnostics, summary }`):
  - `diagnosticsResult(command, Diagnostic[])` — the **rich** path. Each `Diagnostic` carries a **registered** `ruleId` (add it to `src/diagnostics/rules.ts`), a `severity` (`error | warning | info`), a one-sentence `message`, an optional `file`/`line`/`column` locator, and an imperative `fixHint`. Use this for any check with distinct violation kinds or actionable fixes.
  - `resultFromViolations` / `failResult` / `passResult` — the **coarse** path for single-rule checks; each violation string becomes an error `Diagnostic` keyed to `ruleId = command`. Not a shim — fully canonical. Repair findings by **structure**, not by concatenating into the message — the central printer (RFC-0086) renders `ruleId · file:line:column · message` plus a `fix:` line for agents. Do not log findings manually; the runtime renders them on failure. `diagnostic.shape.lint` fails (DSL-02/03) on unregistered or empty `ruleId` literals in checks that call `diagnosticsResult`.
- **RFC-0247: actionable warnings must never be summary-only.** If a check has warning/info debt, return it through `diagnosticsResult()` with a registered `ruleId`, `severity`, `message`, and useful `file`/`fixHint` where possible. Do not put `[warn:...]`, prose-warning arrays, or warning counts only in `KernelCommandResult.summary`; `warning.diagnostics.lint` guards this.
- Path resolution goes through `requireAstroSitePaths(context)` from `@warpgogol/site-kernel-astro`.
- No app-specific business logic here. App-specific commands stay in `apps/*/tools/`.
- No hardcoded app names, languages, or content paths.
- Missing directories return empty results (no throws) — graceful degradation for new/sparse apps.
- **Do not silently filter declared entries by filesystem existence (RFC-0582).** When a blueprint or declaration is declared in `system.md`, do not add `existsSync` filters that silently drop it from processing. Let the expansion/generation logic handle empty or missing collection states — depth-0 hubs are generated from blueprint level definitions, not collection records. If a declared and entitled blueprint produces zero entries, emit a diagnostic (e.g. `SURFACE-GEN-01`) rather than silently skipping it.
- `createCompassInventoryEntries` is part of the public API so that `site-kernel-codegen` can reuse it for backfill operations.
- `APPS_CHECK_PIPELINE` is the authoritative ordered list of active app pipeline steps; spread it in `kernel.config.ts` pipelines and append app-specific steps after.
- `PACKAGES_CHECK_PIPELINE` is the authoritative ordered list of active workspace package validation steps; shared UI copy checks belong there rather than in package-local ad-hoc scripts.
- `createStandardCheckModule` registers all site-kernel-checks commands; pass app-specific and codegen commands via `extraCommands`. New apps need no command boilerplate.
- **Do NOT register `lighthouse.validate` or `lighthouse.budget.check` in app `extraCommands`.** These commands are now centrally registered via `ALL_COMMANDS` (`command-tables/05-seo-audit.ts`). Re-registering them causes a "Kernel command already registered" runtime error.
- **RFC-0205: no silent empty-string fallbacks on UI-visible text props.** Shared UI components in `packages/ui/src/` must not use `= ""`, `?? ""`, `|| ""`, or `defaultContent: ""` on props that render visible text (`title`, `heading`, `label`, `subtitle`, `badgeLabel`, etc.). The `ui.silent-defaults.lint` command scans for these patterns and fails the build. If TypeScript requires a string where a prop may be `undefined`, use a dedicated `orEmpty()` helper instead of inline `?? ""`.
- **See `docs/check-module-guide.md` for detailed onboarding instructions, complete command reference, and troubleshooting (duplicate command registration errors).**
- **RFC-0303: `PAGES_NON_ROUTE_SUBDIRS` has a single owner in `src/lib/route-constants.ts`** — import it instead of re-declaring the excluded-subdirs set locally (`fs.walk.lint`/`dedup.helper.lint` guard the fs/text-helper half of this rule; there is no dedicated lint for constants, so this is a code-review convention).
- `naming.convention.lint` enforces **strict** kebab-case: PascalCase, camelCase, and ALLCAPS are all violations. Exemptions: dot-prefix, underscore-prefix, `config`/`module` in name.
- `naming.components.lint` only checks file type correctness inside `src/components/` — name format is covered by `naming.convention.lint`.
- `assets.structure.lint` covers raster images only; SVG icon source files live in `src/assets/icons/` and are not checked separately (the icon pipeline manages them).
- `naming.suffixes.lint` enforces RFC-0020 suffix contract across three layers: `.astro` (components), `.css` (styles/components), and `.md` (content/components). `layout.md` is a Class-4 singleton exempt from the `-component` rule.
- `naming.layouts.lint` enforces the RFC-0020 singleton contract: `src/layouts/` may only contain `layout.astro` as a file-level entry. Subdirectories are not checked.
- **SVG logo components are excluded from Compass scaffolding** — Files in `src/components/logo/` (e.g., `telegram.astro`, `whatsapp.astro`) contain only static SVG markup and do not require `MODULE_CONTRACT`, `MODULE_MAP`, or `CHANGE_SUMMARY` headers. These are pure presentational components with no business logic.

## Command reads/cacheable contract (RFC-0390)

Every registered kernel command MUST declare either `reads: string[]` (non-empty, valid picomatch globs) or `cacheable: false`. The `command.reads.validate` command enforces this contract and is a step in `PACKAGES_CHECK_PIPELINE`.

- **`reads`** — workspace-root-relative path globs declaring which files a command reads. The pipeline executor hashes matching files via `@warpgogol/fingerprint` and skips re-execution on cache hit. Use the `<app>` token for app-scoped paths (e.g. `<app>/src/content/system.md`).
- **`cacheable: false`** — opts out of caching entirely. Required for commands that depend on external state (network, secrets, time, external binaries). Commands without `reads` MUST set this to false.
- **CRC-01** — command has no `reads` and `cacheable` is not false → error.
- **CRC-02** — `reads` pattern is invalid picomatch syntax → error.
- Network-dependent commands (Cloudflare API, Matomo API, Stripe API, Supabase) MUST be marked `cacheable: false`.
- Commands that depend on external binaries (exiftool, c2patool) SHOULD be marked `cacheable: false` unless the binary version is included in the cache key.

## Pipeline registration (three-place rule)

When adding a new pipeline constant to `src/pipelines/`, register it in **three** locations:

1. **Template** — `packages/os/site-kernel/src/templates/wire/tools/kernel.config.template.ts` (so new Sternsystems get it automatically).
2. **Telemetry** — `src/pipeline/pipeline-telemetry.ts` `standardPipelines()` array.
3. **Ecosystem manifest** — `src/ecosystem/manifest.ts` `exported` array.

Missing (2) or (3) leaves the pipeline invisible to `pipeline.timing.report` and the Agent Control Plane manifest, causing drift between the kernel config and the ecosystem manifest.

## Architecture reference

→ `packages/os/site-kernel/AGENTS.md` — kernel architecture table  
→ `packages/os/site-kernel/docs/site-os.md` — operator guide  
→ `docs/source-markup.xml` — canonical Compass source-file markup contract

- **`docs/source-markup.xml` is a markup contract, not a file inventory.** Do not add individual source-file entries to it. The Compass file inventory (`docs/compass-inventory.xml`) is generated by `compass.inventory.generate` and automatically picks up new source files.

- **Validator output shape: always use the existing `CheckResult` pattern.** RFCs may contain idealized output formats (e.g., `diagnostics[]` with `ruleId` fields), but implementations MUST follow the existing `CheckResult` standard: `violations[]` with `rule`, `file`, `message`, and `fix` fields, returned via `ok(cmd)` / `fail(cmd, violations)` from `./shared.ts`. Do not invent new output shapes — consistency across all validators is more important than RFC aspirational formats. If an RFC specifies a different shape, update the RFC to match the implementation.
