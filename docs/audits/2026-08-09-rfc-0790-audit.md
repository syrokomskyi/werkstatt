## Axis 1: Structural completeness — **Needs revision**

- ✅ All required frontmatter fields present.
- ✅ All required markdown sections present (Context, Problem, Decision, Architectural fit, Design, Rollout, Alternatives, Risks, Acceptance criteria, Implementation notes).
- ⚠️ **F-01**: `satisfies` field lists only DNA-44, DNA-45. The RFC body explicitly changes mission lifecycle (DNA-46) and materialization (DNA-47) — `mission.open/materialize/reconcile/close/abort` and `mission.materialize` cache clone path resolution are modified. DNA-46 and DNA-47 should be in `satisfies` since the RFC extends them.
- ⚠️ **F-02**: `amends` list is incomplete. The RFC changes mission lifecycle (DNA-46, established by RFC-0355) and materialization (DNA-47, established by RFC-0356), but `amends` only lists RFC-0354, RFC-0574, RFC-0472. RFC-0355 and RFC-0356 should be in `amends` (or the RFC should explain why amending RFC-0354 is sufficient to cover mission/materialization changes).
- ⚠️ **F-03**: `packagesImpacted` lists `@warpgogol/werkstatt-site`, but all registry I/O code lives in `@warpgogol/werkstatt`. Grep for `FleetRegistryEntry|FleetRegistry|fleetRegistrySchema` found matches only in `packages/werkstatt/src/`. Either remove `werkstatt-site` from `packagesImpacted` or explain why it's impacted.

## Axis 2: DNA alignment — **Needs revision**

- ✅ DNA-44 (Sternsystem bundle contract): correctly extended — cache clone now carries the complete system package.
- ✅ DNA-45 (Fleet registry): correctly amended — central registry replaced by convention-based discovery.
- ⚠️ **F-04**: DNA-1 (Monorepo boundary) says "Each deployable site is a Sternsystem registered in `systems/registry.yaml`". This DNA entry directly references `systems/registry.yaml` and needs updating. The RFC amends DNA-44 and DNA-45 but does not mention DNA-1 in `satisfies` or `amends`.
- ⚠️ **F-05**: DNA-46 (Mission lifecycle) and DNA-47 (Materialization) are modified by the RFC (cache clone path resolution changes from `mirrors[0].path` to convention path) but are not in `satisfies`. See F-01.

## Axis 3: Ecosystem fit — **Needs revision**

- 🔴 **F-06**: `services/registry.yaml` does not exist. Services are currently defined in `systems/registry.yaml` (lines 57–106: `matomo-proxy`, `rate-fetcher-worker`, `lagebild-sync-worker`, `telegram-alert-bridge`). The RFC says "services/registry.yaml remains in monorepo unchanged" and lists it as an acceptance criterion, but it needs to be **created** by extracting services from `systems/registry.yaml`. The RFC must explain this extraction and add an acceptance criterion for it.
- ⚠️ **F-07**: `deploymentConfigSchema` ambiguity. The RFC's `systemConfigSchema` includes `deployment: deploymentConfigSchema.optional()`, which currently contains `lastPropagated` (lines 53–59 of `leitstand.ts`). The RFC's `systemStateSchema` also has `lastPropagated` at the top level. This creates duplication — `lastPropagated` would be in both `system-config.yaml` (inside `deployment`) and `system-state.yaml`. The RFC should explicitly state that `deploymentConfigSchema` is modified to remove `lastPropagated`, or introduce a `deploymentStaticConfigSchema` without it.
- ⚠️ **F-08**: `lastPropagated` shape mismatch. The current `deploymentConfigSchema.lastPropagated` has `dev`, `alt`, `main` keys. The RFC's `systemStateSchema.lastPropagated` (lines 224–247) has only `alt` and `main` — `dev` is dropped. This is an undocumented schema change. Either explain why `dev` is removed from `lastPropagated` or include it.
- ⚠️ **F-09**: CI behavior. `sternsystem.validate` currently reads `systems/registry.yaml` from the monorepo. The RFC changes it to scan `../systems-cache/`, which is outside the monorepo. In CI, `../systems-cache/` may not be checked out, causing `sternsystem.validate` to find zero systems and pass vacuously. The RFC should address CI checkout behavior (e.g., CI must check out cache clones, or `sternsystem.validate` should warn when zero systems are discovered).
- ⚠️ **F-10**: `registry` lock. `mission.open` (line 100 of `mission-open.ts`) acquires a `registry` lock. `mission.close` also acquires it. With no registry file, this lock is obsolete. The RFC doesn't explain whether the `registry` lock is removed, kept as a no-op, or replaced with a per-system lock. The `sternsystem.register` rollback also reads/writes the registry under this lock.

## Axis 4: Forward-only compliance — **Needs revision**

- ✅ No backward compatibility layer — single atomic migration, consistent with Werkstatt's stance.
- ✅ `readRegistry()`, `writeRegistry()`, `findEntry()` are explicitly removed in acceptance criteria.
- ⚠️ **F-11**: Auto-commit mechanism. The RFC says `writeSystemState` "auto-commits via the existing auto-commit mechanism (RFC-0580)". But RFC-0580's `commitWerkstattSideEffects` commits to the **monorepo** git repo. The cache clone has its own git repo with its own commit mechanism (e.g., `appendAndCommitBordbuch` commits to the cache clone). The RFC should clarify that `writeSystemState` commits to the cache clone git repo, not via `commitWerkstattSideEffects`. The same applies to `sternsystem.pin` which currently writes to `systems/registry.yaml` and auto-commits via `commitWerkstattSideEffects` — with the RFC, it writes to `system-config.yaml` in the cache clone and needs a different commit path.

## Axis 5: Agent-facing policy — **Needs revision**

- ✅ Clear implementation notes with explicit MUST/MAY/MUST NOT directives.
- ✅ "Agents MUST NOT read `systems/registry.yaml`" — explicit prohibition.
- ✅ "Agents MUST use `resolveCacheClonePath()`" — explicit guidance.
- ⚠️ **F-12**: `AGENTS.md` update scope is vague. The acceptance criterion says "AGENTS.md updated: remove references to `systems/registry.yaml`". The root `AGENTS.md` has multiple references: DNA-1 ("registered in `systems/registry.yaml`"), the "External mirror sync" section ("Each Sternsystem declares a `mirrors[]` array in `systems/registry.yaml`"), and the "Monorepo layout" section. The RFC should list the specific sections that need updating or provide the replacement text.

## Axis 6: Pragmatism — **Approved with notes**

- ✅ Convention-based discovery is simpler than a central registry for the current single-system fleet.
- ✅ Alternatives are well-considered (bootstrap circular dependency, configurable path, two-phase migration, sharding).
- ✅ Rollout is a single atomic mission — consistent with Werkstatt's no-backward-compatibility stance.
- ⚠️ **F-13**: "30+ call sites" understates the scope. Grep found 209 matches across 48 files for `readRegistry|writeRegistry|findEntry|resolveCachePath`. The actual number of call sites is large. The RFC should provide a more precise count or acknowledge the implementation scope more accurately. This affects the "single atomic mission" feasibility — the implementation is a large refactor touching nearly every sternsystem/mission/release/leitstand/bordbuch/notausgang command.

## Axis 7: Blind spots — **Needs revision**

- 🔴 **F-14**: See F-06 — `services/registry.yaml` doesn't exist. This is a factual error in the RFC and its acceptance criteria.
- 🔴 **F-15**: See F-07 — `deploymentConfigSchema` not modified. `lastPropagated` would be duplicated across config and state files.
- ⚠️ **F-16**: `systems/warpgogol-com/` directory is empty (0 items). The RFC's acceptance criterion says "systems/<id>/ per-system subdirectories deleted (DNS, suppressions moved to cache clone)" — but there are no per-system subdirectories to delete. `axiom-suppressions.yaml` is at `systems/axiom-suppressions.yaml` (not per-system). The RFC should correct the acceptance criterion to reflect the actual file layout.
- ⚠️ **F-17**: `sternsystem.list` in a fresh monorepo clone. Currently, `sternsystem.list` reads `systems/registry.yaml` from the monorepo and works without cache clones. With the RFC, `sternsystem.list` scans `../systems-cache/` — which is absent in a fresh monorepo clone. The RFC should acknowledge this behavioral change and document that `sternsystem.list` requires cache clones to be present.
- ⚠️ **F-18**: `fleet/` directory. The workspace has a `fleet/` directory with `fleet.sites.yaml`, `fleet.plan.generated.yaml`, etc. Grep found no "registry" references in `fleet/` files, so this is likely unaffected. The RFC should acknowledge `fleet/` and confirm it doesn't reference `systems/registry.yaml`.

## Verdict: **Needs revision**

3 errors (F-06, F-07, F-14/F-15) and 15 warnings. The RFC has a strong architectural direction and well-considered alternatives, but must address:

1. **Services extraction** (F-06): Explain how services are extracted from `systems/registry.yaml` into a new `services/registry.yaml`. Add acceptance criterion.
2. **`deploymentConfigSchema` modification** (F-07): Explicitly state that `lastPropagated` is removed from `deploymentConfigSchema` to avoid duplication with `systemStateSchema`.
3. **`lastPropagated` shape** (F-08): Explain why `dev` is dropped from `lastPropagated` in `systemStateSchema`, or restore it.
4. **`satisfies` and `amends` completeness** (F-01, F-02, F-04, F-05): Add DNA-46, DNA-47 to `satisfies`; add RFC-0355, RFC-0356 to `amends`; address DNA-1 reference to `systems/registry.yaml`.
5. **Auto-commit mechanism** (F-11): Clarify that cache clone file commits use the cache clone git repo, not RFC-0580's monorepo `commitWerkstattSideEffects`.
6. **CI behavior** (F-09): Address `sternsystem.validate` when `../systems-cache/` is absent in CI.
7. **`registry` lock** (F-10): Explain whether the `registry` lock is removed or replaced.
8. **Acceptance criteria accuracy** (F-16): Correct references to `systems/<id>/` subdirectories that don't exist.
