# Audit: RFC-0838

## Verdict: Needs revision

The RFC is structurally complete and architecturally sound, but references a non-existent route manifest file (`<app>/src/routes.generated.yaml`) for route discovery, and proposes registering the command in `04-content-quality.ts` while the pipeline predecessor `lighthouse.budget.check` lives in `05-seo-audit.ts`. These must be resolved before implementation.

## Mechanical validation (rfc.validate)

Pass with 1 warning:
- **V-18** (warning): `related "DNA-68"` is not defined in `docs/architecture-dna.md`. DNA-68 is established by RFC-0837 (still `draft`). This is expected in a series of draft RFCs — the warning will resolve when RFC-0837 is implemented and DNA-68 is appended.

## Axis A — Structural completeness

No issues. All required sections are present with real content:
- Decision is a single statement in present tense.
- CLI surface shows exact invocations with flags and defaults.
- TypeScript contracts are minimal type signatures, not implementations.
- File system responsibilities table names concrete paths.
- Output format documents the `--json` shape with a full example.
- Failure modes specify exit codes and warn-vs-fail behavior.
- Rollout describes default behavior, adoption path, and new-site compliance.
- Alternatives considered has four real alternatives with rejection reasons.
- Risks includes execution time, false positives, Chromium version drift, and CLS accuracy.
- Acceptance criteria are checkable and cover the decision's scope.
- Implementation notes are explicit behavioral rules with correct governance references.

## Axis B — DNA alignment

No issues.
- `satisfies: [DNA-69]` — DNA-69 is not yet in `docs/architecture-dna.md`, but the RFC body explicitly states "Establishes DNA-69" and the acceptance criteria include "DNA-69 entry appended to `docs/architecture-dna.md`". This is the correct pattern for a new DNA invariant.
- The RFC body explains how it extends DNA-66 (workshop testing pyramid) with "a new L4-adjacent geometric check" and complements DNA-67 (pre-deploy Lighthouse parity gate) by "covering runtime properties Lighthouse cannot statically check". These are substantive explanations, not decorative references.
- `related: [DNA-66, DNA-67, DNA-68, RFC-0837, RFC-0839]` — DNA-66 and DNA-67 exist and are relevant. DNA-68 and the RFCs are part of the same three-layer series. All relevant.

## Axis C — Ecosystem fit

**Finding C-1: Command table placement inconsistent with pipeline predecessor.**
The RFC states the command will be "registered in `04-content-quality.ts`" (acceptance criterion: "CLI command registered with name `mobile.layout.check` and scope `app` in `04-content-quality.ts`"). However, `lighthouse.budget.check` — which the RFC says it follows in `SITES_CHECK_POSTBUILD_PIPELINE` — is registered in `05-seo-audit.ts` (`@/packages/werkstatt-site/src/checks/command-tables/05-seo-audit.ts:225`). The `mobile.layout.check` is a runtime Playwright geometric check, semantically closer to Lighthouse performance checks than to content quality checks (which are static file scanners). Either register in `05-seo-audit.ts` alongside `lighthouse.budget.check`, or justify why `04-content-quality.ts` is the correct table.

**Finding C-2: Route discovery references a non-existent file.**
The RFC's file system responsibilities table lists `<app>/src/routes.generated.yaml` as "Read (route discovery)", and the execution flow says "Read the site's route manifest (generated by `routes.generate`)". However, `routes.generate` (`@/packages/werkstatt-site/src/checks/command-tables/01-codegen.ts:89`) generates Astro route files (`.astro` templates), not a YAML route manifest. No file named `routes.generated.yaml` exists anywhere in the codebase. The existing `qa.independent.run` (RFC-0333) discovers routes by scanning `dist/client/**/*.html` directly. The RFC must either:
- Scan `dist/client/**/*.html` directly (like `qa.independent.run`), or
- Read from `system.md` manifest pages, or
- Introduce a new route manifest generation step (which would expand scope).

## Axis F — Pragmatism

**Finding F-1: `@warpgogol/werkstatt` impact is speculative.**
The RFC lists `@warpgogol/werkstatt` in `packagesImpacted` and the file system table says `packages/werkstatt/src/testing/e2e/types.ts` will be "Extended with mobile layout types (if shared)". The "if shared" qualifier is speculative — the types could live entirely in `packages/werkstatt-site/src/checks/mobile-layout-check.ts`. Unless there is a concrete consumer in `@warpgogol/werkstatt` that needs these types, remove `@warpgogol/werkstatt` from `packagesImpacted` and the file system table entry. This follows the minimality ladder: don't create a shared type until a second consumer demands it.

**Finding F-2: Preview server should reference existing pattern.**
The RFC says "Start `astro preview` (or a simple static file server) on a random port serving `dist/`." The existing `qa.independent.run` (RFC-0333) already implements a `createStaticServer` function (`@/packages/werkstatt-site/src/checks/independent-qa.ts:76`) that serves `dist/client` on a random port. The RFC should reference this existing pattern rather than introducing `astro preview` as an option. Using `astro preview` adds an Astro dependency to a post-build check that should only need a static file server.

## Axis G — Blind spots

**Finding G-1: No `dist/` existence check documented.**
The failure modes section does not specify what happens when `dist/` doesn't exist (no build has been run). `qa.independent.run` handles this by skipping with a message ("skipped — no dist/client for <site> (run build first)"). The RFC should add this failure mode or reference the existing pattern.

**Finding G-2: Concurrent execution on same site not addressed.**
Two simultaneous `mobile.layout.check` runs on the same site would both try to start a preview server. The RFC says "random port" which mitigates port conflicts, but both would launch Playwright Chromium instances. This is acceptable but should be noted — on CI, parallel pipeline steps could multiply Chromium memory usage.

## Questions for the author

1. How will route discovery work? `<app>/src/routes.generated.yaml` doesn't exist in the codebase. Will you scan `dist/client/**/*.html` directly (like `qa.independent.run`), read from `system.md` manifest pages, or introduce a new route manifest generation step?
2. Why is the command registered in `04-content-quality.ts` instead of `05-seo-audit.ts` where `lighthouse.budget.check` lives? The `mobile.layout.check` is a runtime Playwright geometric check, semantically closer to Lighthouse checks than to static content quality checks.
3. Is `@warpgogol/werkstatt` really impacted? The RFC says types "if shared" — could the types live entirely in `werkstatt-site` to avoid speculative cross-package impact?
