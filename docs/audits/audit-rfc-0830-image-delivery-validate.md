# Audit: RFC-0830

## Verdict: Needs revision

The RFC addresses a real performance problem (LCP 14.3s from oversized images) and proposes a well-structured validator. However, it contains a factual error in pipeline placement, a major unresolved design gap in how `image.variants.generate` will scan package-level `.astro` files from app scope, and an unspecified escape hatch schema.

## Mechanical validation (rfc.validate)

Pass — zero violations.

## Axis A — Structural completeness

No issues. All sections contain real content: Decision is a single present-tense statement, CLI surface shows invocations, TypeScript contracts are minimal type signatures, file system responsibilities table names concrete paths, output format and failure modes are documented, rollout covers default/existing/new apps, alternatives has 4 real rejections, risks includes agent confusion and false-positive rate, acceptance criteria are checkable, implementation notes are explicit behavioral rules.

## Axis B — DNA alignment

- **DNA-4 connection is weak.** DNA-4 says "All user-visible copy, configuration, and metadata live in `src/content/`." The RFC claims shell-level images "are part of the site's visual content surface" and that this "extends the image delivery contract to cover them." But DNA-4 governs canonical content placement — it doesn't talk about images or delivery. Shell-level images in `packages/werkstatt-site/src/domain/ui/` `.astro` templates are explicitly on the engineering surface, not in `src/content/`. The RFC should either drop DNA-4 from `satisfies` or explain more precisely how enforcing responsive delivery of shell-level images protects the content-layer boundary.

- **DNA-58 excludes binary files.** DNA-58 says "Binary files (PNG, ICO, WebP, ...) are excluded; their determinism is covered by RFC-0602 and RFC-0603." The WebP variants generated by the extended `image.variants.generate` are binary and thus outside DNA-58's scope. The YAML manifest is text-based and already covered by DNA-58 for the existing generator — extending to shell-level images doesn't change this relationship. The `satisfies: [DNA-58]` claim is decorative for the binary variants.

## Axis C — Ecosystem fit

- **Pipeline placement is factually wrong.** The RFC says `image.delivery.validate` runs "after `cloudflare.assets.validate` and before `lighthouse.budget.check`" in `SITES_CHECK_POSTBUILD_PIPELINE`. In the actual pipeline (`packages/werkstatt-site/src/checks/pipelines/sites-check-postbuild.ts`), `lighthouse.budget.check` is at line 49 and `cloudflare.assets.validate` is at line 56. `lighthouse.budget.check` runs BEFORE `cloudflare.assets.validate`, making the RFC's insertion point impossible as described.

- **CLI flag `--app` may conflict with convention.** ADR-0016 established `--site` (not `--app`) as the flag for site-scoped commands. The RFC's CLI examples use `--app warpgogol-com`. If the kernel CLI follows ADR-0016, the examples should use `--site warpgogol-com`.

## Axis D — Forward-only compliance

No issues. The 2-week grace period for IMG-DELIVERY-02/03 is a migration window with automatic escalation, not a compatibility shim or dual-path. No legacy code paths are maintained behind a flag.

## Axis E — Agent-facing policy

No issues. Status gate is correct ("Agents MAY implement code changes ONLY when this RFC has status: accepted (or implemented)"). Implementation notes reference RFC-0224 (accepted→implemented), `rfc.verification.emit`, and `rfc.supersede.propose` for invariant conflicts. No self-authorizing language. No NEEDS CLARIFICATION markers. No cookies or persistence introduced.

## Axis F — Pragmatism

- **`image-delivery.config.yaml` escape hatch is unspecified.** The RFC mentions it in Rollout (point 3) and Risks (mitigation) but never defines its schema, file path, or format. An acceptance criterion says "documented" but there is no design for what to document. This is a design gap that will block implementation.

- **`--include-shell` flag not declared.** The RFC proposes adding a `--include-shell` flag to `image.variants.generate`, but the existing command table entry (`07-structure-naming.ts:522-542`) declares `flags: {}`. The RFC should specify the flag declaration that will be added to the command table.

## Axis G — Blind spots

- **Major design gap: app-scope vs package-scope.** `image.variants.generate` runs with `scope: "app"` and reads content images from `<app>/src/content/` via `requireAstroSitePaths(ctx)`. The RFC proposes extending it to scan `.astro` component files in `packages/werkstatt-site/src/domain/ui/` — a different directory tree outside the app directory. The RFC does not explain how the generator bridges this scope gap: how it resolves the package directory from app-scope context, how it resolves `import heroBg from "./hero-bg.webp"` patterns to source files, or how the generated variants are referenced from the app's `public/_img/` directory. This is the core architectural challenge of the extension and it is unaddressed.

- **Displayed dimensions source unspecified for IMG-DELIVERY-03.** The rule says "served image dimensions MUST NOT exceed 2× the displayed dimensions at the mobile viewport (412px width)." The RFC says this is checked by "reading the image file header" and "comparing against the `boundingRect` from the rendered HTML parse." But parse5 (used elsewhere in the pipeline) parses HTML structure — it does not compute layout or bounding rects. Determining displayed dimensions at a specific viewport width requires CSS layout or a headless browser. The RFC does not explain how `boundingRect` is obtained from static HTML parsing.

## Questions for the author

1. How will `image.variants.generate --include-shell` resolve shell-level image imports from `packages/werkstatt-site/src/domain/ui/` when the command runs with `scope: "app"` and reads from `src/content/`? What is the file resolution path from package `.astro` import to source image to generated variant?
2. What is the schema, file path, and format of `image-delivery.config.yaml`? How does the validator load and match override entries?
3. Where exactly in `SITES_CHECK_POSTBUILD_PIPELINE` should `image.delivery.validate` be inserted, given that `lighthouse.budget.check` (line 49) currently runs before `cloudflare.assets.validate` (line 56)?
4. How will IMG-DELIVERY-03 obtain displayed dimensions (`boundingRect`) from static HTML parsing without a layout engine or headless browser?
