After
                  flowchart TD
                    A[CallToolRequest handler] --> B[ToolDispatcher]
                    B --> C[AuthMiddleware]
                    B --> D[ArgBuilder]
                    B --> E[BuildQueue gate]
                    B --> F[Executor]
                    B -.seam.-> G[add / modify tool pipeline]

Problem: The CallToolRequest handler is a 50-line inline function performing tool lookup, auth verification, arg building, actor injection, build-queue gating, execution, and result formatting — all concerns are coupled in one closure.

Solution: Extract a ToolDispatcher that composes AuthMiddleware, ArgBuilder, and Executor behind a single dispatch(name, args, meta) interface; the handler becomes a thin delegate.

  • locality: each concern in its own module
  • leverage: one dispatch interface, N tools
  • depth: handler interface is one call

Extract AUTH_ERROR_CODES into a dedicated error-code catalog

Worth exploring in-process

Problem: AUTH_ERROR_CODES (10 entries) and formatAuthError (37 lines) live inside index.ts — the error catalog and its hint logic are coupled to the server entrypoint and not reusable by tests or other auth consumers.

Solution: Move them into a dedicated auth-errors.ts module; index.ts imports formatAuthError; the catalog can be tested independently.

  • locality: error catalog in one module
  • leverage: one catalog, testable in isolation
  • depth: index.ts interface shrinks
