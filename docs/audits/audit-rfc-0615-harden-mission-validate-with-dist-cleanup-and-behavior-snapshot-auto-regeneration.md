# Audit: RFC-0615

## Verdict: Needs revision

The RFC addresses real operational pain points (stale `dist/` false positives, manual snapshot regeneration), but the code snippet for snapshot auto-regeneration doesn't match the actual `build.post` pipeline architecture or the `CheckResult` return shape. The `appsImpacted` field is incorrect and the DNA-58 alignment is weak. These must be fixed before planning.

## Mechanical validation (rfc.validate)

Pass with 1 warning:

- **V-19 (warning):** `amends: [RFC-0593]` but RFC-0593's `amendedBy` does not include RFC-0615. Must be fixed during enhance — add `RFC-0615` to RFC-0593's `amendedBy[]`.

## Axis A — Structural completeness

1. **Code snippet field names don't match actual return shape.** The pseudocode uses `snapshotResult.status === "fail" && snapshotResult.violations.some(v => v.rule === "SNAP-01")` (line 138). The actual `behavior.snapshot.validate` returns `KernelCommandResult<CheckResult>` via `diagnosticsResult()` (`@/packages/os/site-kernel-checks/src/result-helpers.ts:29`). The `CheckResult` shape is `{ command, status, diagnostics, summary }` — it uses `data.diagnostics` (not `violations`) and each diagnostic has `ruleId` (not `rule`). The pseudocode must be corrected.

2. **Code snippet shows separate `executeKernelCommand` calls, but `behavior.snapshot.validate` runs inside the `build.post` pipeline.** `mission.validate` already calls `runPipelinePhase(workspaceRoot, "build.post", manifest.systemId)` (`@/packages/os/site-kernel-handoff/src/mission/mission-materialization-commands.ts:276`). `behavior.snapshot.validate` is a step inside `SITES_CHECK_POSTBUILD_PIPELINE` (`@/packages/os/site-kernel-checks/src/pipelines/sites-check-postbuild.ts:62`), which is spread into `SITES_BUILD_POST_PIPELINE` (`@/packages/os/site-kernel-checks/src/pipelines/build-post.ts:35`). The RFC must explain how to extract SNAP-01 diagnostics from the pipeline report (`KernelPipelineReport.steps[]`), not from a separate command call.

3. **File system responsibilities table is incomplete.** It lists `mission-validate.ts` but doesn't mention `packages/os/site-kernel-checks/src/pipelines/build-post.ts` or `packages/os/site-kernel-checks/src/behavior-snapshot.ts` — both are relevant to understanding the snapshot auto-regeneration flow.

## Axis B — DNA alignment

1. **DNA-58 connection is weak.** DNA-58 (Generated-file content determinism) states: "Every text-based generated file committed to git must be byte-identical to what its owning generator would produce from current source data." The RFC's dist cleanup prevents false positives from stale artifacts — that's about validation accuracy, not generated-file determinism. The snapshot auto-regeneration is about operational convenience, not enforcing byte-identity. A stronger fit would be **DNA-47 (Materialization)**, since `mission.validate` is part of the materialization flow (DNA-47 explicitly names `mission.validate` as an enforcer). Consider adding DNA-47 to `satisfies[]`.

## Axis C — Ecosystem fit

1. **`appsImpacted: [warpgogol-com]` is incorrect.** This is a workspace-scoped change to the `mission.validate` command — it affects ALL Sternsystems and missions, not just warpgogol-com. The field should be empty (no app-specific impact) or contain all active systems. The warpgogol-com reference in the Context section is the trigger incident, not the scope.

2. **Interaction with `build.post` pipeline not documented.** `build.post` already runs `behavior.snapshot.generate` immediately after `behavior.snapshot.validate` (`@/packages/os/site-kernel-checks/src/pipelines/build-post.ts:40`). The RFC doesn't address whether the pipeline continues on failure (in which case the snapshot is already regenerated by the pipeline) or stops (in which case a separate call is needed). This is a critical architectural question that determines whether the RFC's separate `behavior.snapshot.generate` call is redundant or necessary.

3. **Interaction with `mission.close` inline validation not documented.** RFC-0593 (implemented) made `mission.close` call `mission.validate` inline before transitioning to `closed` state. The auto-commit behavior proposed by this RFC will also trigger during `mission.close`'s inline validation. This interaction should be documented — `mission.close` would now create a commit as a side effect of its validation gate.

## Axis D — Forward-only compliance

No issues. The RFC amends RFC-0593 directly without introducing a compatibility layer or dual-path.

## Axis E — Agent-facing policy

1. **V-19 backlink must be fixed.** RFC-0593's `amendedBy[]` must include `RFC-0615`. This is a mechanical fix for enhance.

2. **Auto-commit during validation is a new side effect.** `mission.validate` currently only writes evidence reports to `missions/<id>/evidence/`. The RFC proposes adding `mission.git.commit` inside `mission.validate`, creating a workpiece commit as a side effect of validation. This is a semantic shift — `mission.validate` becomes a mutating command, not a read-only check. The RFC should address whether this is appropriate, especially when `mission.validate` is called from `mission.close`'s inline gate (RFC-0593).

3. **`reviewers: []` is empty.** While acceptable for draft status, V-25 will fail when transitioning to `implemented`. Add at least `human:andrii-syrokomskyi` during enhance.

## Axis F — Pragmatism

1. **Separate `behavior.snapshot.generate` call may be redundant.** `build.post` already includes `behavior.snapshot.generate` after `behavior.snapshot.validate` (line 40 of `build-post.ts`). If the pipeline continues on failure, the snapshot is already regenerated — the RFC only needs to commit it. If the pipeline stops on failure, the RFC should explain this and justify the separate call. The current pseudocode doesn't address this.

2. **Dist cleanup is minimal and correct.** The `fs.rm(distDir, { recursive: true, force: true })` approach is a 3-line change that correctly addresses the stale artifacts problem. No concerns.

## Axis G — Blind spots

1. **Pipeline failure behavior not addressed.** Does `build.post` continue running steps after `behavior.snapshot.validate` fails with SNAP-01, or does it stop? If it stops, `behavior.snapshot.generate` never runs and the snapshot is NOT regenerated by the pipeline. If it continues, the snapshot IS regenerated and the RFC's separate call is redundant. This is a critical implementation detail that determines the entire approach.

2. **Distinguishing "stale snapshot" from "genuine route mismatch" after regeneration.** The RFC says "if the snapshot still fails after regeneration, report the persistent SNAP-01 error and exit non-zero. This indicates a genuine route mismatch, not a stale snapshot" (line 160). But `behavior.snapshot.validate` produces the same SNAP-01 diagnostic in both cases — there's no way to distinguish them programmatically. The RFC should explain how the re-validation result is interpreted.

3. **`mission.git.commit` staging scope.** The RFC calls `mission.git.commit` with message "chore: auto-regenerate behavior snapshot" but doesn't specify whether only the snapshot file is staged or all uncommitted changes. If the workpiece has other uncommitted changes, `mission.git.commit` might stage them too, creating an unintended mixed commit. The RFC should specify `--files behavior.snapshot.generated.yaml` or equivalent.

4. **Auto-commit during `mission.close` inline validation.** When `mission.close` calls `mission.validate` inline (RFC-0593), the auto-commit will fire inside the close flow. This means `mission.close` now creates commits as a side effect, which may surprise operators. The RFC should document this interaction.

## Questions for the author

1. Does the `build.post` pipeline continue running after `behavior.snapshot.validate` fails with SNAP-01, or does it stop on first failure? This determines whether the separate `behavior.snapshot.generate` call is needed or redundant.
2. How will the SNAP-01 diagnostic be extracted from the `KernelPipelineReport` returned by `runPipelinePhase`? The current code calls `build.post` as a single pipeline — the RFC needs to show how to inspect individual step results (`report.steps[].data.diagnostics`) to find SNAP-01.
3. Should `mission.validate` auto-commit the regenerated snapshot, or should it leave the working-tree change for the operator to review and commit manually? The auto-commit makes `mission.validate` a mutating command, which is a semantic shift from its current read-only validation role.
