Problem: The action handler in index.ts inlines request parsing, schema validation, rate limiting, event building, and response formatting — each concern is a shallow step inside one function, untestable in isolation.

Solution: Extract an ActionPipeline that composes ordered middleware (rate limit, schema validate, dispatch); the handler becomes a thin delegate that wires the pipeline.

  • locality: each middleware in its own module
  • leverage: one pipeline interface, N middlewares
  • depth: handler interface is one call

Extract rate limiting behind a generic LimitStore port

Worth exploring ports & adapters

Before
                  flowchart TD

                    A -.leak.-> D[in-memory only]
                    classDef leak stroke:#dc2626,stroke-width:2px;

After
                  flowchart TD
                    A[limits.ts] --> B[LimitStore port]
                    B --> C[InMemoryLimitStore]
                    B -.seam.-> D[RedisLimitStore]
                    A --> E[checkLimit: pure logic]

Problem: limits.ts uses a module-level Map for rate-limit state — the fixed-window logic and the storage are coupled, making it impossible to use a shared store (e.g. Redis) in multi-instance deployments.

Solution: Extract a LimitStore interface (get(key): number, increment(key): void, reset(key): void); InMemoryLimitStore is the default; checkLimit becomes a pure function over the store.

  • locality: storage in one adapter
  • leverage: Redis adapter for multi-instance
  • depth: limit logic is pure and testable
