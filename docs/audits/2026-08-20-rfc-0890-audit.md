# Audit: RFC-0890 — Raw website screenshot ingestion and archival for Nachweis evidence

## Verdict: Needs revision

The RFC is structurally complete and well-aligned with DNA-46/DNA-59, but has three findings that should be resolved before implementation: (1) idempotency behavior for re-ingestion is unspecified, (2) the relationship between `rawArtifact` and the existing `websiteScreenshot` display fields is ambiguous when no display variant exists yet, and (3) `--captured-at` flag format is unspecified. Two minor findings on `.gitignore` template ownership and `sharp` dependency placement round out the revision list.

## Mechanical validation (rfc.validate)

**Pass** — `rfc.validate --id RFC-0890 --json` returned zero violations.

No issues. All required sections present: Context, Problem, Decision, Architectural fit, Compass sync, Design (CLI surface, filename parsing, TypeScript contracts, file system responsibilities, R2/local paths, output format, failure modes, image metadata detection), Rollout, Alternatives considered, Risks, Acceptance criteria, Implementation notes for agents. Frontmatter is complete with `proposed` command, `packagesImpacted`, `dependsOn`, `satisfies`, `batch`, `versionBump`.

## Axis B — DNA alignment

No issues.

- **DNA-46 (Mission lifecycle)**: The command acquires system and bordbuch locks, appends a Bordbuch entry, and mutates the evidence-source entity in the cache clone — consistent with the mission lifecycle pattern used by `nachweis.screenshot.upload` (RFC-0886).
- **DNA-59 (Evidence preservation)**: Raw screenshots are preserved in R2 private storage (durable) with a local cache clone copy (ephemeral working copy). This matches the DNA-59 pattern: R2 is durable history, local is working copy.

## Axis F — Pragmatism

- **F-1 (minor): `--captured-at` flag missing from CLI examples.** The acceptance criteria and alternatives section mention a `--captured-at` override flag, but the CLI surface examples (§ Design → CLI surface) do not demonstrate its usage. The flag is listed in acceptance criteria but not in the file system responsibilities table. Add a CLI example and specify the expected format (ISO 8601 datetime).

- **F-2 (minor): `sharp` dependency placement.** The RFC says "Add `sharp` to `packages/werkstatt/package.json` devDependencies." However, `werkstatt` is stack-agnostic (DNA-64) and must not import stack-specific packages statically. The RFC correctly specifies dynamic `import("sharp")` at the call site, which is the sanctioned escape hatch. But adding `sharp` to `werkstatt` devDependencies blurs the stack-agnostic boundary — `sharp` is already a devDependency of `werkstatt-site`. Consider whether the dynamic import alone is sufficient (the monorepo already installs sharp via `werkstatt-site`), or whether `werkstatt` should declare it as an optional/peer dependency instead.

## Axis G — Blind spots

- **G-1 (must fix): Idempotency behavior unspecified.** What happens when `nachweis.screenshot.ingest` is called twice for the same slug with the same file? Does it overwrite the local copy and R2 object? Does it create a duplicate Bordbuch entry? Does it detect the existing `rawArtifact` by SHA-256 and skip? The existing `nachweis.screenshot.upload` (RFC-0886) also lacks explicit idempotency semantics, but for raw archival the question is more important because raw files are large (2–20MB) and re-ingestion is likely during operator workflows. Specify: skip-if-same-sha, overwrite-and-log, or fail-with-existing-rawArtifact.

- **G-2 (must fix): `rawArtifact` vs display variant ordering ambiguity.** The RFC says ingest "updates `EvidenceSource.websiteScreenshot.rawArtifact`" but does not clarify what happens when `websiteScreenshot` does not yet exist on the entity (i.e., `nachweis.screenshot.upload` has not been run). Does ingest create a `websiteScreenshot` object with only `rawArtifact` populated (leaving `sha256`, `mediaType`, `storage`, `url` unset)? The schema shows `sha256` and `mediaType` as required on `pbpWebsiteScreenshotSchema`, so a partial object would fail validation. Specify: ingest requires `websiteScreenshot` to already exist, OR ingest creates a stub with placeholder display fields, OR the schema must make display fields optional when `rawArtifact` is present.

- **G-3 (minor): PII / sensitive content in raw screenshots.** Full-page screenshots may capture cookies, user data, or sensitive UI elements. The RFC does not mention any redaction or access-control consideration for the local cache clone copy. The R2 private storage is access-controlled, but the cache clone copy at `trust/evidence/screenshots/{slug}/raw/` is a plain file on disk. Consider noting that raw screenshots should not be exposed in public builds or logs.

## Questions for the author

1. What is the idempotency behavior when re-ingesting the same raw screenshot (same SHA-256) for an existing `rawArtifact`? Skip, overwrite, or fail?
2. Can `nachweis.screenshot.ingest` run before `nachweis.screenshot.upload`? If yes, how should the `websiteScreenshot` object be structured when only the raw artifact exists (the current schema requires `sha256` and `mediaType` on the display variant)?
3. What is the expected format for the `--captured-at` flag — ISO 8601 with timezone (`2026-08-20T13:44:40Z`), or a date-only string?
