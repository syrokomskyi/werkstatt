# Audit: RFC-0840

## Verdict: Needs revision

The core pattern (extending RFC-0822 env-persist to operator config files) is sound and well-motivated. However, the `commands` frontmatter is incomplete, `materialize.config.validate` has a scope contradiction (workspace-scope scan vs. `SITES_CHECK_PIPELINE`), and `image-delivery.config.yaml` inclusion conflicts with DNA-72 (RFC-0841) which explicitly warns about root-level placement.

## Mechanical validation (rfc.validate)

Pass — zero violations.

## Axis A — Structural completeness

- **A-1: `commands.added` is empty but the RFC introduces a new command.** The RFC body (line 87, line 144) describes `materialize.config.validate` as a new check command, but `commands.added: []` is empty. It should list `materialize.config.validate`.
- **A-2: `commands.changed` is missing `mission.close`.** The RFC adds `persistOperatorConfigFiles` to `mission.close` (line 84, line 111-122), but `commands.changed` lists only `mission.materialize`. `mission.close` should also be in `changed`.
- **A-3: File system responsibilities table omits `materialize.config.validate` handler location.** The table (lines 152-159) lists 4 files for the persist/restore logic but does not include where `materialize.config.validate` is implemented or which command-tables file registers it.
- **A-4: `materialize.config.validate` "NOT generated by `build.prepare`" is under-specified.** Line 148 says the validator scans for root-level files "NOT generated by `build.prepare`" but does not describe the mechanism for distinguishing generated files from operator files (e.g., consult `GENERATOR_OWNERSHIP_MAP`, diff against `build.prepare` output, or maintain an exclusion list).

## Axis B — DNA alignment

- **B-1: "Extends DNA-62" overstates the relationship.** Line 91 says the RFC "Extends DNA-62 (Foundation File Integrity) to cover non-env operator config files." DNA-62 is about pinned-files manifest (`.forge/pinned.yaml`) enforced at git-commit level. RFC-0840 is about untracked file persistence between workpiece and cache clone. These are complementary mechanisms, not an extension. "Complements DNA-62" would be accurate.
- **B-2: DNA-71 is already present in `docs/architecture-dna.md`.** Acceptance criterion 9 (line 197) says "DNA-71 entry appended to `docs/architecture-dna.md`" but DNA-71 is already at line 291-293 of that file. The criterion should say "verified" or note the pre-existence to avoid confusion during implementation.

## Axis C — Ecosystem fit

- **C-1: `materialize.config.validate` scope contradiction.** The RFC body (line 148) says the validator "Scans all active mission workpieces" — this is workspace-scope. But acceptance criterion 6 (line 194) says "wired into `SITES_CHECK_PIPELINE`" — this is site-scope (runs per-site). A workspace-scope command that scans all workpieces cannot be wired into a per-site pipeline without either running once per site redundantly or being mis-scoped. The RFC must resolve this: either make it site-scope (scan only the current site's workpiece) and use `SITES_CHECK_PIPELINE`, or make it workspace-scope and use a workspace-level pipeline.
- **C-2: `packagesImpacted` may be incomplete.** The RFC lists only `@warpgogol/werkstatt` (line 38). If `materialize.config.validate` is a site-scope check registered in site check command-tables (which live in `packages/werkstatt-site/src/checks/command-tables/`), then `@warpgogol/werkstatt-site` should also be in `packagesImpacted`. The RFC doesn't clarify where the command handler lives.
- **C-3: `image-delivery.config.yaml` inclusion conflicts with DNA-72 (RFC-0841).** The RFC preserves `image-delivery.config.yaml` at root (line 105). But DNA-72 (RFC-0841, line 295-297 of `docs/architecture-dna.md`) establishes `IMG-DELIVERY-CONFIG-01`: a warning when `image-delivery.config.yaml` is found in workpiece root but not in `src/`. RFC-0840 is preserving a file in a location that RFC-0841 explicitly flags as wrong. The RFC acknowledges the validator reads from `src/` (line 66) but doesn't resolve the contradiction — if the file belongs in `src/`, it would be covered by `STERNSYSTEM_DATA_PATHS` and wouldn't need root-level persistence.

## Axis D — Forward-only compliance

No issues. The RFC does not introduce backward compatibility shims or dual-path logic.

## Axis E — Agent-facing policy

- **E-1: Superseding-RFC policy vs. warning-only validator inconsistency.** Line 109 says "Adding a new file to this list requires a superseding RFC." But `materialize.config.validate` emits only a warning (MAT-CONFIG-01, line 149) for unrecognized files. If a new file truly requires an RFC, the validator should enforce this more strongly (error, not warning). The current design allows operators to add files without an RFC and only get a warning — contradicting the stated policy.

## Axis F — Pragmatism

- **F-1: `materialize.config.validate` may be over-engineered.** The core problem is that 4 specific files need to be persisted. A validator that scans for "unrecognized" root-level files across all workpieces is speculative — it needs to distinguish operator config from generated files, transient artifacts, and legitimate untracked files (like `.env*`). The RFC doesn't justify why this scanning validator is needed beyond the explicit `OPERATOR_CONFIG_FILES` list. The MAT-CONFIG-02 (dead entry) check is useful, but MAT-CONFIG-01 (unrecognized files) adds complexity with unclear value.
- **F-2: `live-video-manifest.generated.yaml` location is questionable.** The RFC says it's "authored/curated by operators" (line 68) but has `.generated` in its name and lives at root. If it's authored content, it should be in `src/content/` (which is in `STERNSYSTEM_DATA_PATHS` and would be copied automatically). The RFC doesn't explain why this file is at root instead of in `src/`.

## Axis G — Blind spots

- **G-1: Silent overwrite on divergent content.** The persist/restore functions use `copyFile` which overwrites unconditionally. If an operator edits a config file in the workpiece after the last close (e.g., adjusts `.lighthouse-budget-ignore`), then re-materializes, the workpiece version is silently overwritten by the cache clone version. For `.env*` files this is acceptable (secrets don't diverge semantically), but for structured config files, silent overwrites could cause confusion. The RFC should at minimum document this behavior or consider a merge/diff notification.

## Questions for the author

1. Should `materialize.config.validate` be workspace-scope (scanning all workpieces) or site-scope (per-site)? The RFC describes it as workspace-scope but the acceptance criterion says `SITES_CHECK_PIPELINE`. Which is correct?
2. How does `materialize.config.validate` distinguish "NOT generated by `build.prepare`" files from operator config files? What is the concrete mechanism?
3. Why is `image-delivery.config.yaml` preserved at root when `image.delivery.validate` reads from `src/` and DNA-72 (RFC-0841) explicitly warns about root-level placement? Should it be removed from `OPERATOR_CONFIG_FILES` and instead moved to `src/` by the operator?
