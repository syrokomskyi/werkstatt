# Audit: RFC-0614

## Verdict: Needs revision

The RFC correctly identifies a real gap in bordbuch conflict auto-resolution and proposes a minimal, well-scoped fix. However, it has a robustness blind spot in the hardcoded `git checkout --ours` path list, an incorrect `appsImpacted` entry, and minor traceability gaps.

## Mechanical validation (rfc.validate)

Pass with 1 warning:
- **V-19** (warning): `RFC-0614.amends` includes `RFC-0584`, but `RFC-0584.amendedBy` does not include `RFC-0614`. Expected for a draft amending an implemented RFC — the `amendedBy` field on RFC-0584 must be updated during implementation.

## Axis A — Structural completeness

- **Output format section missing.** The RFC does not document the `--json` output shape. While the shape is unchanged from RFC-0584 (the `autoResolvedPaths` field already exists), the RFC should explicitly state this for completeness — a reader unfamiliar with RFC-0584 cannot determine the output format from this RFC alone.

## Axis B — DNA alignment

- **Missing `related[]` entry for RFC-0604.** The body text references RFC-0604 (line 109: "Bordbuch artifacts at `public/.well-known/bordbuch*` are generated by `bordbuch.generate`"), but `related[]` only lists RFC-0584 and RFC-0568. RFC-0604 should be in `related[]` for traceability — it establishes that `public/.well-known/bordbuch*` files are generated artifacts in the cache clone.
- **DNA-51 claim is weak but acceptable.** The RFC says it "maintains" DNA-51 guarantees (atomic, idempotent). This is true — the merge is still atomic and idempotent. The claim is protective rather than extending, which is valid.

## Axis C — Ecosystem fit

- **AGENTS.md update not addressed.** `packages/os/site-kernel-handoff/AGENTS.md` has a "Bordbuch git synchronization" section. The RFC should state whether that section needs updating to reflect the expanded auto-resolution scope, or explicitly state that no AGENTS.md update is needed.

## Axis D — Forward-only compliance

No issues. The RFC amends RFC-0584 directly — it expands the path matching scope, not adds a parallel interpretation. No shims, no dual-paths.

## Axis E — Agent-facing policy

No issues. No self-authorizing language. Implementation notes are explicit behavioral rules.

## Axis F — Pragmatism

- **`appsImpacted` is incorrect.** The RFC lists `appsImpacted: [warpgogol-com]`, but this is a workspace-scoped command change (`scope: workspace`) that affects all sites using `mission.reconcile`, not just warpgogol-com. RFC-0584 (the amended RFC) correctly has `appsImpacted: []`. The field should be empty — the conflict was observed on warpgogol-com, but the fix is in the shared kernel command.

## Axis G — Blind spots

- **Hardcoded `git checkout --ours` path list is not robust.** The RFC proposes (line 134):
  ```ts
  execSync("git checkout --ours bordbuch/ public/.well-known/bordbuch.json public/.well-known/bordbuch/", { cwd: systemDir, ... });
  execSync("git add bordbuch/ public/.well-known/bordbuch.json public/.well-known/bordbuch/", { cwd: systemDir, ... });
  ```
  This hardcodes all three paths. If only a subset is conflicted (e.g., `bordbuch/events.ndjson` is conflicted but `public/.well-known/bordbuch.json` does not exist because `bordbuch.generate` has not been run yet), `git checkout --ours` will error on the non-conflicted/non-existent path. The RFC should use the `conflictedPaths` array to dynamically construct the checkout/add commands:
  ```ts
  const pathArgs = conflictedPaths.map((p) => JSON.stringify(p)).join(" ");
  execSync(`git checkout --ours -- ${pathArgs}`, { cwd: systemDir, ... });
  execSync(`git add -- ${pathArgs}`, { cwd: systemDir, ... });
  ```
  This ensures only actually-conflicted paths are checked out and added.

- **Test file naming inconsistency.** The RFC's file system responsibilities table (line 143) names the test file `mission-reconcile.test.ts`, but no such file exists. The existing test naming convention is either `rfc-NNNN-*.test.ts` (e.g., `release-0585-dist-guard.test.ts`, `leitstand-0608-promote.test.ts`) or `feature-*.test.ts` (e.g., `mission-open-bordbuch-gate.test.ts`). The RFC should use a consistent name like `rfc-0614-public-well-known-bordbuch-conflict.test.ts`.

- **RFC-0584 test evidence gap.** RFC-0584's acceptance criteria reference `rfc-0584-bordbuch-conflict-autoresolve.test.ts` (tests 1, 2, 3), but no such file exists in `packages/os/site-kernel-handoff/src/tests/`. This means RFC-0584's bordbuch conflict auto-resolution has no regression test coverage. RFC-0614 should acknowledge this gap and state that its regression test will also cover the RFC-0584 `bordbuch/` path scenario.

## Questions for the author

1. Should the `git checkout --ours` and `git add` commands use `conflictedPaths` dynamically instead of hardcoding all three paths? What happens if only `bordbuch/events.ndjson` is conflicted but `public/.well-known/bordbuch*` does not exist?
2. Why is `appsImpacted` set to `[warpgogol-com]` when the change is workspace-scoped and affects all sites using `mission.reconcile`?
3. Should RFC-0604 be listed in `related[]` since it establishes that `public/.well-known/bordbuch*` files are cache-clone-only generated artifacts?
