# Audit: RFC-0611

## Verdict: Needs revision

RFC-0611 proposes a well-scoped extension to `forge.agents.generate` for nested workspace AGENTS.md files. The design is architecturally sound and fits the forge command ecosystem. However, there are findings on axes A, C, and G that should be resolved before implementation: an internal inconsistency in the `forge.upgrade` section, a divergent generated-marker format, and unspecified staleness-detection mechanics for `forge.doctor`.

## Mechanical validation (rfc.validate)

Pass — zero violations.

## Axis A — Structural completeness

- **Failure modes lack exit codes.** The "Failure modes" section (lines 223–229) describes behavior ("Not an error", "skipped with a warning") but does not specify exit codes (0 vs 1) for each scenario. The existing `runAgentsGenerate` returns `exitCode: 1` for hand-written root AGENTS.md and `exitCode: 0` for success. The RFC should state the exit code for each failure mode explicitly, especially for the new "package.json unreadable" case (skip with warning — exit 0 or 1?).
- **`forge.upgrade` section is internally inconsistent.** Line 151 says "It generates files only for workspace directories that lack an AGENTS.md", but line 151 (same paragraph) also says "Existing generated files are regenerated." These two statements contradict each other — "only for directories that lack one" excludes regeneration of existing files. The `successSignals` (line 56) aligns with the "only missing" interpretation: "forge.upgrade generates nested AGENTS.md for workspace directories that lack one, without touching hand-written files." The design section should clarify whether upgrade regenerates existing generated nested files or only creates missing ones.

## Axis B — DNA alignment

No issues. `satisfies: []` is empty, which is acceptable for `kind: command` (required only for architecture/contract RFCs per the template comment on line 30). The RFC does not establish a new DNA invariant.

## Axis C — Ecosystem fit

- **Divergent generated-marker format.** The RFC proposes (lines 136–139):
  ```markdown
  <!-- GENERATED BY forge.agents.generate — DO NOT EDIT -->
  <!-- Re-run: pnpm exec forge agents generate -->
  ```
  But the existing `GENERATED_MARKER` constant in `@/packages/forge/src/utils/generated-marker.ts:16` is `"GENERATED. Do not change this line unless the file contains project specific changes."` and the existing `buildGeneratedHeader` function already produces a standard header with owner command and re-run instruction. The RFC should reference the existing marker infrastructure (`GENERATED_MARKER`, `buildGeneratedHeader`, `hasGeneratedMarker`) rather than inventing a new format. The `hasGeneratedMarker` function is what the edit guard uses — a different marker string would not be recognized by the existing guard.
- **No mention of `packages/forge/AGENTS.md` update.** The RFC adds workspace discovery and type auto-detection logic to `packages/forge/src/onboarding/agents-generate.ts`. The forge package's own `AGENTS.md` may need rules about the new workspace discovery behavior (e.g., "agents MUST NOT add workspace-type detection rules to `forge.agents.generate` — the detection table is defined in the RFC"). The RFC should identify which `AGENTS.md` files need rule updates.

## Axis D — Forward-only compliance

No issues. The RFC extends existing commands without compatibility shims. The edit guard (skip hand-written, regenerate generated) is a single-path design — no dual-path or legacy behavior is maintained.

## Axis E — Agent-facing policy

No issues. The RFC correctly gates implementation on `status: accepted` (line 281). Implementation notes reference RFC-0224 (accepted→implemented transition) and `rfc.supersede.propose` for invariant conflicts. No self-authorizing language.

## Axis F — Pragmatism

No issues. The RFC extends three existing commands rather than proposing new ones. `WorkspaceDir` and `AgentsGenerateResult` are minimal type signatures. `packagesImpacted: [forge]` is correct — only the forge package is touched. Non-goals are meaningful (non-workspace directories, template content, warpgogol monorepo itself).

## Axis G — Blind spots

- **Staleness detection mechanism unspecified.** The RFC says `forge.doctor` checks for "Stale generated AGENTS.md — generated files whose content differs from what `forge.agents.generate` would produce" (line 158). But the mechanism is not described. Does doctor re-invoke the generator in dry-run mode and compare output (like `generated.drift.validate` in RFC-0601)? Does it hash-compare? Does it call a pure render function? The existing `runDoctor` in `@/packages/forge/src/onboarding/doctor.ts` has no such capability. The RFC should specify the detection mechanism or explicitly defer it to implementation with a non-goal entry.
- **`generated` array semantics change.** The existing `runAgentsGenerate` returns `generated: ["AGENTS.md"]` (root only). The RFC extends this to include nested files: `generated: ["AGENTS.md", "apps/my-app/AGENTS.md", ...]`. Existing JSON consumers that expect only the root file in `generated` will see more entries. The RFC should note this is a semantic change to the `--json` output, even though it's additive.
- **Concurrent execution and interrupted writes not considered.** Two agents running `forge.agents.generate` simultaneously could race on file writes. A crash mid-write could leave a partially written AGENTS.md. The RFC does not address these edge cases. Minor, but worth a sentence in failure modes or risks.

## Questions for the author

1. Should nested AGENTS.md files use the existing `buildGeneratedHeader` / `GENERATED_MARKER` infrastructure from `packages/forge/src/utils/generated-marker.ts`, or is the divergent marker format (`<!-- GENERATED BY forge.agents.generate — DO NOT EDIT -->`) intentional? If the latter, how will `hasGeneratedMarker` recognize the new format?
2. Does `forge.upgrade` regenerate existing generated nested AGENTS.md files, or only create missing ones? The design section (line 151) says both.
3. How does `forge.doctor` detect stale generated AGENTS.md? Does it re-invoke `forge.agents.generate` in dry-run mode and compare, or use another mechanism?
