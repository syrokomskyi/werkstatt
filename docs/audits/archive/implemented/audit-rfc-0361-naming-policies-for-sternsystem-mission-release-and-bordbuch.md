# Executive Summary RFC-0361

**Требует доработок** — RFC-0361 логически обоснован и решает реальную проблему рассеянных политик именования, но содержит несколько критических упущений: отсутствие стратегии миграции для существующих данных, неполная обработка ошибок при поврежденных файлах, и спорная необходимость отдельного валидатора вместо усиления существующих команд. Проект технически осуществим, но требует уточнения эксплуатационных деталей и edge case handling.

---

# Критические архитектурные уязвимости

1. **Отсутствие стратегии миграции для существующих нарушений** — RFC предполагает "fix any pre-existing violations" в rollout шаге 7, но не определяет, что делать с тысячами существующих артефактов, если они нарушают новые политики. Автоматическая миграция может сломать зависимости (git history, external references), ручная — непрактична на больших флотах. Нужен режим `--migrate` с rollback-стратегией.

2. **Хрупкая обработка поврежденных файлов** — Валидатор читает YAML файлы (`systems/registry.yaml`, `missions/*/mission.yaml`, и т.д.), но не описывает поведение при:
   - Отсутствующем файле (система удалена вручную)
   - Некорректном YAML (синтаксическая ошибка)
   - Файле с неверной кодировкой (UTF-8 vs. Windows-1252) Текущая спецификация "non-zero exit code" недостаточна — нужен graceful degradation с детальной диагностикой.

3. **Race condition при параллельных операциях** — Если два агента одновременно добавляют миссии/релизы, валидатор может увидеть временно несогласованное состояние (например, дублирующиеся `seq` в Bordbuch). RFC не определяет, должен ли валидатор проверять атомарность или только консистентность снапшота. Для fleet-scale систем это критично.

4. **Отсутствие валидации семантических инвариантов** — RFC проверяет форматы, но не проверяет семантику:
   - `mission-close` без соответствующего `mission-open` (mentioned but not enforced in §1.4)
   - `releaseId` с несуществующим `missionId` (mentioned in §2 but not in §1.4)
   - Циклические зависимости между системами (если они будут введены в будущем) Это создает ложное чувство безопасности — формально валидно, семантически сломано.

# Неучтенные Edge Cases

1. **Unicode normalization** — RFC запрещает non-ASCII символы через regex `[a-z0-9]`, но не учитывает Unicode normalization forms (NFC vs. NFD). Строка `café` в NFC и NFD выглядит по-разному байтово, но визуально идентична. Валидатор должен нормализовать перед проверкой или явно запрещать composed/decomposed формы.

2. **Case-insensitive файловые системы** — На Windows/macOS filenames case-insensitive, но RFC требует lowercase-only для ids. Если кто-то создаст директорию `Webgogol-Com` вместо `webgogol-com`, валидатор пропустит id (он валиден), но файловая система может создать проблемы при cross-platform деплое. Нужна cross-check между id и dirname.

3. **Zero-padded sequence overflow** — RFC требует zero-padded three digits (`m001`, `m999`), но не определяет поведение при `m1000`. Валидатор должен либо явно запрещать 4+ цифры, либо поддерживать автоматическое расширение формата. Текущий regex `\d{3}` жестко ограничивает до 999.

4. **Bordbuch seq после ручного редактирования** — Если кто-то вручную отредактирует `bordbuch.yaml` и удалит entry с `seq=5`, валидатор обнаружит gap (expected 5, got 6). Но RFC не определяет, должен ли он:
   - Автоматически перенумеровать?
   - Запретить коммит?
   - Предложить `--fix-gaps` режим? Текущая спецификация "non-zero exit code" недостаточна для production.

5. **cosmicStar коллизии при архивации** — RFC разрешает reuse cosmicStar только после архивации предыдущей системы (§1.5). Но не определяет, что делать, если система архивируется, cosmicStar освобождается, затем система разархивируется — коллизия возможна. Нужен механизм "soft lock" или явный lifecycle check.

# Конкретные улучшения

1. **Добавить режим `--dry-run` и `--fix`** — Текущий валидатор только проверяет. Для production нужен режим, который:
   - `--dry-run`: показывает, что будет исправлено, без изменений
   - `--fix`: автоматически исправляет исправляемые нарушения (renumbering seq, lowercase conversion)
   - `--fix-gaps`: только для Bordbuch seq gaps Это снижает операционную нагрузку при миграциях.

2. **Интегрировать в существующие валидаторы вместо нового command** — RFC создает `naming.policy.validate` как отдельную команду, но §3 показывает overlap с `sternsystem.validate`, `bordbuch.validate`, `release.validate`. Более прагматично:
   - Добавить naming checks в существующие команды (они уже читают те же файлы)
   - Экспортировать shared naming policy functions из `@gogol/ontology`
   - Создать `naming.policy.validate` только как aggregator для fleet-wide audit Это уменьшает дублирование кода и поддерживает single responsibility.

3. **Добавить кэширование и инкрементальную валидацию** — Для fleets с тысячами систем полный scan может быть медленным. Добавить:
   - `--since <timestamp>`: валидировать только измененные файлы
   - `--cache-dir`: кэшировать parse results в `.cache/naming-policy.json`
   - `--incremental`: использовать file mtime для определения изменений Это делает валидатор пригодным для pre-commit hooks.

4. **Уточнить Latin-only enforcement** — Текущий regex `^[a-z0-9]+(-[a-z0-9]+)*$` уже ASCII-only в стандартных regex engines, но RFC утверждает "does not explicitly reject non-ASCII". Это путает. Уточнить:
   - Явно добавить Unicode property escape: `^[a-z0-9]+(-[a-z0-9]+)*$u` с флагом `u` для гарантии ASCII-only
   - Или добавить explicit check: `/[^\x00-\x7F]/.test(value)` для отклонения non-ASCII
   - Добавить unit tests для edge cases: `nicaragüa-projekt`, `café`, `Москва`

5. **Добавить structured logging и метрики** — Для production мониторинга:
   - Log format: JSON с полями `timestamp`, `level`, `artifact`, `field`, `value`, `rule`
   - Metrics: `naming_policy_validation_duration_seconds`, `naming_policy_violations_total{artifact, rule}`
   - Интеграция с существующей logging инфраструктурой (если есть) Без этого невозможно triage проблемы в production.
