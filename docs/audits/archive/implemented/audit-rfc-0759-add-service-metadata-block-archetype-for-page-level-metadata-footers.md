# Audit: RFC-0759

## Verdict: Needs revision

The `stats[].dataSource` field introduces an underspecified build-time data resolution mechanism with no implementation path. `versionBump: minor` contradicts the Rollout section's "No migrator needed." Acceptance criteria are incomplete (missing `stats?`). File system responsibilities contain stale information about `PLANET_IMPORT_PATHS` and `index.yaml` that are now registry-derived.

## Mechanical validation (rfc.validate)

Pass with 1 V-30 warning: `@warpgogol/ontology` is in `packagesImpacted` but `breaksC` is not true. The RFC only adds to `packages/ontology/archetypes/sections/`, not `packages/ontology/src/external-surfaces/`, so `breaksC: false` is correct — the warning is a false positive for this case. No action needed.

## Axis A — Structural completeness

1. **Acceptance criterion #1 incomplete.** The criterion lists "propsSchema (version?, effectiveDate?, nextReviewDate?, links?, footnote?)" but the Design section's propsSchema also includes `stats?` and `footnote?` is listed but `stats?` is not. The criterion must match the full propsSchema.

2. **CLI surface example uses non-existent `--site` flag.** The example `section.scaffold --archetype service-metadata-block --site warpgogol-com` is incorrect. `section.scaffold` requires `--name=<slug>` and `--archetype=<id>` — there is no `--site` flag (see `@/packages/os/site-kernel-codegen/src/section-scaffold.ts:101-107`). The correct invocation is `section.scaffold --name service-metadata-block --archetype service-metadata-block`.

3. **Archetype YAML missing `description` field.** All existing archetype YAMLs include a `description` field (e.g. `@/packages/ontology/archetypes/sections/transparency.yaml:5-6`). The RFC's archetype YAML example omits it.

4. **File extension mismatch.** File system responsibilities table says `.types.ts` but actual files are `.types.generated.ts` (generated by `props.types.generate`, see `@/packages/ui/src/sections/transparency/` for example).

## Axis B — DNA alignment

No issues. DNA-17 (Uni manifest contract) is correctly referenced — the new archetype ships a colocated `manifest.yaml`. DNA-19 (Closed ontology vocabularies) is correctly handled — `SemanticRole` is an open type alias since RFC-0084, so `page-metadata-footer` is a valid new role derived from the archetype catalog.

## Axis C — Ecosystem fit

1. **Stale `PLANET_IMPORT_PATHS` instruction.** File system responsibilities say "Add `PLANET_IMPORT_PATHS` entry for the picked cosmic name" in `packages/share/src/page.ts`. However, `PLANET_IMPORT_PATHS` is now registry-derived via `archetype.registry.build` (RFC-0091, see `@/packages/share/src/page.ts:160-163`). No manual `page.ts` edit is needed — the entry is automatically added when `archetype.registry.build` regenerates `index.yaml`. This row should be removed or updated to "Run `archetype.registry.build` to regenerate `PLANET_IMPORT_PATHS`."

2. **Stale `index.yaml` registration instruction.** File system responsibilities say "Register `service-metadata-block` in `packages/ontology/archetypes/index.yaml`". But `index.yaml` is generated by `archetype.registry.build` (see `@/packages/os/site-kernel-checks/src/command-tables/01-codegen.ts:318-328`), not hand-edited. The RFC should say "Run `archetype.registry.build` after adding the archetype YAML" instead.

3. **Missing `props.types.generate` step.** The file system responsibilities list `.types.ts` (should be `.types.generated.ts`) but don't mention that this file is generated by the `props.types.generate` command. The Rollout section should include running `props.types.generate` after `section.scaffold`.

## Axis D — Forward-only compliance

No issues. The archetype is additive — no existing code is changed, no compatibility shims, no dual-paths.

## Axis E — Agent-facing policy

1. **`versionBump: minor` contradicts Rollout.** The frontmatter declares `versionBump: minor` which means "Breaks-B, requires migrator" per the frontmatter comment. But the Rollout section says "No migrator needed: the archetype is additive." Adding a new archetype to the catalog is additive — no existing contract changes. This should be `patch` (safe), not `minor`.

2. No self-authorizing language — the RFC correctly states "Agents MAY implement code changes ONLY when this RFC has status: accepted."

3. No NEEDS CLARIFICATION markers.

## Axis F — Pragmatism

1. **Significant overlap with RFC-0758 (`dynamic-status-block`).** RFC-0758 creates `dynamic-status-block` specifically for "data-driven status indicators" on the same "Відповідальні рекомендації" page — its Context explicitly mentions "open mandate count." RFC-0759 adds `stats[]` to `service-metadata-block` for the same purpose: "dynamic mandate counts (open pilot mandates, open full mandates)." This is a functional overlap — two archetypes solving the same problem for the same page. The RFC should either justify why `stats[]` is needed in `service-metadata-block` when `dynamic-status-block` exists for this pattern, or remove `stats[]` and defer dynamic values to RFC-0758.

2. **`stats[].dataSource` is speculative generality.** The field introduces a build-time data resolution mechanism (`dataSource: "open-mandates:pilot"`) but no such mechanism exists in the platform. There is no data provider framework, no build-time injection hook, and no command that populates these values. The Failure modes section describes fallback behavior ("falls back to the authored `value` string") but the resolution path is unspecified. This is a field without an implementation path — it should be removed or deferred to a future RFC that establishes the data provider contract.

## Axis G — Blind spots

1. **`stats[].dataSource` resolution mechanism is a significant blind spot.** The RFC says "the section resolves the value at build time from the referenced data provider" but does not describe: what data providers exist, how the `dataSource` string is resolved, what command injects the values, or what the contract is for data source names. Without this, the field is unimplementable.

2. **Empty state handled.** The RFC correctly describes the case where all fields are absent (renders an empty muted block, `page.block.validate` may warn but not fail).

3. **No performance concerns.** The section is a static HTML render at build time — no I/O or scan cost.

## Questions for the author

1. Why does `service-metadata-block` include `stats[]` when RFC-0758 creates `dynamic-status-block` for the same purpose (data-driven mandate counts on the same "Відповідальні рекомендації" page)? Should the mandate counts be a separate `dynamic-status-block` section instead of embedded in the metadata footer?

2. How does `stats[].dataSource` resolve at build time? What framework, command, or hook injects the values? If no mechanism exists, should `dataSource` be removed from this RFC and deferred to a future RFC that establishes the data provider contract?

3. Why is `versionBump: minor` (Breaks-B, requires migrator) when the Rollout section says "No migrator needed: the archetype is additive"? Should this be `patch`?
