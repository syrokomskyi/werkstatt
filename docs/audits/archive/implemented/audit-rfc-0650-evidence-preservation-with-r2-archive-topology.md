# Audit: RFC-0650

## Verdict: Needs revision

Three findings: DNA-59 is established by this RFC but missing from `satisfies[]`; success signals describe outcomes that depend on RFC-0651 and operator setup rather than RFC-0650's own code changes; Context section attributes `report.html` to `mission.check` when it is generated by `axiom.report`.

## Mechanical validation (rfc.validate)

Pass — `rfc.validate --id RFC-0650` reports 0 errors, 0 warnings.

## Axis A — Structural completeness

No issues.

## Axis B — DNA alignment

**Finding B1**: The RFC establishes DNA-59 ("This RFC establishes DNA-59 (Evidence preservation)") and the Rollout section says "DNA-59: After this RFC is accepted, the `## DNA-59` entry is appended to `docs/architecture-dna.md`." However, `satisfies[]` lists only `DNA-46` and `DNA-52` — DNA-59 is absent. Since the RFC creates and implements DNA-59, it should be listed in `satisfies[]`. Note: adding it will produce a V-18 warning ("DNA-59 is not defined in docs/architecture-dna.md") until the entry is appended after acceptance — this is expected and consistent with the rollout plan.

## Axis F — Pragmatism

**Finding F1**: `successSignals` contains four entries, but only one is directly verifiable from RFC-0650's code changes:

- Signal 3 ("evidence-metadata.json includes runTimestamp field") — directly verifiable from `mission-check.ts` write path. ✓
- Signal 1 ("R2 bucket axiom-evidence contains timestamped run objects for every mission.check execution") — depends on `evidence.sync` (RFC-0651) and operator R2 bucket creation. Not achievable by RFC-0650 alone.
- Signal 2 ("R2 Data Catalog table axiom_evidence_runs is queryable via R2 SQL") — depends on `evidence.sync` (RFC-0651) and operator Data Catalog enablement. Not achievable by RFC-0650 alone.
- Signal 4 ("Lifecycle rule transitions raw/ objects to Infrequent Access after 7 days") — depends on operator `wrangler r2 bucket lifecycle` configuration. Not achievable by RFC-0650 alone.

Signals 1, 2, and 4 should either be removed (they belong in RFC-0651's success signals) or reworded to describe RFC-0650's actual scope (e.g., "R2 bucket layout and lifecycle rules documented in AGENTS.md").

## Axis G — Blind spots

**Finding G1**: The Context section states "`mission.check` (RFC-0629, RFC-0630) generates Axiom evidence artifacts in `missions/{mission}/evidence/axiom/` on each run: ... `report.html` (~5 MB), and `raw/`". However, `report.html` is generated by `axiom.report` (RFC-0633), not by `mission.check`. The `mission-check.ts` write path (lines 717-745) writes only `staged-capsule.json`, `observation-bundle.json`, `study-run.json`, `evidence-metadata.json`, and `raw/` artifacts. `leitstand.dev-deploy` auto-invokes `axiom.report` after `mission.check` (handoff AGENTS.md line 34), which writes `report.html` to the same directory. The Context section should distinguish between `mission.check` artifacts and `axiom.report` artifacts to avoid confusion during implementation.

## Questions for the author

1. Should `satisfies[]` include `DNA-59` alongside `DNA-46` and `DNA-52`, given that this RFC establishes DNA-59?
2. Should success signals 1, 2, and 4 be removed or reworded to reflect RFC-0650's actual implementation scope (adding `runTimestamp` + documenting R2 topology), leaving R2 upload/queryability signals to RFC-0651?
3. Should the Context section distinguish `report.html` as an `axiom.report` artifact rather than attributing it to `mission.check`?
