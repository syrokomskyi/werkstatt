# Audit: RFC-0811

## Verdict: Needs revision

The RFC's core idea (whitelist via `GENERATOR_OWNERSHIP_MAP`) is sound, but the proposed implementation has two critical flaws: (1) `auth.md` is itself registered in the ownership map, so an extension-only filter would still include it, and (2) the `collectFiles` `ignore` callback receives only the filename, not a relative path, making the proposed `ignore`-based whitelist unworkable for files in subdirectories.

## Mechanical validation (rfc.validate)

Pass — `rfc.validate --id RFC-0811` returns zero violations.

## Axis A — Structural completeness

- **A1 (critical): `getOwnershipMapPathsByExtension` includes `auth.md`.** `auth.md` is registered in `GENERATOR_OWNERSHIP_MAP` at `generator-ownership.ts:504-508` under `agent.discovery-endpoints.generate` with `markerPolicy: "registry-only"`. The RFC's helper `getOwnershipMapPathsByExtension(".md")` filters by extension only, so `public/auth.md` would be included in the whitelist. `MDMETA-01` would still fire. The filter must also restrict by command (e.g. only `page.markdown.generate`) or by a "twin-producing" flag on `OwnershipEntry`.

- **A2 (critical): `collectFiles` `ignore` callback receives filename, not relative path.** The `collectFiles` implementation at `@warpgogol/werkstatt-site/share/fs` (`index.ts:52-53`) calls `ignore(entry.name)` — just the filename, not the relative path from `root`. The RFC's code `ignore: (relPath) => !isOwnershipPath(twinPaths, relPath)` implies relative-path matching against patterns like `public/{route}.md`, but the callback only receives e.g. `index.md`. For files in subdirectories, the filename alone cannot match the ownership pattern. The implementation must filter after collection (collect all `.md` files, then filter by relative path against ownership patterns), not via the `ignore` callback.

- **A3: `matchGlob` does not exist.** The RFC references `matchGlob` in the `isOwnershipPath` helper. No such utility exists in the codebase. The actual pattern-matching utilities are `ownPatternToExactRegex` + `expandPlaceholderVariants` in `generated-file-lookup.ts:43-66`, or `expandGlob` in `generated-files-validate.ts:108-183` (which does filesystem glob expansion, not pure pattern matching). The RFC should reference the correct utility or propose extracting one.

- **A4: `isGeneratedMarkdownTwin` not mentioned.** The function at `page-markdown.ts:84-87` always returns `true` (RFC-0375: "Category B files no longer carry markers — always treat as generated"). This is the actual gatekeeper that decides whether a scanned file is validated as a twin. The RFC doesn't mention it or propose changing it. With the whitelist, non-twin files are never scanned, so the function becomes moot — but the RFC should acknowledge this explicitly.

- **A5: Contradictory nonGoal wording.** `nonGoals` lists "Removing the auth.md exclusion" — meaning the exclusion concept remains, just the mechanism changes. But `Rollout` says "Remove the hardcoded `ignore: (relPath) => relPath === "auth.md"` callback — it becomes redundant." These appear contradictory on first read. Clarify the nonGoal to say "Removing the auth.md exclusion from the validator's scope" (the exclusion remains via whitelist, only the hardcoded callback is removed).

- **A6: `agent.knowledge.generate` claim unverified.** The RFC says "Markdown twins are generated by specific generators (e.g. `page.markdown.generate`, `agent.knowledge.generate`)." There are no `.md` paths in `GENERATOR_OWNERSHIP_MAP` under `agent.knowledge.generate`. Either remove this example or verify and add the ownership entries.

## Axis B — DNA alignment

- **B1: DNA-58 connection is indirect.** DNA-58 is about content drift detection — committed generated files must be byte-identical to what their generator would produce. The RFC changes file discovery scope (which files to validate), not determinism enforcement (whether content matches generator output). The connection is that narrowing scope to ownership-declared files strengthens the ownership-based determinism contract, but this is a stretch. Consider whether DNA-58 is the right invariant to satisfy, or whether the RFC is better classified as `kind: policy` (no DNA satisfaction required).

## Axis C — Ecosystem fit

- **C1: Pipeline placement not stated.** The RFC doesn't mention which pipeline `page.markdown.validate` runs in. The change is transparent to pipeline placement, but the RFC should state this explicitly (e.g. "remains in `SITES_BUILD_CHECK_PIPELINE`, no pipeline changes").

- **C2: No AGENTS.md updates needed.** Correct — no AGENTS.md rules change. The RFC doesn't propose any, which is fine.

- **C3: Package boundaries correct.** `packagesImpacted: ["@warpgogol/werkstatt-site"]` is correct — the change is in `packages/werkstatt-site/src/checks/page-markdown.ts`.

## Axis D — Forward-only compliance

No issues. The RFC removes the hardcoded blacklist and replaces it with the whitelist. No backward compatibility layer, no dual-path, no shim. Clean break.

## Axis E — Agent-facing policy

No issues. The RFC correctly states "Agents MAY implement code changes ONLY when this RFC has status: accepted (or implemented)." No self-authorizing language. No `NEEDS CLARIFICATION` markers.

## Axis F — Pragmatism

- **F1 (critical): Extension-only filter is insufficient — see A1.** The minimal fix is to filter by command (`page.markdown.generate`) in addition to extension. This is a one-line change to the proposed helper, but the RFC must specify it.

- **F2: Existing pattern reuse.** The RFC should reuse `matchOwnershipEntry` from `generated-file-lookup.ts:99-127` instead of proposing a new `isOwnershipPath` helper. That function already handles placeholder expansion, pattern-to-regex conversion, and app-prefix normalization. The validator could collect all `.md` files, compute relative paths, and call `matchOwnershipEntry(relPath, app)` to check if each file is a registered twin — then additionally verify the matched entry's `command` is `page.markdown.generate`.

## Axis G — Blind spots

- **G1: Empty state.** The RFC mentions "No `.md` files in ownership map: The validator skips" but doesn't confirm this matches the existing skip behavior at `page-markdown.ts:700-706` (`if (!htmlSeen && markdownFiles.length === 0)`). With the whitelist, `markdownFiles.length` would be 0 if no on-disk files match ownership patterns. The existing skip logic handles this, but the RFC should confirm.

- **G2: Performance.** The whitelist adds a pattern-match per file. Cost is negligible (~50 ownership entries, ~100 files in `public/`). Not a concern, but the RFC could state this.

- **G3: Glob matching complexity.** The RFC mentions "The `matchGlob` helper must handle `{system}` placeholders and `**` globs." The existing `expandPlaceholderVariants` + `ownPatternToExactRegex` chain already handles these. The RFC should reference these existing utilities rather than proposing a new `matchGlob`.

## Questions for the author

1. How does the whitelist exclude `auth.md` when `auth.md` is itself in `GENERATOR_OWNERSHIP_MAP`? Must the filter restrict by command (e.g. only `page.markdown.generate`), and if so, how is a "twin-producing command" identified?
2. How will the implementation match on-disk files against ownership patterns when `collectFiles`'s `ignore` callback only receives the filename, not the relative path? Will you filter after collection instead?
3. Why does the RFC propose a new `matchGlob` utility when `matchOwnershipEntry` in `generated-file-lookup.ts` already handles placeholder expansion and pattern matching? Can it be reused?
