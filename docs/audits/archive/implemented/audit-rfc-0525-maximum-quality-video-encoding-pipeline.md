# Audit: RFC-0525

## Verdict: Needs revision

The RFC has two DNA misidentifications (Axis B) that must be fixed before acceptance, and a non-standard `<source type>` value (`video/av1`) that will cause browsers to skip the AV1 source entirely (Axis G). The `versionBump: minor` is overstated — no data contract is broken. The core design (AV1 progressive, upgraded encoding parameters, per-rendition HLS audio) is sound and well-motivated.

## Mechanical validation (rfc.validate)

Pass — `rfc.validate RFC-0525 --json` returns 0 violations.

## Axis A — Structural completeness

1. **`AUDIO_BITRATE_BY_HEIGHT` type error.** The RFC declares `Record<number, number>` but the values are strings (`"64k"`, `"96k"`, `"128k"`). Should be `Record<number, string>`. (RFC line 253–258.)

2. **Source ordering inconsistency.** The "Source ordering in `<video>`" section (RFC line 148–156) states the priority as AV1 → WebM VP9 → MP4 H.264. But the code example (RFC line 344–346) emits AV1 → MP4 → WebM. The acceptance criteria (line 420) also says "(AV1, MP4, WebM)". MP4 is the universal fallback and should be last, not second. The code example and acceptance criteria contradict the stated design rationale.

3. **`video.variants.validate` changes undescribed.** The `commands.changed` frontmatter lists `video.variants.validate`, but the RFC body never describes what changes to the validator. The current validator (`video-variants.ts:553–560`) checks `entry.sources.hls`, `mp4`, `webm` — it does not check `entry.sources.av1`. If the AV1 file is missing on disk, the validator won't catch it. The RFC should specify adding `entry.sources.av1` to the validator's URL iteration.

## Axis B — DNA alignment

1. **FAIL — DNA-4 misidentified.** The `satisfies` field lists `DNA-4`, and the body says "DNA-04 (build-time-only processing): No change — all encoding remains build-time via ffmpeg." (line 170). But DNA-4 is "Canonical content in `src/content/`" — it concerns where user-visible copy and configuration live, not build-time processing. This RFC does not enforce, protect, or extend DNA-4. There is no DNA invariant about "build-time-only processing"; that concept comes from RFC-0149 (a regular RFC, not a DNA invariant). The `satisfies` field should be empty or reference an actually-applicable DNA invariant.

2. **FAIL — DNA-15 misidentified.** The `related` field includes `DNA-15`, and the body says "DNA-15 (Cloudflare 25 MiB asset limit)" (line 171). But DNA-15 is "Scripts follow placement contract" — it concerns client-side JavaScript placement, not Cloudflare asset limits. There is no DNA invariant about a 25 MiB asset limit; that constraint comes from RFC-0210's context and Cloudflare Pages deployment limits. The `related` field should remove `DNA-15` or replace it with the correct reference.

## Axis C — Ecosystem fit

1. **`video.ios-fallback.validate` not impacted.** The `video-fallback.ts` validator checks for MP4 existence only. Since MP4 remains the universal fallback, this validator does not need AV1 awareness. No issue — noted for completeness.

2. **`credits-gallery-section.astro` consumer.** This consumer reads `entry.sources.webm ?? entry.sources.mp4!` (line 144) and does not handle AV1. Since it uses webm/mp4, it doesn't need updating. No issue — noted as a blind spot, not a finding.

3. **Compass sync.** The RFC changes encoding parameters and adds a format but does not change repository-wide requirements, shared package contracts, or app-package relationships. No `docs/*.xml` synchronization is required. OK.

4. **Command lifecycle.** `commands.changed` lists `video.variants.generate` and `video.variants.validate` — both are existing registered commands. Consistent. But see Axis A finding #3 — the validate changes are undescribed.

## Axis D — Forward-only compliance

No issues. The `av1` field is additive (optional). The `ENCODER_SETTINGS_VERSION` bump invalidates caches and forces re-encoding — no legacy path is maintained. No compatibility shim or dual-path.

## Axis E — Agent-facing policy

1. **`versionBump: minor` is overstated.** Per RFC-0478, `minor` = "Breaks-B, requires migrator". But this RFC adds an optional field to a generated manifest schema and invalidates an ephemeral cache. No persisted data needs migration — the manifest is regenerated by `video.variants.generate`, and `.cache/video/` is gitignored and ephemeral. This should be `versionBump: patch` (safe, non-breaking). If `minor` is kept, a migrator is required per RFC-0479, but the RFC mentions none.

2. **Implementation notes** correctly reference RFC-0224 (accepted→implemented) and RFC-0334 (supersede escalation). OK.

3. No self-authorizing language. OK.

## Axis F — Pragmatism

1. **AV1 as a third progressive format is justified.** AV1 delivers 20-40% better compression than VP9 at equivalent quality. The graceful fallback (browsers without AV1 fall through to VP9/MP4) means no downside. The alternatives section is honest and covers the real options.

2. **Encoding time estimates are honest.** SVT-AV1 preset 2: 20-40 min for 1080p. VP9 `cpu-used 0`: 10-20 min. Acceptable because encoding is cached and runs once per source change.

3. **`packagesImpacted` and `appsImpacted` are accurate.** `@gogol/share` (schema), `@gogol/ui` (Media component), `@gogol/site-kernel-checks` (encoding functions). `webgogol-com` and `nicaragua-projekt` are the sites with authored videos.

## Axis G — Blind spots

1. **FAIL — `type="video/av1"` is non-standard.** The RFC explicitly instructs using `type="video/av1"` and argues against `video/webm; codecs=av01` (line 431). But `video/av1` is not a registered MIME type. Browsers use `video/webm; codecs="av01.*"` for AV1-in-WebM. The HTML spec says the `<source>` `type` attribute should be a valid MIME type; if the type is unrecognized, browsers may skip the source entirely without fetching it — defeating the purpose of AV1 delivery. The RFC's reasoning ("The WebM container is implied by the `.webm` extension; the `type` attribute tells the browser the codec, not the container") is incorrect: the `type` attribute specifies the full MIME type (container + codecs), and browsers do NOT infer the container from the file extension. The correct value is `type="video/webm; codecs=&quot;av01.0.05M.08&quot;"` (or a similar AV1 codec string).

2. **`libsvtav1` availability check undescribed.** The RFC's Risks section (line 403) and acceptance criteria (line 421) mention extending the ffmpeg/ffprobe availability check to verify `libsvtav1`, but the Design section doesn't specify how. The current check (`video-variants.ts:408–410`) runs `ffmpeg -version` and `ffprobe -version`. To check for `libsvtav1`, the code should run `ffmpeg -encoders` and grep for `libsvtav1`, or attempt a minimal null encode. The RFC should specify the exact check.

3. **H.264 CRF 17 file size vs 25 MiB limit for longer content.** The RFC acknowledges this in Risks (line 399) but the mitigation is only `video.dist.prune` and the non-bundled `media/` folder. The RFC says videos range from 1-30 minutes (RFC-0210 context). A 30-minute 1080p video at CRF 17 `slow` could produce a 60-100 MB MP4 — far exceeding 25 MiB. The RFC should address what happens when the progressive MP4 exceeds the limit: is it pruned from deploy? Is only HLS served? This is a real blind spot for longer content.

4. **Concurrent encoding risk.** The RFC doesn't discuss concurrent `video.variants.generate` execution. The longer encoding times (20-40 min for AV1) increase the risk window for two builds racing on the same source. This is an existing issue, not new to this RFC, but the longer encode times amplify it.

## Questions for the author

1. Why does `satisfies` list DNA-4 ("Canonical content in `src/content/`") when this RFC is about encoding parameters? Which DNA invariant does this RFC actually enforce, protect, or extend?
2. What is the correct `<source type>` value for AV1-in-WebM? `video/av1` is not a recognized MIME type — have you verified that browsers select the source with this type attribute?
3. Why is `versionBump: minor` (Breaks-B, requires migrator) when the schema change is additive (optional field) and the cache is ephemeral? Should this be `patch`?
