1. Hardcoded component-path dispatcher

Files

  • packages/share/src/astro/content.ts (376 lines)

Problem

getSemanticSiteContentData() (lines 40–195) is a 155-line if/else chain dispatching on hardcoded componentPath strings ("brand-label", "breadcrumbs", "header", "footer", etc.). Each branch manually fetches from different collections and assembles a different ad-hoc shape. The function's interface is narrow (3 params → 1 record) but the implementation is a flat conditional — complexity is length, not depth. Adding a new component path means editing this single function. There is no registry, no extensibility seam, and no per-path testability.

Solution

Extract each componentPath branch into a named handler function (brandLabelHandler, headerHandler, footerHandler, etc.) and register them in a Map<string, ComponentContentHandler>. The public function becomes a 5-line registry lookup. Each handler is independently testable and new paths are added by registering a new handler — no edit to the dispatcher.

Benefits

Locality

Each handler lives next to its collection-fetch logic, not in a 155-line function.

Leverage

New component paths are additive (register a handler) — no edit to the dispatcher.

Testability

Each handler is a pure function testable in isolation with mock collections.

Before / After

Before — Flat conditional (shallow)

Interface: narrow · Implementation: flat conditional · Depth: low

After — Registry dispatch (deepened)

Interface: same · Implementation: registry + handlers · Depth: high

2. Duplicated deep-merge functions

Files

  • packages/share/src/content/merge.ts (77 lines)
  • packages/share/src/shared-context.ts (imports deepMergeEntryData)
  • packages/share/src/astro/content.ts (imports mergeComponentContent)
  • packages/share/src/astro/page-handler/content-fallback.ts (imports deepMergeEntryData)

Problem

deepMergeEntryData() (lines 18–43) and mergeComponentContent() (lines 49–76) do essentially the same thing: recursively merge two records, override wins, arrays replaced wholesale. The only semantic difference is that deepMergeEntryData preserves the default array when the override array is empty, while mergeComponentContent always replaces arrays. Two functions, two names, two call sites each — a shallow duplicate where a single configurable function would serve all consumers.

Solution

Unify into a single deepMerge(defaults, override, options?) with an { keepDefaultOnEmptyArray?: boolean } option. Re-export the old names as thin wrappers (or update call sites — only 4 files). The implementation stays at ~30 lines instead of ~60.

Benefits

Locality

One merge implementation in one place — no hunting for which variant is used where.

Leverage

Bug fixes (e.g. null handling) apply once, not twice.

Testability

One test suite covers all merge semantics, including the array edge case.

Before / After

Before — Two parallel functions

Two shallow implementations · ~52 total lines · divergent array semantics

After — One configurable function

One deep implementation · ~30 lines · all consumers covered

3. Mixed barrel + orchestration in integration hub

Files

  • packages/share/src/integration/index.ts (419 lines)
  • packages/share/src/integration/port.ts (144 lines)
  • packages/share/src/integration/adapters.ts
  • packages/share/src/integration/funnel.ts (380 lines)
  • packages/share/src/integration/crm-buffer.ts (492 lines)

Problem

integration/index.ts is simultaneously a barrel (re-exports from 6 sibling modules: port.ts, crm-buffer.ts, funnel.ts, lifecycle.ts, sharding.ts, dispatch.ts, qstash.ts) and the orchestration layer (defines deliverLead, routeEvent, deliverEvent, authenticateInbound, consumeIntegrationBatch, upsertLead, plus the closed adapter registries CHANNEL_ADAPTERS, CRM_ADAPTERS, DESTINATION_ADAPTERS). This is 419 lines mixing two responsibilities — export surface and runtime orchestration. The barrel role makes it impossible to import just the orchestration without pulling in all sibling type exports.

Solution

Split index.ts into a pure barrel (index.ts, ~40 lines of re-exports) and an orchestration.ts module containing the registries, deliverLead, routeEvent, deliverEvent, authenticateInbound, and the legacy queue/KV types. Consumers who need orchestration import from @gogol/share/integration/orchestration; consumers who only need types import from @gogol/share/integration.

Benefits

Locality

Registries + fan-out logic live together, separate from the type-only barrel.

Leverage

Type-only consumers don't transitively import adapter implementations.

Testability

Orchestration can be tested without mounting the full barrel.

Before / After

Before — One file, two roles

Mixed responsibilities · 419 lines · no import seam between types and logic

After — Separated barrel and orchestration

4. Sync/async duplication in feature-policy resolver

Files

  • packages/share/src/feature-policy.ts (383 lines)

Problem

resolveFeaturePolicy() (lines 288–310) and resolveFeaturePolicySync() (lines 315–337) are byte-for-byte identical except for the async keyword and await on internal calls. The resolution itself is synchronous (resolvePolicyInternal is not async). The async variant exists "for compatibility with content-loading patterns" — but it adds no actual async work. Similarly, createFeaturePolicyResolver() (lines 342–358) wraps both in a factory that returns resolve, resolveSync, isEnabled, getBehavior — all calling the same synchronous core.

Solution

Keep only resolveFeaturePolicySync (rename to resolveFeaturePolicy). The async wrapper provides no value — callers can await Promise.resolve(syncResult) if they need a Promise. The factory's resolve method can return the sync result wrapped in Promise.resolve() if async compatibility is needed. This removes ~30 lines of pure duplication.

Benefits

Locality

One resolver, one cache path — no risk of the two variants diverging.

Leverage

Bug fixes apply once. ~30 lines removed.

Testability

One test path instead of two identical ones.

Before / After

Before — Two identical functions

44 lines of duplicated logic · zero async benefit

After — Single resolver

22 lines · single cache path · no divergence risk

5. Hand-rolled JSON Schema validator

Files

  • packages/share/src/dev-props-validator.ts (161 lines)

Problem

validateShape() (lines 29–89) is a hand-rolled JSON Schema subset validator. It handles type, const, enum, oneOf/anyOf, properties, required, additionalProperties, and items — but silently ignores $ref, pattern, format, if/then/else, minLength, maximum, and many other JSON Schema keywords. This means a manifest using any unsupported keyword silently passes validation even when props are invalid — a false sense of safety. The function is 60 lines of recursive type-checking that reinvents what ajv or even Zod's z.fromJsonSchema (available in Zod 4) already do, more completely.

Solution

Replace validateShape with a standard validator. Two options: (a) use ajv (already a transitive dependency in the monorepo) — 3 lines to compile and validate; or (b) convert the resolved schema to a Zod schema via z.fromJsonSchema() (Zod 4). Either way, the 60-line custom validator is replaced by a 5-line standard call that handles the full JSON Schema spec. The workspace-root resolution and caching logic (lines 91–160) stays unchanged.

Benefits

Locality

Validation logic lives in a well-maintained library, not in a 60-line custom function.

Leverage

Full JSON Schema coverage — no silent passes on unsupported keywords.

Testability

Standard validator is already tested upstream; only integration needs testing.

Before / After

Before — Custom subset validator

60 lines · partial coverage · false sense of safety

After — Standard library validator

5 lines · full coverage · well-tested upstream

6. Re-export shim proliferation

Files

  • packages/share/src/image-utils.ts (44 lines — re-exports from @gogol/content-source)
  • packages/share/src/astro/loaders.ts (24 lines — re-exports from @gogol/content-source)
  • packages/share/src/astro/page-handler.ts (20 lines — re-exports from ./page-handler/resolve-route.ts)
  • packages/share/src/astro/routes.ts (48 lines — re-exports from ./routes/*)

Problem

Four files totaling 136 lines contain zero logic — they are pure re-export shims created by RFC-0141 (content-source port extraction) and RFC-0303 (file-size splits). Each exists to preserve a historical import path. image-utils.ts and loaders.ts re-export from @gogol/content-source — a different package. page-handler.ts and routes.ts re-export from sub-modules within the same directory. Deletion test: if deleted, complexity does not move — consumers simply update their import path. These are the definition of shallow modules: zero implementation behind a re-export interface.

Solution

Evaluate which shims still have external consumers. For shims re-exporting from @gogol/content-source (a separate package), update consumers to import directly from @gogol/content-source and delete the shim. For internal split shims (page-handler.ts, routes.ts), update the package.json exports map to point directly at the sub-module and delete the shim. If any shim still has many consumers, keep it but mark with a deprecation JSDoc and a target removal date.

Benefits

Locality

Import paths point at the real source, not an indirection layer.

Leverage

136 lines of zero-logic files removed. Less grep noise when searching for implementations.

Testability

No change — shims have no tests (they have no logic).

7. Semantic barrel is too wide

Files

  • packages/share/src/semantic/index.ts (37 lines, 24+ re-exports)
  • packages/share/src/semantic/jsonld/ (11 files)
  • packages/share/src/semantic/page-builders/ (2 files)
  • packages/share/src/semantic/block-extractors/ (multiple files)

Problem

The semantic barrel re-exports from 24+ modules: models, breadcrumbs, extract, ids, jsonld (11 sub-files), llms, llms-policy, output-projection, business-projection, organization-profile, ai, robots, page-utils, page-markdown, feed, image-sitemap, page-builders (2), build-page, block-extraction, block-extractors, update-stamp, markdown-twin-provenance. A consumer importing SemanticBreadcrumb type transitively pulls in the entire semantic layer — including heavy modules like home-page.ts (11KB) and output-projection.ts. This is not shallow per se (the barrel is correct), but it is too wide for tree-shaking and violates the RFC-0264 spirit of subpath isolation.

Solution

Split the semantic barrel into 3-4 subpath entry points: @gogol/share/semantic/models (types + ids + breadcrumbs), @gogol/share/semantic/jsonld (JSON-LD builders), @gogol/share/semantic/builders (page-builders + block-extraction + build-page), @gogol/share/semantic/seo (llms + robots + feed + image-sitemap + output-projection). The root semantic/index.ts remains as a compatibility barrel but consumers migrate to targeted subpaths. This follows the same pattern as the root barrel migration (RFC-0264).

Benefits

Locality

Related modules are grouped by concern, not dumped in one barrel.

Leverage

Consumers import only what they need — smaller transitive dependency graph.

Testability

Test files can import from specific subpaths, reducing mock surface.

Before / After

Before — One mega-barrel

24+ re-exports · any import pulls everything

After — Targeted subpaths

4 subpaths · targeted imports · compat barrel preserved

8. Micro-module consolidation

Files

  • packages/share/src/rfc0042-utils.ts (96 lines — 3 tiny functions)
  • packages/share/src/string-utils.ts (17 lines — 1 function)
  • packages/share/src/content/dispatch.ts (25 lines — 1 function factory)
  • packages/share/src/counter-utils.ts (76 lines — 4 functions)

Problem

Four files totaling 214 lines contain 9 functions — an average of 24 lines per file. Each file is a separate subpath export in package.json, a separate module contract, and a separate import path. string-utils.ts exports a single 5-line toKebabCase(). rfc0042-utils.ts exports cast() which is literally return pageOverride as unknown as T — a one-line type assertion. content/dispatch.ts exports a 7-line closure factory. Deletion test: deleting any of these moves ~5 lines to the caller — complexity does not concentrate, it barely moves. These are shallow modules with minimal leverage.

Solution

Consolidate by domain affinity: rfc0042-utils.ts → inline cast() at call sites (it's a one-liner), move need() and withDefault() into content/ or counter-utils.ts (they're content helpers); string-utils.ts → merge into content/entity-id.ts (already does string normalization); content/dispatch.ts → merge into content/entity-id.ts (it uses stripEntryLanguage and toDataEntryId from there). This reduces 4 files + 4 subpath exports to 1-2 files.

Benefits

Locality

Related helpers live next to their consumers, not in isolated micro-files.

Leverage

Fewer import paths, fewer module contracts, less package.json export map churn.

Testability

Tests consolidate naturally — one test file per domain, not per micro-function.
