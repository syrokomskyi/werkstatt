# Audit: RFC-0757

## Verdict: Needs revision

The RFC has solid architectural fit and clear design, but contains a factual inconsistency in the `ChecklistRuleType` enum (Decision lists 5 types, TypeScript contract lists 4), a missing `packagesImpacted` entry for `@warpgogol/site-kernel-handoff`, a contradictory migrator rationale (defaults work when `checklistItems[]` is absent, yet the migrator adds explicit `checklistItems[]` "for explicitness"), and an incorrect archetype version baseline. These must be resolved before implementation.

## Mechanical validation (rfc.validate)

Pass with 1 warning:

- **V-30** (warning): `@warpgogol/ontology` is in `packagesImpacted` but `breaksC` is not `true`. The RFC modifies `packages/ontology/archetypes/sections/send-message.yaml`, not `packages/ontology/src/external-surfaces/` — so `breaksC: false` is semantically correct. Add an explicit `breaksC: false` field to the frontmatter to silence the warning, or accept it as a known false positive.

## Axis A — Structural completeness

- **Decision vs TypeScript contract mismatch.** The Decision (line 105) lists 5 rule types: "length, contact-details, url-presence, keyword-match, min-length-custom". The TypeScript contract (lines 137–141) defines only 4: `min-length`, `contact-details`, `url-presence`, `keyword-match`. There is no `min-length-custom` in the type. The Decision's "min-length-custom" appears to be a leftover from an earlier draft — it should be removed or the TypeScript contract should include it. As written, an implementer would not know whether `min-length-custom` is a valid rule type.
- **Archetype version baseline incorrect.** The "Architectural fit" section (line 109) says "The manifest version bumps from `1.2.0` to `1.3.0`." This is correct for the UI manifest (`send-message-section.manifest.yaml` is at `1.2.0`). But the archetype YAML (`send-message.yaml`) is at `1.0.0` (line 3 of the archetype file), not `1.2.0`. The file system responsibilities table (line 191) says "bump version to 1.3.0" for the archetype — a jump from `1.0.0` to `1.3.0` (3 minor versions). The RFC should state the actual baseline for each file.
- **Acceptance criterion vague.** Criterion 6 (line 254) says "backward compatibility test or manual verification" — "or manual verification" is not checkable. Specify a concrete test (e.g. "existing warpgogol-com contact page renders identically before and after the change, verified by behavior.snapshot.validate").

## Axis B — DNA alignment

- **DNA-17 alignment is correct.** The RFC modifies the archetype manifest `propsSchema` and the UI section manifest `propsSchema` — both are DNA-17 surfaces. Generated types are regenerated by `props.types.generate`. The manifest remains the authoritative source.
- **No new DNA invariant established.** The RFC does not claim to establish a new DNA invariant — `satisfies: [DNA-17]` is appropriate.

## Axis C — Ecosystem fit

- **Missing `packagesImpacted` entry.** The RFC adds a migrator at `packages/os/site-kernel-handoff/src/migrators/rfc-0757.ts` and registers it in `packages/os/site-kernel-handoff/src/migrators/registry.ts`. But `packagesImpacted` (line 50–52) lists only `@warpgogol/ui` and `@warpgogol/ontology`. Add `@warpgogol/site-kernel-handoff` to `packagesImpacted`.
- **Package boundaries are correct.** The RFC modifies `packages/ontology` (archetype), `packages/ui` (section), and `packages/os/site-kernel-handoff` (migrator) — all are shared package changes, no app-local logic.
- **Cosmic naming unaffected.** The RFC does not change `cosmicName` (Ceres) or introduce new sections/components.
- **Command lifecycle is correct.** `commands.proposed/added/changed/removed` are all empty — no new commands. `props.types.generate` and `mission.migrate` are existing commands.

## Axis D — Forward-only compliance

- **Individual label props kept indefinitely.** The RFC says "Agents MUST NOT remove the individual checklist label props (`checklistTitle`, `checklistReadyLabel`, `checklistLengthLabel`, `checklistContactLabel`)" (line 266). These props serve as fallback labels for the default `checklistItems[]` when the prop is absent. This is a permanent dual-path: sites can use either `checklistItems[]` or the individual labels. While the RFC frames this as "default values" rather than a "compatibility layer," the individual labels are never removed — they are kept as a permanent fallback. Consider whether this violates the forward-only principle or whether it is acceptable as "default configuration derived from existing props." If the individual labels are truly just defaults, the RFC should state that they MAY be removed in a future RFC once all sites have `checklistItems[]`.

## Axis E — Agent-facing policy

- **Status gate is correct.** The RFC is in `draft` status and does not contain self-authorizing language. Implementation notes say "Agents MAY implement code changes ONLY when this RFC has status: accepted (or implemented)."
- **Governance references are correct.** RFC-0224 (accepted→implemented), RFC-0334 (supersede escalation), RFC-0330 (verification evidence) are referenced.
- **No NEEDS CLARIFICATION markers.** No unresolved markers found.
- **Storage policy is correct.** No cookies, no `document.cookie`. Client-side only.

## Axis F — Pragmatism

- **Migrator is contradictory.** The RFC says "The `checklistItems[]` prop defaults to the current 2-item configuration (length + contact) when absent" (line 216) AND "A migrator adds an explicit `checklistItems[]` array with the default 2 items to the block configuration" (line 217). If the defaults work when absent, the migrator is unnecessary — it adds redundant data that duplicates the default behavior. If the migrator is needed (because defaults don't work), then the "defaults when absent" claim is false. The RFC should pick one: either (a) rely on defaults and make the migrator a no-op (cursor advance only, like RFC-0495/0496/0497), or (b) require explicit `checklistItems[]` and make the migrator transform content. Option (a) is more pragmatic — the defaults are sufficient, the migrator is a no-op.
- **Migrator version numbers incorrect.** The RFC says `fromVersion: "4.67.32", toVersion: "4.68.0"` (line 197). Current platform version is `4.70.10`. The `fromVersion` should reflect the current platform version at implementation time. Looking at existing migrators (e.g. RFC-0572: `fromVersion: "4.19.0", toVersion: "4.20.0"`), these are informational fields — but `4.67.32` does not match any known platform version. Use the current version (`4.70.10` → `4.71.0` or similar).
- **Closed rule set is pragmatic.** 4 rule types cover the stated use cases. `keyword-match` with `keywords[]` is flexible enough for custom detection without arbitrary code. New rule types via follow-up RFC is the right extension path.

## Axis G — Blind spots

- **Template attribute naming.** The RFC says CSS generalizes to `.send-message__checklist-item` with `data-item-id` attribute (line 196). But the current template uses `data-send-message-checklist-item="length"` (line 167 of the .astro file). The RFC should specify the exact attribute name — is it `data-item-id` (new) or `data-send-message-checklist-item` (existing, just generalized)? The client script queries by `data-send-message-checklist-item` — if the attribute name changes, the client script must match.
- **Length item text asymmetry.** In the current template, the length item's text span is empty (filled by client script with label + remaining count), while the contact item's text span has the label hardcoded in the template. The new N-item template must handle both cases: items where the label is dynamic (length with remaining count) and items where the label is static. The RFC does not address how `evaluateRule()` results feed back into the DOM text for each item type.
- **Empty checklist edge case.** The RFC says "If `checklistItems: []` is explicitly set, the checklist UI is not rendered" (line 212). But the template always renders the checklist container (`<div class="send-message__checklist" data-send-message-checklist>`). The template must conditionally hide the entire checklist when `checklistItems[]` is empty. The RFC should specify this template behavior.
- **Performance is addressed.** N regex/string checks per input event, N typically 2–5 — negligible. Correct.

## Questions for the author

1. Is `min-length-custom` a valid rule type or a leftover from an earlier draft? The Decision lists 5 types but the TypeScript contract defines 4 — which is authoritative?
2. If `checklistItems[]` defaults to the 2-item configuration when absent, why does the migrator need to add explicit `checklistItems[]`? Should the migrator be a no-op (cursor advance only)?
3. What is the exact attribute name for checklist items in the new template — `data-item-id` (new) or `data-send-message-checklist-item` (existing, generalized)? The client script must match.
