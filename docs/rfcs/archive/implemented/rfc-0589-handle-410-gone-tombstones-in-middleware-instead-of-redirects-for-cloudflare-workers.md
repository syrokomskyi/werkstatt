# RFC-0589: Handle 410 Gone tombstones in middleware instead of _redirects for Cloudflare Workers

## Context

The first real-world Cloudflare Workers propagation of `warpgogol-com-r000001` revealed that the `_redirects` file generated by `public.infrastructure.generate` contains HTTP 410 (Gone) status codes for retired page routes. Cloudflare Workers static assets `_redirects` only supports status codes 200, 301, 302, 303, 307, and 308 — 410 is not supported and causes `wrangler deploy` to fail.

The 410 tombstones are generated by `buildRetiredPageRoutesBlock` in `packages/os/site-kernel-codegen/src/app-boilerplate-helpers.ts:235-256`, which emits `/<slug>/* / <status>` for retired routes with `status: 410`. The `redirect.map.validate` validator (REDIR-03) in `site-kernel-checks` currently allows 410 as a valid status code, so the invalid entries pass validation and reach the deployment.

The workaround during the propagation was to manually remove 410 entries from the release dist's `_redirects` file and re-store the artifact. This is not a durable solution — the next `public.infrastructure.generate` regenerates the invalid entries.

## Problem

DNA-49 (Fleet propagation) requires that published releases deploy successfully to Cloudflare Workers. The current `_redirects` generation produces entries with HTTP 410 status codes that Cloudflare Workers static assets does not support, causing `wrangler deploy` to fail:

1. **410 in `_redirects`** (`packages/os/site-kernel-codegen/src/app-boilerplate-helpers.ts:246`): `buildRetiredPageRoutesBlock` emits `/<slug>/* / 410` for retired routes with `status: 410`. Cloudflare Workers `_redirects` only supports 200, 301, 302, 303, 307, 308.

2. **Validator allows 410** (`packages/os/site-kernel-checks/src/public-surface/managed-public.ts:175`): `runRedirectMapValidate` (REDIR-03) accepts 410 as a valid status code, so the invalid entries pass validation.

3. **No middleware fallback**: The system has no Astro middleware to handle 410 tombstones at runtime. The only mechanism for retired routes is `_redirects`, which is platform-specific.

## Decision

`buildRetiredPageRoutesBlock` no longer emits 410 entries to `_redirects`. Retired page routes with `status: 410` are handled by an Astro middleware that returns a 410 response at runtime. `redirect.map.validate` (REDIR-03) prohibits 410 in `_redirects` files for Cloudflare Workers adapter sites, resolving the adapter type from `systems/registry.yaml`. The tombstone middleware file (`src/middleware/retired-tombstones.ts`) is generated by `routes.generate` as a boilerplate file, and the root `src/middleware.ts` template is updated to chain it first via `sequence()`. This RFC amends RFC-0487: its success signal "redirect.map.validate passes with 410 entries for retired routes" is replaced by "redirect.map.validate passes without 410 entries (410 handled by middleware)."

## Architectural fit

- **DNA-49 (Fleet propagation)**: DNA-49 requires that published releases deploy successfully and that preflight checks pass. 410 entries in `_redirects` cause `wrangler deploy` to fail, which blocks propagation. This RFC fixes the generation and validation so the preflight gate can pass and releases deploy successfully.
- **RFC-0149**: Unified deployment on Cloudflare Workers. This RFC aligns `_redirects` generation with Cloudflare Workers' supported status codes.
- **RFC-0318**: Clean managed public trees and redirect retired PSEO URLs. This RFC changes how retired routes are handled — from `_redirects` to middleware.
- **RFC-0487/RFC-0509**: Retired page routes — 410 Gone tombstones + 301 redirects. This RFC amends RFC-0487 by moving 410 handling from `_redirects` to middleware. RFC-0487's success signal "redirect.map.validate passes with 410 entries" is superseded — 410 entries now fail validation.
- **RFC-0587**: Fixes Leitstand preflight. This RFC complements it by fixing the `_redirects` generation that caused deploy failures.
- **RFC-0588**: Fixes behavior snapshot route collection. This RFC complements it by ensuring `_redirects` only contains supported status codes.

// buildRetiredPageRoutesBlock — no longer emits 410 entries
export function buildRetiredPageRoutesBlock(manifest: SystemManifest): string {
  const retiredRoutes = manifest.retiredRoutes ?? [];
  if (retiredRoutes.length === 0) return "";

  const entries = retiredRoutes
    .filter((entry) => entry.status === 301)  // only 301 redirects in _redirects
    .map((entry) => {
      const slug = entry.slug.replace(/^\/+|\/+$/g, "");
      const target = entry.to.replace(/^\/+|\/+$/g, "");
      return `/${slug}/* /${target} 301`;

### Failure modes

- **`buildRetiredPageRoutesBlock` with only 410 routes**: Returns empty string (no `_redirects` entries). The 410 routes are handled by middleware.
- **`buildRetiredTombstoneMiddleware` with no 410 routes**: Returns passthrough middleware source (calls `next()`). The middleware file is always generated so the root `src/middleware.ts` can unconditionally import it.
- **`redirect.map.validate` on non-Cloudflare Workers sites**: The validator resolves the adapter type from `systems/registry.yaml`. For `cloudflare-workers`, 410 is rejected. For `null` (testing), 410 is also rejected (no runtime middleware in test mode). No other adapters exist in the fleet.
- **Middleware already exists**: `routes.generate` overwrites the middleware file (it is a generated boilerplate file, not authored content).
- **Registry entry missing**: If the system is not in `systems/registry.yaml`, the validator falls back to rejecting 410 unconditionally (safe default).

## Rollout

- **Default behavior**: All fixes are active immediately upon implementation. No feature flags.
- **Existing sites**: Sites with 410 entries in `_redirects` will fail `redirect.map.validate` after this RFC is implemented. Re-running `routes.generate` generates the middleware file and updates `src/middleware.ts`. Re-running `public.infrastructure.generate` removes 410 entries from `_redirects`.
- **New sites**: Automatically generate tombstone middleware from day one.
- **Pipeline integration**: `routes.generate` is called during `build.prepare`. The middleware file is generated alongside `src/middleware.ts` and `src/middleware/language-redirect.ts`. `public.infrastructure.generate` runs separately for `public/` files.
- **Existing releases**: Releases with 410 in `_redirects` will fail `redirect.map.validate` after implementation. Re-run `routes.generate`, `public.infrastructure.generate`, and `release.prepare` to produce a new valid release. Existing release branches that are not re-validated are not grandfathered — they must be re-built.

## Alternatives considered

1. **Replace 410 with 301 redirect to a tombstone page**: Rejected — 301 is a permanent redirect, not a tombstone. Search engines would index the tombstone page instead of de-indexing the retired URL. 410 is semantically correct for permanently removed content.

2. **Replace 410 with 404 in `_redirects`**: Rejected — 404 is also not supported by Cloudflare Workers `_redirects` (only 200, 301, 302, 303, 307, 308). And 404 is semantically different from 410 (Not Found vs Gone).

3. **Handle 410 in Cloudflare Worker script (not middleware)**: Rejected — the Worker script is generated by the Astro Cloudflare adapter and should not be hand-edited. Astro middleware is the correct extension point.

4. **Remove 410 support entirely**: Rejected — 410 tombstones are a requirement of RFC-0487/RFC-0509 for retired page routes. The semantic meaning of "permanently removed" must be preserved.

5. **Platform-specific `_redirects` generation**: Rejected — adding adapter-awareness to `_redirects` generation couples codegen to deployment platform. Middleware is platform-agnostic and works everywhere.

6. **Conditional middleware file generation**: Rejected — generating the middleware file only when 410 routes exist would require conditional imports in `src/middleware.ts`, which is incompatible with Astro's static import model. Always generating the file (passthrough when no tombstones) is simpler and avoids build failures.

## Risks

- **Middleware performance**: The middleware runs on every request. For sites with many retired routes, the route matching may add latency. Mitigation: use prefix-based matching for wildcard routes (`/<slug>/*`) — a `Map<string, true>` of slug prefixes, checked via `url.startsWith(prefix)`. No regex needed since all retired routes use the same `/<slug>/*` pattern.
- **Middleware ordering**: The retired-tombstone middleware must run before the language redirect middleware. Mitigation: the root `src/middleware.ts` template chains via `sequence(tombstoneMiddleware, languageRedirectMiddleware, devNormalize)`. Tombstone runs first, matches unprefixed retired paths (`/widerruf/`), and returns 410 immediately. For prefixed paths (`/de/widerruf/`), language redirect returns 308 → client requests `/widerruf/` → tombstone returns 410.
- **Validator false positives**: `redirect.map.validate` may reject 410 for non-Cloudflare Workers sites where 410 is supported. Mitigation: the validator resolves the adapter type from `systems/registry.yaml`. Currently only `cloudflare-workers` and `null` exist — both reject 410. If a future platform supports 410 in `_redirects`, the validator can be extended.
- **Agent misinterpretation**: Agents may think 410 is removed from the system. Mitigation: `packages/os/site-kernel-codegen/AGENTS.md` documents that 410 is still in the `retiredRoutes` schema but handled by middleware, not `_redirects`.
- **Existing releases**: Releases with 410 in `_redirects` will fail `redirect.map.validate` after implementation. Mitigation: re-run `routes.generate`, `public.infrastructure.generate`, and `release.prepare`.
