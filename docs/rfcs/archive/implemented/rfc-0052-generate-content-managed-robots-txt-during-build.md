# RFC-0052: Generate content-managed robots.txt during build with CMS policy

## Context

`apps/nicaragua-projekt` currently has a manually maintained `public/robots.txt`:

```txt
User-agent: *
Allow: /

# Block typical vulnerability scanners
User-agent: nikto
User-agent: nmap
User-agent: sqlmap
Disallow: /

Sitemap: /sitemap.xml
```

The site already follows a proven pattern for content-managed static file generation during build:

- **Sitemap** (RFC-0049): `sitemap.generate` writes `public/sitemap.xml` from `system.md pages[].routes`.
- **llms.txt** (RFC-0050): `llms.generate` writes `public/llms.txt` from the content layer.
- **ai.txt** (RFC-0051): `ai.generate` writes `public/ai.txt` from `system.md ai:` block.

All three share the same architecture: **content-managed config in `system.md`** → **pure formatter in `@gogol/share`** → **thin command in `site-kernel-checks`** → **`public/` file during `build.prepare`** → **Astro copies to `dist/`**.

The `robots:` block in `system.md` has no existing precedent, but the same pattern applies naturally: a CMS-editable crawl policy that auto-generates the robots.txt file on every build.

The WGogol Platform uses the **open-by-default** approach for robots.txt (recommended by SEO best practices 2024-2026): a minimal file that lists the sitemap and allows all well-behaved crawlers. Technical sections (admin, login, internal search) are explicitly disallowed. Known low-value crawlers (vulnerability scanners, SEO audit bots) are listed with a blanket `Disallow: /`.

## Problem

The unprotected invariants are:

> Every deployed site must have a valid `robots.txt` at its root URL.

> The robots.txt must accurately reflect the site's crawl policy — not block indexable content, not leave technical sections open to indexing.

Current failure modes:

1. **Manually maintained file.** The current `public/robots.txt` is a static file that must be hand-edited when the site structure changes (new technical routes, new crawler blocklist entries). There is no automation to keep it in sync.
2. **No validation.** There is no check that `robots.txt` exists, is non-empty, or contains a sitemap reference. A build can silently ship without a robots.txt.
3. **No CMS control.** The `ai:` block in `system.md` is client-editable (DNA-22). The robots.txt policy is not — only engineering can change it by editing `public/robots.txt`.
4. **No per-app customization.** Each app currently needs its own manual `public/robots.txt`. A shared generation command would eliminate duplication.
5. **Inconsistent sitemap references.** The sitemap URL in the manual file (`/sitemap.xml`) must match the actual generated sitemap structure. There is no cross-validation.

## Decision

Introduce a `robots:` configuration block in `src/content/system.md` and a site-kernel generation command that writes `public/robots.txt` during `build.prepare`. The pattern mirrors the existing `ai:` → `ai.generate` architecture (RFC-0051).

**`robots.generate` command** reads the `robots:` block from `system.md`, calls a pure formatter `buildRobotsTxt()` from `@gogol/share/semantic`, and writes `public/robots.txt`.

**`robots.validate` command** checks that `public/robots.txt` exists, is non-empty, contains at least one `User-agent` directive and the required `Sitemap:` reference, and that referenced sitemap URLs correspond to files that are actually generated.

**Default behavior.** If a site has no `robots:` block in `system.md`, the generator falls back to a sensible default: `User-agent: *` with `Disallow:` (nothing disallowed) and a sitemap reference. This means every build automatically produces a valid robots.txt even without explicit configuration.

**Content-managed.** The `robots:` block is declared in `system.md` at the same level as `ai:`, `growth:`, and `release:`. It is part of the `clientEditable` surface (DNA-22) so that non-engineering editors can adjust crawl policy without touching the codebase.

## Architectural fit

**DNA-22 / Client surface.** The `robots:` block in `system.md` joins `ai:` as a client-editable crawl and AI policy surface. The client edit whitelist in `system.md clientEditable` does not need to list individual blocks — `system.md` itself is a single content file, and its individual keys are not separately validated by `client.edit.validate`. Adding `robots:` as a top-level key is consistent with `ai:`, `growth:`, and `release:`.

**DNA-25 / Thin delivery.** No Astro route file is created. The `robots.generate` command writes to `public/robots.txt` during build, and Astro copies it to `dist/robots.txt`. The file is served at the correct root URL by the static host.

**RFC-0047 / CMS-friendly surface.** The `robots:` block lives in the single `system.md` manifest. No new content collection or schema file is needed outside `@gogol/share`.

**RFC-0049 / Sitemap interoperability.** The `robots:` block automatically references the correct sitemap path from the Astro site config, staying in sync with the actual generated sitemap files.

**RFC-0051 / ai.txt pattern clone.** The architecture is a direct parallel: a config block in `system.md` → a pure formatter function → a command pair (generate + validate) → pipeline registration. The code structure deliberately mirrors `ai.ts`.

## Design

### `system.md` schema addition — `robots:` block

```yaml
robots:
  defaultPolicy: allow                    # "allow" | "disallow": default for User-agent: *
  disallowedPaths:                        # paths blocked for the default user-agent
    - /admin/
    - /login
    - /cart/
    - /checkout/
    - /search?
    - /*?session=
    - /*?utm_
  allowedPaths: []                        # optional: exceptions within disallowed paths
  crawlerBlocklist:                       # User-agents to block entirely
    - nikto
    - nmap
    - sqlmap
    - AhrefsBot
    - SemrushBot
    - MJ12bot
  sitemap: /sitemap.xml                   # optional: defaults to "/sitemap.xml"
  customRules:                            # optional: additional User-agent groups with specific rules
    - userAgent: Googlebot
      disallow: []
      allow: []
    - userAgent: GPTBot
      disallow:
        - /
    - userAgent: anthropic-ai
      disallow:
        -
```

### TypeScript contracts

```ts
// packages/share/src/semantic/robots.ts

export interface RobotsRule {
  userAgent: string;
  disallow: string[];
  allow: string[];
}

export interface RobotsPolicy {
  defaultPolicy?: "allow" | "disallow";     // default: "allow"
  disallowedPaths?: string[];                // Disallow paths for User-agent: *
  allowedPaths?: string[];                   // Allow paths for User-agent: *
  crawlerBlocklist?: string[];               // User-agents to block entirely
  sitemap?: string;                          // default: "/sitemap.xml"
  customRules?: RobotsRule[];                // Additional per-user-agent rule groups
}

export function buildRobotsTxt(policy: RobotsPolicy): string;
```

### Formatter logic (`buildRobotsTxt`)

The pure function assembles the robots.txt text following the RFC 9309 format:

1. **Default User-agent group** — generated from `defaultPolicy`, `disallowedPaths`, and `allowedPaths`. If `defaultPolicy` is `"allow"`, emits `Disallow:` (empty = nothing disallowed). If `"disallow"`, emits `Disallow: /`.
2. **Crawler blocklist** — each entry becomes `User-agent: <name>\nDisallow: /`.
3. **Custom rules** — each `RobotsRule` generates a `User-agent: <name>` section with its own `Disallow`/`Allow` entries.
4. **Sitemap reference** — always appended as the final line.

Default output when no `robots:` block is present (equivalent to the empty policy):

```txt
User-agent: *
Disallow:

Sitemap: /sitemap.xml
```

Example output for the Nicaragua Projekt site with the recommended configuration:

```txt
User-agent: *
Allow: /

# Block typical vulnerability scanners
User-agent: nikto
User-agent: nmap
User-agent: sqlmap
Disallow: /

Sitemap: /sitemap.xml
```

Example output for a larger commercial site with custom rules:

```txt
User-agent: *
Disallow: /admin/
Disallow: /login
Disallow: /cart/
Disallow: /checkout/
Disallow: /search?
Disallow: /*?session=
Disallow: /*?utm_

User-agent: Googlebot
Allow: /

User-agent: GPTBot
Disallow: /

User-agent: anthropic-ai
Disallow: /

Sitemap: https://example.com/sitemap.xml
```

**Comment generation.** The formatter inserts section-comment lines (`# ...`) before semantically distinct groups — the default policy, the blocklist, custom rules, and the sitemap reference. This keeps the output human-readable and debuggable.

### CLI surface

```sh
pnpm exec werkstatt run robots.generate --app nicaragua-projekt
pnpm exec werkstatt run robots.generate --all --json

pnpm exec werkstatt run robots.validate --app nicaragua-projekt
pnpm exec werkstatt run robots.validate --all --json
```

`robots.generate` writes `public/robots.txt`. It also prints the generated content to stdout for CI inspection and reports the byte count.

`robots.validate` reads `public/robots.txt` and checks:

- File exists and is non-empty.
- File contains at least one `User-agent:` directive.
- File contains a `Sitemap:` directive.
- File contains either `Allow:` or `Disallow:` directive(s) (at least one rule group is functional).
- File size is within a reasonable range (≥20 bytes, ≤100 KiB).
- The sitemap path referenced in the `Sitemap:` directive actually exists as a generated file in `public/`.

### Output format

`robots.generate --json`:

```json
{
  "command": "robots.generate",
  "status": "pass",
  "app": "nicaragua-projekt",
  "byteCount": 145,
  "defaultPolicy": "allow",
  "blocklistCount": 3,
  "customRuleCount": 0,
  "sitemapRef": "/sitemap.xml"
}
```

`robots.validate --json`:

```json
{
  "command": "robots.validate",
  "status": "fail",
  "app": "nicaragua-projekt",
  "violations": [
    {
      "rule": "missing-user-agent",
      "severity": "error",
      "message": "robots.txt does not contain a User-agent directive."
    },
    {
      "rule": "missing-sitemap",
      "severity": "error",
      "message": "robots.txt does not contain a Sitemap directive."
    }
  ]
}
```

### Failure modes

`robots.validate` exits non-zero on any error.

Fail-hard errors:

- File not found (run `robots.generate` first).
- File is empty.
- No `User-agent:` directive found.
- No `Sitemap:` directive found.
- No `Allow:` or `Disallow:` directive found (no functional rules).
- File exceeds 100 KiB (likely malformed or includes unintended content).

Warnings:

- Referenced sitemap file does not exist on disk (sitemap not yet generated, or path mismatch).
- File is very small (<20 bytes — almost certainly empty after trimming).
- File contains unexpected encoding (non-ASCII, non-UTF-8 detectable issues).

### File system responsibilities

| Path | Role |
| --- | --- |
| `apps/<app>/public/robots.txt` | Generated robots.txt; produced by `robots.generate` and copied to `dist/robots.txt` by Astro |
| `apps/<app>/src/content/system.md` | Optional `robots:` block (default policy, disallowed paths, crawler blocklist, custom rules, sitemap ref) |
| `packages/share/src/semantic/robots.ts` | `buildRobotsTxt` pure formatter function |
| `packages/os/site-kernel-checks/src/robots.ts` | `runRobotsGenerate` and `runRobotsValidate` commands |

### What happens to the existing manual file

The existing `public/robots.txt` in each app is **deleted** after `robots.generate` is implemented and verified. The content of the current manual file becomes the default configuration for that app's `robots:` block in `system.md`. The generated file replaces the manual one at the same path.

## Rollout

1. Add `buildRobotsTxt` and `RobotsPolicy`/`RobotsRule` types to `@gogol/share/semantic/robots.ts`.
2. Export from `@gogol/share/semantic` (add to the barrel in `index.ts`).
3. Implement `runRobotsGenerate` and `runRobotsValidate` in `packages/site-kernel-checks/src/robots.ts`.
4. Register `robots.generate` and `robots.validate` commands in `createStandardCheckModule` (in `module.ts`).
5. Add `{ command: "robots.generate" }` to `STANDARD_BUILD_PREPARE_PIPELINE` after `ai.generate`.
6. Add `robots.validate` to `app.contract.full`.
7. Add the `robots:` block to `apps/nicaragua-projekt/src/content/system.md` with the current policy.
8. Delete the manual `apps/nicaragua-projekt/public/robots.txt`.
9. Verify: run `pnpm --filter nicaragua-projekt build` and inspect `dist/robots.txt`.
10. Update `onboarding.scaffold` to add `robots.generate` to the new app's `build.prepare` pipeline.

No flag-day migration is needed for existing apps: when `robots.generate` runs for the first time, it produces the default allow-all + sitemap output for apps without a `robots:` block, which is always a valid robots.txt. Apps that already have a manual `public/robots.txt` get the generated file once the command runs. The manual file should be deleted only after verification.

## Alternatives considered

**Keep the manual `public/robots.txt`.** Rejected. The manual file is invisible to validation, not content-managed, and must be maintained per app. Every other static discovery file (sitemap, llms, ai.txt) is generated. Robots.txt should follow the same pattern for consistency.

**Use an Astro API route (`src/pages/robots.txt.ts`).** Rejected. The existing pattern for all static discovery files is generation during `build.prepare` into `public/`. API routes add request-time overhead and are inconsistent with the sitemap/llms/ai.txt approach.

**Embed robots.txt logic in the existing sitemap command.** Rejected. Robots.txt is a separate concern (crawl policy vs. URL inventory). Combining them violates separation of concerns and makes validation harder.

**Support inline raw robots.txt in system.md as a single string.** Rejected. A structured `robots:` block is content-managed and can be validated, defaulted, and composed programmatically. A raw string would bypass validation and defeat the purpose of content management.

**Add `@astrojs/robots-txt` integration.** Rejected. The integration framework does not exist in Astro core and adding a dependency for a single file that can be generated in 50 lines of code is unnecessary weight.

## Risks

**Missing `robots:` block.** Without a `robots:` block, the generator falls back to the default: `User-agent: *` with `Disallow:` (nothing disallowed) and a sitemap reference. This is always valid and SEO-safe. Mitigation: the default policy is documented as the safe fallback.

**Sitemap path mismatch.** The sitemap path in the `robots:` block must match the actual generated sitemap filename. The default (`/sitemap.xml`) matches RFC-0049 output. A configurable `sitemap` field allows per-app override. Mitigation: `robots.validate` cross-checks the sitemap reference against the actual `public/` file listing.

**Accidental over-blocking.** An editor could set `defaultPolicy: disallow` and block the entire site from crawling. This is a content-management risk, not an engineering risk — the same applies to any CMS setting. Mitigation: the `robots.validate` warning for full-site disallow is an optional enhancement.

**Duplicate `Sitemap:` directives.** If both `robots.txt` and the sitemap index contain sitemap references, there is no conflict — Google reads both. The robots.txt `Sitemap:` directive is the recommended way to point crawlers to the sitemap.

**Agent drift.** Agents may try to create an Astro API route for robots.txt or add it as a `src/pages/robots.txt.ts` file. Mitigation: this RFC explicitly prohibits API routes and mandates generation into `public/`.

## Implementation notes for agents

- Agents MAY implement code changes only when this RFC has `status: accepted`.
- Agents MUST NOT change status fields in any RFC.
- Agents MUST NOT create an Astro route file for robots.txt — it is generated into `public/` during `build.prepare`.
- Agents MUST NOT add `@astrojs/robots-txt` or any third-party robots.txt dependency to any app or package.
- Agents MUST keep the robots.txt command thin: read `robots:` block from `system.md`, call `buildRobotsTxt()`, write file.
- Agents MUST keep formatting logic in `@gogol/share/semantic/robots.ts`, not in app code or command code.
- Agents MUST delete the manual `public/robots.txt` after implementing and verifying the generation command.
- Agents MUST add the `robots:` block to `apps/nicaragua-projekt/src/content/system.md` with the policy equivalent to the current manual file.
- When implementing, agents MUST reference `RFC-0052` in commit messages or PR descriptions.
- Agents MUST run `robots.validate --app <app>` after any change to the `robots:` block in `system.md`.
- Agents MUST NOT block CSS/JS assets via robots.txt — Google needs them for rendering.
