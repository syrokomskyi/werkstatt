# RFC-0048: Support localized page slugs and route resolution

## Context

`apps/nicaragua-projekt` currently uses the CMS-friendly content surface from RFC-0047:

```txt
src/content/
  system.md
  pages/{lang}/...
  prose/{lang}/...
  business/{lang}/...
  navigation/{lang}/...
  site/{lang}/...
```

Routes are generated by `apps/nicaragua-projekt/src/pages/[lang]/[...slug].astro` from the `pages` collection. The route currently derives the public slug from the content entry id:

```txt
src/content/pages/de/datenschutz.md -> /de/datenschutz
src/content/pages/en/datenschutz.md -> /en/datenschutz
```

Navigation content from RFC-0044 already uses semantic targets:

```yaml
semanticTarget:
  kind: internal
  pageId: datenschutz
routeSlug: datenschutz
```

However, `routeSlug` is still repeated in localized `navigation.md`, and `system.md pages[].route` stores one language-neutral route. That makes it hard to support natural localized URLs such as:

```txt
/de/datenschutz
/en/privacy
```

without duplicating route decisions across page files, system manifest, navigation content, breadcrumbs, CTA targets, and the language switcher.

## Problem

The unprotected invariant is:

> Internal page identity must be stable across languages, while public slugs may be localized per language.

Current failure modes:

1. **Slug identity is overloaded.** The content file stem, `system.md pages[].route`, and `navigation.md targets[].routeSlug` all act as partial route sources.
2. **Language switching preserves the raw slug.** `getLocalizedUrlSync("/de/datenschutz", "en")` can only produce `/en/datenschutz`; it cannot know that the English sibling is `/en/privacy`.
3. **Header and footer links depend on duplicated routeSlug values.** `resolveSemanticTarget()` reads navigation targets and builds URLs from `routeSlug`, so navigation owns a route concern that should be shared across all internal links.
4. **Fallback paths keep default-language slugs.** RFC-0008 fallback generation can create `/en/datenschutz` for a missing English page, but it has no canonical localized slug table.
5. **System page pins are route-keyed.** `system.md pages[].route` makes shell blocks and planet pins depend on one public path instead of stable page identity.

## Decision

The platform introduces a shared localized route registry.

The canonical internal page identity is `pageId`. The canonical public route for a page is a language-keyed slug in `system.md pages[].routes`.

```yaml
pages:
  - pageId: privacyPolicy
    routes:
      de: datenschutz
      en: privacy
    cosmicStar: Fomalhaut
    planets:
      - { cosmicPlanet: Thebe, pin: "1.0.0" }
      - { cosmicPlanet: Hyperion, pin: "1.2.0" }
```

The home page uses an empty slug per language:

```yaml
pages:
  - pageId: home
    routes:
      de: ""
      en: ""
```

All internal URL generation must resolve through this registry:

- Header links
- Footer links
- CTA targets
- Breadcrumb URLs
- Language switcher sibling URLs
- Route `getStaticPaths()`
- Semantic outputs that emit canonical URLs, alternate URLs, or breadcrumbs

`navigation.md` remains the CMS-editable source for labels, order, grouping, and semantic targets. It no longer owns canonical internal page slugs. `targets[].routeSlug` becomes a migration-only compatibility field: if present, validators must require it to match the route registry for that `semanticTarget.pageId` and language.

This RFC narrows the RFC-0047 `AuthorPageEntry.routeSlug` concept: a page entry may retain `routeSlug` during migration, but the durable source of public routes is `system.md pages[].routes`.

## Architectural fit

**RFC-0038 / language configuration.** Language prefixes remain canonical. The `routes` object keys must be drawn from `system.md i18n.supported`.

**RFC-0044 / content-declared navigation.** Navigation stays content-declared for visitor-facing labels and grouping, but route resolution moves to a shared registry so header and footer links cannot drift from page routes.

**RFC-0047 / CMS-friendly surface.** The route registry lives in `src/content/system.md`, which is already part of the CMS-friendly content surface. Page authors work with stable page identity and localized public slugs, not cosmic names or component internals.

**DNA-24 / block-declarative pages.** Page entries remain frontmatter-only block-declarative content. They gain or retain a stable `pageId` field so localized entries can be paired without relying on identical filenames.

**DNA-25 / thin routes.** The Astro catch-all route remains thin. It delegates path generation and content entry lookup to shared route helpers instead of hand-assembling slug logic.

**Package boundaries.** App-specific route data stays in app content. App-agnostic route loading, indexing, and target resolution live in `@gogol/share` or `@gogol/site-kernel-content`. Packages must not import from `apps/*`.

## Design

### CLI surface

This RFC proposes one validation command:

```sh
pnpm exec werkstatt run routes.localized.validate --app nicaragua-projekt
pnpm exec werkstatt run routes.localized.validate --all --json
```

`routes.localized.validate` is app-scoped and checks:

- every `system.md pages[]` item has a stable `pageId`;
- every `routes` key is a supported language from `i18n.supported`;
- route slugs are unique per language;
- route slugs do not start or end with `/`;
- the home route uses `""`, not `/`;
- every non-home route slug is non-empty;
- every internal `navigation.md targets[].semanticTarget.pageId` exists in the route registry;
- any transitional `navigation.md targets[].routeSlug` matches the registry for that language;
- every default-language route has a page content entry with the same `pageId`;
- localized page entries either match the route registry by `pageId` or are explicitly covered by RFC-0008 fallback behavior.

Changed commands:

- `system.manifest.validate` validates `pages[].pageId` and `pages[].routes`.
- `page.block.validate` resolves page pins by `pageId`, not by `route`.
- `content.surface.validate` rejects new routeSlug-as-primary patterns after migration.
- `onboarding.scaffold` generates `pageId` and `routes` for new sites.
- `app.contract.full` includes `routes.localized.validate`.

### TypeScript contracts

```ts
export type LanguageCode = string;
export type PageId = string;

export interface LocalizedRouteEntry {
  pageId: PageId;
  cosmicStar: string;
  routes: Record<LanguageCode, string>;
}

export interface RouteRegistry {
  byPageId: Map<PageId, LocalizedRouteEntry>;
  byLanguageAndSlug: Map<LanguageCode, Map<string, LocalizedRouteEntry>>;
}

export interface InternalTargetRef {
  kind: "internal";
  pageId: PageId;
  anchor?: string;
}

export interface ExternalTargetRef {
  kind: "external";
  href: string;
}

export interface ResolvedLocalizedRoute {
  pageId: PageId;
  lang: LanguageCode;
  slug: string;
  pathname: string;
}
```

Required shared helpers:

```ts
export async function getRouteRegistry(): Promise<RouteRegistry>;

export async function resolveLocalizedPagePath(
  target: InternalTargetRef,
  lang: LanguageCode,
): Promise<string | null>;

export async function resolvePageEntryForPath(
  lang: LanguageCode,
  slug: string,
): Promise<{
  route: ResolvedLocalizedRoute;
  entry: unknown;
}>;

export async function getLocalizedSiblingPath(
  currentLang: LanguageCode,
  currentSlug: string,
  targetLang: LanguageCode,
): Promise<string>;
```

Compatibility behavior:

- `resolveLocalizedPagePath({ pageId: "privacyPolicy" }, "de")` returns `/de/datenschutz`.
- `resolveLocalizedPagePath({ pageId: "privacyPolicy" }, "en")` returns `/en/privacy`.
- `getLocalizedSiblingPath("de", "datenschutz", "en")` returns `/en/privacy`.
- If a target language has no route entry for a page, the helper returns `/{targetLang}/` or another explicit safe fallback, not a guessed translated slug.

### Failure modes

Fail-hard errors:

- missing `pageId` on any `system.md pages[]` item;
- duplicate `pageId` values;
- duplicate slugs within one language;
- unsupported language key in `routes`;
- navigation target references a missing internal `pageId`;
- transitional `navigation.md routeSlug` conflicts with the route registry;
- default-language route has no matching page content entry.

Warnings:

- a supported language has no route for a non-critical page that is not linked from navigation;
- a localized page entry is missing and RFC-0008 fallback will use default-language content;
- a page content file name no longer matches the localized slug during migration.

The command exits non-zero on any error. `--json` emits stable machine-readable output with the same rule ids as pretty output.

## Localized anchors

Section anchor values in `navigation.md targets[].semanticTarget.anchor` currently hold a raw HTML `id` string. This couples the navigation content to the section's rendered markup language, so `/en/#unser-ansatz` is produced even when browsing the English site.

The correct model is the same one used for page routes: a **stable identifier** in navigation content that resolves to a language-specific HTML fragment through a shared registry.

### Anchor registry in `system.md`

Each page entry may declare an `anchors` map. Keys are stable `anchorId` values (analogous to `pageId`); values are language-keyed HTML fragment identifiers (analogous to `routes`):

```yaml
pages:
  - pageId: home
    routes:
      de: ""
      en: ""
    anchors:
      approach:
        de: unser-ansatz
        en: our-approach
      transparency:
        de: transparenz
        en: transparency
```

### Navigation content

`navigation.md targets[].semanticTarget.anchor` becomes a stable `anchorId` string that references an entry in the page's `anchors` registry:

```yaml
- id: approach
  label: Our Approach
  semanticTarget:
    kind: internal
    pageId: home
    anchor: approach
```

The value `approach` is language-neutral — identical across all `navigation/{lang}/navigation.md` files — just as `pageId` is language-neutral.

### Resolution

`resolveSemanticTarget()` resolves the anchor with the following priority:

1. Look up `anchor` in `system.md pages[pageId].anchors[anchorId][lang]`.
2. If found, append the language-specific fragment to the URL: `/en/#our-approach`.
3. If the `anchorId` exists in the registry but has no entry for `lang`, fall back to the default language value.
4. If the `anchorId` is not in the registry (plain HTML id or migration artifact), use it as-is (no regression).
5. If `anchor` is absent, emit no fragment.

### TypeScript contract addition

```ts
export interface LocalizedRouteEntry {
  pageId: PageId;
  cosmicStar: string;
  routes: Record<LanguageCode, string>;
  // RFC-0048: optional anchor registry for this page
  anchors?: Record<string, Record<LanguageCode, string>>;
}
```

### Validation additions for `routes.localized.validate`

- Every `anchorId` referenced in `navigation.md targets[].semanticTarget.anchor` that exists in the registry must have an entry for every supported language.
- A warning is emitted when a navigation `anchor` value is not found in the registry, suggesting it may be a raw HTML id that could be promoted to a registered anchorId.
- `system.md pages[].anchors` keys must be unique within the page; duplicate anchorIds are a fail-hard error.

### Section HTML `id` contract

For localized anchors to work, sections that serve as anchor targets must render the correct `id` for the current language. Sections should read their `id` from a prop or from content, not from a hardcoded German string.

## Alternatives considered

**Keep per-language `navigation.md routeSlug` as canonical.** Rejected. Navigation should own labels, order, and grouping, not the canonical URL table used by routes, breadcrumbs, semantic outputs, and language switching.

**Use page file names as the only route source.** Rejected. File names are convenient but cannot reliably pair localized siblings when slugs differ, and they make fallback route generation ambiguous.

**Put localized slugs only in page frontmatter.** Rejected as the durable source because missing localized page entries would have no localized slug for RFC-0008 fallback paths. Page frontmatter may mirror or validate identity, but `system.md` owns the complete page route table.

**Use `cosmicStar` as the cross-language identity.** Rejected. Cosmic names are internal platform identifiers and should not become the author-facing or navigation-facing page identity.

## Risks

**Migration churn.** Existing `system.md`, page entries, navigation files, route helpers, and validators all touch route identity. Mitigation: keep compatibility fields and staged validation.

**Duplicate identity concepts.** `pageId`, `cosmicStar`, route slug, and file path can be confused. Mitigation: document exact ownership: `pageId` identifies a logical page, `cosmicStar` identifies the cosmic overlay page contract, `routes[lang]` identifies the public URL, file path stores content.

**Broken language switcher links.** If a page lacks a target-language route, the switcher must not guess. Mitigation: helper returns a safe fallback and validator warns about missing sibling routes.

**Agent drift.** Agents may keep editing `navigation.md routeSlug` instead of the route registry. Mitigation: validation fails on drift and AGENTS guidance must direct route edits to `system.md pages[].routes`.
