# RFC-0245: Add an Agent Control Plane and maintenance debt ledger

## Context

The platform is explicitly designed to be operated and extended by AI agents. The repository already has strong source-of-truth layers: `AGENTS.md`, GRACE XML, RFCs, kernel command registries, package manifests, generated markers, and validation pipelines.

An ecosystem audit on 2026-06-30 found that agents can still miss important state because the facts are scattered:

- `packages-check.run` and app checks expose many warnings only inside nested command output.
- Warning-mode debt such as missing material credits, unresolved asset tokens, text normalization signals, and skipped optional tools is not summarized in a single ledger.
- Command docs are now generated by RFC-0222, but apps, packages, pipelines, generated ownership, RFC state, and current warning posture still lack one machine-readable control-plane manifest.
- `generator.ownership.lint` validates duplicate owners, but agents still need a broader ownership/coverage view before changing generated app files.

## Problem

Agents currently reconstruct the ecosystem by reading many files and running multiple commands. That manual reconstruction creates several failure modes:

- An agent may inspect stale hand-written docs instead of live registries.
- An agent may see a passing composite check and miss warning-mode debt that should shape the next change.
- An agent may add a generator, command, or app capability without updating the machine-readable map other agents depend on.
- A new agent has no single "start here" artifact that answers what apps exist, which packages own which responsibilities, which commands mutate state, and which warnings are known but unresolved.

## Decision

The Site OS gains an Agent Control Plane projection and a maintenance debt ledger:

- `ecosystem.manifest.generate` writes `docs/ecosystem.generated.json` from live workspace state.
- `ecosystem.manifest.validate` compares the committed manifest to generated output and fails on drift.
- `maintenance.debt.report` runs or reads selected warning-mode checks and emits one warning ledger for agent planning.

The generated manifest is a projection, not a source of truth. The normative sources remain RFCs, AGENTS.md, GRACE XML, package manifests, command tables, and app `system.md` files.

## Architectural fit

This extends RFC-0222 from a generated command document to a broader machine-readable operator map. It complements RFC-0203 diagnostics by giving warning-mode results a common ledger, and it strengthens RFC-0087 generated ownership by making ownership visible in the same manifest agents use to plan.

The commands are workspace-scoped and belong in `@gogol/site-kernel-checks`. Generation should reuse live registries and parsers rather than duplicating facts in static hand-authored files.

## Design

### CLI surface

```sh
pnpm exec site-kernel run ecosystem.manifest.generate
pnpm exec site-kernel run ecosystem.manifest.validate --json
pnpm exec site-kernel run maintenance.debt.report --json
```

All commands are workspace-scoped. `ecosystem.manifest.generate` mutates `docs/ecosystem.generated.json`; the validators/reports are read-only.

### TypeScript contracts

```ts
interface EcosystemManifest {
  generatedAt: string;
  workspace: { name: string; version: string; packageManager: string };
  apps: Array<{ name: string; directory: string; packageName?: string }>;
  packages: Array<{ name: string; directory: string; dependencies: string[] }>;
  commands: Array<{
    name: string;
    scope: "app" | "workspace";
    mutatesState: boolean;
    supportsAllApps: boolean;
    providers: string[];
  }>;
  pipelines: Array<{ name: string; commands: string[] }>;
  generatedOwnership: Array<{ path: string; command: string }>;
  rfcs: { accepted: number; implemented: number; draft: number; reviewing: number };
}

interface MaintenanceDebtReport {
  command: "maintenance.debt.report";
  status: "pass" | "warn" | "fail";
  items: Array<{
    sourceCommand: string;
    severity: "warning" | "info" | "skipped";
    app?: string;
    message: string;
    file?: string;
    fixHint?: string;
  }>;
}
```

### File system responsibilities

| Path | Role |
| --- | --- |
| `docs/ecosystem.generated.json` | Generated Agent Control Plane projection |
| `docs/COMMANDS.md` | Existing RFC-0222 generated command document; read for consistency only |
| `docs/rfcs/*.md` | Read for RFC status counts |
| `apps/*/src/content/system.md` | Read for app identity and capabilities |
| `packages/*/package.json`, `packages/os/*/package.json` | Read for package graph |
| `packages/os/site-kernel-checks/src/pipelines/*.ts` | Read or imported for pipeline membership |
| `GENERATOR_OWNERSHIP_MAP` | Read for generated ownership projection |

### Output format

```json
{
  "command": "maintenance.debt.report",
  "status": "warn",
  "items": [
    {
      "sourceCommand": "material.credits.validate",
      "severity": "warning",
      "app": "webgogol-com",
      "message": "Missing prose credit for authored material reference"
    }
  ]
}
```

### Failure modes

`ecosystem.manifest.validate` exits non-zero on drift. `maintenance.debt.report` exits zero when it only reports advisory debt; a future `--strict` flag may make selected debt classes fail-hard after rollout.

All commands must keep `--json` pure: stdout is exactly one JSON envelope.

## Rollout

1. Implement `ecosystem.manifest.generate` and commit the generated manifest.
2. Add `ecosystem.manifest.validate` to `packages-check.run`.
3. Implement `maintenance.debt.report` as read-only advisory output.
4. Add a short `AGENTS.md` pointer telling agents to read `docs/ecosystem.generated.json` after root instructions.

## Alternatives considered

Expanding `docs/COMMANDS.md` into a giant prose guide was rejected because agents need a structured manifest, not more hand-authored prose. Making every warning fail-hard was rejected because several checks are intentionally warn-first during CKL/material-credit rollout.

## Baseline projection (amendment RFC-0327)

The manifest gains a `baseline` object that serves as the system's configuration baseline — the authoritative answer to "what is the current approved architectural state?" at the moment of generation.

### Structure

```ts
interface EcosystemManifest {
  // ... existing fields ...
  baseline: {
    implementedRfcs: Array<{
      id: string;          // e.g. "RFC-0023"
      implementedAt: string; // ISO date from frontmatter
      kind: string;        // architecture | contract | command | policy | deprecation
      scope: string;       // workspace | app
      dnaRefs: string[];   // DNA-N ids referenced in the RFC body
    }>;
    nonImplementedRfcs: Record<string, string[]>; // by status: accepted, draft, reviewing, superseded, rejected
    dnaRegistry: Array<{
      id: string;          // e.g. "DNA-23"
      title: string;
      provenance: "foundational" | "rfc";
      establishingRfc: string | null; // RFC-XXXX or null for foundational
      status: "active" | "reclassified";
    }>;
  };
}
```

### Design decisions

- **No new command.** `ecosystem.manifest.generate` already produces the manifest; the baseline is simply a new projection within it. `ecosystem.manifest.validate` already fails on drift — this covers baseline drift detection.
- **DNA refs are extracted from RFC bodies** via `\bDNA-(\d+)\b` regex, not from frontmatter. This captures both formal `Established by` citations and informal references.
- **`docs/architecture-dna.md` is added to source hashes** so changes to the DNA registry trigger manifest drift.
- **The baseline does not replace `dna.registry.validate` (RFC-0158)** — that command remains the live invariant consistency guard. The baseline is a snapshot projection.
- **No separate `baseline.generated.json` file.** The baseline lives inside `ecosystem.generated.json` to avoid a second generated artifact with its own drift cycle.

### Agent usage

An agent working on a new RFC can read `ecosystem.generated.json.baseline` to:

1. See which DNA invariants are active and which RFCs establish them.
2. Check whether a conflicting invariant exists that requires an explicit `supersedes` declaration.
3. Reference the baseline in commit messages or PR descriptions.

## Risks

The main risk is duplicating source-of-truth facts in a generated projection. The validator must therefore fail on drift, and the manifest must carry a clear generated marker. The debt report also risks becoming noisy; it should include source command, severity, app, and fix hints so agents can prioritize.

The baseline projection adds a second dimension of duplication risk — DNA registry data from `docs/architecture-dna.md` and RFC metadata from `docs/rfcs/*.md` are now also projected into the manifest. This is mitigated by: (1) adding `docs/architecture-dna.md` to source hashes, (2) the existing `ecosystem.manifest.validate` drift check, and (3) keeping `dna.registry.validate` as the canonical invariant guard.

- Agents MUST NOT weaken or remove enforcement rules established by this RFC without a new RFC that supersedes it.
