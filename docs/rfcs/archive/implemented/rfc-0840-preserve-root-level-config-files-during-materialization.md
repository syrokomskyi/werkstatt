# RFC-0840: Preserve root-level operator config files during materialization

## Context

During deployment of mission `warpgogol-com-m000055`, `mission.validate` failed because `.lighthouse-budget-ignore` was missing from the workpiece. The file existed in the cache clone but was lost during `mission.materialize` — the `STERNSYSTEM_DATA_PATHS` list only copies `src/content`, `public`, `provenance`, `behavior.snapshot.generated.yaml`, `system-config.yaml`, `system-state.yaml`. Root-level operator config files are not in this list and are not restored after `atomicMoveDir` replaces the workpiece.

RFC-0822 solved this problem for `.env*` files by persisting them to the cache clone (untracked) during `mission.close` and restoring them during `mission.materialize`. This RFC extends the same pattern to root-level operator config files that are not git-tracked in the workpiece but are required for validation and deployment.

## Problem

The following root-level files are required during `mission.validate` or `mission.close` but are lost during re-materialization:

1. **`.lighthouse-budget-ignore`** — Required by `lighthouse.budget.check` (LH-12). Without it, unreferenced JS bundles cause validation failure. The file is workpiece-specific (different sites have different ignored bundles).

2. **`image-delivery.config.yaml`** — Required by `image.delivery.validate` (RFC-0830) as an escape hatch for pre-existing image issues. The validator reads it from `src/` (not root), but operators may initially place it in the workpiece root. The file is site-specific.

3. **`live-video-manifest.generated.yaml`** — Required by video manifest validators. Although "generated" in name, it is authored/curated by operators for some sites and stored at the workpiece root.

4. **`dns-records.yaml`** — Required by `dns.record.upsert` during `mission.validate`. Contains DNS record declarations. Site-specific.

Each of these files is:

- Not in `STERNSYSTEM_DATA_PATHS` (so not copied during data-path copy)
- Not a build output (so not regenerated by `build.prepare`)
- Not git-tracked in the workpiece (or git-tracked but lost when the workpiece is replaced by `atomicMoveDir`)
- Required for validation or deployment

When a mission is re-materialized (e.g., after `mission.close` + new `mission.open`), these files are absent and `mission.validate` fails with confusing errors that require manual restoration from the cache clone.

## Decision

Extend the RFC-0822 env-persist pattern to root-level operator config files:

1. **`mission.close`** persists operator config files from workpiece to cache clone (untracked, not committed to git).
2. **`mission.materialize`** restores operator config files from cache clone to workpiece after `atomicMoveDir`, alongside the existing `.env*` restoration.
3. A new constant `OPERATOR_CONFIG_FILES` declares the canonical list of preserved files.
4. A new check command `materialize.config.validate` verifies that the `OPERATOR_CONFIG_FILES` list is in sync with the actual files found in active workpieces and cache clones.

## Architectural fit

- **Architecture DNA:** Establishes DNA-71 (Operator config file persistence). Extends DNA-62 (Foundation File Integrity) to cover non-env operator config files. Complements RFC-0822 (env persistence) by applying the same pattern to a broader set of files.
- **Site OS operator model:** No new Werkstatt command for operators. The persistence is automatic — `mission.close` and `mission.materialize` handle it transparently.
- **Data-only contract (DNA-44):** Operator config files are NOT staged in git commits during `mission.materialize`. They are untracked artifacts in the workpiece (same as `.env*` files). The data-only git staging contract is preserved.
- **Scaling Playbook:** Applies uniformly across all sites. Each site may have different operator config files present — the restoration is best-effort (missing files in the cache clone are silently skipped).

## Design

### `OPERATOR_CONFIG_FILES` constant

```ts
const OPERATOR_CONFIG_FILES = [
  ".lighthouse-budget-ignore",
  "image-delivery.config.yaml",
  "live-video-manifest.generated.yaml",
  "dns-records.yaml",
];
```

This list is intentionally explicit (not glob-based) to avoid accidentally persisting generated files or secrets. Adding a new file to this list requires a superseding RFC.

### `mission.close` changes

After the existing `persistEnvFilesToCacheClone` call, add a new `persistOperatorConfigFiles` call:

```ts
const operatorConfigResult = await persistOperatorConfigFiles(workpieceDir, systemDir);
if (operatorConfigResult.copied.length > 0) {
  logger.info(
    `  Persisted ${operatorConfigResult.copied.length} operator config file(s) to cache clone: ${operatorConfigResult.copied.join(", ")}`,
  );
}
```

### `mission.materialize` changes

After the existing `restoreEnvFilesFromCacheClone` call, add a new `restoreOperatorConfigFiles` call:

```ts
const operatorConfigResult = await restoreOperatorConfigFiles(cacheCloneDir, workpieceDir);
if (operatorConfigResult.copied.length > 0) {
  logger.info(
    `  Restored ${operatorConfigResult.copied.length} operator config file(s) from cache clone: ${operatorConfigResult.copied.join(", ")}`,
  );
}
```

### `persistOperatorConfigFiles` / `restoreOperatorConfigFiles`

These functions follow the same pattern as `persistEnvFilesToCacheClone` / `restoreEnvFilesFromCacheClone` in `env-persist.ts`:

- `persistOperatorConfigFiles(workpieceDir, cacheCloneDir)`: copies each file in `OPERATOR_CONFIG_FILES` from workpiece to cache clone if it exists. Non-fatal on failure.
- `restoreOperatorConfigFiles(cacheCloneDir, workpieceDir)`: copies each file in `OPERATOR_CONFIG_FILES` from cache clone to workpiece if it exists. Non-fatal on failure. Does NOT modify file contents (unlike env restoration which rewrites `PUBLIC_IMAGE_PROVIDER`).

### `materialize.config.validate` check command

A new check command that:

1. Reads the `OPERATOR_CONFIG_FILES` constant.
2. Scans all active mission workpieces for root-level files NOT in `OPERATOR_CONFIG_FILES` and NOT in `STERNSYSTEM_DATA_PATHS` and NOT generated by `build.prepare`.
3. Emits `MAT-CONFIG-01` (warning) for unrecognized root-level files that might need preservation.
4. Emits `MAT-CONFIG-02` (error) if `OPERATOR_CONFIG_FILES` references a file that does not exist in any cache clone or active workpiece (dead entry).

### File system responsibilities

| Path | Role |
| --- | --- |
| `packages/werkstatt/src/mission/env-persist.ts` | Extended with `persistOperatorConfigFiles` / `restoreOperatorConfigFiles` |
| `packages/werkstatt/src/mission/mission-materialize.ts` | Calls `restoreOperatorConfigFiles` after `restoreEnvFilesFromCacheClone` |
| `packages/werkstatt/src/mission/mission-close.ts` | Calls `persistOperatorConfigFiles` after `persistEnvFilesToCacheClone` |
| `packages/werkstatt/src/mission/operator-config-files.ts` | New file with `OPERATOR_CONFIG_FILES` constant and persist/restore functions |

### Failure modes

- **File missing in cache clone:** Silently skipped — the workpiece proceeds without the file. This is the same behavior as `.env*` restoration.
- **File missing in workpiece during close:** Silently skipped — nothing to persist.
- **Copy failure:** Non-fatal warning logged. Mission close/materialize proceeds.
- **`materialize.config.validate` finds unrecognized file:** Warning only — the operator may need to add it to `OPERATOR_CONFIG_FILES` in a future RFC.

## Rollout

1. **Add `OPERATOR_CONFIG_FILES` constant and persist/restore functions** in `operator-config-files.ts`.
2. **Wire into `mission.close`** after `persistEnvFilesToCacheClone`.
3. **Wire into `mission.materialize`** after `restoreEnvFilesFromCacheClone`.
4. **Add `materialize.config.validate`** check command.
5. **Existing sites:** Next `mission.close` + `mission.materialize` cycle automatically persists and restores the files. No manual migration needed.

## Alternatives considered

- **Add root-level config files to `STERNSYSTEM_DATA_PATHS`:** This would copy them during the data-path copy, but it would also stage them in git commits (violating the data-only contract for non-content files). The RFC-0822 untracked persistence pattern is cleaner.
- **Git-track operator config files in the workpiece:** Some of these files (`.lighthouse-budget-ignore`) could be git-tracked. However, they are site-specific configuration that changes independently of content, and git-tracking them in the workpiece would cause merge conflicts during `mission.reconcile`. The untracked cache-clone persistence avoids this.
- **Glob-based preservation (`*.-ignore`, `*.config.yaml`):** Too broad — risks persisting generated files or secrets. Explicit list is safer.

## Risks

- **Stale config files:** If an operator config file is no longer needed (e.g., `image-delivery.config.yaml` after images are fixed), it persists in the cache clone indefinitely. This is harmless — the file is untracked and does not affect validation if the validator doesn't need it.
- **New file types:** When a new validator requires a new root-level config file, the operator must update `OPERATOR_CONFIG_FILES` via a superseding RFC. This is intentional — it forces conscious consideration of what files are persisted.
