# RFC-0489: Redesign the open-source page as a deployment-specific SBOM registry

## Problem

The `/open-source/` page is generated by `open-source.generate` (`runGenerateOpenSourcePage` in `@gogol/site-kernel-codegen/src/service.ts`). The current generator produces a ~49 800-line German-only markdown file with full license texts embedded in the DOM, derives its inventory from the root workspace `pnpm licenses list --prod` output (which includes build tools, type packages, and language servers that are not in the deployed artifact), and hardcodes `de/` paths in `getAstroSitePaths` — so the UK page is broken (references a `prose/uk/open-source.md` that the generator never writes). There is no SBOM, no license normalization, no deduplication, no deployment metadata, and no validation of the generated output.

## Context

The `/open-source/` page is generated by `open-source.generate` (`runGenerateOpenSourcePage` in `@gogol/site-kernel-codegen/src/service.ts`). The current generator:

1. Runs `pnpm licenses list --prod --json` at the app root.
2. Uses `@quantco/pnpm-licenses` to produce a disclaimer text and a flat dependency list.
3. Writes German-only output to `pages/de/open-source.md` and `prose/de/open-source.md` (hardcoded `lang: de` in both templates, hardcoded `de` paths in `getAstroSitePaths`).
4. Embeds the full `generate-disclaimer` text (all license texts for all packages) inside a `<details>` block in the prose file.
5. Repeats per-package license texts in individual `<details>` blocks.
6. Outputs a dependency table with columns: Paket, Version, Lizenz, Links.

An external expert review (file 12) has identified fundamental problems with this approach.

### Current problems

1. **Page is unusable for humans.** The generated `prose/de/open-source.md` is ~49 800 lines (2 MB). The HTML page exceeds 39 000 lines. The full `generate-disclaimer` text is embedded in the DOM, then the dependency table repeats the packages, then per-package `<details>` blocks repeat the full license texts again. A visitor cannot find anything without browser `Strg+F`.

2. **UK page is broken.** The UK page manifest at `pages/uk/open-source.md` references `contentRef: "prose/open-source"`, but the generator only writes to `prose/de/open-source.md`. No `prose/uk/open-source.md` exists. UK visitors see an empty or errored page. The generator has no i18n awareness — `getAstroSitePaths` hardcodes `openSourcePagePath` and `openSourceProsePath` to `de/`.

3. **Inventory is not deployment-specific.** The generator runs `pnpm licenses list --prod` at the app root. This includes build tools (`@astrojs/check`, `@astrojs/compiler`), language servers, `@types/*` packages, Windows-specific bindings, test tools, and dependencies of other packages/systems in the monorepo workspace. One package (`@astrojs/compiler`) even appears twice in the table. The registry reflects the workspace dependency graph, not the actual published deployment artifact.

4. **No SBOM.** No machine-readable Software Bill of Materials is generated. The only output is a German markdown file with embedded license texts. There is no CycloneDX or SPDX artifact for automated consumers.

5. **No license normalization.** License strings are taken raw from `package.json` via `@quantco/pnpm-licenses`. Unverified strings like `"MIT OR Apache-2.0"`, `"BSD-3-Clause"`, or custom strings are published as-is without SPDX validation. Unknown or conflicting licenses do not block the build.

6. **No deployment metadata.** The page does not show which deployment it belongs to. There is no deployment ID, commit SHA, build timestamp, or target platform. After a site update, the page may still show the previous build's registry.

7. **No downloadable artifacts.** Full license texts and NOTICE files are only available inside the page HTML. There are no downloadable `THIRD_PARTY_LICENSES.txt`, `THIRD_PARTY_NOTICES.txt`, or `sbom.cdx.json` files.

8. **No validation.** There is no `open-source.validate` command. The generator runs in `SITES_BUILD_PREPARE_PIPELINE` but nothing validates the output for consistency, deduplication, or license status.

## Decision

The open-source page is redesigned from a monolithic license-text dump to a **deployment-specific SBOM registry** with:

- **Multi-language generation**: the generator produces page + prose files for every supported language in `system.md i18n.supported`, not only `de`.
- **Compact page structure**: summary counts, license distribution, deployment metadata, and a component table — no full license texts in the DOM.
- **Downloadable artifacts**: `THIRD_PARTY_LICENSES.txt`, `THIRD_PARTY_NOTICES.txt`, `sbom.cdx.json` generated as separate files in `public/open-source/` and linked from the page.
- **Deployment-specific inventory**: the dependency list is derived from the actual build output, not the root workspace `--prod` graph.
- **SPDX license normalization**: license strings are validated against SPDX identifiers; unknown or conflicting licenses block the build.
- **Deduplication**: the same `package@version` appears once in the table.
- **Deployment metadata**: the page shows deployment ID, commit SHA, build timestamp, and target platform.
- **Validation**: `open-source.validate` checks SBOM consistency, deduplication, license status, and scope separation.

This RFC amends the generator's behavior and output contract under the existing generated-file governance protocol (RFC-0081, which superseded RFC-0078). The generator remains in `site-kernel-codegen`, runs in `SITES_BUILD_PREPARE_PIPELINE`, and writes generated files with the `GENERATED` marker.

## Architectural fit

- **RFC-0081 (generated file governance, superseded RFC-0078):** the generator follows the established pattern of `open-source.generate` as a build-prepare step. The command name is preserved. All output files carry the `GENERATED` marker with `ownerCommand: "open-source.generate"` (fixing a pre-existing bug where the page manifest template incorrectly declared `ownerCommand: "material.credits.generate"`). The generator is the single owner of `src/content/pages/{lang}/open-source.md` and `src/content/prose/{lang}/open-source.md` (registered in `GENERATOR_OWNERSHIP_MAP`). New downloadable artifacts in `public/open-source/` are also generator-owned. The existing ownership map entry for `src/content/pages/{lang}/open-source.md` references `RFC-0049` in its comment — this is incorrect (RFC-0049 is about hreflang sitemaps) and will be fixed to reference RFC-0081. The missing ownership entry for `src/content/prose/{lang}/open-source.md` (a pre-existing RFC-0081 violation) will be added.
- **RFC-0087 (content-driven generation):** the generator reads `system.md` for i18n config (supported languages, default language) and page config. Output is a pure function of source (RFC-0154).
- **RFC-0154 (build idempotency):** the generator must remain a pure function of source. Deployment metadata (build timestamp, deployment ID) must be derived from the build context, not from a wall-clock call that changes on every run. The fingerprint cache mechanism is preserved.
- **RFC-0220 (material credits):** the open-source page documents software components and their licenses; the credits page documents media materials and their provenance. These are separate concerns and separate pages — this RFC does not merge them.
- **RFC-0480 (Layer C protection):** the page URLs (`/open-source/` DE, `/vidkrytyy-kod/` UK) are preserved. No URL schema, sitemap, or JSON-LD type changes. `breaksC: false`.
- **RFC-0488 (material credits redesign):** parallel design philosophy — compact registry with stable metadata, not a flat text dump. The two RFCs are independent but follow the same pattern.
- **Platform versioning (RFC-0478):** this RFC changes `@gogol/site-kernel-astro` (path helper interface) and `@gogol/site-kernel-codegen` (generator logic). Declares `versionBump: patch` — the `AstroSitePaths` interface change is internal (the generator is the only consumer of the removed fields), and no authored content migration is needed because generated files are regenerated from source. No migrator required (RFC-0479).

## Design

### Path helper changes (`packages/os/site-kernel-astro/src/index.ts`)

The hardcoded `openSourcePagePath` and `openSourceProsePath` (both pointing to `de/`) are removed. The generator uses the existing `contentPagesDirectory` and `contentDirectory` fields to resolve per-language paths:

```ts
const pagePath = path.join(paths.contentPagesDirectory, lang, "open-source.md");
const prosePath = path.join(paths.contentDirectory, "prose", lang, "open-source.md");
const artifactsDir = path.join(paths.publicDirectory, "open-source");
```

No new fields are added to `AstroSitePaths` — the existing `contentPagesDirectory`, `contentDirectory`, and `publicDirectory` fields suffice. The generator is the only consumer of the removed `openSourcePagePath`/`openSourceProsePath` fields (confirmed: `packages/os/site-kernel-codegen/src/service.ts` and `packages/os/site-kernel-astro/README.md`), so no external code breaks. The README must be updated to remove the documented `openSourcePagePath` field.

### Generator changes (`packages/os/site-kernel-codegen/src/service.ts`)

#### Multi-language generation

`runGenerateOpenSourcePage` is updated to:

1. Guard with `hasSystemPage(system, "openSource")` — skip generation if the `openSource` page is not declared in `system.md` (same pattern as `runGenerateMaterialCreditsPage` which guards with `hasSystemPage(system, "credits")`). This prevents sites without an open-source page from being forced to generate one.
2. Read i18n config from `system.md` via `loadI18nConfigSync` (same pattern as `runGenerateMaterialCreditsPage`).
3. For each supported language, generate a page manifest (two blocks: markdown + section), a text-only prose file, and a JSON data file with localized headings, labels, and UI text.
4. Use localized templates (or token-based template interpolation) for each language.

The page manifest template is updated to accept `LANG`, `TITLE`, `DESCRIPTION`, and `HEADING` tokens instead of hardcoding `lang: de` and German strings.

The prose template is restructured (see below).

#### Text-only prose structure

The prose file is restructured to contain only text parts — no component table, summary card, deployment metadata, or download buttons (those are rendered by the UI section from the JSON data file). New structure:

```markdown
---
kind: prose
lang: {{LANG}}
---
{{GENERATED_HEADER}}

# {{HEADING}}

<p class="lead">{{LEAD_TEXT}}</p>

## {{SCOPE_HEADING}}

**{{SCOPE_INCLUDED_LABEL}}:** {{SCOPE_INCLUDED_TEXT}}

**{{SCOPE_EXCLUDED_LABEL}}:** {{SCOPE_EXCLUDED_TEXT}}

## {{PROCESS_NOTE_TEXT}}
```

The component table, summary counts, license distribution, deployment metadata, and download buttons are rendered by the `open-source-registry` UI section from the JSON data file (`src/content/data/{lang}/open-source-registry.json`).

Full license texts and per-package `<details>` blocks are **removed** from the prose file. They are available only as downloadable artifacts.

#### Downloadable artifacts

The generator writes the following files to `public/open-source/`:

| File                       | Content                                                 |
| -------------------------- | ------------------------------------------------------- |
| `THIRD_PARTY_NOTICES.txt`  | Package-specific copyright notices and attribution text |
| `THIRD_PARTY_LICENSES.txt` | Full license texts, deduplicated by SPDX license ID     |
| `sbom.cdx.json`            | CycloneDX SBOM (JSON format)                            |

The artifacts are linked from the page via download buttons rendered by the UI section.

#### Deployment-specific inventory

The generator is updated to scope the dependency analysis to the actual deployment:

1. **Current approach**: `pnpm licenses list --prod` at the app root → includes workspace-wide dependencies.
2. **New approach**: the site workspace (`missions/*/workpiece`) is a pnpm workspace member. `pnpm licenses list --prod` already excludes `devDependencies` from the license list. The remaining scoping is done by post-filtering the `pnpm licenses list --prod` output against a classification heuristic that separates runtime-shipped packages from build-only packages that are in `dependencies` but not shipped to the browser or worker:
   - Build tools (`@astrojs/check`, `@astrojs/compiler`, `typescript`, etc.)
   - Type packages (`@types/*`)
   - Language servers
   - Test tools (`vitest`, `playwright`, etc.)
   - Platform-specific binaries for other OSes
   - Dependencies of other packages/systems in the monorepo

The scoping is implemented by filtering the `pnpm licenses list` output against a classification:

- `runtime`: packages required to run the deployed site (server/worker).
- `browser-bundle`: packages shipped to the browser (JS/CSS/WASM).
- `build-only`: packages used during build but not shipped (excluded from public page).
- `development-only`: packages used only in development (excluded from public page).
- `test-only`: packages used only in tests (excluded from public page).

The public page shows `runtime`, `browser-bundle`, and `worker-runtime` scopes only.

The classification heuristic:

- Packages in `dependencies` (not `devDependencies`) in the site's `package.json` are `runtime`.
- Packages in `devDependencies` are classified as `build-only` or `development-only` based on known categories.
- The filter uses a maintainable allowlist/denylist of known build-only and dev-only package name patterns.

**Known limitation**: the classification heuristic cannot detect a runtime package incorrectly classified as `build-only` (false negative). The validator catches `build-only-in-runtime` leaks (false positive) but not the opposite. The allowlist/denylist must be maintained manually as new build tools are adopted.

#### SPDX license normalization

License strings from `package.json` are normalized to SPDX identifiers using the `spdx-license-list` package (already available as a transitive dependency of `@quantco/pnpm-licenses` at version 6.11.0 in the lockfile). The normalization steps:

1. Parse the license string as an SPDX expression (`MIT`, `Apache-2.0`, `MIT OR Apache-2.0`, etc.) using `spdx-license-list` for identifier validation.
2. If the string is a valid SPDX identifier or expression, mark as `verified`.
3. If the string is a known alias (e.g. `Apache 2.0` → `Apache-2.0`), normalize and mark as `normalized`.
4. If the string cannot be parsed, mark as `unknown`.
5. If a package has multiple conflicting license strings, mark as `conflict`.

The validator blocks on `unknown` and `conflict` statuses.

**False-positive rate**: common non-standard license strings (e.g. `SEE LICENSE IN LICENSE`, `UNLICENSED`, custom URLs) will trigger `unknown`. The generator should include a small alias map for known non-SPDX strings that map to valid SPDX identifiers. Packages with genuinely non-SPDX licenses require manual resolution (add to the alias map or accept the block).

#### Deduplication

The same `package@version` appears once in the table. If the same package appears in multiple scopes (e.g. both `browser-bundle` and `runtime`), it is listed once with a combined scope field. Different versions of the same package are listed as separate rows.

#### Deployment metadata

The generator receives deployment context from the build environment:

- `deploymentId`: from `context.deploymentId` or `process.env.DEPLOYMENT_ID`.
- `commitSha`: from `process.env.COMMIT_SHA` or `git rev-parse HEAD`.
- `buildTimestamp`: from `process.env.BUILD_TIMESTAMP` or the fingerprint cache timestamp.
- `targetPlatform`: from `context.targetPlatform` or inferred from the build config.

To preserve RFC-0154 idempotency, the deployment metadata is only included when available from the build context. If the metadata is not available (e.g. local dev build), the fields show a placeholder like `—` and the page notes that the registry is from a local build.

### CycloneDX SBOM generation

The generator produces a CycloneDX JSON SBOM using `@cyclonedx/cyclonedx-library` (added as a dependency to `@gogol/site-kernel-codegen`). The library guarantees CycloneDX 1.5 schema compliance. The SBOM has the following fields per component:

```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "metadata": {
    "timestamp": "{{BUILD_TIMESTAMP}}",
    "tools": [{ "vendor": "Warpgogol", "name": "open-source.generate", "version": "1.0.0" }],
    "component": {
      "type": "application",
      "name": "warpgogol-com",
      "version": "{{DEPLOYMENT_ID}}"
    }
  },
  "components": [
    {
      "type": "library",
      "name": "astro",
      "version": "5.0.0",
      "purl": "pkg:npm/astro@5.0.0",
      "licenses": [{ "expression": "MIT" }],
      "scope": "runtime",
      "properties": [
        { "name": "wgogol:relationship", "value": "direct" },
        { "name": "wgogol:distributionScope", "value": "browser-bundle" }
      ]
    }
  ]
}
```

The SBOM is written to `public/open-source/sbom.cdx.json`.

### UI section (`packages/ui/src/sections/open-source-registry/`)

A new UI section is created to render the structured registry data with semantic HTML, accessibility attributes, and type-safe props. The section receives a Zod-validated `OpenSourceRegistryData` object (loaded from a generated JSON data file) and renders:

1. A summary card with component counts and license distribution (`<dl>`).
2. A deployment metadata block (`<dl>`).
3. A download buttons row (`<a>` with `download` attribute and `aria-label`).
4. A component table with columns: Package, Version, License, Scope, Relationship, Source (`<table>` with `<caption>`, `<th scope="col">`).

The section is server-rendered (no client-side JavaScript required).

#### Data contract and page manifest

The generator writes a JSON data file to `src/content/data/{lang}/open-source-registry.json` alongside the prose markdown. The JSON file contains the structured data (`OpenSourceRegistryData` schema): summary counts, license distribution, deployment metadata, download links, and the component array.

The prose markdown is simplified to contain only text parts: heading, lead text, scope explanation, and process note. The component table, summary card, deployment metadata, and download buttons are rendered by the UI section — not in the prose markdown.

The page manifest has two blocks:

1. `markdown` block with `contentRef: "prose/open-source"` for text content.
2. A block referencing the UI section with the JSON data file for structured rendering.

The block type for the second block must support passing structured JSON data to a UI section. The implementation should first check if an existing block type supports this. If no existing block type suffices, a new block type is needed — this would require a follow-up RFC for the new block type registration in `@gogol/ontology`.

### Validation (`open-source.validate`)

A new `open-source.validate` command is added to `SITES_BUILD_CHECK_PIPELINE`. It checks:

- **SBOM consistency**: every runtime component in the deployment is present in the SBOM.
- **SBOM schema validity**: the generated `sbom.cdx.json` is valid against the CycloneDX 1.5 JSON schema.
- **Scope separation**: no `build-only` or `development-only` packages in the runtime scope.
- **Component completeness**: every component has a version and purl.
- **License status**: every component has a license status of `verified` or `normalized`. `unknown` and `conflict` block the build.
- **Deduplication**: no duplicate `package@version` entries in the SBOM.
- **Public counts match SBOM**: the component count shown on the page matches the SBOM component count.
- **Download artifacts exist**: `THIRD_PARTY_NOTICES.txt`, `THIRD_PARTY_LICENSES.txt`, and `sbom.cdx.json` exist in `public/open-source/`.

**Performance estimate**: the validator parses one JSON file (`sbom.cdx.json`), scans the generated prose markdown for the component count, and checks file existence for three artifacts. Expected duration: <5 seconds. Pipeline step should declare `expectedDurationMs: 5_000, timeoutMs: 30_000`.

### Failure modes

New validation failure modes (`open-source.validate`):

- `unknown-license` (fail): a component has a license string that cannot be parsed as an SPDX identifier or expression.
- `conflicting-license` (fail): a component has multiple conflicting license strings.
- `duplicate-package` (fail): the same `package@version` appears more than once in the SBOM.
- `build-only-in-runtime` (fail): a package classified as `build-only` or `development-only` appears in the runtime scope.
- `missing-purl` (fail): a component in the SBOM has no purl.
- `missing-version` (fail): a component in the SBOM has no version.
- `missing-artifact` (fail): a downloadable artifact (`THIRD_PARTY_NOTICES.txt`, `THIRD_PARTY_LICENSES.txt`, `sbom.cdx.json`) is missing from `public/open-source/`.
- `count-mismatch` (fail): the component count on the page does not match the SBOM component count.
- `invalid-sbom-schema` (fail): the generated `sbom.cdx.json` does not validate against the CycloneDX 1.5 JSON schema.

## Alternatives considered

- **Hand-edit the generated page.** Rejected — the page is generator-owned (RFC-0081 marker). Hand-editing would be overwritten on the next `open-source.generate` run.
- **Keep the current generator and just add UK translation.** Rejected — the fundamental problems (39 000-line DOM, workspace-wide inventory, no SBOM, no license normalization) remain. A translation-only fix would double the problem by creating a second 39 000-line page.
- **Remove the page entirely and link to an external SBOM.** Rejected — the page is a legal compliance requirement (Drittanbieter-Hinweise) and must be accessible on the site. External SBOMs are not a substitute for a human-readable page.
- **Generate SPDX SBOM instead of CycloneDX.** Deferred — CycloneDX is the primary format because it has better tooling support in the JS ecosystem. SPDX can be added later if a consumer requires it.
- **Add client-side search and filtering.** Deferred — the compact table (a few hundred rows after deduplication and scope filtering) is manageable without client-side JavaScript. Filters are a possible future enhancement.
- **Implement a full license policy engine.** Deferred — the validator checks for unknown/conflicting licenses and blocks, but a full allowed/blocked list with waiver workflows is a separate RFC.
- **Implement historical SBOM archiving.** Deferred — the page shows the current deployment only. History is a future enhancement.

## Risks

- **Deployment-specific inventory accuracy.** The scoping heuristic (classifying packages as runtime vs build-only) may misclassify packages. The allowlist/denylist must be maintained. Misclassification could hide a real dependency or show a build-only package. The validator catches build-only-in-runtime leaks but cannot catch the opposite (a runtime package incorrectly classified as build-only and hidden).
- **SPDX normalization gaps.** Some packages have non-standard license strings that are valid but not SPDX-compliant. The normalization step must handle common aliases. Unknown licenses block the build, which may require manual intervention to resolve.
- **Deployment metadata availability.** In local dev builds, deployment metadata may not be available. The page shows placeholders in this case. The fingerprint cache mechanism must handle metadata changes without breaking idempotency (RFC-0154).
- **SBOM format compliance.** The generated CycloneDX JSON must be valid against the CycloneDX 1.5 schema. The validator includes an `invalid-sbom-schema` failure mode that blocks the build on schema violations.
- **Fingerprint cache inputs.** The current fingerprint is based on `package.json`, app `pnpm-lock.yaml`, and root `pnpm-lock.yaml`. The new generator adds i18n config and localized labels as inputs. The fingerprint must include `src/content/system.md` (for i18n config) and `src/content/site/{lang}/labels.md` (for localized text) to ensure regeneration when labels change. Deployment metadata (commit SHA, build timestamp) is not included in the fingerprint — it comes from the build context and does not affect idempotency.
- **Multi-language label completeness.** Every UI text string must have a localized label in both DE and UK. Missing labels fall back to the raw key, which is a visible regression. The label schema should be `.strict()` to catch missing keys.

## Implementation notes for agents

- Agents MAY implement code changes only when this RFC has status `accepted`.
- Agents MUST NOT change status fields in any RFC.
- Agents MUST NOT hand-edit generated open-source page or prose files — they are generator-owned (RFC-0081).
- Agents MUST NOT embed full license texts in the page DOM — full texts go in downloadable artifacts only.
- Agents MUST NOT hardcode language-specific paths — use i18n config from `system.md`.
- Agents MUST preserve RFC-0154 idempotency — the generator must be a pure function of source. Deployment metadata must come from the build context, not from a wall-clock call.
- Agents MUST register `open-source.validate` in `SITES_BUILD_CHECK_PIPELINE` and update `GENERATOR_OWNERSHIP_MAP` for new artifact paths.
- Agents MUST add localized labels for both DE and UK — never leave German text in the UK page.
- When implementing, reference RFC-0489 in commit messages or PR descriptions.
