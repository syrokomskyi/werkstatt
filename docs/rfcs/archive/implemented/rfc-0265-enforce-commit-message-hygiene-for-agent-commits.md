# RFC-0265: Enforce commit message hygiene for agent commits

## Context

Part E of the 2026-07-02 AEO audit series (hygiene and governance; see rfc-0258 for series order).

Git history is an agent-legible knowledge source in this workspace: agents reconstruct initiative context from `git log`, and memory notes reference commit hashes as anchors. The audit found the history polluted with pasted agent narration committed verbatim as subjects:

- `8b3e62ab` — subject begins "Found the bug — `app.qa.validate` passes `args:` …" (multi-sentence analysis as a subject).
- `76766188` — subject begins "Good — `PlanetCatalog` and `MoonCatalog` are exported …".
- `b75feeb7` — subject is markdown bold in Ukrainian: `**05-audit — пройдено (з очікуваними build-deferred блокерами).**`.

Each of these is a turn of assistant chat output pasted into `git commit -m`. They break `--oneline` scanning, defeat grep-by-type, and teach future agents the wrong convention by example.

## Problem

The unprotected invariant is: **a commit subject is a short imperative statement of WHAT changed; analysis, greetings, and status narration belong in the body or the PR, never in the subject.** Today nothing enforces this; the convention exists only by majority example (`feat:`, `fix:`, `docs:` prefixes dominate recent history) and degrades whenever an agent pipes its own narration into the commit.

## Decision

A new workspace command `commit.message.lint` validates commit messages in a range (default: commits ahead of the default branch; `--range <rev-range>` to override) and runs as a CI gate. Rules:

- `COMMIT-01` (error): subject longer than 120 characters.
- `COMMIT-02` (error): subject does not match `^(feat|fix|docs|refactor|test|chore|build|ci|perf|style)(\([a-z0-9-]+\))?: [a-z]` — a conventional-commit prefix followed by a lowercase imperative clause.
- `COMMIT-03` (error): subject contains narration/markdown markers: leading `**`, leading backtick, an em dash used as a discourse connector after an interjection (patterns like `^(Good|Great|Found|Okay|Now|Let me|Perfect|Excellent)\b`), or sentence-final `.` followed by a second sentence in the subject line.
- `COMMIT-04` (warning): commit touches `packages/os/**` or `docs/rfcs/**` and neither subject nor body references an `RFC-\d{4}` or `rfc-\d{4}` id.

Merge commits and revert commits generated by git are exempt.

> **Update 2026-07-03 (founder-directed):** the `COMMIT-01` ceiling was raised from 72 to **120** characters. The original 72 followed the git `--oneline` convention, but the workspace's own `feat(scope): implement rfc-NNNN <descriptive title>` subjects routinely run 75–90 characters, and enforcing 72 would have required rewriting already-pushed history for purely cosmetic reasons. 120 keeps subjects scannable while accommodating the RFC-title-in-subject house style. COMMIT-02/03/04 are unchanged.

## Architectural fit

- Governance policy in the spirit of RFC-0224: it protects a machine-readable record (git history) the same way `rfc.validate` protects RFC frontmatter.
- Implemented as a Site OS command in `@gogol/site-kernel` (it needs only `git log`, no app context), registered workspace-scope, wired into the CI workflow — not into `build.check` (commit metadata is not a build artifact).

## Design

### CLI surface

```sh
pnpm exec site-kernel run commit.message.lint                 # commits ahead of origin/main
pnpm exec site-kernel run commit.message.lint --range HEAD~10..HEAD
pnpm exec site-kernel run commit.message.lint --json
```

### TypeScript contracts

```ts
// packages/os/site-kernel/src/commit-message-lint.ts (new)
export interface CommitMessageFinding {
  hash: string;
  subject: string;
  ruleId: "COMMIT-01" | "COMMIT-02" | "COMMIT-03" | "COMMIT-04";
  severity: "error" | "warning";
  message: string;
}
```

### File system responsibilities

| Path | Role |
| --- | --- |
| `packages/os/site-kernel/src/commit-message-lint.ts` | Implementation (spawns `git log --format`) |
| CI workflow template (`github-deploy.template.yml` owner package) | New lint step on push/PR |
| `AGENTS.md` | New "Commit message contract" paragraph under Global working rules |

### Output format

Standard RFC-0203 `CheckResult`; each diagnostic's locator is the commit hash (no file path). `--json` stable.

### Failure modes

Exit 1 on any error-severity finding in the range. `COMMIT-04` warns only. When the range is empty (no commits ahead), pass with an explanatory summary.

## Rollout

1. Land the command + fixture tests (message-string fixtures, no real git needed for rule logic; one integration test over a temp git repo).
2. Add the `AGENTS.md` paragraph in the same change — the rule text agents will read BEFORE committing.
3. Enable in CI as a required check after one week of local-only observation (gives in-flight branches time to rebase-reword).

## Alternatives considered

- **husky commit-msg hook**: rejected as the primary mechanism — hooks are per-clone opt-in and this repo's agents commit from many environments; CI is the authoritative gate. A hook MAY be added later as a convenience.
- **Off-the-shelf commitlint**: viable, but the narration rules (`COMMIT-03`) are custom anyway, the kernel already owns command/diagnostic infrastructure, and one less node toolchain dependency keeps the surface small.

## Risks

- False positives on legitimate subjects starting with a listed interjection-like word; mitigated by requiring the word-boundary + discourse pattern, and by `--range` re-runs during tuning week.
- Agents may game the prefix (`chore: stuff`); the lint enforces shape, not quality — review and the RFC-0224 governance still own semantics.

**As-built, 2026-07-02:** implemented in `@gogol/site-kernel` (not `site-kernel-checks`) per the Design section's file-responsibility table — `commit-message-lint.ts` (pure `lintCommitSubject`/`parseGitLogOutput`/`parseNameOnlyOutput`/`isExempt` + `runCommitMessageLint` git integration) and `commit-message.module.ts`, registered via `tools/kernel.config.ts`. `COMMIT-01..04` are registered in `site-kernel-checks`'s rule-id catalog for documentation, but — unlike most RFC-0203 rules — are NOT scanned by `diagnostic.shape.lint`'s DSL-02 check, since that check's `checksDir` only walks `packages/os/site-kernel-checks/src`; this command lives one package over by design (noted in the rule registry's CHANGE_SUMMARY). CI step landed as a new dedicated `.github/workflows/commit-message-lint.yml` (triggered on every PR + push to `main`, `fetch-depth: 0` for range resolution) rather than folded into the per-app deploy template or `rfc-governance.yml`'s path-filtered trigger — this lint applies to every commit regardless of which paths changed, so a path-filtered workflow would under-fire. Running the command against this repo's real `origin/main..HEAD` range surfaced 165 pre-existing commits with findings (181 errors, 40 warnings) — expected and NOT a regression to fix: per this RFC's own nonGoals, the lint is forward-only and applies to new commits from here on; the backlog predates this RFC.

## Implementation notes for agents

- Agents MAY implement code changes ONLY when this RFC has status: accepted (or implemented).
- When this policy is active: NEVER pass your own analysis or chat narration to `git commit -m`. Write the subject as `<type>: <imperative clause>` and put reasoning in the body.
- Do not rewrite or reword existing history to satisfy the lint; it applies forward only.
- Agents MAY transition this RFC `accepted` → `implemented` per RFC-0224 preconditions only; reference `rfc-0265` in commits.
- Agents MUST NOT weaken or remove enforcement rules established by this RFC without a superseding RFC.
