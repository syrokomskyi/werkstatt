# RFC-0222: Generate and validate human-facing architecture docs

## Context

`docs/COMMANDS.md` is currently a hand-maintained snapshot of Site OS commands. Human-facing README architecture snippets are also hand-authored summaries of the same system described in root `AGENTS.md`, workspace AGENTS files, and the GRACE XML documents.

On 2026-06-20 an ecosystem audit found several drift classes: `handoff.pack` / `handoff.absorb` code and docs disagreed about implementation status, README still described an older single-route app model, and package-manager versions diverged between root docs, templates, and app package files. The fixes were straightforward, but detection depended on a human/agent whole-repo read rather than a deterministic command.

## Problem

The repository has a strong machine-readable command registry, but its primary human index is manual:

- `docs/COMMANDS.md` can omit commands, stale scopes, stale mutation flags, or package ownership notes.
- Root `README.md` can describe an older app route/content model while `AGENTS.md`, `docs/*.xml`, and generators have moved on.
- Agents currently learn these mismatches by grep and validation side effects, not by a dedicated docs-drift gate.
- Because `docs/COMMANDS.md` explicitly says no generator rebuilds it, agents cannot safely infer whether they should edit it, generate it, or validate it.

## Decision

The Site OS gains deterministic documentation drift commands for human-facing architecture docs:

- `docs.commands.generate` renders `docs/COMMANDS.md` from registered kernel commands and package-level command metadata.
- `docs.commands.validate` compares the committed `docs/COMMANDS.md` to generated output and fails on drift.
- `docs.architecture.validate` checks a small set of structured README architecture facts against root `AGENTS.md` and GRACE XML values.

## Architectural fit

This follows RFC-0087's content-driven generation discipline and RFC-0143's warning that the kernel command registry is the registry. The generated command document is a projection, not a second source of truth.

The commands belong in `@gogol/site-kernel-checks` / `@gogol/site-kernel-codegen` because they validate and project workspace-level operator documentation. They should run in `packages-check.run` once the generated form is stable.

## Design

### CLI surface

```sh
pnpm exec site-kernel run docs.commands.generate
pnpm exec site-kernel run docs.commands.validate
pnpm exec site-kernel run docs.architecture.validate
pnpm exec site-kernel run docs.architecture.validate --json
```

All three commands are workspace-scoped. `docs.commands.generate` mutates `docs/COMMANDS.md`; the two validators are read-only.

### TypeScript contracts

```ts
interface CommandDocRow {
  command: string;
  packageName: string;
  scope: "workspace" | "app";
  mutates: boolean;
  description: string;
}

interface DocsDriftViolation {
  file: string;
  rule: "missing-command" | "extra-command" | "scope-drift" | "mutates-drift" | "architecture-drift";
  expected?: string;
  actual?: string;
  message: string;
}
```

### File system responsibilities

| Path | Role |
| --- | --- |
| `docs/COMMANDS.md` | Generated by `docs.commands.generate`; validated by `docs.commands.validate` |
| `README.md` | Validated for structured architecture facts only |
| `AGENTS.md`, `apps/AGENTS.md`, `packages/AGENTS.md` | Read as instruction-layer facts |
| `docs/*.xml` | Read as GRACE semantic facts |
| `packages/os/**/src/**/*.ts` | Command registry source scan |

### Output format

```json
{
  "command": "docs.commands.validate",
  "status": "fail",
  "violations": [
    {
      "file": "docs/COMMANDS.md",
      "rule": "missing-command",
      "expected": "handoff.pack",
      "message": "Registered command handoff.pack is missing from docs/COMMANDS.md"
    }
  ]
}
```

### Failure modes

Validators exit non-zero for command registry drift. README architecture checks start fail-hard only for facts that can be represented as closed values: app route shape, package manager version, mandatory GRACE doc list, and implemented command status. Freeform wording differences are not violations.

## Rollout

First land the generator and validator as standalone commands. Run the generator once and commit the normalized `docs/COMMANDS.md`. Then add `docs.commands.validate` to `packages-check.run`. Add `docs.architecture.validate` to the same pipeline once the first closed fact set is stable.

## Alternatives considered

Keeping `docs/COMMANDS.md` fully hand-maintained was rejected because it repeatedly drifts during command rollout. Generating all README prose was rejected because prose carries human context; only closed architecture facts should be validated.

## Risks

The main risk is false precision: a generated command table is useful, but README prose should not become unreadable just to satisfy a validator. The architecture validator must therefore start with a tiny closed set and expand only when facts are stable and machine-readable.
