# RFC-0143: Per-page output projection schema and generator contract

## Context

The platform now has four build-time generators that write machine-readable files into `public/` during `build.prepare`, all sharing one architecture — _config in `system.md` → pure formatter in `@gogol/share` → thin command in `site-kernel-checks` → `public/` file → Astro copies to `dist/`_:

| Generator          | RFC                 | Config shape                                  |
| ------------------ | ------------------- | --------------------------------------------- |
| `sitemap.generate` | RFC-0049            | per-page `sitemapExclude: boolean` + `routes` |
| `llms.generate`    | RFC-0050 / RFC-0142 | per-page `llms` inclusion depth               |
| `ai.generate`      | RFC-0051            | site-wide `ai:` block                         |
| `robots.generate`  | RFC-0052            | site-wide `robots:` block                     |

Two observations:

1. **Two distinct config shapes are mixed together.** `sitemap` and `llms` are _per-page projections_ — they answer "how does this page contribute to a machine-readable output?". `ai` and `robots` are _site-wide policies_ — a single declarative block per site. These are different kinds of configuration.
2. **The per-page projection config is informal and scattered.** `semanticType` and `sitemapExclude` are read by the loaders but are **not present in `systemManifestSchema`** ([`packages/ontology/src/schemas/system.ts`](../../packages/ontology/src/schemas/system.ts)) — they are unvalidated "extension fields." RFC-0142 is about to add a third such per-page field (`llms`). Without a structural home, every new per-page projection generator will bolt on another top-level page field.

The ecosystem goal is **thin, standard, manageable** sites. With only two apps today (`nicaragua-projekt`, `warpgogol-com`, the latter not yet declaring `semanticType`), the cost of standardizing the per-page projection surface is near-zero. The cost grows with every new app and every new generator.

## Problem

The unprotected invariants are:

> The per-page configuration that controls how a page projects into machine-readable outputs must have one typed, validated, extensible home — not an open-ended set of unvalidated sibling fields.

> Adding a new build-time file generator must follow a single documented contract so that thin sites stay standard and predictable as the set of generators grows.

Current failure modes:

1. **Unvalidated per-page fields.** `semanticType` / `sitemapExclude` bypass the schema; a typo (`sitmapExclude: true`) silently does nothing.
2. **Field sprawl.** Each per-page projection generator adds its own root-level page field (`sitemapExclude`, then `llms`, then the next one), with no shared structure or naming convention.
3. **No generator contract.** New generators are written by pattern-matching existing ones. The pattern is real but undocumented, so drift (a generator that skips `*.validate`, or invents a parallel config file) is possible.
4. **Sitemap/LLMS coupling residue.** Because `sitemapExclude` was the only per-page projection lever, it has been informally reused as a proxy for "exclude from everything" (see RFC-0142 Problem). A typed per-generator surface removes the temptation.

## Decision

Introduce a typed per-page **`output`** block, formalize the per-page projection fields in the schema, and codify a **Generator Contract**. Explicitly do **not** build a generic runtime generator framework.

### 1. Per-page `output` block

Each `pages[]` entry gains an optional typed `output` object. Each known per-page projection generator owns one key:

```yaml
pages:
  - pageId: openSource
    semanticType: openSource
    output:
      sitemap: false          # shorthand for { include: false }
      llms: index-only        # owned by RFC-0142

  - pageId: digitalesFundament
    semanticType: content
    output:
      sitemap: { include: true, priority: 0.8 }   # object form
      llms: full
```

`output` is a **closed** object: only keys for known generators are accepted, each with its own per-generator schema. Unknown keys are a validation error. New per-page generators extend this object — they do not add new top-level page fields.

`output.sitemap` accepts a boolean shorthand (`include`) or an object (`{ include, priority?, changefreq? }`). `output.llms` is owned by RFC-0142 (`full | summary | index-only | exclude`, or object form).

### 2. Schema formalization

`systemManifestSchema` page entry is extended to formally declare:

- `semanticType` (enum, optional) — previously informal.
- `sitemapExclude` (boolean, optional) — **deprecated alias**, see migration.
- `output` (the closed object above).

`system.manifest.validate` rejects invalid `semanticType` values, unknown `output` keys, and invalid per-generator values. When `sitemapExclude` is present it emits a **deprecation warning** pointing at `output.sitemap`.

### 3. Site-wide policy blocks unchanged

`ai:` and `robots:` remain typed top-level siblings of `growth:` / `release:`. They are **not** moved under `output` (which is per-page) and **not** wrapped in a generic container. Per-page projection (`output`) and site-wide policy (top-level blocks) are deliberately kept as two separate, typed surfaces.

### 4. The Generator Contract

A documented invariant for **every** build-time file generator. It is a contract/convention, not a runtime registry — the existing `STANDARD_BUILD_PREPARE_PIPELINE` and kernel command registry remain the only registry.

> A build-time file generator MUST provide:
>
> 1. **Typed config**, in exactly one of two families:
>    - _per-page projection_ → a key under `pages[].output`, or
>    - _site-wide policy_ → a typed top-level block in `system.md`. Config MUST be formalized in `systemManifestSchema`.
> 2. A **pure formatter** in `@gogol/share` (no I/O).
> 3. A **command pair** `*.generate` + `*.validate` in `@gogol/site-kernel-checks`; `*.generate` has `mutatesState: true`.
> 4. **Pipeline registration** in `STANDARD_BUILD_PREPARE_PIPELINE`.
> 5. **Safe default**: absent config yields valid output and unchanged bytes for pages/sites that do not opt in.
>
> A generator MUST NOT: introduce a `src/pages/*` runtime route for the file; introduce a parallel config file outside `system.md`; or duplicate formatter logic in the command.

Codegen generators (`routes`, `styles`, `icons`, `agents`, `biome.css`, `i18n.middleware`, `open-source`) are **out of scope** of this contract — they are engineering-derived artifacts, not client-editable content projections.

## Architectural fit

**RFC-0047 / thin CMS surface.** `output` lives in the single `system.md` manifest; no new content file or collection.

**RFC-0049 / sitemap.** `output.sitemap.include` generalizes `sitemapExclude`. The sitemap formatter reads the resolved per-page projection instead of the raw boolean. `sitemapExclude` stays as a read-compatible alias.

**RFC-0050 / RFC-0142 / llms.** `output.llms` is the home for the RFC-0142 depth policy. RFC-0142 is amended to declare its field under `output.llms` rather than a bare `llms:` field.

**RFC-0051 / RFC-0052 / ai + robots.** Confirmed as the _site-wide policy_ family; this RFC documents that classification and leaves them untouched.

**DNA-25 / thin delivery.** Resolution helpers (per-generator default resolution) live in `@gogol/share`; loaders and commands consume them; formatters stay pure.

**DNA-22 / client surface.** `output` is part of the client-editable `system.md`.

## Design

### TypeScript contracts

```ts
// packages/share/src/semantic/output-projection.ts (new, pure)

export type SitemapProjection = {
  include: boolean;          // default true
  priority?: number;
  changefreq?: "always" | "hourly" | "daily" | "weekly" | "monthly" | "yearly" | "never";
};

// llms policy type is owned by RFC-0142 (SemanticLlmsPolicy)
export type PageOutputProjection = {
  sitemap: SitemapProjection;
  llms: import("./models.ts").SemanticLlmsPolicy;
};

/** Raw `output` block as authored in system.md (shorthands allowed). */
export type RawPageOutput = {
  sitemap?: boolean | Partial<SitemapProjection>;
  llms?: import("./llms-policy.ts").RawLlmsPolicy;
};

/** Resolve every per-page projection to its effective value, applying defaults + legacy sitemapExclude. */
export function resolvePageOutput(
  raw: RawPageOutput | undefined,
  opts: { semanticType: string; legacySitemapExclude?: boolean },
): PageOutputProjection;
```

`resolvePageOutput` is the single resolution point. It:

- resolves `sitemap.include` from `output.sitemap` if present, else from the deprecated `sitemapExclude` (negated), else `true`;
- delegates `llms` to `resolveLlmsPolicy` (RFC-0142);
- is consumed by **both** the disk loader (`semantic-loader.ts`) and the Astro path (`semantic-model.ts`), so static and runtime models cannot drift.

The resolved `PageOutputProjection` is attached to `SemanticPageModel` (e.g. `model.output`), and the sitemap and llms formatters read `model.output.sitemap` / `model.output.llms`.

### Schema shape (Zod, in `@gogol/ontology`)

```ts
const semanticPageTypeSchema = z.enum([
  "home", "about", "projects", "donationContact", "openSource", "content",
]);

const sitemapProjectionSchema = z.union([
  z.boolean(),
  z.object({
    include: z.boolean().optional().default(true),
    priority: z.number().min(0).max(1).optional(),
    changefreq: z.enum([
      "always","hourly","daily","weekly","monthly","yearly","never",
    ]).optional(),
  }),
]);

const pageOutputSchema = z.object({
  sitemap: sitemapProjectionSchema.optional(),
  llms: llmsPolicySchema.optional(),          // from RFC-0142
}).strict();                                    // closed: unknown keys rejected

// page object gains:
//   semanticType: semanticPageTypeSchema.optional(),
//   sitemapExclude: z.boolean().optional(),    // DEPRECATED alias
//   output: pageOutputSchema.optional(),
```

`.strict()` on `pageOutputSchema` is what enforces the "closed object" rule — a new generator must extend the schema, which is the intended, reviewable extension point.

### Migration

`sitemapExclude: true` → `output: { sitemap: false }`. Mechanical and reviewable; only `nicaragua-projekt` currently uses any per-page projection field, and `warpgogol-com` has none.

- **Phase 1**: schema accepts both; `resolvePageOutput` honors the legacy field; `system.manifest.validate` warns on `sitemapExclude`.
- **Phase 2**: migrate the two apps + onboarding template to `output`.
- **Phase 3 (later, separate deprecation RFC)**: remove `sitemapExclude` support once no app uses it.

No flag day at any phase: defaults preserve current output.

## Failure modes

- **Unknown `output` key** (e.g. `output.sitmap`) → `system.manifest.validate` error (closed schema).
- **Both `sitemapExclude` and `output.sitemap` present and disagreeing** → `output.sitemap` wins; `system.manifest.validate` emits a conflict warning.
- **Invalid `semanticType`** → validation error (previously silently ignored).
- **`output` on a page with no `semanticType`** → the page never enters the semantic model, so `output.llms` is inert; `output.sitemap` still applies (sitemap does not require `semanticType`). Advisory note in `--json`.

## Rollout

1. **Phase 1 — types + resolver.** Add projection types and `resolvePageOutput` in `@gogol/share`; add `output` to `SemanticPageModel`.
2. **Phase 2 — schema.** Formalize `semanticType`, `sitemapExclude` (deprecated), `output` in `systemManifestSchema`; wire `system.manifest.validate` checks + deprecation warning.
3. **Phase 3 — loaders.** Resolve `model.output` in both loaders via the shared helper.
4. **Phase 4 — consumers.** Point `sitemap.generate` at `model.output.sitemap`; `llms.generate` at `model.output.llms` (coordinated with RFC-0142).
5. **Phase 5 — app + template migration.** Migrate `nicaragua-projekt`, `warpgogol-com`, and the onboarding `system.template.md`.
6. **Phase 6 — contract doc.** Publish the Generator Contract in the architecture docs (`packages/os/site-kernel/docs/`) and reference it from `apps/AGENTS.md` so new generators follow it.

## Alternatives considered

**Generic `generators: { <id>: <freeform> }` registry in the manifest.** Rejected. It trades per-generator type safety for false uniformity and duplicates the existing command registry. The pipeline already is the registry; the manifest should hold _typed config_, not a generator catalog.

**Keep adding top-level per-page fields (`sitemapExclude`, `llms`, …).** Rejected. Field sprawl with no shared structure or validation; exactly the drift this RFC stops while the cost is still near-zero.

**Fold `ai:` / `robots:` into `output` too.** Rejected. `output` is per-page; `ai`/`robots` are site-wide. Forcing both under one key would conflate two different config lifecycles.

**Make `output` an open object (no `.strict()`).** Rejected. An open object re-creates the "unvalidated extension field" problem at a deeper level. The closed object makes adding a generator an explicit, reviewed schema change — which is the desired control point.

**Do nothing until a third generator appears.** Rejected. The third per-page generator is already arriving (RFC-0142 `llms`). Standardizing now, with two apps, is the cheapest it will ever be.

## Risks

**Schema churn touches a hot file.** `systemManifestSchema` is central. Mitigation: changes are additive (new optional fields); existing manifests stay valid; the only breaking-ish move (`sitemapExclude` removal) is deferred to a separate later RFC.

**Two loaders drift.** Mitigation: both call the single `resolvePageOutput`; neither contains projection logic.

**Over-strictness blocks experimentation.** A closed `output` schema means a prototype generator can't quietly read a custom key. Mitigation: that is intentional — a new generator lands its schema key in the same PR, keeping the manifest honest.

**Coordination with RFC-0142.** `output.llms` is defined here but its semantics live in RFC-0142. Mitigation: RFC-0142 is amended to reference this RFC and place its field under `output.llms`; the two ship together (this RFC owns the container, RFC-0142 owns the llms value).

## Implementation notes for agents

- Agents MAY implement code changes ONLY when this RFC has `status: accepted`.
- Agents MUST NOT change status fields in any RFC.
- Agents MUST keep `output` a **closed** (`.strict`) schema — a new per-page generator extends it in the same PR that adds the generator.
- Agents MUST resolve all per-page projections through `resolvePageOutput` in `@gogol/share` — never inline projection logic in a loader, command, or formatter.
- Agents MUST update both `semantic-loader.ts` and `semantic-model.ts` together.
- Agents MUST keep `ai:` and `robots:` as top-level site-wide blocks — do not move them under `output`.
- Agents MUST NOT introduce a generic `generators:` registry in the manifest.
- Agents MUST keep `sitemapExclude` working as a deprecated alias; its removal is a separate future RFC.
- When implementing, agents MUST reference `RFC-0143` in commit messages or PR descriptions, and coordinate the `output.llms` value with `RFC-0142`.
