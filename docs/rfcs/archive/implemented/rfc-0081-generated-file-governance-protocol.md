# RFC-0081: Unified generated-file governance protocol with project-specific override marker

## Context

RFC-0078 and RFC-0079 established a **generation-first discipline** where engineering-only files in `apps/*` are produced by generators rather than hand-authored. Both RFCs defined a `GENERATED BY <command>` header as a marker that generators use to identify files they own. The `writeManagedFile` utility in `site-kernel-codegen` checks for this marker: if the marker is absent, the file is treated as hand-authored and skipped.

This approach has three gaps:

1. **No unified marker string.** Every generator invents its own format: `GENERATED BY agents.generate — DO NOT EDIT`, `GENERATED BY kernel.wire — DO NOT EDIT`, `/* AUTO-GENERATED — DO NOT EDIT */`. A validator cannot reliably answer "is this a generated file?" without knowing every possible format.

2. **Marker semantics are implicit.** The marker says "do not edit" but does not express what happens when a developer intentionally edits a generated file. Currently, removing the marker causes the file to be silently skipped — there is no informational message, no build-time feedback, and no clear signal that the file is now "project-specific."

3. **Generated files were excluded from commits** (via gitignore of `tools/` and other generated paths). This removed local control over regressions: a developer cannot `git diff` generated output, cannot review generated changes in PRs, and cannot bisect regressions that originate in generated code.

## Problem

The following invariants are currently unprotected:

1. **No single detection surface.** A tool or agent that needs to answer "is this file generated?" must parse multiple marker formats or fall back to path heuristics. This makes drift detection fragile and validator logic imprecise.
2. **No feedback loop for project-specific files.** When a developer customises a generated file, the regeneration silently skips it. No build message confirms the skip, so the developer cannot be sure their customisation is actually protected. Conversely, another developer may not realise the file diverged from the template.
3. **Lost regression visibility.** Generated files are excluded from git tracking, so CI/CD cannot detect regressions introduced by generator changes, and reviewers cannot see the impact of a generator change on the committed output.
4. **AI agents have no reliable rule.** An agent working in this repository cannot reliably distinguish files it should regenerate from files the project has intentionally customised.

## Decision

Every generator in the ecosystem uses a **single, standardised marker string** to identify files it owns and manages. The marker string is:

```
GENERATED. Do not change this line unless the file contains project specific changes.
```

The marker is placed in every file the generator creates. The exact syntax varies by file type:

| File type | Placement | Example |
| --- | --- | --- |
| `.ts`, `.js`, `.astro` | Top-of-file line comment | `// GENERATED. Do not change this line unless the file contains project specific changes.` |
| `.md`, `.html`, `.astro` (template) | Top-of-file HTML comment | `<!-- GENERATED. Do not change this line unless the file contains project specific changes. -->` |
| `.css`, `.jsonc` | Top-of-file block comment | `/* GENERATED. Do not change this line unless the file contains project specific changes. */` |
| `.json` | First field `generatedMarker` | `"generatedMarker": "GENERATED. Do not change this line unless the file contains project specific changes."` |
| `.yaml`, `.yml` | Top-of-file comment | `# GENERATED. Do not change this line unless the file contains project specific changes.` |

**Behaviour:**

- **Marker present (exact match):** The generator **always overwrites** the file on every run (`build.prepare`, generator command, whatever trigger). The file is treated as "managed by generator."
- **Marker absent (modified or removed):** The generator **skips** the file and emits an informational message (or warning) that the file is marked as project-specific and will not be recreated or overwritten.
- **File does not exist:** The generator creates it with the marker.

**Git tracking:**

- All generated files are committed to version control. No generated path is gitignored purely because it is generated. Transient build artifacts (`dist/`, `node_modules/`) remain gitignored as before.
- Generated files are reviewed in PRs like any other file. A generator change that affects output is visible as a regular diff.

This RFC **supersedes** RFC-0078 and RFC-0079 in their regeneration semantics. The generation logic (which files, from which templates, at which pipeline step) is unchanged. Only the marker string and the skip/overwrite rule are replaced.

## Architectural fit

- **Anti-Patterns:** Prevents the anti-pattern where generated files silently diverge from their generator templates without any signal.
- **Page Contracts:** No direct effect — page content remains canonical in `src/content/`. The protocol applies to engineering-only files in the app skeleton.
- **Component Contracts:** No direct effect — component templates are generated by `section.scaffold` and now carry the unified marker.
- **Site OS operator model:** The `generated.marker.validate` command checks that all files declared as generated in the pipeline carry the exact marker string. `app.boilerplate.validate` is updated to use the new marker string for drift detection.
- **Scaling Playbook:** Applies uniformly across all growth stages. The marker protocol is equally important for a single-site project and a multi-client onboarding pipeline.

## Design

### Marker detection

Every generator that writes a file MUST check for the marker using a shared utility:

```ts
const MARKER_PREFIX = "GENERATED. Do not change this line unless the file contains project specific changes.";

function hasGeneratedMarker(content: string): boolean {
  return content.includes(MARKER_PREFIX);
}
```

This is an exact substring match. The exact string (not a regex, not a prefix-only match) is what defines "generated." A file that contains the string anywhere in its content is treated as managed by the generator.

The shared utility lives in `@gogol/site-kernel-codegen` and is exported for use by all generator modules:

```ts
// packages/os/site-kernel-codegen/src/generated-marker.ts
export const GENERATED_MARKER = "GENERATED. Do not change this line unless the file contains project specific changes.";

export function hasGeneratedMarker(content: string): boolean {
  return content.includes(GENERATED_MARKER);
}
```

### Generator behaviour contract

Every generator that writes files MUST follow this exact sequence:

```
if file does not exist:
    create file with marker header + generated content
elsif file contains GENERATED_MARKER:
    overwrite file entirely with fresh generated content
else (file exists but marker is absent/modified):
    skip file
    emit message: "[generator-name] File <path> is marked as project-specific — skipped to preserve custom changes."
```

"Message" may be `console.info`, a structured warning in the kernel command result, or a CI annotation. The message must be visible in both CLI and CI output.

Generators MUST NOT:

- Delete a project-customised file (one without the marker).
- Prompt the developer interactively.
- Fall back to a different file name.

### CLI surface

```
pnpm exec site-kernel run generated.marker.validate --app <app>
```

Scans all files in `<app>/` that are known to be generator output (declared by each generator's manifest or by the existing `app.boilerplate.validate` file list). Reports:

- Files that carry the marker but were not modified by any generator on this run (stale — should have been regenerated if the marker is present).
- Files without the marker that diverge from the last known generated output (informational — these are project-customised files).

The command uses `--json` output for CI consumption.

### TypeScript contracts

```ts
interface GeneratedMarkerValidateInput {
  app: string;
  // If true, also checks files that have no marker but are
  // known generated paths — this catches marker removal
  // that may have been accidental.
  strict?: boolean;
}

interface GeneratedMarkerValidateResult {
  command: "generated.marker.validate";
  status: "ok" | "warn" | "fail";
  managedFiles: number;       // files carrying the marker
  projectSpecificFiles: number;  // files without the marker
  staleManagedFiles: string[];   // files with marker but content differs from generator
  unmarkedGeneratedFiles: string[]; // known-generated files missing the marker
}
```

| Path | Role |
| --- | --- |
| `packages/os/site-kernel-codegen/src/generated-marker.ts` | Shared `GENERATED_MARKER` constant and `hasGeneratedMarker()` helper |
| Every generator module | Uses the shared constant; follows the marker protocol |
| `packages/os/site-kernel-checks/src/module.ts` | Updates `writeManagedFile` reference in `app.boilerplate.validate` to use the new marker |
| `packages/os/site-kernel-codegen/src/app-boilerplate.ts` | `writeManagedFile` updated to use `GENERATED_MARKER` constant |

| `packages/os/site-kernel-codegen/src/service.ts` | Icon generator and open-source generator use the constant |
| All `src/templates/app-boilerplate/` templates | Comment header changed to `GENERATED_MARKER` |

### Output format

All generator commands return the same uniform JSON structure enhanced with marker information:

```json
{
  "command": "<generator-name>",
  "status": "ok",
  "generated": ["src/pages/index.astro", "src/styles/global.css"],
  "unchanged": ["src/content/pages/de/cosmic/passport.md"],
  "projectSpecific": [
    {
      "file": "src/styles/global.css",
      "message": "File is marked as project-specific — skipped to preserve custom changes."
    }
  ]
}
```

### Failure modes

- **File has marker but was not regenerated.** This is a bug in the generator or in the pipeline step. `generated.marker.validate --strict` catches it and exits non-zero.
- **Known-generated file missing the marker entirely.** This indicates accidental marker removal or a generator that did not write the marker. `generated.marker.validate` reports it with a warning.
- **Project-customised file with outdated generated content.** This is intentional by design. The informational message tells the developer what happened. No build failure.
- **JSON file with `"generatedMarker"` field set to a different value.** The file is treated as project-specific (same as any file without the exact marker match in its content).

## Rollout

1. **Shared constant.** Add `GENERATED_MARKER` and `hasGeneratedMarker()` to `site-kernel-codegen`.
2. **Update `writeManagedFile`.** The existing `writeManagedFile` in `app-boilerplate.ts` already checks for a marker string. Change the check from `"GENERATED BY"` prefix to `hasGeneratedMarker()`. Update the warning message to match the new protocol.
3. **Update individual generators.** One by one, change each generator to use the shared constant instead of a local marker string:
   - AGENTS.md generator (already uses `GENERATED BY agents.generate` → change to `GENERATED_MARKER`)
   - Biome CSS generator (`/* AUTO-GENERATED — DO NOT EDIT */` → `GENERATED_MARKER`)
   - Icon generator (no marker currently → add `GENERATED_MARKER`)
   - Route/styles/scripts/public generators via `writeManagedFile` (already covered by step 2)
   - `kernel.wire` template headers (change from `GENERATED BY kernel.wire — DO NOT EDIT` to `GENERATED_MARKER`)
4. **Add informational skip message.** Ensure every generator emits a visible message when skipping a project-customised file.
5. **Update `app.boilerplate.validate`.** The validator currently checks for "GENERATED BY" marker. Update to check for `GENERATED_MARKER`.
6. **Add `generated.marker.validate`.** New command as described above.
7. **Migration.** Run all generators against `nicaragua-projekt` to write the new marker. All existing generated files are overwritten (they had the old marker, now get the new one). Project-customised files (no old marker) are skipped.
8. **Documentation.** Update `AGENTS.md` at all levels with the new protocol.

Each step is independent and can be committed separately.

## Alternatives considered

**Gitignore all generated files.** Rejected — this was the actual negative experience that triggered this RFC. Loss of local regression control and PR visibility is unacceptable.

**Hash-based content comparison.** Instead of a marker, compare generated output byte-for-byte with the expected output and skip on match. Rejected — this requires running the generator every time just to compare, provides no feedback loop for intentional customisation, and cannot distinguish "customised by project" from "regenerated from newer template."

**Hash-based marker (e.g. `GENERATED // sha256:<hash>`).** Rejected — the marker should be human-readable and project-customisation should be a deliberate act (remove the line), not an accidental hash collision.

**Opt-in marker (file opts into generation instead of opting out).** Rejected — the generation-first discipline is already established. The default should be "generated" with "project-customised" being the explicit opt-out.

**Separate registry file (e.g. `generated-files.json` listing which files are managed).** Rejected — creates a synchronisation problem between the registry and the filesystem. The marker should be self-describing in each file.

## Risks

- **False positives in marker detection.** The string could appear in file content that is not actually a generation marker. Mitigation: the string is distinctive enough to be unlikely in normal source code. The `generated.marker.validate` command can be configured with known false positive paths.
- **Agent confusion.** An agent might see a file with the marker, edit it, and have its edits overwritten on the next build. Mitigation: the `AGENTS.md` rules are explicit: "Do not edit files that carry the GENERATED marker. If you need to customise a generated file, remove the marker line first."
- **Transition period.** During migration, some generators use the old marker and some use the new one. Mitigation: `hasGeneratedMarker` is intentionally backwards-compatible — the old markers (`GENERATED BY`, `AUTO-GENERATED`) can be kept as partial detection targets alongside the new marker during the transition.
- **`generatedMarker` field conflict in JSON.** A JSON file that legitimately has a `"generatedMarker"` field could collide with the marker. Mitigation: the field name is distinctive enough for generated files. If a JSON file needs to use `"generatedMarker"` for another purpose, it should not be a generated file. RFC-0336 extends this convention with additional advisory fields (`doNotEdit`, `ownerCommand`, `editInstead`, `regenerateCommand`) for AI-agent guidance.

## Implementation notes for agents

- Agents MAY implement code changes for this RFC only when its status becomes `accepted`.
- Agents MUST NOT change the status field.
- Agents MUST use `GENERATED_MARKER` constant from `@gogol/site-kernel-codegen/generated-marker` when implementing generators, not a local string literal.
- **Agents MUST NOT edit files that contain the GENERATED marker.** Such edits will be overwritten on the next generator run. To customise a generated file, remove the exact marker line first — the file then becomes project-specific and will be preserved.
- When reviewing a PR or diff, agents MUST flag any edit to a file carrying the marker as potentially wasted work (the edit will be overwritten).
- When a project-customised file (no marker) is found during a generator run, the informational message is a first-class signal — agents MUST NOT treat it as an error.
- If an agent needs to regenerate all files in an app from templates (e.g. after a shared template update), it must first verify that no customised files will be overwritten. The `generated.marker.validate` command provides this safety check.
