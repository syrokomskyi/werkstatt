# RFC-0289: Generate an OpenAPI projection of the agent surface

## Context

RFC-0286 fixed the invariant: protocols are sibling projections of one manifest (AS-1), and protocol documents advertise the manifest's version and hash (AS-7). RFC-0287 provides the knowledge files; RFC-0288 provides typed actions. OpenAPI 3.1 is today's lingua franca for describing HTTP surfaces to external businesses and agent frameworks — most tool-using stacks can ingest an OpenAPI document directly. It is also, per AS-5, disposable: this RFC adds a formatter and a command pair, nothing more, so retiring or replacing OpenAPI someday is one reviewed deletion.

## Problem

- External consumers who do not speak MCP have no self-describing entry point: knowledge file URLs and action schemas are discoverable only through the gogol-specific `agent.json`.
- Without a generated document, any OpenAPI description of a site would be hand-written — instant AS-1 violation and guaranteed drift from the manifest.

## Decision

`build.prepare` gains `agent.openapi.generate`: it reads the site's Agent Surface Manifest (`src/agent-surface.generated.json`) and writes a deterministic OpenAPI 3.1 document to `public/.well-known/agent.openapi.json`. The manifest's `interfaces.openapi` field (RFC-0286) points at it. `agent.openapi.validate` enforces well-formedness and manifest↔document bijection. The formatter is pure, dependency-free, in `@gogol/share`.

## Architectural fit

- **Generator Contract (RFC-0143).** Standard generator: config is the existing `agent:` block (no new keys — the document exists iff the agent surface is enabled), pure formatter, command pair, safe default, `APPS_BUILD_PREPARE_PIPELINE` registration, writes to `public/` only.
- **AS-1/AS-7.** The document is projected mechanically from the manifest; `info.version` = `surfaceVersion`, `info.x-gogol-content-hash` = manifest `contentHash`. Hand-editing is detectable (hash mismatch ⇒ `AGO-03`).
- **RFC-0288 closed schema subset.** Capability `input`/`output` schemas are valid OpenAPI 3.1 schema objects as-is (the subset was chosen for exactly this bijectivity); projection is verbatim copy, never transformation.
- **Pipeline order.** Runs after `agent.manifest.generate` (RFC-0287 canonical order), completing the read-tier chain: `entitlements.resolve` → `agent.knowledge.generate` → `agent.manifest.generate` → `agent.openapi.generate`.

## Design

### CLI surface

```sh
pnpm exec werkstatt run agent.openapi.generate --app warpgogol-com
pnpm exec werkstatt run agent.openapi.validate --app warpgogol-com --json
```

App-scoped; generate is `mutatesState: true`; validate runs in `APPS_CHECK_PIPELINE`.

### Document shape

```ts
// packages/share/src/agent/openapi.ts
/** Pure formatter: manifest in, OpenAPI 3.1 document out. Deterministic: sorted keys, no timestamps. */
export function formatAgentOpenApi(manifest: AgentSurfaceManifest): OpenApiDocument;
```

Projection rules (exhaustive — an implementing agent adds nothing beyond these):

| Manifest element | OpenAPI projection |
| --- | --- |
| header | `openapi: "3.1.0"`; `info: { title: "<site> agent surface", version: surfaceVersion, x-gogol-content-hash: contentHash }`; `servers: [{ url: baseUrl }]` |
| each `AgentKnowledgeRef` | `GET <url>` — `operationId: "knowledge.<domain>.get"`, tag `knowledge`, response `200` with `application/json` schema `$ref: "#/components/schemas/knowledge-<domain>"` (the envelope schema from RFC-0287, embedded as a component) |
| each `AgentActionRef` | `POST <url>` — `operationId: "action.<id>"`, tag `actions`, summary from `title` (default language), `requestBody` schema = capability `input` verbatim, response `200` schema = capability `output` verbatim, response `429` (rate limit, RFC-0291), response `400` (schema violation) |
| `interfaces.mcp` (when non-null) | `x-gogol-mcp: { url, protocolVersion }` at document root — discovery hint, not a path |
| `interfaces.llms` / `twins` | `externalDocs: { url: "<baseUrl>/llms.txt", description: "LLM-oriented text surface" }` |
| `proof` (when non-null, RFC-0291) | `x-gogol-proof` copied verbatim at document root |

Determinism: all object keys emitted in lexicographic order; paths sorted; two runs on one manifest are byte-identical.

### File system responsibilities

| Path | Role |
| --- | --- |
| `apps/<site>/public/.well-known/agent.openapi.json` | The document. Generated, **gitignored**, byte-stable. |
| `apps/<site>/src/agent-surface.generated.json` | Read-only input. |
| `packages/share/src/agent/openapi.ts` | Pure formatter + minimal structural `OpenApiDocument` type (local type, not a dependency). |

### Output format

`agent.openapi.validate --json` — canonical Diagnostics:

| Rule | Severity | Meaning |
| --- | --- | --- |
| `AGO-01` | error | Document missing, unparseable, or `openapi` ≠ `3.1.0`. |
| `AGO-02` | error | Bijection break: manifest ref without exactly one matching operation, or an operation/path with no manifest ref. |
| `AGO-03` | error | `info.version`/`x-gogol-content-hash` disagree with the manifest (stale or hand-edited — rerun the generator). |
| `AGO-04` | error | An action operation's request/response schema differs from the capability record's `input`/`output` (byte-level after key sorting). |

### Failure modes

- Errors fail `build.check`. `agent: { enabled: false }` ⇒ no document; the validator asserts its absence.
- A manifest with empty `knowledge`/`actions` still yields a valid document (info + servers + externalDocs only) — an honest "surface exists, nothing published yet".

## Rollout

1. Ship formatter + command pair; wire pipelines; gitignore the artifact in apps + scaffold.
2. `agent.manifest.generate` (changed) fills `interfaces.openapi` when generation is enabled.
3. Both apps emit documents on next build; warpgogol-com is the reference consumer test: the document must load in a stock OpenAPI viewer without errors (manual spot-check, not a pipeline step).
4. Future protocol documents (if any) follow this RFC as the template: one formatter, one command pair, one manifest `interfaces` key — nothing else (AS-5).

## Alternatives considered

- **Adopt `openapi-types` / swagger libraries.** Rejected: the projected subset is small and closed; a local structural type plus fixtures is cheaper than a dependency treadmill on a decades horizon.
- **YAML output.** Rejected: JSON matches every other generated artifact, diffing, and hashing; OpenAPI consumers accept JSON universally.
- **Documenting the whole site API (webhooks, form endpoint).** Rejected: those are private contracts between the site and its vendors; publishing them invites abuse and freezes internals (nonGoal).
- **Serving at `/openapi.json` root.** Rejected: `.well-known/` co-locates all machine-identity artifacts (passport, agent.json, bordbuch) — one directory to secure, sign, and reason about.

## Risks

- **Spec evolution.** OpenAPI 3.2+ someday: bump is a formatter change behind AGO-01, one reviewed change (AS-5 by design).
- **Viewer expectations.** Some tooling expects `operationId` uniqueness and specific auth blocks; the projection guarantees uniqueness by construction and declares no auth for v1 (public read tier, action auth semantics arrive with RFC-0291 limits documented as 429s).
- **Schema duplication with MCP.** The same capability schemas appear in OpenAPI and MCP tool definitions; AGO-04 plus the RFC-0290 equivalent rule keep both pinned to the catalog, so duplication cannot drift.

## Implementation notes for agents

- Agents MAY implement code changes ONLY when this RFC has status: accepted (or implemented). Requires RFC-0286+0287+0288 implemented first.
- Agents MAY transition `accepted` → `implemented` per RFC-0224 once all criteria are checked and committed.
- The projection table above is exhaustive: do NOT add paths, operations, tags, or vendor extensions beyond it. A new projection element requires amending this RFC.
- Copy capability schemas verbatim; never "improve" them in the projection (AGO-04 will fail).
- Reference RFC-0289 in commit messages.
