# RFC-0614: Expand bordbuch conflict auto-resolution to include public well-known bordbuch paths in mission reconcile

## Context

RFC-0584 introduced auto-resolution of bordbuch delete/modify conflicts in `mission.reconcile`. When the cache clone has modified `bordbuch/events.ndjson` (e.g., by `mission.open` appending a bordbuch entry) and the workpiece has deleted it (because the workpiece is a clean clone without bordbuch files), the merge produces a delete/modify conflict. RFC-0584's auto-resolution keeps the cache clone's version (`--ours`) for `bordbuch/` paths.

However, bordbuch artifacts also live at `public/.well-known/bordbuch.json` and `public/.well-known/bordbuch/index.html`. These files are generated by `bordbuch.generate` (RFC-0604) and exist in the cache clone but not in the workpiece. During `mission.reconcile` of `warpgogol-com-m000022` (2026-07-30), the merge failed with delete/modify conflicts on these three paths:

- `bordbuch/events.ndjson` (already auto-resolved by RFC-0584)
- `public/.well-known/bordbuch.json` (NOT auto-resolved — not under `bordbuch/`)
- `public/.well-known/bordbuch/index.html` (NOT auto-resolved)

The auto-resolution logic in `mission-materialization-commands.ts` only checked `p.startsWith("bordbuch/")`, missing the `public/.well-known/bordbuch*` paths.

## Problem

`mission.reconcile` auto-resolves delete/modify conflicts only for paths under `bordbuch/`, but bordbuch artifacts also exist at `public/.well-known/bordbuch.json` and `public/.well-known/bordbuch/`. When these paths conflict, the merge fails with a manual resolution error, blocking mission completion.

This gap is protected by manual discipline only — the operator must manually resolve the conflict or the agent must edit the cache clone directly (which is forbidden by AGENTS.md).

## Decision

`mission.reconcile` auto-resolves delete/modify conflicts for all bordbuch-related paths: both `bordbuch/` and `public/.well-known/bordbuch*` (including `bordbuch.json` and `bordbuch/index.html`). The auto-resolution always keeps the cache clone's version (`--ours`), consistent with RFC-0584.

This amends RFC-0584 to expand the conflict path matching scope.

## Architectural fit

- **DNA-51 (Werkstatt consistency primitives)**: `mission.reconcile` uses shared lock, idempotency, and atomic staging primitives. Expanding the auto-resolution scope maintains these guarantees — the merge is still atomic and idempotent.
- **RFC-0584 (Auto-resolve bordbuch delete-modify conflicts)**: Amended — the path matching scope expands from `bordbuch/` to include `public/.well-known/bordbuch*`.
- **RFC-0568 (Clone-based workpiece materialization)**: Compatible — the merge strategy (`git merge --no-ff`) is unchanged; only the conflict resolution scope expands.
- **RFC-0604 (bordbuch.generate in build.prepare)**: Bordbuch artifacts at `public/.well-known/bordbuch*` are generated by `bordbuch.generate` and exist only in the cache clone, making them inherently delete/modify conflict candidates.

## Design

### CLI surface

No CLI change — `mission.reconcile` keeps its existing flags and interface. The change is internal to the conflict resolution logic.

### Implementation change

In `packages/os/site-kernel-handoff/src/mission/mission-materialization-commands.ts`, the `isBordbuchPath` check expands:

```ts
// Before (RFC-0584):
const allBordbuch = conflictedPaths.every((p) => p.startsWith("bordbuch/"));

// After:
const isBordbuchPath = (p: string) =>
  p.startsWith("bordbuch/") || p.startsWith("public/.well-known/bordbuch");
const allBordbuch = conflictedPaths.every(isBordbuchPath);
```

The `git checkout --ours` and `git add` commands use the `conflictedPaths` array dynamically rather than hardcoding path literals. This ensures only actually-conflicted paths are checked out and added, avoiding errors when some bordbuch artifacts do not exist (e.g., `public/.well-known/bordbuch*` may not exist if `bordbuch.generate` has not been run yet):

```ts
const pathArgs = conflictedPaths.map((p) => JSON.stringify(p)).join(" ");
execSync(`git checkout --ours -- ${pathArgs}`, { cwd: systemDir, ... });
execSync(`git add -- ${pathArgs}`, { cwd: systemDir, ... });
```

### Output format

The `--json` output shape is unchanged from RFC-0584. The `autoResolvedPaths` field (optional `string[]` in `MissionReconcileData`) already exists and now includes `public/.well-known/bordbuch*` paths in addition to `bordbuch/` paths when auto-resolution occurs. No new fields are introduced.

### Failure modes

- **All-bordbuch conflicts**: Auto-resolved, merge proceeds. Reconcile report includes `autoResolvedPaths`.
- **Mixed conflicts (bordbuch + non-bordbuch)**: Merge is aborted with the existing error message. The operator must resolve non-bordbuch conflicts manually.
- **No conflicts**: Normal merge proceeds without auto-resolution.

## Rollout

- **No migration needed**: The expanded auto-resolution applies immediately to all missions. Existing and future missions benefit from the fix without any flag day.
- **No pipeline change**: `mission.reconcile` remains in the same lifecycle position.
- **Idempotent re-run**: If a previous reconcile failed due to this conflict, re-running after the fix will reset the cache clone to `preReconcileSha` and re-merge with the expanded auto-resolution.
- **AGENTS.md**: No update needed to `packages/os/site-kernel-handoff/AGENTS.md` — the expanded auto-resolution is an internal implementation detail of `mission.reconcile`, not a new agent-facing rule.
- **RFC-0584 amendedBy**: Implementation must update RFC-0584's `amendedBy` field to include `RFC-0614` (V-19 bidirectional referential integrity).

## Alternatives considered

- **Auto-resolve all delete/modify conflicts**: Rejected because non-bordbuch delete/modify conflicts may indicate genuine data loss (e.g., a generated file was deleted in the workpiece but modified in the cache clone). Only bordbuch paths are safe to auto-resolve because they are cache-clone-only artifacts.
- **Move bordbuch artifacts out of `public/.well-known/`**: Rejected because `public/.well-known/bordbuch.json` is a public API endpoint (RFC-0604) that must remain at that path for external consumers.

## Risks

- **Over-broad path matching**: `p.startsWith("public/.well-known/bordbuch")` could match future files like `public/.well-known/bordbuch-archive.json`. This is acceptable — all bordbuch-prefixed files in `.well-known/` are cache-clone-only artifacts.
- **Agent misinterpretation**: Agents may think the auto-resolution applies to all `.well-known/` files. The path prefix is specifically `public/.well-known/bordbuch`, not `public/.well-known/`.
- **Test coverage**: Without a regression test, a future refactor could narrow the path matching again. A unit test must verify that `public/.well-known/bordbuch*` conflicts are auto-resolved.
