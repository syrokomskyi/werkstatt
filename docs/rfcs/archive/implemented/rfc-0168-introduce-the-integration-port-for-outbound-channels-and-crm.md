# RFC-0168: Introduce the Integration Port for outbound channels and CRM

## Context

The studio wants to sell "send a message to the client's channel" (Telegram, WhatsApp, email, …) and "integrate with the client's CRM" as paid capabilities. The foundation exists but is single-vendor: the [`send-message` section API](../../packages/ui/src/sections/send-message/send-message-section.api.ts) is a portable Astro APIRoute (RFC-0149) that forwards a one-field message to **Telegram only**, reading `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` from `astro:env/server`. Its own contract states the channel surface is "extensible" and that "follow-up RFC owns per-channel secret naming." This is that follow-up.

The platform already models vendor-agnostic capabilities as **ports with adapters**: growth (RFC-0027) and content-source (RFC-0141). An Integration Port is the same pattern applied to outbound delivery and CRM.

## Problem

- Channel transport is hardcoded to Telegram; WhatsApp/email and CRM upsert cannot be configured without editing the section handler.
- Per-channel secret names are ad hoc and unvalidated.
- Lead capture has no CRM destination, so the "integrate with Pipedrive" product cannot be built.
- Without a port, every new destination would duplicate transport, validation, and secret-handling logic.

## Decision

An Integration Port is introduced in a shared package: a closed `IntegrationChannelAdapter` contract (deliver a normalized `LeadMessage`) and a `CrmAdapter` contract (upsert a normalized `Lead`/`Contact`). Reference adapters ship for `telegram`, `email`, `whatsapp` (channels) and `pipedrive` (CRM); a `null` adapter is the safe default. The `send-message` handler is refactored to resolve configured adapters from `system.md integrations.*`, deliver to all configured channels, and optionally upsert to the configured CRM. Per-channel secret names are standardized (e.g. `INTEGRATION_TELEGRAM_BOT_TOKEN`, `INTEGRATION_PIPEDRIVE_API_TOKEN`) and the env schema is generated by `api.routes.generate`. `integration.secrets.validate` and `integration.config.validate` join `apps-check.run`.

## Architectural fit

- **Port/adapter symmetry with RFC-0027 (growth) and RFC-0141 (content-source):** app code calls a single `deliver()`/`upsert()`; vendor specifics stay in adapters. No vendor SDK is imported in app routes.
- **RFC-0149 portable APIRoutes:** handlers read secrets via `astro:env/server` and never use Cloudflare-specific signatures; secrets stay server-only.
- **RFC-0169 entitlements:** channels and CRM are features; an app compiles an adapter only when entitled and configured.
- **Privacy/PII:** the `LeadMessage`/`Lead` shapes are minimal and never logged with secrets; handlers never return secrets to the client.

## Design

### CLI surface

```sh
pnpm exec site-kernel run integration.config.validate --app webgogol-com --json
pnpm exec site-kernel run integration.secrets.validate --all
```

### TypeScript contracts

```ts
export interface LeadMessage {
  message: string;
  formId: string;
  locale: string;
  submittedAt: string;     // ISO
  contact?: { email?: string; phone?: string };
}

export interface IntegrationChannelAdapter {
  readonly id: string;                       // "telegram" | "email" | "whatsapp" | "null"
  deliver(msg: LeadMessage): Promise<void>;  // throws on transport failure
}

export interface Lead { name?: string; email?: string; phone?: string; note: string; source: string; }
export interface CrmAdapter {
  readonly id: string;                       // "pipedrive" | "null"
  upsertLead(lead: Lead): Promise<{ id: string } | null>;
}

// system.md
// integrations:
//   channels: [{ adapter: telegram }, { adapter: email, options: { to: "info@…" } }]
//   crm: { adapter: pipedrive }
```

### Failure modes

`integration.config.validate` fails on unknown adapter ids or channel options that violate an adapter's schema. `integration.secrets.validate` fails when a configured adapter's required secret name is absent from the generated env schema. The runtime handler delivers to every configured channel; a single channel failure returns `channel-delivery-failed` but the handler attempts all channels and reports partial success in server logs (never to the client). CRM upsert failure is non-fatal to channel delivery (best-effort, logged).

## Rollout

- The Telegram path is preserved behaviorally; existing `TELEGRAM_*` secrets are aliased to the standardized names during a deprecation window.
- `api.routes.generate` emits the per-app env schema from the configured adapters (extends the RFC-0149 generation).
- Channels/CRM compile only when configured AND entitled (RFC-0169); the `null` adapter keeps local/CI safe.
- New apps inherit the port and the `null` defaults from the scaffold.

## Alternatives considered

- **Keep per-section transport, add a second `if` per channel:** rejected — duplicates transport/secret logic and has no module boundary to sell or gate.
- **Use a third-party form backend (Formspree/Basin):** rejected — adds a third-party dependency, weakens privacy, and cannot upsert to the client's CRM.
- **Direct Pipedrive SDK in the route:** rejected — violates the no-vendor-SDK-in-app-code rule mirrored from growth/content-source ports.

## Risks

- **Secret sprawl:** standardized `INTEGRATION_<VENDOR>_<KEY>` naming + `integration.secrets.validate` keep names predictable.
- **Spam/abuse:** the existing contact-presence + length checks remain; a rate-limit/turnstile hook is noted for a follow-up.
- **PII handling:** `Lead`/`LeadMessage` must never be logged alongside secrets; adapters must not echo secrets in errors.
- **Partial delivery semantics:** documented — channels are best-effort fan-out; CRM upsert is non-blocking.

## Implementation notes for agents

- Agents MAY implement only when this RFC is `accepted`.
- Never import a channel/CRM vendor SDK in `apps/*` or in section routes — only inside its adapter package.
- Read secrets only via `astro:env/server`; never return or log them.
- Channel/CRM ids come from the closed ontology catalog; unknown ids must `console.warn` and no-op (enum-dispatch rule).
- Agents MUST NOT weaken the integration validators without a superseding RFC.
