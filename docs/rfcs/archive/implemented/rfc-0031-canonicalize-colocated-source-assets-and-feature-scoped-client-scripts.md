# RFC-0031: Canonicalize colocated source assets and feature-scoped client scripts

## Context

[RFC-0025](RFC-0025-activate-cosmic-overlay-and-feature-first-app-layout.md) established the feature-first app layout and, in its canonical tree, already showed `src/content/<layer>/<name>/assets/` as the natural home for feature-local media. At the same time, later wording in the same RFC, in `apps/AGENTS.md`, and in migration guides hardened a different rule: raster images are forbidden in `src/` and must be moved to `public/images/`. The workspace now contains both positions at once.

This contradiction is not cosmetic. It changes build behavior:

1. **Source assets under `src/` participate in Astro/Vite's import graph.** They can be optimized, fingerprinted, tree-shaken from unused paths, and resolved relative to the content entry that owns them.
2. **Files in `public/` bypass the build graph.** They are copied verbatim to `dist/`, keep literal URLs, and cannot benefit from Astro's image pipeline or content-collection `image()` helper.
3. **Cloudflare Pages serves `dist/`, not `src/assets/`.** The platform has no opinion about source layout. Whether an asset originated in `src/assets/`, `src/content/**/assets/`, or `public/`, the only relevant boundary is whether the build pipeline touched it before emission.

A parallel contradiction exists for scripts. [RFC-0011](RFC-0011-script-placement-contract.md) correctly established `src/scripts/` as the canonical home for app-global and component-loaded behavioral code. But RFC-0025's feature-first layout already reserved optional `*.client.ts` files inside `src/content/<layer>/<name>/`, implying a second class of script: **feature-scoped source modules that belong to one content bundle, not to the app shell as a whole**.

The repository therefore needs one explicit rule that separates:

- build-managed source assets vs direct-URL passthrough assets,
- app-global scripts vs feature-scoped scripts,
- client-editable optimized source files vs engineering-only runtime infrastructure.

## Problem

Four invariants are currently under-specified or contradictory:

1. **Asset placement drift.** Some documents describe `src/content/**/assets/` as canonical; others force all raster files into `public/images/`. This creates different behavior for the same class of file and guarantees agent confusion.
2. **Optimization is currently undercut by policy.** Moving editable images to `public/` prevents Astro-native optimization and weakens content-entry colocation even though Astro explicitly supports image imports from any folder under `src/`.
3. **Feature-scoped scripts have no settled contract.** `src/scripts/` is correct for app-global and shared behavioral modules, but the current contract does not cleanly describe scripts that belong to one page/section/component content bundle and should be editable alongside that bundle.
4. **`public/` lacks a strict semantic boundary.** Today it acts as both a direct-URL delivery surface and a workaround bucket for assets that should have remained source-managed.

## Decision

The workspace adopts a three-surface model for media and client scripts.

### 1. `src/content/**/assets/` is the canonical editable source-asset surface

Any asset that belongs to a page, section, or component content bundle and should benefit from build-time optimization lives under:

- `src/content/pages/<name>/assets/`
- `src/content/sections/<name>/assets/`
- `src/content/components/<name>/assets/`

This includes raster images and other importable media used by content entries or block props.

These files are **source assets**, not passthrough files. They are expected to enter the Astro/Vite graph through one of two mechanisms:

- relative imports from `.astro` / `.ts` modules, or
- content-collection schemas using Astro's `image()` resolver against relative paths from the owning `.md` entry.

### 2. `src/content/**/<name>.client.ts` is the canonical feature-scoped script surface

A feature bundle may carry one colocated client entry module:

- `src/content/pages/<name>/<name>.client.ts`
- `src/content/sections/<name>/<name>.client.ts`
- `src/content/components/<name>/<name>.client.ts`

These files are reserved for behavior that is owned by a single content bundle and is edited as part of that bundle.

They are **not** a replacement for `src/scripts/`.

- `src/scripts/` remains the canonical home for app-global, layout-global, vendor, orchestration, and reusable behavioral modules.
- `src/content/**/<name>.client.ts` is for feature-local entry modules only.
- Shared logic imported by a feature-scoped entry should live in `src/scripts/` or a shared package; the colocated file is the bundle-owned adapter, not a dumping ground.

### 3. `public/` is reserved for direct-URL passthrough artifacts

`public/` contains only files whose runtime contract depends on a stable literal URL and no bundler intervention.

Canonical examples:

- `robots.txt`
- `favicon.ico`
- `site.webmanifest`
- `browserconfig.xml`
- `.well-known/**`
- verification files for search engines / PKI / app links
- legal downloads that must keep a literal path
- any file intentionally referenced as a fixed URL and not imported into source code

`public/` is therefore **not** the default home for editable images just because they are images.

## Design

### Canonical layout

```text
apps/*/src/
├── content.config.ts
├── content/
│   ├── pages/<name>/
│   │   ├── <name>.<lang>.md
│   │   ├── <name>.client.ts        # optional, feature-scoped entry module
│   │   └── assets/                 # canonical editable source assets
│   ├── sections/<name>/
│   │   ├── <name>.<lang>.md
│   │   ├── <name>.client.ts        # optional
│   │   └── assets/
│   ├── components/<name>/
│   │   ├── <name>.<lang>.md
│   │   ├── <name>.client.ts        # optional
│   │   └── assets/
│   ├── business/
│   └── loaders/
├── pages/
├── styles/
├── scripts/                        # app-global only
└── assets/                         # app-global imported assets only
    ├── favicon.ico
    └── og-image.png

apps/*/public/
├── robots.txt
├── site.webmanifest
├── .well-known/**
└── downloads/**                    # stable direct-URL files only
```

### Client-editable surface

If this RFC is accepted, the client-editable surface becomes:

| Path pattern | Meaning |
| --- | --- |
| `apps/<app>/src/content/**/*.md` | content entries |
| `apps/<app>/src/content/**/assets/**/*.{jpg,jpeg,png,webp,avif,gif,svg,pdf,mp4,webm}` | feature-owned editable source assets |
| `apps/<app>/src/content/**/<name>.client.ts` | feature-scoped client entry modules |
| `apps/<app>/src/content/business/**/*.{yaml,yml}` | business data |
| `apps/<app>/src/content/features/**/*.{md,yaml,yml}` | feature-graph content |
| `apps/<app>/system.yaml` partial keys only | unchanged partial-edit rule |

Engineering-only surfaces remain unchanged, including `src/pages/`, `src/layouts/`, `src/middleware/`, `src/scripts/`, `astro.config.*`, and app-global `src/assets/`.

### Validation changes

If accepted, the following command contracts change:

| Command | Change |
| --- | --- |
| `assets.structure.lint` | Must allow raster files under `src/content/**/assets/` and `src/assets/`; must reject raster files elsewhere in `src/`. |
| `app.layout.validate` | Must enforce canonical presence/absence rules for `src/content/**/assets/`, forbid `src/assets/images/**` legacy trees, and reserve `public/` for direct-URL passthrough categories. |
| `client.edit.validate` | Must include `src/content/**/assets/**` and bounded `*.client.ts` as client-editable; must continue rejecting app-global `src/scripts/**`. |
| `scripts.placement.validate` | Must recognize feature-scoped `src/content/**/<name>.client.ts` as valid entry modules while preserving RFC-0011 placement classes for app-global behavior. |
| `onboarding.scaffold` | Must generate the clarified source layout and stop teaching `public/images/` as the default image home. |
| `app.contract.full` | Must aggregate the updated validator semantics. |

### Proposed new validator

```sh
pnpm exec site-kernel run content.asset.resolve.validate --app nicaragua-projekt
```

Responsibility:

- walks `src/content/**/*.md`,
- finds relative asset references in frontmatter fields covered by the page/component schemas,
- verifies each referenced file exists under the owning bundle's `assets/` directory,
- ensures references resolve to source assets rather than accidental `public/` URLs when the field is declared as an importable content asset.

This command is optional as a separate surface; the same checks may also be absorbed into `page.block.validate` and sibling content validators if that yields a cleaner implementation.

- Update `onboarding.scaffold` templates and smoke tests.
- Add `content.asset.resolve.validate` if needed.

### Phase 3 — App proving in `nicaragua-projekt`

- Move feature-owned editable images from `public/images/` or legacy `src/assets/images/` into `src/content/**/assets/`.
- Move feature-owned editable scripts into colocated `*.client.ts` entry files where appropriate.
- Leave only literal-URL files in `public/`.
- Run `app.contract.full --app nicaragua-projekt`.

## Alternatives considered

1. **Keep all editable images in `public/`.** Rejected. It maximizes URL simplicity at the cost of build-time optimization, hashed invalidation, and source colocation.
2. **Use only root `src/assets/`, never `src/content/**/assets/`.\*\* Rejected. It restores a parallel-tree model and weakens bundle locality.
3. **Put feature scripts in `public/scripts/`.** Rejected. This bypasses Astro bundling and repeats the exact problems RFC-0011 was created to prevent.
4. **Allow arbitrary TypeScript under `src/content/`.** Rejected. Only bounded feature entry modules are in scope; shared or app-global logic still belongs elsewhere.

## Risks

- **Client-editable code risk.** Allowing `*.client.ts` on the editable surface increases the chance of build breaks. Mitigated by keeping the scope narrow, validating imports, and preserving engineering-only status for app-global script infrastructure.
- **Validator complexity.** `assets.structure.lint`, `app.layout.validate`, and `scripts.placement.validate` must all change together. Mitigated by making RFC-0031 the single source of truth for the boundary.
- **Migration churn.** Existing guides and scaffold templates still teach `public/images/`. Mitigated by a dedicated documentation-sync phase immediately after acceptance.
- **Relative asset reference ambiguity.** Content schemas must clearly distinguish "importable source asset" fields from literal public URLs. Mitigated by typed schema helpers and validation.

## Implementation notes for agents

- Agents MAY create and refine this RFC while it is `draft`.
- Agents MUST NOT implement the placement changes proposed here until the RFC is `accepted`.
- Until acceptance, agents MUST treat the currently accepted RFCs and active `AGENTS.md` files as the authoritative runtime policy, even where those documents are internally inconsistent.
- When this RFC is accepted, agents MUST update all touched policy surfaces in one change set: RFC references, DNA, AGENTS, validators, scaffold docs, and migration docs.
- Agents MUST NOT collapse app-global scripts into `src/content/`; the proposal is only for bounded feature-scoped entry modules.
- Agents MUST preserve `public/` for direct-URL artifacts; acceptance of this RFC does not justify moving `.well-known/**`, manifest files, or verification files into `src/`.
