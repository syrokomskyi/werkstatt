# RFC-0079: Generate AGENTS.md files for every app from templates

## Context

RFC-0078 established the generation-first discipline for engineering boilerplate in apps: every file that carries no customer-editable meaning must be derived from `src/content/system.md` via a generator command, not hand-authored after the initial scaffold. The accepted list of generated categories covers routes, styles, scripts, public infrastructure, and kernel wiring.

`AGENTS.md` files inside `apps/<site>/` are agent instruction files — they carry no visitor-facing meaning and no customer-editable content. Their purpose is to guide AI coding agents that work in a particular app workspace. Today, `apps/nicaragua-projekt/AGENTS.md` is a 462-line hand-maintained document that encodes site-specific architectural decisions (biome, content surface, page composition patterns, generated-file contracts, routing conventions) on top of a shared structural template.

Every new app built via `onboarding.scaffold` needs an equivalent `AGENTS.md`. Currently, that file is either:

1. Partially generated by `onboarding.scaffold` as a one-time stamp (opaque copy of `nicaragua-projekt/AGENTS.md` with a few substitutions), or
2. Left absent, relying on agents to infer rules from `apps/AGENTS.md` and root `AGENTS.md`.

Neither option is sustainable. A hand-stamped copy becomes stale as shared patterns evolve (e.g., RFC-0047 migration, RFC-0048 routing, new generated files). An absent app-level `AGENTS.md` forces agents to guess site-specific invariants from cross-app guides.

RFC-0078 also established that templates live under `packages/os/site-kernel-codegen/src/templates/app-boilerplate/` (mirroring the target app path) and use `{{TOKEN}}` substitution. The same mechanism should apply to `AGENTS.md`.

## Problem

**Problem 1 — Stale per-app AGENTS.md after shared-pattern changes.** When a cross-app rule changes (e.g., a new RFC, a renamed command, a new content domain), the app-level `AGENTS.md` must be manually updated. With multiple apps, this creates linear maintenance cost identical to the one RFC-0078 addressed for engineering boilerplate.

**Problem 2 — New apps bootstrapped with partial or missing agent instruction.** `onboarding.scaffold` does not currently generate a complete `AGENTS.md`. New apps start with a guidance deficit that agents must infer from higher-level guides, increasing error risk on app-specific decisions (biome, content surface, page patterns, generated files).

**Problem 3 — AGENTS.md content is 90% shared boilerplate.** The current `nicaragua-projekt/AGENTS.md` contains the following sections, nearly all of which are structural templates parameterised by a handful of per-app values:

- Workspace role (same across all apps)
- How this app is wired — file tree diagram (parameterised by `app` name)
- Site invariants (shared with minor per-app overrides)
- Business layer wiring (identical structure, already shared in `apps/AGENTS.md`)
- Content architecture — block-declarative pages (identical, already in `apps/AGENTS.md`)
- Standard page composition for the biome (parameterised by `biome` and `languages`)
- Generated files table (parameterised by the app's generated-file set, derived from `system.md`)
- Local rule map (parameterised by which sub-directory `AGENTS.md` files exist)
- Script placement rules (identical across all apps)

The only truly site-specific sections are the biome-specific page composition patterns and the canonical block composition for the site's biome type.

## Decision

The site OS gains an `agents.generate` command in `@gogol/site-kernel-codegen` that generates `apps/<app>/AGENTS.md`, `apps/<app>/src/content/AGENTS.md`, and `apps/<app>/src/styles/AGENTS.md` from templates stored under `packages/os/site-kernel-codegen/src/templates/app-boilerplate/` alongside the other RFC-0078 boilerplate templates. The command follows the RFC-0078 generation-first discipline:

- Templates mirror the target app path: `AGENTS.md.template` → `apps/<app>/AGENTS.md`.
- Token syntax: `{{TOKEN}}` literal replacement at runtime (same as all other generators).
- Generated files carry a `<!-- GENERATED BY agents.generate -->` header comment so drift detection can identify them.
- `onboarding.scaffold` calls `agents.generate` as a post-scaffold step so new apps always start with a complete agent instruction file.
- Drift detection is provided by `app.boilerplate.validate` (RFC-0078), which runs `agents.generate` in dry-run mode alongside all other boilerplate generators.

## Architectural fit

**RFC-0078 (Generation-first).** This RFC extends the RFC-0078 generation-first principle to the `AGENTS.md` layer. The discipline is identical: templates co-located with other app-boilerplate templates in `site-kernel-codegen`, `{{TOKEN}}` substitution, `GENERATED BY` header, drift detection via `app.boilerplate.validate`.

**RFC-0029 / RFC-0075 (Onboarding).** `onboarding.scaffold` gains `agents.generate` as a post-scaffold step alongside the existing generators. This keeps the scaffold templates in `site-kernel-onboarding` focused on content skeleton while agent instruction generation moves to `site-kernel-codegen`.

**RFC-0047 (CMS-friendly content surface).** `AGENTS.md` files are explicitly outside `src/content/` and are never CMS-editable. They belong in the engineering surface that RFC-0078 targets for generation.

**AP-7 (Dead configuration).** By deriving `AGENTS.md` from templates, agents who work on any app always get an up-to-date instruction file after running `agents.generate`.

## Design

### Template structure

Templates live inside the existing `app-boilerplate` directory, co-located with all other RFC-0078 boilerplate templates:

```
packages/os/site-kernel-codegen/src/templates/app-boilerplate/
├── AGENTS.template.md              ← → apps/<app>/AGENTS.md
├── src/
│   ├── content/
│   │   └── AGENTS.template.md      ← → apps/<app>/src/content/AGENTS.md
│   └── styles/
│       └── AGENTS.template.md      ← → apps/<app>/src/styles/AGENTS.md
│   └── ... (other RFC-0078 templates)
└── public/ (other RFC-0078 templates)
```

All three templates are generated in the first iteration. The hierarchy mirrors the target app path, consistent with how `global.template.css`, `index.template.astro`, and other boilerplate templates are organised.

### Token set

Tokens are resolved from `src/content/system.md` plus the brief contract:

| Token | Source | Example |
| --- | --- | --- |
| `{{APP_ID}}` | `system.md app` | `nicaragua-projekt` |
| `{{APP_NAME_DISPLAY}}` | `system.md identity.tagline` (falls back to `app`) | `Aufbauarbeit für Nicaragua` |
| `{{BIOME_ID}}` | `system.md identity.biome` | `nonprofit-trust` |
| `{{BIOME_DISPLAY_NAME}}` | `packages/ontology/biomes/<id>.yaml displayName` (falls back to `biome id`) | `Nonprofit Trust` |
| `{{DEFAULT_LANG}}` | `system.md i18n.default` | `de` |
| `{{SUPPORTED_LANGS}}` | `system.md i18n.supported` keys joined with `, ` | `de, en` |

Tokens that are missing in `system.md` fall back to safe placeholder values (e.g., `{{APP_NAME_DISPLAY}}` → `{{APP_ID}}`). The command never exits non-zero due to missing optional tokens.

### Command contract

```
pnpm exec werkstatt run agents.generate --app <app>
```

Flags:

- `--app <id>` — target app under `apps/<id>/`; required.
- `--dry-run` — print what would be written without writing.
- `--json` — emit structured JSON result (uniform with other generators).

**TypeScript contract** (shared `GeneratedResult` shape from `app-boilerplate.ts`):

```ts
interface GeneratedResult {
  command: string;          // "agents.generate"
  status: "ok" | "fail";
  generated: string[];      // relative paths of files written
  warnings?: { file: string; message: string }[];
}
```

Drift detection is provided by including `runGenerateAgentsDocs` in `runAppBoilerplateValidate` (dry-run mode), consistent with all other RFC-0078 generators. There is no separate `--check` flag.

### Scaffold-once semantics

When `onboarding.scaffold` calls `agents.generate` as a post-scaffold step:

- If `apps/<app>/AGENTS.md` does not yet exist → generate it.
- If `apps/<app>/AGENTS.md` already exists **and** carries the `GENERATED BY agents.generate` header → overwrite (regenerate).
- If `apps/<app>/AGENTS.md` already exists **without** the `GENERATED BY` header → skip with a warning (hand-authored file, user must opt in to generation).

This matches the scaffold-once semantics described in RFC-0078 for other generated files.

### Generated file header

Every generated `AGENTS.md` starts with:

```markdown
<!-- GENERATED BY agents.generate — DO NOT EDIT -->
<!-- Re-run: pnpm exec werkstatt run agents.generate --app {{APP_ID}} -->
```

### Pipeline integration

`agents.generate` is added to `STANDARD_BUILD_PREPARE_PIPELINE` alongside the RFC-0078 generators:

```ts
export const STANDARD_BUILD_PREPARE_PIPELINE: PipelineDef = [
  { command: "agents.generate" },          // ← new
  { command: "overlay.pages.generate" },
  { command: "routes.generate" },
  { command: "styles.global.generate" },
  // ... existing entries
];
```

`runGenerateAgentsDocs` is added to the `commands` array inside `runAppBoilerplateValidate`, so drift in any of the three AGENTS.md files is reported by `app.boilerplate.validate` alongside all other RFC-0078 stale-file checks.

## Alternatives considered

**Keep AGENTS.md hand-authored, enforce via review.** This was rejected because it reproduces the linear-scaling maintenance problem RFC-0078 solved for engineering boilerplate. Every shared pattern change requires manual propagation to all app-level `AGENTS.md` files.

**Merge all app guidance into apps/AGENTS.md (no app-level file).** This was rejected because app-level `AGENTS.md` carries biome-specific page composition patterns, generated-file contracts, and routing rules that differ meaningfully per site. Putting all of that in the shared file would make it unwieldy and force agents to filter out irrelevant guidance on every change.

**Generate only a minimal stub, leave the rest hand-authored.** This was rejected because it still requires manual maintenance of the majority of the file. A generated stub that is immediately extended by hand loses the regenerability property.

**One template per biome (instead of one universal template with tokens).** This was considered as an extension. In the first iteration, a single universal template with `{{BIOME_DISPLAY_NAME}}` and `{{BIOME_ID}}` tokens covers all biomes. Per-biome template variants may be added as follow-up if the canonical page composition diverges sufficiently between biomes.

**Separate `templates/agents/` directory (instead of co-locating with `app-boilerplate`).** An isolated `templates/agents/` directory was created initially but moved into `templates/app-boilerplate/` to maintain a single consistent hierarchy that mirrors the target app path. This matches the established convention for all other RFC-0078 boilerplate templates and eliminates the need for a second `readTemplate` helper.

## Risks

**Risk: Template diverges from hand-authored AGENTS.md in nicaragua-projekt.** Mitigation: `agents.generate --check` run in `app.boilerplate.validate` surfaces drift immediately. The migration step (below) adopts the template-generated version for nicaragua-projekt first, so the template is validated against the reference app.

**Risk: Generated AGENTS.md is too generic and misses app-specific edge cases.** Mitigation: The `{{BIOME_DISPLAY_NAME}}` / `{{BIOME_ID}}` tokens and the biome-specific page composition section ensure the most app-specific content is parameterised. Genuinely site-unique rules that cannot be captured by a token can be added to the `## Site-specific notes` section at the end of `AGENTS.md.template`. The generator extracts and preserves this section when regenerating an existing file, so manual additions are never lost.

**Risk: Agents ignore the `GENERATED BY` header and edit the file manually.** Mitigation: The header is prominent and includes the re-run command. `agents.generate --check` in `app.boilerplate.validate` provides automatic enforcement on the next build.

## Implementation notes for agents

- Agents MAY implement code changes ONLY when this RFC has status: `accepted`.
- Agents MUST NOT change the `status` field of this or any other RFC.
- Implementation is in `packages/os/site-kernel-codegen/src/app-boilerplate.ts` (`runGenerateAgentsDocs`). It reuses `readTemplate`, `applyTokens`, and `runGeneratedFileSet` — the same helpers used by all other RFC-0078 generators.
- Token resolution: `APP_ID` / `BIOME_ID` / `DEFAULT_LANG` / `SUPPORTED_LANGS` from `loadSystemManifestSync`; `APP_NAME_DISPLAY` from `identity.tagline` with `app` fallback; `BIOME_DISPLAY_NAME` from `packages/ontology/biomes/<id>.yaml` `displayName` field with `biome id` fallback.
- The `## Site-specific notes` section in `AGENTS.md.template` is preserved on regeneration: `runGenerateAgentsDocs` extracts any hand-written content from that section in the existing file before overwriting.
- Templates live in `packages/os/site-kernel-codegen/src/templates/app-boilerplate/` alongside all other RFC-0078 boilerplate templates. No separate template directory.
- Agents MUST NOT weaken or remove the generation-first principle established by RFC-0078 and extended here.
