# RFC-0078: Generate engineering boilerplate in apps for radically thin client sites

## Context

RFC-0047 established the CMS-friendly content surface: customer-editable content lives in `src/content/` under five semantic domains (pages, prose, business, navigation, site). RFC-0049 established the build-prepare pipeline pattern where generated artifacts are written into the project tree before `astro build`. RFC-0029 defined `onboarding.scaffold` as the canonical new-app generator.

The reference app `nicaragua-projekt` today contains ~73 customer-editable files (markdown + images) and ~36 engineering-only files that carry no business meaning. The 36 engineering files span 7 categories: config files, tooling wiring, thin entrypoints, infrastructure content pages, public/ boilerplate, scripts, and styles.

Every new app that is scaffolded (`onboarding.scaffold`) inherits this same engineering surface. When a shared package adds or changes a command, every existing app's `tools/` directory must be manually updated. This scales linearly with the number of apps and is a source of silent drift.

The architecture reachable today: app = content + thin routes + tools wiring + config boilerplate. The target architecture: app = content only, with everything else generated from `src/content/system.md`.

## Problem

Seven categories of engineering-only files in every app are currently hand-maintained after the initial scaffold, creating architectural debt:

**Category 1 — Overlay content pages (5 files).** `src/content/pages/{lang}/cosmic/passport.md`, `cosmic/star-map.md`, and `pages/root-redirect.md` are pure engineering artifacts. They exist as markdown files only because `src/pages/[lang]/[...slug].astro` resolves all pages through content collections. They are indistinguishable from customer content to a casual reader. Currently created by `onboarding.scaffold` but never regenerated.

**Category 2 — Thin engineering entrypoints (5 files).** `src/pages/index.astro`, `src/pages/[lang]/[...slug].astro`, `src/middleware.ts`, `src/content.config.ts`, `src/env.d.ts`. These are stable boilerplate patterns generated by `onboarding.scaffold` but thereafter hand-maintained. If the catch-all route's `buildPage` contract changes, every app must update its `[...slug].astro` by hand.

**Category 3 — Styles boilerplate (1 file).** `src/styles/global.css` imports token packages, sets CSS layer ordering, and declares the Volume Edge contract. The only app-specific part is the biome import path, which is already known from `system.md identity.biome`. Currently scaffolded once, never regenerated.

**Category 4 — Client-side orchestrator (1 file).** `src/scripts/layout-orchestrator.ts` calls `runStandardLayoutOrchestration` from `@gogol/share/scripts`. It is identical across apps modulo the `headerOffset` parameter.

**Category 5 — Public/ infrastructure files (5 files).** `public/robots.txt`, `_headers`, `.assetsignore`, `ai.txt`, `studio.public.pem`. Some are already generated (sitemaps, llms), but the remaining five are hand-authored or scaffolded once. `studio.public.pem` is part of the passport pipeline — its generation is split between `onboarding.scaffold` and `passport.key.rotate`.

**Category 6 — Tools/kernel wiring (12 files).** The entire `tools/` directory (`kernel.config.ts`, `modules/*.ts`, `runtime/*.ts`) consists of thin re-exports and module registrations. These files exist only to wire packages into the site OS. Adding a new check command to `@gogol/site-kernel-checks` requires touching every app's `check.module.ts`. Removing a module requires touching every app. There is no mechanism to derive the tooling configuration from `system.md`.

**Category 7 — Root config files (7 files).** `astro.config.mjs`, `tsconfig.json`, `postcss.config.cjs`, `wrangler.jsonc`, `package.json`, `.gitignore`, `.markdownlint.json`. Currently scaffolded once from `site-kernel-onboarding` templates. When the stack evolves (e.g., Astro 7, new integration), there is no command to regenerate them.

**The risk is linear scaling.** With 4 apps, the engineering surface is 4 × 36 = 144 files. With 10 apps, 360 files. Each addition to a shared package requires touching all apps, and non-compliant apps silently diverge.

## Decision

The site OS gains a set of generation commands that derive engineering artifacts from the canonical manifest (`src/content/system.md`) plus a small per-app configuration surface. The commands follow the pattern established by RFC-0049: write artifacts into the project tree, not into `dist/`.

The seven categories are addressed in three tiers:

**Tier 1 — immediate generation (Categories 1, 4, 5).** New standalone commands in `@gogol/site-kernel-codegen` that generate overlay pages, the orchestrator script, and public/ infrastructure files. These are low-risk, side-effect-free generators that read `system.md`.

**Tier 2 — derived entrypoints (Categories 2, 3).** Thin entrypoints become regenerable from templates in `@gogol/site-kernel-codegen`, using the existing template + `{{VAR}}` substitution model from `site-kernel-onboarding`. A single `routes.generate` command replaces `index.astro`, `[...slug].astro`, `middleware.ts`, `content.config.ts`, and `global.css`.

**Tier 3 — kernel wiring (Category 6).** A new `kernel.wire` command in `@gogol/site-kernel` reads `system.md` feature flags (passport, growth, integrity, changelog, etc.) and generates the complete `tools/` directory. The command is idempotent and safe to run after every change to `system.md`.

Category 7 (root configs) remains scaffold-generated. A `config.regenerate` command is added as a safety net for stack upgrades, but these files are too environment-specific to fully template. They remain in version control and are updated via `onboarding.scaffold --force` or `config.regenerate`.

## Architectural fit

**DNA-22 (Client-editable surface).** This RFC extends the client-editable whitelist principle. Currently DNA-22 defines which paths CMS editors may touch. After this RFC, the _inverse_ is also explicit: everything outside `src/content/{business,pages,prose,navigation,site}/**` and `system.md` is _generated_, not hand-authored. The `client.edit.validate` gate gains a companion `app.generated.check` that verifies generated files are not stale.

**DNA-36 (Readiness).** The RFC lowers the barrier to `app.contract.full` passing. When engineering files are generated, the validators can check freshness (are the generated files up to date with `system.md`?) instead of checking hand-maintained correctness.

**RFC-0049 (Build output invariant).** All seven categories write into the project tree (`src/`, `public/`, `tools/`, root), never into `dist/`. The existing `STANDARD_BUILD_PREPARE_PIPELINE` grows new steps for the new generators.

**RFC-0029 / RFC-0075 (Onboarding).** `onboarding.scaffold` continues to generate the initial app skeleton, but the new generators are called as post-scaffold steps so the engineering files are derived, not stamped. This keeps the template count in `site-kernel-onboarding` stable while the generation logic moves to `site-kernel-codegen`.

**AP-7 (Dead configuration).** By deriving tools/ from `system.md`, the kernel eliminates per-app configuration that becomes stale when a module is added to or removed from a package.

## Design

### Category 1 — Overlay pages (`overlay.pages.generate`)

```
pnpm exec werkstatt run overlay.pages.generate --app <app>
```

Reads `system.md` and determines which overlay pages the app needs:

- `release.passport.enabled: true` → generate `cosmic/passport.md` (DE + EN)
- `release.passport.enabled: true` → generate `cosmic/star-map.md` (DE + EN)
- Always → generate `root-redirect.md`

Each overlay page is a frontmatter-only `.md` with `blocks[]` that reference standard sections from `@gogol/ui`. The generated content is indistinguishable from hand-authored customer pages: same `kind: page`, `pageId`, `blocks[]`, `cosmicStar` pattern.

**TypeScript contract:**

```ts
interface OverlayPagesInput {
  app: string;
  lang: string[];
}

interface OverlayPagesResult {
  command: "overlay.pages.generate";
  status: "ok" | "fail";
  generated: string[];
}
```

**File system:** | Path | Role | |---|---| | `system.md` | Read for passport/growth feature flags | | `src/content/pages/{lang}/cosmic/passport.md` | Generated if passport enabled | | `src/content/pages/{lang}/cosmic/star-map.md` | Generated if passport enabled | | `src/content/pages/root-redirect.md` | Always generated |

**Failure mode:** Writes files idempotently. Exits non-zero if `system.md` is unreadable. Warns if a hand-authored overlay page exists with unexpected content (stale drift detection).

---

### Category 2 — Thin entrypoints (`routes.generate`)

```
pnpm exec werkstatt run routes.generate --app <app>
```

Generates from internal templates:

- `src/pages/index.astro` — `<RootRedirectContent />` wrapper
- `src/pages/[lang]/[...slug].astro` — `resolvePageRoute` + `BlocksRenderer` loop
- `src/middleware.ts` — `sequence(languageRedirect)` middleware chain
- `src/content.config.ts` — `defineCollection(...)` for each content domain, including `businessCollections` spread
- `src/env.d.ts` — `/// <reference types="astro/client" />` + Cloudflare Env if applicable

Templates live in `packages/os/site-kernel-codegen/templates/routes/` using the `{{VAR}}` substitution model already established by `site-kernel-onboarding`.

**File system:** | Path | Role | |---|---| | `src/pages/index.astro` | Generated | | `src/pages/[lang]/[...slug].astro` | Generated | | `src/middleware.ts` | Generated | | `src/content.config.ts` | Generated | | `src/env.d.ts` | Generated |

**Failure mode:** All files are overwritten. The command warns if any file differs from its template content (to surface manual changes that may need porting), but overwrites regardless. Exits non-zero on parse errors in `system.md`.

---

### Category 3 — Styles boilerplate (`styles.global.generate`)

```
pnpm exec werkstatt run styles.global.generate --app <app>
```

Reads `system.md identity.biome` and generates `src/styles/global.css` with:

- `@import "@gogol/tokens/tokens.css"`
- `@import "@gogol/tokens/biomes/{biome}.css"` (resolved from biome ID)
- CSS layer ordering (`tokens`, `biome`, `base`, `components`, `pages`)
- Volume Edge contract (`[data-volume]` attribute selectors)
- Base element resets

The biome-specific import is the only variable. The rest is stable boilerplate owned by `site-kernel-codegen`.

**Failure mode:** Overwrites `global.css` entirely. Warns if the existing file has custom additions outside the expected pattern. Exits non-zero if biome ID is unknown.

---

### Category 4 — Client-side orchestrator (`scripts.orchestrator.generate`)

```
pnpm exec werkstatt run scripts.orchestrator.generate --app <app>
```

Generates `src/scripts/layout-orchestrator.ts`:

```ts
import { runStandardLayoutOrchestration } from "@gogol/share/scripts";

runStandardLayoutOrchestration({ headerOffset: 80 });
```

The `headerOffset` value is read from `system.md` if declared, otherwise defaults to `80`. The import path is always `@gogol/share/scripts`.

**Failure mode:** Overwrites existing orchestrator. If the existing file has custom imports beyond the standard pattern, the command logs a warning and emits placeholder `<-- CUSTOM_SCRIPT -->` markers for the developer to re-apply.

---

### Category 5 — Public/ infrastructure (`public.infrastructure.generate`)

```
pnpm exec werkstatt run public.infrastructure.generate --app <app> --domain <fqdn>
```

Generates from templates:

| File                   | Source                                     |
| ---------------------- | ------------------------------------------ |
| `public/robots.txt`    | Template with domain                       |
| `public/_headers`      | Cloudflare security headers, domain-aware  |
| `public/.assetsignore` | Standard Cloudflare assets ignore patterns |
| `public/ai.txt`        | AI crawling policy                         |

Does NOT generate `studio.public.pem` (that lives in the passport pipeline), `favicon.svg` (too brand-specific), or sitemaps/llms (already generated elsewhere).

**Failure mode:** Overwrites files. Exits non-zero if `--domain` is missing. The `_headers` file is mostly commented-out by default (as in the current app) and only activates when explicitly configured.

---

### Category 6 — Kernel wiring (`kernel.wire`)

```
pnpm exec werkstatt run kernel.wire --app <app>
```

This is the most impactful command. It reads `system.md` and generates the entire `tools/` directory.

**How it works:**

1. Reads `system.md` for feature flags:
   - `release.passport.enabled` — enables integrity module
   - `growth.vendor.adapter` — determines if changelog is relevant
   - System-level: which packages are installed in `package.json`

2. Generates `tools/kernel.config.ts` with pipelines composed from detected modules:
   - Always: check pipeline (APPS_CHECK_PIPELINE from site-kernel-checks)
   - Always: build.prepare pipeline (STANDARD_BUILD_PREPARE_PIPELINE)
   - If passport enabled: integrity, sign, verify pipelines
   - If changelog module registered: changelog pipeline

3. Generates `tools/modules/` files:
   - `check.module.ts` — always (uses `createStandardCheckModule`)
   - `service.module.ts` — always (icons, open-source)
   - `changelog.module.ts` — if `@gogol/site-kernel-changelog` is in dependencies
   - `deploy.module.ts` — always
   - `integrity.module.ts` — if `release.passport.enabled`

4. Generates `tools/runtime/` files as thin re-exports:
   - Each `runtime/*.ts` is a pass-through: `export { ... } from "@gogol/package"`

**TypeScript contract:**

```ts
interface KernelWireInput {
  app: string;
  systemManifest: SystemManifest; // parsed system.md
}

interface KernelWireResult {
  command: "kernel.wire";
  status: "ok" | "fail";
  generated: string[];       // files written
  modulesDetected: string[]; // modules identified from system.md
  modulesSkipped: string[];  // modules whose packages are not installed
}
```

**File system:** | Path | Role | |---|---| | `tools/kernel.config.ts` | Generated | | `tools/modules/*.ts` | Generated (4–5 files) | | `tools/runtime/*.ts` | Generated (4–6 files) |

Generated files include a header comment:

```ts
// GENERATED BY kernel.wire — DO NOT EDIT
// Re-run: pnpm exec werkstatt run kernel.wire --app <app>
```

**Failure mode:** Exits non-zero if `system.md` is unreadable. Overwrites all files in `tools/`. The `.gitignore` includes `tools/` (or a user chooses to commit generated wiring). Drift detection: `kernel.wire --check` exits non-zero if generated files differ from expected output.

---

### Category 7 — Root config regeneration (`config.regenerate` or `onboarding.scaffold --force`)

```
pnpm exec werkstatt run config.regenerate --app <app> [--force]
```

Re-applies `site-kernel-onboarding` templates to root config files. Uses the same `{{VAR}}` substitution as the initial scaffold. Only regenerates files that match the template structure; preserves custom additions.

This is explicitly a **safety net**, not a daily driver. Root config files remain in version control and are rarely regenerated.

**File system:** | Path | Role | |---|---| | `astro.config.mjs` | Regenerated (Vite aliases, integrations) | | `tsconfig.json` | Regenerated (path aliases) | | `postcss.config.cjs` | Regenerated (always identical) | | `wrangler.jsonc` | Regenerated (Cloudflare config) | | `.gitignore` | Regenerated | | `.markdownlint.json` | Regenerated (always identical) |

Does NOT touch `package.json` (dependency management is too dynamic).

All generators are added to `STANDARD_BUILD_PREPARE_PIPELINE`:

```ts
// In packages/os/site-kernel-checks/src/module.ts
export const STANDARD_BUILD_PREPARE_PIPELINE: PipelineDef = [
  { command: "overlay.pages.generate" },
  { command: "routes.generate" },
  { command: "styles.global.generate" },
  { command: "scripts.orchestrator.generate" },
  { command: "public.infrastructure.generate" },
  { command: "biome.css.generate" },
  { command: "open-source.generate" },
  { command: "icons.generate" },
  { command: "sitemap.generate" },
  { command: "i18n.middleware.generate" },

```

`kernel.wire` remains a standalone command (not in the build pipeline), because changing `tools/` affects the kernel runtime itself and should be an explicit developer action.

### Output format (common across all six generators)

All generators return a uniform JSON structure:

```json
{
  "command": "routes.generate",
  "status": "ok",
  "generated": [
    "src/pages/index.astro",
    "src/pages/de/[...slug].astro",
    "src/middleware.ts",
    "src/content.config.ts",
    "src/env.d.ts"
  ],
  "warnings": [
    {
      "file": "src/pages/[lang]/[...slug].astro",
      "message": "File had custom additions — overwritten. Check git diff."
    }
  ]
}
```

## Rollout

**For new apps.** `onboarding.scaffold` calls all generators as post-scaffold steps. The scaffold templates in `site-kernel-onboarding` are reduced: they only create the content skeleton (`src/content/`), not the engineering boilerplate. The engineering files are derived by the generators.

**For existing apps.** A migration command runs all generators against nicaragua-projekt and any other existing apps. The generated files are compared to current files; manual additions (e.g., custom middleware logic, custom route logic) are surfaced as warnings. The developer inspects the diff and commits the generated output.

**Validation.** A `--check` flag on every generator (and a meta `app.boilerplate.validate` command) verifies that generated files are not stale. This runs in `build.check` as a warning, not a hard failure, during a transition period. After all apps migrate, it graduates to a hard failure.

**Deprecation.** No existing commands are removed. `kernel.wire` complements rather than replaces `createStandardCheckModule`. The module registration API remains available for apps that need custom registrations beyond what `system.md` describes.

## Alternatives considered

**Auto-discovery (instead of `kernel.wire`).** The kernel could detect installed packages at runtime and auto-register their commands without any `tools/` files. This was rejected because: (a) it makes the module registration invisible — a developer cannot see which commands are available without running the kernel; (b) it couples package installation to CLI availability, which is fragile; (c) the `tools/` directory documents the app's OS surface explicitly and is useful for debugging.

**Hand-rolled generation per-file (instead of `routes.generate` monolithic command).** Each entrypoint could have its own command (`pages.index.generate`, `pages.catchall.generate`, `content.config.generate`, etc.). This was rejected because it over-fragments the CLI surface. All five thin entrypoints are generated together, regenerate as a unit, and are almost never regenerated independently.

**Gitignore all generated files (including `tools/`).** This was rejected because generated engineering files should be auditable in code review. Only truly transient artifacts (biome.generated.css, language-redirect.ts) remain gitignored.

**Moving `astro.config.mjs` into a shared package.** This was rejected because Vite aliases and integrations are inherently app-specific. Template regeneration via `config.regenerate` is sufficient.

## Risks

**Risk: Developers hand-edit generated files.** Mitigation: every generated file contains a `GENERATED BY` header comment. Drift detection via `--check` flags catches deviations. The build pipeline will eventually fail on drift.

**Risk: `kernel.wire` output does not match the developer's intention.** Mitigation: `kernel.wire --dry-run` shows what would be generated without writing files. The developer commits the generated output and reviews it.

**Risk: Template versioning.** If `packages/os/site-kernel-codegen` updates a template, existing apps keep the old generated output until they re-run the generator. Mitigation: `build.prepare` runs generators on every build, so templates update automatically on the next CI run.

**Risk: Breakage when a generator is run on an app with custom wiring.** Mitigation: generators produce warnings for unexpected file content. The `routes.generate` command is designed to be safe — it overwrites standard routing and middleware, which should be thin by contract (DNA-25 enforces thin routes).

**Risk: `kernel.wire` lock-in.** Apps that genuinely need custom module registrations can opt out by marking `tools/` as hand-authored in `system.md` (`tools.managed: false`). The validator skips generation and does not flag drift.

## Implementation notes for agents

- Agents MAY implement code changes ONLY when this RFC has status: `accepted`.
- Agents MUST NOT change the `status` field of this or any other RFC.
- Implementation order is Tier 1 → Tier 2 → Tier 3; each tier is independent and mergcable.
- Tier 1 generators (`overlay.pages.generate`, `scripts.orchestrator.generate`, `public.infrastructure.generate`) follow the pattern of `open-source.generate` in `site-kernel-codegen/src/service.ts` — same function signature, same template approach.
- Tier 2 (`routes.generate`, `styles.global.generate`) extends `site-kernel-codegen` with a new `src/routes.ts` and `src/styles.ts` module. Templates live in `templates/routes/` and `templates/styles/`.
- Tier 3 (`kernel.wire`) adds a new `src/wire.ts` module in `@gogol/site-kernel`. It consumes `loadSystemManifest` from `@gogol/site-kernel-content` and writes files using the atomic-fs pattern from `site-kernel-integrity`.
- When implementing, agents MUST reference this RFC ID as `Implements RFC-0078` in commit messages and PR descriptions.
- Agents MUST NOT weaken or remove the generation-first principle established by this RFC without a new superseding RFC.
- Agents MUST run `kernel.wire --dry-run` against nicaragua-projekt as a validation step before producing a PR.
