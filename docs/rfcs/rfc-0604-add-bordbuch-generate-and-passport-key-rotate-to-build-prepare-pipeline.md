# RFC-0604: Add bordbuch.generate and passport.key.rotate to build.prepare pipeline

## Context

A public folder regeneration experiment on warpgogol-com (2026-07-30) revealed that `build.prepare` does not include two commands that produce git-tracked public artifacts:

1. **`bordbuch.generate`**: Produces `public/.well-known/bordbuch.json` and `public/.well-known/bordbuch/index.html`. These files are in `GENERATOR_OWNERSHIP_MAP` and are git-tracked, but they were not regenerated by `build.prepare` and were reported as missing by `generated.files.validate`.

2. **`passport.key.rotate`**: Produces `public/.well-known/cosmic-passport-key.json`. Same issue — git-tracked, in the ownership map, but not regenerated by `build.prepare`.

The operator confirmed that both commands should be added to `build.prepare`.

## Problem

The `build.prepare` pipeline in `packages/os/site-kernel-checks/src/pipelines/build-prepare.ts` is a sequence of kernel commands that prepare the site build. It includes commands for config, routes, surface, agent manifests, styles, public infrastructure, sitemap, llms, feed, and media variants. However, it does not include `bordbuch.generate` or `passport.key.rotate`.

This means:

1. After `build.prepare`, the bordbuch and passport artifacts are missing from `public/`.
2. `generated.files.validate` (RFC-0375) reports them as missing.
3. `generated.stale.validate` (RFC-0600) may flag them as stale (if they exist from a previous build but are not regenerated).
4. The site deploys without bordbuch status or passport key files in `public/.well-known/`.

The root cause is that these commands were originally designed as separate-operator commands (not build pipeline commands) because they have side effects: `bordbuch.generate` creates git commits (bordbuch entries), and `passport.key.rotate` rotates cryptographic keys. However, their **output files** are git-tracked public artifacts that must be present after `build.prepare`.

## Decision

The `build.prepare` pipeline includes `bordbuch.generate` and `passport.key.rotate` as final steps, after all other generation commands. The dev-mode subset pipeline excludes both commands to avoid side effects (git commits, key rotation) during development.

## Architectural fit

- **DNA-18 (Uni registry is the single UI index)**: Extends the pipeline completeness principle — all git-tracked generated files must be produced by `build.prepare`.
- **RFC-0375 (generated.files.validate)**: This RFC ensures the validator passes after `build.prepare` by including the missing commands.
- **RFC-0600 (generated.stale.validate)**: This RFC ensures bordbuch and passport files are not flagged as stale.
- **RFC-0599 (open-source.generate fix)**: Related — both RFCs address output completeness from different angles.
- **Site OS operator model**: `build.prepare` is the canonical pre-build pipeline. Any command that produces git-tracked public artifacts must be in it. The dev-mode subset is for mission materialization and excludes commands with side effects.

## Design

### CLI surface

No new commands. The fix is internal to the `build.prepare` pipeline definition:

```sh
pnpm exec site-kernel run build.prepare --site warpgogol-com
```

### Pipeline changes

The `SITES_BUILD_PREPARE_PIPELINE` array in `packages/os/site-kernel-checks/src/pipelines/build-prepare.ts` is extended with two new entries at the end:

```ts
// Existing entries...
{ cmd: "media.variants.generate",     label: "Media variants" },
// New entries:
{ cmd: "bordbuch.generate",           label: "Bordbuch status" },
{ cmd: "passport.key.rotate",         label: "Passport key rotation" },
```

The dev-mode subset pipeline (`SITES_BUILD_PREPARE_DEV_SUBSET`) is NOT extended — `bordbuch.generate` and `passport.key.rotate` are excluded from dev mode because:

- `bordbuch.generate` creates git commits (bordbuch entries) which should not happen during development.
- `passport.key.rotate` rotates cryptographic keys which should only happen during a release.

### Side effect safety

- **`bordbuch.generate`**: In the context of `build.prepare`, the command should generate the public-facing bordbuch status projection (`public/.well-known/bordbuch.json` and `public/.well-known/bordbuch/index.html`) without creating new bordbuch entries. If the command's current implementation creates git commits as a side effect, it must be refactored to separate the projection generation from the entry creation. The projection generation is idempotent and safe for `build.prepare`; the entry creation is a separate operator action.
- **`passport.key.rotate`**: In the context of `build.prepare`, the command should ensure the passport key file exists (`public/.well-known/cosmic-passport-key.json`) without rotating the key if it already exists. If the key does not exist, it generates a new one. If it exists, it is a no-op. This makes it safe for `build.prepare`.

### File system responsibilities

| Path | Role |
| --- | --- |
| `packages/os/site-kernel-checks/src/pipelines/build-prepare.ts` | Fix target — add two commands to `SITES_BUILD_PREPARE_PIPELINE` |
| `packages/os/site-kernel-checks/src/generator-ownership.ts` | Reference — confirms bordbuch and passport outputs are registered |
| `public/.well-known/bordbuch.json` | Output — must exist after `build.prepare` |
| `public/.well-known/bordbuch/index.html` | Output — must exist after `build.prepare` |
| `public/.well-known/cosmic-passport-key.json` | Output — must exist after `build.prepare` |

### Failure modes

- If `bordbuch.generate` fails (e.g., no bordbuch entries in git history), the pipeline fails. The command should handle this gracefully by generating an empty projection.
- If `passport.key.rotate` fails (e.g., permissions issue), the pipeline fails. The command should report the error clearly.

## Rollout

- **Default behavior**: Both commands are active in `build.prepare` immediately upon implementation.
- **Existing apps**: Must run `build.prepare` once after implementation to generate the missing bordbuch and passport artifacts. After that, they are kept up to date automatically.
- **New apps**: Automatically benefit.
- **Dev mode**: Both commands are excluded from the dev-mode subset pipeline. Developers running `build.prepare --dev` will not see bordbuch or passport artifacts generated.
- **Side effect refactoring**: If `bordbuch.generate` or `passport.key.rotate` currently have side effects that are unsafe for `build.prepare`, they must be refactored before this RFC is implemented. The refactoring separates the projection generation (safe, idempotent) from the side-effectful operation (git commit, key rotation).

## Alternatives considered

- **Keep bordbuch.generate and passport.key.rotate as separate operator commands**: Rejected by operator. The operator confirmed that both should be in `build.prepare` to ensure their outputs are always present.
- **Add only bordbuch.generate, not passport.key.rotate**: Rejected by operator. The operator confirmed both should be added.
- **Create a separate `build.prepare.sensitive` pipeline for these commands**: Rejected — adding a third pipeline variant increases complexity. The commands are safe for `build.prepare` once side effects are separated from projection generation.
- **Add a `--no-sensitive` flag to `build.prepare`**: Rejected — the dev-mode subset already handles this. No additional flag is needed.

## Risks

- **Side effects in build.prepare**: If `bordbuch.generate` creates git commits during `build.prepare`, it could create unexpected commits during CI builds. Mitigation: refactor the command to separate projection generation from entry creation before adding to the pipeline.
- **Key rotation in build.prepare**: If `passport.key.rotate` rotates the key on every `build.prepare` run, it could invalidate existing tokens. Mitigation: the command must be idempotent — if the key file exists, it is a no-op.
- **Pipeline ordering**: Both commands must run after all other generation commands because they may depend on the site's route registry and content index. Placing them at the end of the pipeline ensures all dependencies are available.
- **Dev-mode exclusion**: Developers may expect bordbuch and passport artifacts in their local `public/` directory. If they are excluded from dev mode, developers must run the full `build.prepare` once to generate them. This is acceptable — the dev-mode subset is for fast iteration, not for producing a deployable `public/` directory.

## Acceptance criteria

- [ ] `bordbuch.generate` added to `SITES_BUILD_PREPARE_PIPELINE` after `media.variants.generate`
- [ ] `passport.key.rotate` added to `SITES_BUILD_PREPARE_PIPELINE` after `bordbuch.generate`
- [ ] Neither command is added to `SITES_BUILD_PREPARE_DEV_SUBSET`
- [ ] After running `build.prepare`, `public/.well-known/bordbuch.json` exists
- [ ] After running `build.prepare`, `public/.well-known/bordbuch/index.html` exists
- [ ] After running `build.prepare`, `public/.well-known/cosmic-passport-key.json` exists
- [ ] `generated.files.validate` passes after `build.prepare` with no missing-output errors for bordbuch or passport
- [ ] `bordbuch.generate` is idempotent in the `build.prepare` context (no new git commits on re-run)
- [ ] `passport.key.rotate` is idempotent (no key rotation if key file already exists)
- [ ] `rfc.validate` passes on this file

## Implementation notes for agents

- Agents MAY implement code changes ONLY when this RFC has status: accepted (or implemented).
- Before adding `bordbuch.generate` to the pipeline, verify that it does not create git commits when run in `build.prepare` context. If it does, refactor it to separate projection generation from entry creation first.
- Before adding `passport.key.rotate` to the pipeline, verify that it is idempotent (no-op if key file exists). If it rotates on every run, refactor it first.
- The commands MUST be added at the end of `SITES_BUILD_PREPARE_PIPELINE`, after `media.variants.generate`.
- The commands MUST NOT be added to `SITES_BUILD_PREPARE_DEV_SUBSET`.
