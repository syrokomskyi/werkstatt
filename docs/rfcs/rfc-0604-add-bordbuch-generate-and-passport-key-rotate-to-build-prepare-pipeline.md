# RFC-0604: Add bordbuch.generate and passport.key.ensure to build.prepare pipeline

## Context

A public folder regeneration experiment on warpgogol-com (2026-07-30) revealed that `build.prepare` does not include two commands that produce git-tracked public artifacts:

1. **`bordbuch.generate`** (RFC-0473): Produces `systems/<id>/public/.well-known/bordbuch.json` and `systems/<id>/public/.well-known/bordbuch/index.html`. These files are in `GENERATOR_OWNERSHIP_MAP` and are git-tracked, but they were not regenerated by `build.prepare` and were reported as missing by `generated.files.validate`.

2. **Passport key**: Produces `public/.well-known/cosmic-passport-key.json`. Same issue — git-tracked, in the ownership map, but not regenerated by `build.prepare`. The existing `passport.key.rotate` command (RFC-0028) is unsafe for pipeline use (always rotates, prints private key to stdout). RFC-0605 creates a new `passport.key.ensure` command that is pipeline-safe.

The operator confirmed that both commands should be added to `build.prepare`.

## Problem

The `build.prepare` pipeline in `packages/os/site-kernel-checks/src/pipelines/build-prepare.ts` is a sequence of kernel commands that prepare the site build. It includes commands for config, routes, surface, agent manifests, styles, public infrastructure, sitemap, llms, feed, and media variants. However, it does not include `bordbuch.generate` or `passport.key.ensure`.

This means:

1. After `build.prepare`, the bordbuch and passport artifacts are missing.
2. `generated.files.validate` (RFC-0375) reports them as missing.
3. `generated.stale.validate` (RFC-0600) may flag them as stale (if they exist from a previous build but are not regenerated).
4. The site deploys without bordbuch status or passport key files in `.well-known/`.

The root cause is that these commands were originally designed as separate operator commands. `bordbuch.generate` was assumed to have side effects (git commits), but in reality it only writes projection files via `writeFileIfChanged` — no git commits, no bordbuch entry creation (its MODULE_CONTRACT says: "Does not append events — use bordbuch.append for that"). `passport.key.rotate` always generates a new keypair and prints the private key to stdout, which is unsafe for pipeline use. RFC-0605 creates `passport.key.ensure` as a pipeline-safe variant.

## Decision

The `build.prepare` pipeline includes `bordbuch.generate` and `passport.key.ensure` as final steps, after all other generation commands. The dev-mode subset pipeline excludes both commands to avoid side effects during development.

## Architectural fit

- **RFC-0375 (generated.files.validate)**: This RFC ensures the validator passes after `build.prepare` by including the missing commands. Note: `generated.files.validate` path resolution for `systems/{system}/` paths requires RFC-0606.
- **RFC-0600 (generated.stale.validate)**: This RFC ensures bordbuch and passport files are not flagged as stale.
- **RFC-0599 (open-source.generate fix)**: Related — both RFCs address output completeness from different angles.
- **RFC-0473 (bordbuch.generate)**: The command is already pipeline-safe — it writes projections via `writeFileIfChanged`, does not create git commits, and does not append bordbuch entries.
- **RFC-0028 (passport.key.rotate)**: The existing command is operator-only. RFC-0605 creates `passport.key.ensure` as the pipeline-safe variant.
- **RFC-0605 (passport.key.ensure)**: Must be accepted and implemented before this RFC can add `passport.key.ensure` to the pipeline.
- **RFC-0606 (generated.files.validate path fix)**: Must be accepted and implemented before `generated.files.validate` can correctly find bordbuch files at `systems/{system}/public/`.
- **Site OS operator model**: `build.prepare` is the canonical pre-build pipeline. Any command that produces git-tracked public artifacts must be in it. The dev-mode subset is for mission materialization and excludes commands with side effects.

## Design

### CLI surface

No new commands. The fix is internal to the `build.prepare` pipeline definition:

```sh
pnpm exec site-kernel run build.prepare --site warpgogol-com
```

### Pipeline changes

The `SITES_BUILD_PREPARE_PIPELINE` array in `packages/os/site-kernel-checks/src/pipelines/build-prepare.ts` is extended with two new entries at the end:

```ts
// Existing entries...
{ command: "media.variants.generate",     label: "Media variants" },
// New entries:
{ command: "bordbuch.generate",           label: "Bordbuch status" },
{ command: "passport.key.ensure",         label: "Passport key ensure" },
```

The dev-mode subset pipeline (`SITES_BUILD_PREPARE_DEV_PIPELINE`) is NOT extended — `bordbuch.generate` and `passport.key.ensure` are excluded from dev mode because:

- `bordbuch.generate` acquires Werkstatt locks (`system:<id>` and `bordbuch:<id>`) which is unnecessary during development.
- `passport.key.ensure` may generate a new key if the key file does not exist, which should be an explicit operator action, not a side effect of dev builds.

### Side effect safety

- **`bordbuch.generate`**: Already pipeline-safe. The command (`packages/os/site-kernel-handoff/src/bordbuch/bordbuch-generate.ts:177-227`) writes projections via `writeFileIfChanged` (idempotent — only writes if content changed). Its MODULE_CONTRACT states: "Does not append events — use bordbuch.append for that." The command does NOT create git commits and does NOT append bordbuch entries. It acquires Werkstatt locks (`system:<id>` and `bordbuch:<id>`) for concurrency safety, which is acceptable in pipeline context. No refactoring needed.
- **`passport.key.ensure`** (RFC-0605): Pipeline-safe by design. Creates the key file if missing, no-op if it exists. Never prints the private key to stdout. The `--private-key-out` flag optionally writes the private key to a file when a new key is created. `passport.key.rotate` remains the operator-only command for manual rotation with private key output.

### File system responsibilities

| Path | Role |
| --- | --- |
| `packages/os/site-kernel-checks/src/pipelines/build-prepare.ts` | Fix target — add two commands to `SITES_BUILD_PREPARE_PIPELINE` |
| `packages/os/site-kernel-checks/src/generator-ownership.ts` | Reference — confirms bordbuch and passport outputs are registered |
| `systems/<id>/public/.well-known/bordbuch.json` | Output — must exist after `build.prepare` (written by `bordbuch.generate` to cache clone) |
| `systems/<id>/public/.well-known/bordbuch/index.html` | Output — must exist after `build.prepare` (written by `bordbuch.generate` to cache clone) |
| `public/.well-known/cosmic-passport-key.json` | Output — must exist after `build.prepare` (written by `passport.key.ensure`) |

### Failure modes

- If `bordbuch.generate` fails (e.g., bordbuch file not found, lock acquisition failure), the pipeline fails. The command already handles empty bordbuch gracefully — `readBordbuch` returns an empty array, and the projection is generated with `eventCount: 0`.
- If `passport.key.ensure` fails (e.g., manifest missing, key generation error, corrupt existing key file), the pipeline fails. See RFC-0605 for detailed failure modes.
- **`bordbuch.generate` requires `--system` flag**: The command falls back to `context.site?.name` when `--system` is not provided. The pipeline executor injects `--site` for workspace-scoped commands (line 347 of `execute-pipeline.ts`), and `bordbuch.generate` is `scope: "workspace"`, so it receives the site name from the pipeline context.
- **`bordbuch.generate` writes to cache clone, not build workspace**: The command uses `resolveCachePath(workspaceRoot, systemId)` to determine the output path, resolving to `systems/<id>/public/.well-known/`. This is the Sternsystem cache clone (mirrors[0]), not the build workspace `public/` directory. `generated.files.validate` must be able to resolve `systems/{system}/` paths — see RFC-0606.

## Rollout

- **Default behavior**: Both commands are active in `build.prepare` immediately upon implementation.
- **Prerequisites**: RFC-0605 (`passport.key.ensure` command) and RFC-0606 (`generated.files.validate` path fix) must be accepted and implemented before this RFC.
- **Existing apps**: Must run `build.prepare` once after implementation to generate the missing bordbuch and passport artifacts. After that, they are kept up to date automatically.
- **New apps**: Automatically benefit.
- **Dev mode**: Both commands are excluded from the dev-mode subset pipeline. Developers running `build.prepare --dev` will not see bordbuch or passport artifacts generated.

## Alternatives considered

- **Keep bordbuch.generate and passport.key.rotate as separate operator commands**: Rejected by operator. The operator confirmed that both should be in `build.prepare` to ensure their outputs are always present.
- **Add only bordbuch.generate, not passport key**: Rejected by operator. The operator confirmed both should be added.
- **Use `passport.key.rotate` with `--ensure` flag**: Rejected — muddies the command's contract. A separate `passport.key.ensure` command (RFC-0605) keeps each command's semantics clean.
- **Create a separate `build.prepare.sensitive` pipeline for these commands**: Rejected — adding a third pipeline variant increases complexity. The commands are safe for `build.prepare`.
- **Add a `--no-sensitive` flag to `build.prepare`**: Rejected — the dev-mode subset already handles this. No additional flag is needed.

## Risks

- **Pipeline ordering**: Both commands must run after all other generation commands because they may depend on the site's route registry and content index. Placing them at the end of the pipeline ensures all dependencies are available.
- **Dev-mode exclusion**: Developers may expect bordbuch and passport artifacts in their local `public/` directory. If they are excluded from dev mode, developers must run the full `build.prepare` once to generate them. This is acceptable — the dev-mode subset is for fast iteration, not for producing a deployable `public/` directory.
- **Concurrent execution**: `bordbuch.generate` acquires Werkstatt locks (`system:<id>` and `bordbuch:<id>`) for concurrency safety. If two `build.prepare` runs target the same Sternsystem simultaneously, the second will wait for the lock. `passport.key.ensure` does not acquire locks — if two runs execute simultaneously and the key file does not exist, both may generate a key and the last write wins. This is acceptable because `passport.key.ensure` is only expected to generate a key on the very first run; subsequent runs are no-op.
- **Private key not stored in pipeline**: If `passport.key.ensure` generates a new key in the pipeline (first run only) and `--private-key-out` is not provided, the private key is not stored anywhere. The operator must either run `passport.key.rotate` manually for the initial key creation to obtain the private key, or provide `--private-key-out` in a controlled CI environment.
