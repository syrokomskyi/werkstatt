# RFC-0811: Switch page.markdown.validate from blacklist to whitelist scanning

## Context

`page.markdown.validate` (in `packages/werkstatt-site/src/checks/page-markdown.ts`) scans all `.md` files in `public/` and treats them as generated markdown twins per RFC-0375. The validator checks YAML frontmatter, provenance fields, semantic metadata, and body section structure (MDMETA-01 through MDBODY-05).

The current implementation uses a **blacklist** approach: scan all `.md` files, then exclude specific filenames via an `ignore` callback:

```ts
const markdownFiles = await collectFiles(publicDir, {
  extensions: [".md"],
  ignore: (relPath) => relPath === "auth.md",
});
```

During the warpgogol-com-m000050 release, `agent.discovery-endpoints.generate` (RFC-0785) created `public/auth.md` — a static informational page for AI agent discovery, not a markdown twin. The validator flagged it with `MDMETA-01: missing YAML frontmatter` because `auth.md` has no frontmatter (it is not a twin). This required adding `auth.md` to the blacklist, which was a reactive fix.

## Problem

The blacklist approach means every new non-twin `.md` file in `public/` will be flagged by `page.markdown.validate` until it is manually added to the `ignore` callback. This is fragile and scales poorly — any future generator that writes `.md` files to `public/` for purposes other than markdown twins will hit the same issue.

The root cause is that the validator assumes **all** `.md` files in `public/` are markdown twins (RFC-0375: "Category B files no longer carry markers — always treat as generated"). This was true when the only `.md` files in `public/` were twins, but RFC-0785 introduced `auth.md` as a non-twin `.md` file.

## Decision

Switch `page.markdown.validate` from blacklist to **whitelist** scanning. Instead of scanning all `.md` files and excluding known non-twins, scan only `.md` files whose path matches a registered markdown-twin generator in `GENERATOR_OWNERSHIP_MAP`.

The `GENERATOR_OWNERSHIP_MAP` already declares which files are generated by which command. Markdown twins in `public/` are generated exclusively by `page.markdown.generate` (ownership map entries `public/index.md` and `public/{route}.md`). Other `.md` files in `public/` — such as `auth.md` (owned by `agent.discovery-endpoints.generate`) — are not twins and must be excluded. The whitelist filters by both extension (`.md`) and command (`page.markdown.generate`), not by extension alone.

## Architectural fit

- **RFC-0375 (Category B files)**: The "always treat as generated" policy is preserved — but the scope is narrowed to files that have an ownership map entry under a twin-producing command.
- **RFC-0320 (Markdown twin provenance)**: The frontmatter validation itself is unchanged. Only the file discovery scope changes.
- **RFC-0810 (Generator ownership cross-check)**: Catches missing ownership entries for generated files, mitigating the risk of twins being silently skipped by the whitelist.

## Design

### CLI surface

No CLI changes. The command remains:

```sh
pnpm exec werkstatt run page.markdown.validate --site warpgogol-com
```

### TypeScript contracts

The `collectFiles` `ignore` callback receives only the entry filename, not the relative path from the root directory. Therefore, the whitelist cannot be applied via the `ignore` callback — the validator must collect all `.md` files first, then filter by relative path against ownership map entries.

```ts
// packages/werkstatt-site/src/checks/page-markdown.ts

// Before (blacklist):
const markdownFiles = await collectFiles(publicDir, {
  extensions: [".md"],
  ignore: (relPath) => relPath === "auth.md",
});

// After (whitelist): collect all .md files, then filter by ownership match.
const allMdFiles = await collectFiles(publicDir, { extensions: [".md"] });
const markdownFiles = allMdFiles.filter((abs) => {
  const relPath = toPosix(relative(siteDir, abs)); // e.g. "public/de/some-page/index.md"
  const entry = matchOwnershipEntry(relPath, app);
  return entry !== null && entry.command === "page.markdown.generate";
});
```

The `matchOwnershipEntry` function from `generated-file-lookup.ts` already handles placeholder expansion (`{route}`, `{lang}`, etc.), pattern-to-regex conversion (`ownPatternToExactRegex`), and app-prefix normalization (`normalizeOwnershipPath`). No new `matchGlob` utility is needed.

The existing `isGeneratedMarkdownTwin` function (which always returns `true` per RFC-0375) becomes moot for non-twin files — they are never reached because the whitelist filters them out before the `isGeneratedMarkdownTwin` check. The function itself does not need to change.

### File system responsibilities

| Path | Role |
| --- | --- |
| `packages/werkstatt-site/src/checks/page-markdown.ts` | Change file discovery from blacklist to whitelist |
| `packages/werkstatt-site/src/checks/generator-ownership.ts` | Source of truth for generated file paths |
| `packages/werkstatt-site/src/checks/generated-file-lookup.ts` | `matchOwnershipEntry` helper for path matching |

### Pipeline placement

`page.markdown.validate` remains in its current pipeline (build check). No pipeline changes — the command's interface and placement are unchanged, only its file discovery logic changes.

### Failure modes

- **No `.md` files matching `page.markdown.generate` ownership entries**: The validator skips with "no markdown twins found" (existing behavior at `page-markdown.ts:700-706` for empty `public/`).
- **`.md` file on disk not matching any `page.markdown.generate` ownership entry**: Silently ignored — it is not a twin. This is the desired behavior.
- **`.md` file in ownership map but missing from disk**: Not flagged by `page.markdown.validate` (file existence is checked by `ownership.sync.validate` and `generated.stale.validate`).

### Performance

The whitelist adds one `matchOwnershipEntry` call per `.md` file in `public/`. Cost is negligible: ~50 ownership map entries, ~100 files in a typical `public/` directory. The pattern-to-regex compilation is cached by `ownPatternToExactRegex` per call.

## Rollout

- **Default behavior**: The change is transparent — all existing markdown twins are already in the ownership map, so they continue to be validated. Non-twin `.md` files (like `auth.md`) are automatically excluded.
- **Migration**: Remove the hardcoded `ignore: (relPath) => relPath === "auth.md"` callback — it becomes redundant.
- **New generators**: Any future generator that writes `.md` files to `public/` must add ownership map entries (enforced by RFC-0810). If the `.md` files are twins, they will be automatically picked up by the whitelist. If they are not twins, they will be automatically excluded.

## Alternatives considered

- **Marker-based detection**: Require non-twin `.md` files to carry a marker comment (e.g. `<!-- not-a-twin -->`). Rejected — adds authoring burden and is easy to forget.
- **Frontmatter presence as filter**: Only validate `.md` files that have YAML frontmatter. Rejected — `MDMETA-01` exists specifically to catch twins that are missing frontmatter. This would make that check unreachable.
- **Separate directory for twins**: Move all twins to `public/.twins/`. Rejected — breaks existing URL paths and requires a migration.

## Risks

- **Missing ownership map entries for existing twins**: If a markdown twin's path is not in the ownership map, it will be silently skipped. Mitigated by RFC-0810 (cross-check) which catches missing ownership entries.
- **Glob matching complexity**: The ownership map uses `{route}`, `{lang}` placeholders and `**` globs. The existing `matchOwnershipEntry` from `generated-file-lookup.ts` already handles these via `expandPlaceholderVariants` and `ownPatternToExactRegex`. No new glob utility is needed.

## Acceptance criteria

- [ ] `page.markdown.validate` uses ownership map entries filtered by `command === "page.markdown.generate"` as whitelist
- [ ] `auth.md` excluded without hardcoded ignore callback (because its ownership entry has `command: "agent.discovery-endpoints.generate"`)
- [ ] All existing markdown twins continue to pass validation

## Implementation notes for agents

- Agents MAY implement code changes ONLY when this RFC has status: accepted (or implemented).
- Reuse `matchOwnershipEntry` from `generated-file-lookup.ts` for path matching. Do not create a new `matchGlob` utility.
- The `collectFiles` `ignore` callback receives only the entry filename, not the relative path. Filter after collection, not via the `ignore` callback.
- Filter ownership entries by `command === "page.markdown.generate"` — not by extension alone. `auth.md` is in the ownership map under `agent.discovery-endpoints.generate` and must be excluded.
- After implementation, remove the `ignore: (relPath) => relPath === "auth.md"` line — it becomes dead code.
- The `isGeneratedMarkdownTwin` function (which always returns `true`) does not need to change. With the whitelist, non-twin files are filtered out before the function is reached.
