# RFC-0811: Switch page.markdown.validate from blacklist to whitelist scanning

## Context

`page.markdown.validate` (in `packages/werkstatt-site/src/checks/page-markdown.ts`) scans all `.md` files in `public/` and treats them as generated markdown twins per RFC-0375. The validator checks YAML frontmatter, provenance fields, semantic metadata, and body section structure (MDMETA-01 through MDBODY-05).

The current implementation uses a **blacklist** approach: scan all `.md` files, then exclude specific filenames via an `ignore` callback:

```ts
const markdownFiles = await collectFiles(publicDir, {
  extensions: [".md"],
  ignore: (relPath) => relPath === "auth.md",
});
```

During the warpgogol-com-m000050 release, `agent.discovery-endpoints.generate` (RFC-0785) created `public/auth.md` — a static informational page for AI agent discovery, not a markdown twin. The validator flagged it with `MDMETA-01: missing YAML frontmatter` because `auth.md` has no frontmatter (it is not a twin). This required adding `auth.md` to the blacklist, which was a reactive fix.

## Problem

The blacklist approach means every new non-twin `.md` file in `public/` will be flagged by `page.markdown.validate` until it is manually added to the `ignore` callback. This is fragile and scales poorly — any future generator that writes `.md` files to `public/` for purposes other than markdown twins will hit the same issue.

The root cause is that the validator assumes **all** `.md` files in `public/` are markdown twins (RFC-0375: "Category B files no longer carry markers — always treat as generated"). This was true when the only `.md` files in `public/` were twins, but RFC-0785 introduced `auth.md` as a non-twin `.md` file.

## Decision

Switch `page.markdown.validate` from blacklist to **whitelist** scanning. Instead of scanning all `.md` files and excluding known non-twins, scan only `.md` files whose path matches a registered markdown-twin generator in `GENERATOR_OWNERSHIP_MAP`.

The `GENERATOR_OWNERSHIP_MAP` already declares which files are generated by which command. Markdown twins are generated by specific generators (e.g. `page.markdown.generate`, `agent.knowledge.generate`). The validator will only scan `.md` files that match paths declared in the ownership map under a markdown-twin-producing command.

## Architectural fit

- **DNA-58 (Generated-file content determinism)**: Strengthens the ownership-based determinism contract. Only files with a declared generator are validated.
- **RFC-0375 (Category B files)**: The "always treat as generated" policy is preserved — but the scope is narrowed to files that have an ownership map entry.
- **RFC-0320 (Markdown twin provenance)**: The frontmatter validation itself is unchanged. Only the file discovery scope changes.

## Design

### CLI surface

No CLI changes. The command remains:

```sh
pnpm exec werkstatt run page.markdown.validate --site warpgogol-com
```

### TypeScript contracts

```ts
// packages/werkstatt-site/src/checks/page-markdown.ts

// Before (blacklist):
const markdownFiles = await collectFiles(publicDir, {
  extensions: [".md"],
  ignore: (relPath) => relPath === "auth.md",
});

// After (whitelist):
const twinPaths = getOwnershipMapPathsByExtension(".md");
const markdownFiles = await collectFiles(publicDir, {
  extensions: [".md"],
  ignore: (relPath) => !isOwnershipPath(twinPaths, relPath),
});
```

```ts
// Helper: extract .md paths from GENERATOR_OWNERSHIP_MAP
function getOwnershipMapPathsByExtension(ext: string): string[] {
  return GENERATOR_OWNERSHIP_MAP
    .filter((entry) => entry.path.endsWith(ext))
    .map((entry) => entry.path);
}

// Helper: check if a relative path matches any ownership map path pattern
function isOwnershipPath(patterns: string[], relPath: string): boolean {
  return patterns.some((pattern) => matchGlob(pattern, relPath));
}
```

### File system responsibilities

| Path | Role |
| --- | --- |
| `packages/werkstatt-site/src/checks/page-markdown.ts` | Change file discovery from blacklist to whitelist |
| `packages/werkstatt-site/src/checks/generator-ownership.ts` | Source of truth for generated file paths |

### Failure modes

- **No `.md` files in ownership map**: The validator skips with "no markdown twins found" (existing behavior for empty `public/`).
- **`.md` file on disk not in ownership map**: Silently ignored — it is not a twin. This is the desired behavior.
- **`.md` file in ownership map but missing from disk**: Not flagged by `page.markdown.validate` (file existence is checked by `ownership.sync.validate` and `generated.stale.validate`).

## Rollout

- **Default behavior**: The change is transparent — all existing markdown twins are already in the ownership map, so they continue to be validated. Non-twin `.md` files (like `auth.md`) are automatically excluded.
- **Migration**: Remove the hardcoded `ignore: (relPath) => relPath === "auth.md"` callback — it becomes redundant.
- **New generators**: Any future generator that writes `.md` files to `public/` must add ownership map entries (enforced by RFC-0810). If the `.md` files are twins, they will be automatically picked up by the whitelist. If they are not twins, they will be automatically excluded.

## Alternatives considered

- **Marker-based detection**: Require non-twin `.md` files to carry a marker comment (e.g. `<!-- not-a-twin -->`). Rejected — adds authoring burden and is easy to forget.
- **Frontmatter presence as filter**: Only validate `.md` files that have YAML frontmatter. Rejected — `MDMETA-01` exists specifically to catch twins that are missing frontmatter. This would make that check unreachable.
- **Separate directory for twins**: Move all twins to `public/.twins/`. Rejected — breaks existing URL paths and requires a migration.

## Risks

- **Missing ownership map entries for existing twins**: If a markdown twin's path is not in the ownership map, it will be silently skipped. Mitigated by RFC-0810 (cross-check) which catches missing ownership entries.
- **Glob matching complexity**: The ownership map uses `{system}` placeholders and `**` globs. The `matchGlob` helper must handle these correctly. Use the existing glob matching utility used by `ownership.sync.validate`.

## Acceptance criteria

- [ ] `page.markdown.validate` uses ownership map paths as whitelist
- [ ] `auth.md` excluded without hardcoded ignore callback
- [ ] All existing markdown twins continue to pass validation
- [ ] `MDMETA-01` still fires for twins missing frontmatter
- [ ] Unit test: non-twin `.md` file in `public/` is not flagged
- [ ] Unit test: twin `.md` file with missing frontmatter is flagged
- [ ] Unit test: twin `.md` file with valid frontmatter passes
- [ ] `rfc.validate` passes on this file before merging

## Implementation notes for agents

- Agents MAY implement code changes ONLY when this RFC has status: accepted (or implemented).
- The glob matching must be consistent with `ownership.sync.validate`'s path matching. Reuse the same helper if possible.
- The `ignore` callback in `collectFiles` should return `true` to **exclude** a file. With the whitelist, return `true` when the path does NOT match any ownership pattern.
- After implementation, remove the `ignore: (relPath) => relPath === "auth.md"` line — it becomes dead code.
