# RFC-0906: Canonical URL trailing-slash parity between HTML and sitemap

## Context

The workshop uses `canonicalPageUrl` (RFC-0317) as the single source of truth for canonical URL generation. It is configured with `trailingSlash: "always"` — every canonical URL ends with `/`. The sitemap generator, feed generator, and llms.txt generator all use `canonicalPageUrl`, ensuring their URLs are byte-identical.

However, the rendered HTML `<link rel="canonical">` tag is **not** generated by `canonicalPageUrl`. It is set in `layout-component.astro:84`:

```ts
const canonicalUrl = canonicalUrlOverride ?? Astro.url.toString();
```

The `canonicalUrlOverride` is passed from `[...slug].template.astro:123`:

```ts
canonicalUrl={data.semanticPage?.url}
```

And `semanticPage.url` is constructed in `resolve-route.ts:1113`:

```ts
const pageUrl = new URL(
  localizeUrl(lang, canonicalSlug, { defaultLanguage: defaultLang }),
  origin,
);
```

The problem: `localizeUrl` does **not** append a trailing slash. It produces URLs like `https://warpgogol.com/leistungen` (no trailing slash), while `canonicalPageUrl` produces `https://warpgogol.com/leistungen/` (with trailing slash). This means:

1. **Sitemap** contains `https://warpgogol.com/leistungen/` (trailing slash, from `canonicalPageUrl`)
2. **HTML `<link rel="canonical">`** contains `https://warpgogol.com/leistungen` (no trailing slash, from `localizeUrl` via `pageUrl`)
3. **og:url** contains the same no-trailing-slash URL (passed from `canonicalUrl` in `layout-component.astro`)

Google Search Console reported these as duplicate pages — the sitemap URL and the canonical URL differ, causing Google to index both variants or ignore the canonical tag.

The existing `canonical.url.validate` (RFC-0317, CANON-01..03) checks sitemap/feed/llms URLs against the expected canonical set — but it does **not** check the HTML `<link rel="canonical">` tag. The existing `seo.domain.validate` (RFC-0898) checks that canonical origins match `Astro.site` — but it does not check trailing-slash parity.

## Problem

**HTML canonical URLs diverge from sitemap canonical URLs due to trailing-slash mismatch.** The root cause is that `pageUrl` in `resolve-route.ts` uses `localizeUrl` (which does not append a trailing slash) while `canonicalPageUrl` (used by sitemap/feed/llms generators) appends a trailing slash.

This is a deterministic inconsistency: both URL construction paths are in the codebase, and their outputs can be compared at build time. No existing validator performs this comparison.

The fix has two parts:

1. **Runtime fix:** `pageUrl` in `resolve-route.ts` must use `canonicalPageUrl` instead of `localizeUrl` to construct the canonical URL, ensuring the HTML `<link rel="canonical">` and `og:url` match the sitemap URLs.
2. **Validator:** a new `canonical.html-parity.validate` command cross-references HTML `<link rel="canonical">` and `og:url` against `canonicalPageUrl` output for every rendered page.

## Decision

The kernel gains one new post-build validator and one existing validator is enhanced:

1. **`canonical.html-parity.validate`** (new) — scans every rendered HTML file in `dist/client/` for `<link rel="canonical">` and `<meta property="og:url">`, compares each against the expected canonical URL computed by `canonicalPageUrl` for the corresponding route. Emits errors when they diverge (trailing slash, path, or origin mismatch).

2. **`canonical.url.validate`** (enhanced) — CANON-01..03 (sitemap/feed/llms parity) is extended with CANON-04: check HTML `<link rel="canonical">` against the expected canonical set. This is a subset of `canonical.html-parity.validate` but is added to `canonical.url.validate` because the expected canonical set is already built in that command.

3. **Runtime fix:** `pageUrl` in `resolve-route.ts` is changed to use `canonicalPageUrl` instead of `localizeUrl`, ensuring the HTML canonical URL matches the sitemap canonical URL from the source.

Both validators are integrated into `SITES_CHECK_POSTBUILD_PIPELINE` after `canonical.url.validate`.

## Architectural fit

**Architecture DNA:**

- **DNA-85** (new, established by this RFC) — Canonical URL trailing-slash parity gate: every canonical URL emitted in rendered HTML (`<link rel="canonical">`, `og:url`, JSON-LD `url`) MUST be byte-identical to the `canonicalPageUrl` output used by the sitemap, feed, and llms generators. The `trailingSlash` policy declared in `CanonicalUrlOptions` is the single source of truth — no URL construction path may bypass it.

- **DNA-58** (Generated-file content determinism) — extends to canonical URLs: the same route MUST produce the same canonical URL across all generators and the HTML render. Divergence is a determinism violation.

**Existing RFCs:**

- **RFC-0317** (`canonical.url.validate`, CANON-01..03) — this RFC amends it with CANON-04 (HTML canonical parity). The new `canonical.html-parity.validate` command complements it with detailed per-page comparison.
- **RFC-0898** (`seo.domain.validate`) — checks canonical origin against `Astro.site`. This RFC checks the full URL (including path and trailing slash) against `canonicalPageUrl`. Both are needed: origin correctness and path correctness.
- **RFC-0160** (default language unprefixed) — `canonicalPageUrl` already implements this policy. The runtime fix ensures `pageUrl` also implements it via `canonicalPageUrl`.

**Site OS operator model:**

- Both commands are post-build validators registered in `packages/werkstatt-site/src/checks/`.
- Both follow the existing pattern: read `dist/client/**/*.html`, compute expected canonical URLs from `system.md` manifest, emit `Diagnostic[]` via `diagnosticsResult`.
- Both are integrated into `SITES_CHECK_POSTBUILD_PIPELINE`.

## Design


### TypeScript contracts

**`canonical.html-parity.validate`** — new file: `packages/werkstatt-site/src/checks/canonical-html-parity.ts`

```ts
interface CanonicalHtmlParityResult {
  checkedPages: number;
  mismatches: number;
}

// Rules:
// CANON-HTML-01 (canonical href mismatch) — severity: error
//   The <link rel="canonical"> href in a rendered HTML file does not match
//   the expected canonicalPageUrl output for that route.
// CANON-HTML-02 (og:url mismatch) — severity: error
//   The <meta property="og:url"> content does not match the expected
//   canonicalPageUrl output for that route.
// CANON-HTML-03 (canonical vs og:url divergence) — severity: error
//   The <link rel="canonical"> href and <meta property="og:url"> content
//   in the same HTML file do not match each other.

// Logic:
// 1. Load system.md manifest, build expected canonical URL map:
//    pageId × lang → canonicalPageUrl({ lang, route: slug, kind: "html" }, canonicalOpts)
//    (reuse the same logic as canonical.url.validate, lines 99-110)
// 2. Walk dist/client/**/*.html
// 3. For each HTML file:
//    a. Extract <link rel="canonical"> href
//    b. Extract <meta property="og:url"> content
//    c. Resolve the expected canonical URL from the file path:
//       - Strip dist/client/ prefix and /index.html suffix
//       - Map back to (pageId, lang) via the route registry
//       - Look up expected canonical URL
//    d. If canonical href ≠ expected → CANON-HTML-01 error
//    e. If og:url ≠ expected → CANON-HTML-02 error
//    f. If canonical href ≠ og:url → CANON-HTML-03 error
// 4. Return diagnostics
```

**`canonical.url.validate`** (enhanced) — existing file: `packages/werkstatt-site/src/checks/canonical-url.ts`

```ts
// New rule added to existing runCanonicalUrlValidate:
// CANON-04 (HTML canonical not in expected set) — severity: warning
//   A <link rel="canonical"> href in a rendered HTML file is not in the
//   expected canonical set built from system.md.
//   This is a subset of CANON-HTML-01 but integrated into canonical.url.validate
//   because the expected canonical set is already built in that command.
//   Severity rationale: CANON-04 checks set membership (is the URL in the
//   expected set?), which is a weaker check than CANON-HTML-01 (exact per-page
//   equality against canonicalPageUrl output). A set membership failure may
//   be a false alarm for edge-case routes not yet in the manifest, while an
//   exact equality failure is always a real mismatch. Hence warning vs error.
//
// Implementation: after the existing CANON-01..03 checks, walk dist/client/**/*.html,
// extract <link rel="canonical"> hrefs, and check each against expectedUrls.
```

**Runtime fix** — `packages/werkstatt-site/src/domain/share/astro/page-handler/resolve-route.ts`

```ts
// Before (line 1113):
const pageUrl = new URL(
  localizeUrl(lang, canonicalSlug, { defaultLanguage: defaultLang }),
  origin,
);

// After:
const pageUrl = new URL(
  canonicalPageUrl(
    { lang, route: canonicalSlug, kind: "html" },
    {
      baseUrl: origin,
      defaultLanguage: defaultLang,
      supportedLanguages: supportedLangs,
      trailingSlash: "always",
    },
  ),
);
```

This ensures `pageUrl` (used for `<link rel="canonical">`, `og:url`, and JSON-LD `url`) is byte-identical to the sitemap URLs.

### Failure modes

- If `dist/client/` is missing → skip with info message (not built yet).
- If `system.md` manifest is missing → skip with info message.
- If a rendered HTML file has no `<link rel="canonical">` → skip that file (other validators handle missing canonical tags).
- If violations found → `exitCode: 1`, diagnostics emitted. All three rules (CANON-HTML-01..03) are errors.
- If no violations → `exitCode: 0`, summary with `checkedPages` count.

## Rollout

**Default behavior: fail-hard from day one.** CANON-HTML-01..03 are errors. No grace period — canonical URL mismatch causes Google indexing issues.

**Existing apps:** Sites with trailing-slash mismatches will fail the validator. The runtime fix (`pageUrl` uses `canonicalPageUrl`) resolves the mismatch at the source. Sites that have not yet rebuilt will get CANON-HTML-01 errors, which is the correct signal to rebuild.

**New apps:** Automatically compliant — the validator runs in `SITES_CHECK_POSTBUILD_PIPELINE`, and the runtime fix ensures `pageUrl` uses `canonicalPageUrl` from the start.

**Pipeline integration:** `canonical.html-parity.validate` is added to `SITES_CHECK_POSTBUILD_PIPELINE` after `canonical.url.validate`:

```
canonical.url.validate            (existing, enhanced with CANON-04)
canonical.html-parity.validate    ← NEW
seo.domain.validate
```

## Alternatives considered

**1. Extend `canonical.url.validate` instead of creating a new command.** Rejected: `canonical.url.validate` checks sitemap/feed/llms URLs against the expected canonical set — it operates on generated XML/text files. The new validator operates on rendered HTML files, extracting `<link rel="canonical">` and `og:url` from each page. Different input format, different extraction logic. The workshop principle is to split when input domains differ. CANON-04 is added to `canonical.url.validate` as a cheap subset check (is the HTML canonical in the expected set?), while `canonical.html-parity.validate` does the detailed per-page comparison.

**2. Fix only the runtime code, no validator.** Rejected: the runtime fix resolves the current issue, but without a validator, the same regression can reappear if someone changes `pageUrl` construction in the future. DNA-67 (pre-deploy Lighthouse parity gate) establishes that every deterministically checkable issue MUST have a build-time validator.

**3. Use `seo.domain.validate` (RFC-0898) for trailing-slash checks.** Rejected: `seo.domain.validate` checks origin correctness (is the canonical URL on the right domain?). Trailing-slash parity is a path-level check, not an origin check. Extending `seo.domain.validate` would mix two different validation concerns.

## Risks

**Performance:** `canonical.html-parity.validate` scans `dist/client/**/*.html` and extracts two meta tags per file. This is the same pattern used by `seo.domain.validate` and `csp.origins.validate`. Performance impact is negligible.

**False positive rate:** CANON-HTML-01 and CANON-HTML-02 have no false positives by design — if the canonical href or og:url does not match `canonicalPageUrl` output, that is always a real mismatch. CANON-HTML-03 (canonical vs og:url divergence) has no false positives — both are in the same HTML file and should always match.

**Maintenance burden:** One new file (~180 lines) plus a small enhancement to `canonical-url.ts` and the runtime fix in `resolve-route.ts` (one-line change). The canonical URL extraction reuses the same regex pattern as `seo.domain.validate`.
