# RFC-0783: Add agent discovery metadata generators for API Catalog and MCP Server Card

## Context

The Werkstatt agent surface (RFC-0286) established `/.well-known/agent.json` as the site's agent discovery manifest and RFC-0289 added `/.well-known/agent.openapi.json` as its OpenAPI 3.1 projection. RFC-0290 introduced the Agent Gate — a stateless HTTP MCP endpoint at `/api/agent/mcp` (protocol `2025-06-18`). These artifacts are generated by `agent.manifest.generate` and `agent.openapi.generate` from the internal Agent Surface Manifest (`src/agent-surface.generated.yaml`).

The [isitagentready.com](https://isitagentready.com/warpgogol.com) audit checks for two additional standardized discovery endpoints that we do not yet generate:

1. **API Catalog** (RFC 9727) — `/.well-known/api-catalog` served as `application/linkset+json`, a standardized link relation format for API discovery.
2. **MCP Server Card** (SEP-1649) — `/.well-known/mcp/server-card.json`, a standardized metadata file describing the MCP server's transport, protocol version, and capabilities.

Both are projections of data already present in the Agent Surface Manifest — the same source that produces `agent.json` and `agent.openapi.json`.

## Problem

Agent discovery tooling (isitagentready.com and similar auditors) checks for `/.well-known/api-catalog` and `/.well-known/mcp/server-card.json` and reports their absence as readiness gaps. While our `agent.json` already contains the underlying data (API endpoints, MCP transport URL, protocol version), we lack the standardized format projections that external agent tools expect.

There is no Site OS command that generates or validates these two files. Without generators, they would need to be hand-maintained — violating the generated-file determinism principle (DNA-58) and the agent surface's build-time automation contract (RFC-0286).

## Decision

The kernel gains four new Site OS commands: `agent.api-catalog.generate`, `agent.api-catalog.validate`, `agent.mcp-card.generate`, and `agent.mcp-card.validate`. The generate commands read the internal Agent Surface Manifest (`src/agent-surface.generated.yaml`) — the same source used by `agent.openapi.generate` — and produce `/.well-known/api-catalog` (RFC 9727 linkset+json) and `/.well-known/mcp/server-card.json` (SEP-1649 server card) respectively. The validate commands enforce manifest↔artifact bijection and well-formedness, following the same pattern as `agent.openapi.validate` (AGO-01..04).

## Architectural fit

- **DNA-34** (VC signing + `/.well-known/` discovery) — extends the `.well-known/` discovery surface with two new standardized files. Both files are candidates for Ed25519Signature2020 signing via `agent.surface.sign`, same as `agent.json` and knowledge files.
- **DNA-35** (`app.contract.full` readiness signal) — the new validate commands integrate into the build pipeline alongside `agent.surface.validate` and `agent.openapi.validate`.
- **DNA-58** (generated-file content determinism) — both files are generator-owned and deterministic; `generated.drift.validate` covers them.
- **RFC-0286** (agent surface) — these are new projections of the same Agent Surface Manifest, extending the AS-1 artifact set.
- **RFC-0289** (OpenAPI projection) — the new generators follow the exact same pattern: read internal manifest, produce a standardized format projection, validate bijection.
- **RFC-0290** (Agent Gate MCP) — the MCP Server Card describes the public HTTP MCP endpoint established by this RFC.
- **RFC-0315** (HTTP security headers) — the `/.well-known/*` cache headers in `_headers` already cover these new files.

## Design

### CLI surface

```sh
pnpm exec werkstatt run agent.api-catalog.generate --site warpgogol-com
pnpm exec werkstatt run agent.api-catalog.validate --site warpgogol-com
pnpm exec werkstatt run agent.mcp-card.generate --site warpgogol-com
pnpm exec werkstatt run agent.mcp-card.validate --site warpgogol-com
```

All four commands are `scope: app`, `supportsAllSites: true`. No custom flags. They follow the same `agent.enabled` skip pattern as `agent.openapi.generate` — when `agent.enabled: false` in `system.md`, generate commands remove stale artifacts and validate commands are silent.

**`mcp: null` edge case**: When `manifest.interfaces.mcp` is `null` (the agent surface has no MCP endpoint), `agent.mcp-card.generate` skips and removes any stale `server-card.json` file — same as the `agent.enabled: false` skip pattern. `agent.mcp-card.validate` is silent in this case.

### TypeScript contracts

```ts
// packages/werkstatt-site/src/domain/share/agent/api-catalog.ts

/** RFC 9727 linkset+json entry — one per API endpoint or discovery resource. */
interface ApiCatalogLink {
  href: string;
  rel: string;
  type: string;
  title?: string;
  anchor?: string;
}

/** RFC 9727 linkset document — the root JSON shape. */
interface ApiCatalog {
  // linkset+json: map of anchor → link array
  [anchor: string]: ApiCatalogLink[];
}

/** Pure: project Agent Surface Manifest → RFC 9727 linkset+json. */
function buildApiCatalog(manifest: AgentSurfaceManifest): ApiCatalog;

// packages/werkstatt-site/src/domain/share/agent/mcp-card.ts

/** SEP-1649 MCP Server Card. */
interface McpServerCard {
  serverInfo: {
    name: string;
    version: string;
    description?: string;
  };
  transport: {
    type: "streamable-http";
    url: string;
  };
  protocolVersion: string;
  capabilities: {
    tools: { listChanged: boolean };
    resources: { listChanged: boolean; subscribe: boolean };
    prompts: { listChanged: boolean };
  };
}

/** Pure: project Agent Surface Manifest → SEP-1649 server card. */
function buildMcpServerCard(manifest: AgentSurfaceManifest): McpServerCard;
```

### Output format

**`agent.api-catalog.generate` — `/.well-known/api-catalog`** (RFC 9727 linkset+json):

```json
{
  "": [
    { "href": "/api/agent/v1/company.json", "rel": "item", "type": "application/json", "title": "company knowledge" },
    { "href": "/api/agent/v1/people.json", "rel": "item", "type": "application/json", "title": "people knowledge" },
    { "href": "/.well-known/agent.json", "rel": "service-meta", "type": "application/json" },
    { "href": "/.well-known/agent.openapi.json", "rel": "service-desc", "type": "application/json" },
    { "href": "/.well-known/mcp/server-card.json", "rel": "service-desc", "type": "application/json" },
    { "href": "/api/agent/mcp", "rel": "service", "type": "application/json" },
    { "href": "/llms.txt", "rel": "service-doc", "type": "text/plain" }
  ]
}
```

**`agent.mcp-card.generate` — `/.well-known/mcp/server-card.json`** (SEP-1649):

```json
{
  "serverInfo": {
    "name": "warpgogol-com-agent-gate",
    "version": "1.0.0",
    "description": "Agent Gate MCP endpoint for warpgogol-com"
  },
  "transport": {
    "type": "streamable-http",
    "url": "https://warpgogol.com/api/agent/mcp"
  },
  "protocolVersion": "2025-06-18",
  "capabilities": {
    "tools": { "listChanged": false },
    "resources": { "listChanged": false, "subscribe": false },
    "prompts": { "listChanged": false }
  }
}
```

### Failure modes

**`agent.api-catalog.validate`** (rule IDs `AGC-01..03`):

- `AGC-01`: File missing or invalid JSON → error, fixHint: rerun generate.
- `AGC-02`: Linkset entries diverge from manifest refs (missing endpoint, extra endpoint) → error, fixHint: rerun generate.
- `AGC-03`: `agent.enabled: false` but file still exists → error, fixHint: rerun generate to remove stale artifact.

**`agent.mcp-card.validate`** (rule IDs `AGM-01..03`):

- `AGM-01`: File missing or invalid JSON → error.
- `AGM-02`: `transport.url` or `protocolVersion` diverges from manifest `interfaces.mcp` → error.
- `AGM-03`: `agent.enabled: false` but file still exists → error.

Both validators exit non-zero on any error. `--json` output follows the standard `CheckResult` shape with `diagnostics[]`.

## Rollout

- **Pipeline integration**: Both generate commands run in `build.prepare` immediately after `agent.openapi.generate`, before `agent.surface.validate`. Both validate commands run alongside `agent.openapi.validate`.
- **Existing apps**: All apps with `agent.enabled !== false` (currently warpgogol-com) get the new files on their next `build.prepare` run. No flag day, no migration — the files are additive.
- **New apps**: Onboarding scaffold already runs `agent.manifest.generate` + `agent.openapi.generate`; the new generators run automatically in the same pipeline step.
- **`agent.enabled: false` apps**: Generate commands remove stale artifacts (same skip pattern as `agent.openapi.generate`).
- **Signing**: Both files are candidates for `agent.surface.sign` in a follow-up amendment. The existing `AgentProofArtifactKind` type (`"manifest" | "knowledge" | "openapi"`) would need extending to include `"api-catalog"` and `"mcp-card"`. For now, they ship unsigned — `agent.openapi.json` is already signable via `agent.surface.sign` when `PASSPORT_SIGNING_KEY` is set; the new files will get the same treatment in a follow-up.

## Alternatives considered

1. **Single aggregated generator** (`agent.discovery.generate` producing all files) — rejected because the existing pattern is one generator per output format (`agent.manifest.generate`, `agent.openapi.generate`, `agent.knowledge.generate`). Separate generators allow independent pipeline scheduling and validation.

2. **Agent Skills Discovery Index** (`/.well-known/agent-skills/index.json`) — excluded from this RFC. Workshop skills (`wg-site-content-edit`, `fo-*`) are development-time tools used inside the monorepo; client sites are static builds that do not know or advertise how they were built. The MCP `tools/list` method already exposes runtime capabilities to visiting agents.

3. **Cascading generation from public `agent.json`** — rejected because `agent.openapi.generate` reads the internal manifest (`src/agent-surface.generated.yaml`), not the public mirror. Following the same pattern keeps the generation graph consistent.

## Risks

- **Spec instability**: SEP-1649 (MCP Server Card) is a PR, not a finalized spec. The field shape may change. Mitigation: the generator reads from the manifest's `interfaces.mcp` block, so a schema update is a one-file change in `buildMcpServerCard`.
- **RFC 9727 linkset format ambiguity**: The `anchor` key in linkset+json is the context URL (empty string for site-root). Some consumers may expect a different anchor. Mitigation: use empty-string anchor (site root context) which is the most common interpretation.
- **Maintenance burden**: Two new generators + two validators + two pure projection functions. This is the same per-format cost as RFC-0289 (OpenAPI).
- **Agent misinterpretation**: Agents might assume the MCP Server Card describes the Studio Gate stdio server. The `transport.type: "streamable-http"` field makes it clear this is an HTTP endpoint, not stdio.
