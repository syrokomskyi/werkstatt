# RFC-0905: Redirect effectiveness in Worker-first deployments

## Context

The workshop deploys Astro sites via Cloudflare Pages with a Worker-first architecture: a Cloudflare Worker intercepts incoming requests and either serves a static file, applies a redirect, or returns a synthetic response. The `public/_redirects` file (generated by `public.infrastructure.generate`, RFC-0318) contains retirement redirect rules — old URLs that should 301/308 redirect to new canonical URLs.

Google Search Console data for `warpgogol.com` (August 2026) revealed that multiple retired URLs returned HTTP 200 instead of redirecting. The root cause: the Cloudflare Worker intercepted requests for retired URLs and served static HTML files from `dist/client/` that existed at those paths, bypassing the `_redirects` rules entirely. The `_redirects` file was correctly generated but never processed for those routes because the Worker's static-file lookup ran before redirect evaluation.

Two shadowing modes exist:

1. **Worker route shadowing:** the Worker's route table or fetch handler matches a retired URL pattern and returns a static file or synthetic response without checking `_redirects`.
2. **Static file shadowing:** a static HTML file exists in `dist/client/` at the same path as a redirect source. Cloudflare Pages serves the static file before evaluating `_redirects` rules.

Neither `redirect.map.validate` (RFC-0318, REDIR-01..06) nor any existing validator detects these shadowing conditions. `redirect.map.validate` checks that redirect sources are not live canonical routes (REDIR-04) and targets exist (REDIR-05), but it does not check whether a static file or Worker route shadows the redirect source.

## Problem

**Redirect shadowing is undetectable before deployment today.** The existing `redirect.map.validate` (RFC-0318) validates the `_redirects` file in isolation:

- REDIR-04 checks that a redirect source is not in the sitemap (not a live canonical route) — but a static HTML file can exist at a path that is not in the sitemap (e.g., a retired PSEO page that was not cleaned up).
- REDIR-05 checks that the redirect target is in the sitemap — but does not check whether the target is itself shadowed.

The gap: a redirect rule `old-url 301 /new-url/` in `_redirects` is correct on paper, but if `dist/client/old-url/index.html` exists, Cloudflare Pages serves the static file and the redirect never fires. Google crawls the old URL, sees HTTP 200 with stale content, and indexes it instead of following the redirect.

This problem is deterministic: the `_redirects` file, the `dist/client/` file tree, and the Worker route configuration are all available at build time. A validator can cross-reference them before deployment.

## Decision

The kernel gains one new post-build validator and one existing validator is enhanced:

1. **`redirect.shadow.validate`** (new) — cross-references every redirect source in `public/_redirects` against:
   - Static files in `dist/client/` — if a file exists at the redirect source path (with or without trailing slash, with `/index.html` suffix), the redirect is shadowed and will never fire.
   - Worker route patterns (from `wrangler.toml` / `wrangler.jsonc` route declarations) — if a Worker route pattern matches a redirect source, the Worker may intercept the request before `_redirects` is evaluated.

2. **`redirect.map.validate`** (enhanced) — REDIR-04 is extended: in addition to checking that the redirect source is not in the sitemap, it also checks that no static file in `dist/client/` exists at the redirect source path. This is a subset of `redirect.shadow.validate` but is added to `redirect.map.validate` because the check is cheap and belongs logically with the existing REDIR-04 "source is not live" check. REDIR-07 and RSHAD-01 MUST share a common `checkStaticFileShadow` helper function to prevent implementation drift between the two validators.

Both validators are integrated into `SITES_CHECK_POSTBUILD_PIPELINE` after `redirect.map.validate`.

## Architectural fit

**Architecture DNA:**

- **DNA-84** (new, established by this RFC) — Redirect effectiveness gate: every redirect rule in `public/_redirects` MUST be checked for static-file and Worker-route shadowing before deployment. A redirect that is shadowed by a static file or Worker route is a silent failure — Google indexes the stale content instead of following the redirect.

**Existing RFCs:**

- **RFC-0318** (`redirect.map.validate`, REDIR-01..06) — this RFC extends it with REDIR-07 (static file shadow). The new `redirect.shadow.validate` command complements it with Worker-route shadow detection.
- **RFC-0589** (REDIR-03 rejects 410 for cloudflare-workers adapter) — this RFC is aware of the adapter context: `redirect.shadow.validate` only checks Worker routes when the deployment adapter is `cloudflare-workers` or `cloudflare-pages`.
- **RFC-0495** (surface URL restructuring) — generated redirects for old URLs are the primary consumers of this validation.

**Site OS operator model:**

- Both commands are post-build validators registered in `packages/werkstatt-site/src/checks/`.
- Both follow the existing pattern: read `public/_redirects`, scan `dist/client/`, emit `Diagnostic[]` via `diagnosticsResult`.
- Both are integrated into `SITES_CHECK_POSTBUILD_PIPELINE`, which runs inside `build.post` and `sites-check.postbuild`.

### TypeScript contracts

**`redirect.shadow.validate`** — new file: `packages/werkstatt-site/src/checks/redirect-shadow.ts`

```ts
interface RedirectShadowResult {
  checkedRules: number;
  shadowed: number;
}

// Rules:
// RSHAD-01 (static file shadows redirect source) — severity: error
//   A static file exists in dist/client/ at the redirect source path.
//   The redirect will never fire because Cloudflare Pages serves the static file first.
// RSHAD-02 (Worker route shadows redirect source) — severity: error
//   A Worker route pattern in wrangler.toml/wrangler.jsonc matches the redirect source.
//   The Worker may intercept the request before _redirects is evaluated.
// RSHAD-03 (redirect target is shadowed by static file) — severity: warning
//   The redirect target path has a static file in dist/client/ AND the target is in
//   the sitemap. This is expected (target should be a live page) — the warning fires
//   only when the target is NOT in the sitemap but a static file exists, indicating
//   a stale file that should have been cleaned up.

// Logic:
// 1. Parse _redirects via parseRedirectRules (reuse from @warpgogol/werkstatt-shared/share/redirects)
// 2. For each rule:
//    a. Normalize source path (strip query, fragment, trailing slash variants)
//    b. Check static file shadow:
//       - dist/client/{source}/index.html
//       - dist/client/{source}.html
//       - dist/client/{source} (if no extension, skip — directories are not served)
//       If any exists → RSHAD-01 error
//    c. Check Worker route shadow (only when adapter is cloudflare-workers or cloudflare-pages):
//       - Read wrangler.toml or wrangler.jsonc from app directory
//       - Parse routes[] array (each entry is a Cloudflare route pattern like "warpgogol.com/*")
//       - Convert route pattern to regex (Cloudflare uses * as wildcard)
//       - If any route pattern matches the redirect source → RSHAD-02 error
//    d. Check target shadow:
//       - If target is not in sitemap AND a static file exists at target path → RSHAD-03 warning
// 3. Return diagnostics
```

**`redirect.map.validate`** (enhanced) — existing file: `packages/werkstatt-site/src/checks/public-surface/managed-public.ts`

### Failure modes

- If `public/_redirects` is missing → skip with info message (REDIR-01 in `redirect.map.validate` handles this).
- If `dist/client/` is missing → skip with info message (not built yet).
- If `wrangler.toml` / `wrangler.jsonc` is missing → skip Worker route check (RSHAD-02) with info message. Static file check (RSHAD-01) still runs.
- If deployment adapter is not `cloudflare-workers` or `cloudflare-pages` → skip Worker route check (RSHAD-02). Static file check (RSHAD-01) still runs.
- `wrangler.toml` / `wrangler.jsonc` path is resolved via `loadPublicContext(context)` — same app directory resolution as `redirect.map.validate`. The validator checks for `wrangler.toml` first, then `wrangler.jsonc`.
- If violations found → `exitCode: 1`, diagnostics emitted. RSHAD-01 and RSHAD-02 are errors; RSHAD-03 is a warning.
- If no violations → `exitCode: 0`, summary with `checkedRules` count.

## Rollout

**Default behavior: fail-hard from day one.** RSHAD-01 and RSHAD-02 are errors. No grace period — shadowed redirects are silent failures that cause Google indexing issues.

**Existing apps:** Sites with shadowed redirects will fail the validator. The fix is to either remove the static file (run `public.managed.clean`) or remove the redirect (if the URL is actually live). Worker route shadowing requires adjusting the Worker fetch handler to process `_redirects` before static-file lookup.

**New apps:** Automatically compliant — the validator runs in `SITES_CHECK_POSTBUILD_PIPELINE`.

**Pipeline integration:** `redirect.shadow.validate` is added to `SITES_CHECK_POSTBUILD_PIPELINE` after `redirect.map.validate`:

```
redirect.map.validate          (existing, enhanced with REDIR-07)
redirect.shadow.validate       ← NEW
robots.page.validate
```

## Alternatives considered

**1. Extend `redirect.map.validate` instead of creating a new command.** Rejected: `redirect.map.validate` validates the `_redirects` file in isolation (source/target/chain correctness). Shadow detection cross-references `_redirects` against `dist/client/` files and Worker route configuration — a different concern. Mixing them would create a command with two unrelated rule families. The workshop principle is to split when responsibilities differ.

**2. Fix the Worker to process `_redirects` before static files.** This is the runtime fix (implementation, not validation) and will be done separately. This RFC establishes the validator that catches the problem before deployment, regardless of whether the Worker is fixed.

**3. Runtime probe (post-deploy) instead of post-build validator.** Rejected: the goal is to catch issues before deployment. Runtime probes complement post-build validators but cannot replace them for pre-deploy detection.

## Risks

**Performance:** `redirect.shadow.validate` scans `dist/client/` for file existence at each redirect source path. This is O(R) where R is the number of redirect rules — a file-existence check, not a full directory scan. Performance impact is negligible.

**False positive rate:** RSHAD-01 (static file shadow) has no false positives by design — if a static file exists at a redirect source path, the redirect is always shadowed. RSHAD-02 (Worker route shadow) could produce false positives if the Worker fetch handler processes `_redirects` before static-file lookup. However, the current Worker middleware chain (access-protection → tombstone → language-redirect → markdown-negotiation) does NOT process `_redirects` — `_redirects` is a Cloudflare Pages infrastructure feature evaluated independently. If a Worker route pattern matches a redirect source, the Worker intercepts the request before Pages can evaluate `_redirects`, so RSHAD-02 is correct by default. A follow-up RFC can add a `--skip-worker-shadow` flag or config escape hatch if false positives emerge in practice.

**Maintenance burden:** One new file (~200 lines) plus pipeline registration, tests, and a small enhancement to `managed-public.ts`. The Worker route parsing is a simple glob-to-regex conversion.
