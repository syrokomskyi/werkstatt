# RFC-0611: Generate nested AGENTS.md files for workspace directories during forge onboarding

## Context

`forge.create` (RFC-0544) composes `forge.scaffold` + `forge.init` + `forge.agents.generate` to bootstrap a new forge project. The root `AGENTS.md` is generated by `forge.agents.generate` from `forge.yaml` (RFC-0548 added a behavioral layer with intent-to-skill routing). The root file instructs agents to "follow the closest `AGENTS.md` for workspace or directory details" — but no nested `AGENTS.md` files are created during onboarding.

The warpgogol monorepo itself has hand-written `AGENTS.md` files at multiple levels (root, `packages/AGENTS.md`, `packages/forge/AGENTS.md`, etc.). This layered convention is the intended model: each workspace has a local `AGENTS.md` with workspace-specific rules. But forge-consumer projects bootstrapped via `forge.create` start with only the root file — workspace-level `AGENTS.md` files are expected to be created manually as the project grows.

RFC-0079 previously introduced `agents.generate` for the warpgogol monorepo's `apps/<app>/` directories, generating app-level `AGENTS.md` from templates. It was superseded by RFC-0081. That work was monorepo-internal and did not address forge-consumer projects.

## Problem

**Problem 1 — Agents working inside a workspace lack local context.** When an agent works inside `apps/<name>/` or `packages/<name>/` in a forge-consumer project, the root `AGENTS.md` is the only instruction file. The root file says to "follow the closest `AGENTS.md`" but none exists at the workspace level. The agent must infer workspace-specific rules from the root file or from the code itself, increasing error risk.

**Problem 2 — No regeneration path for nested AGENTS.md.** Even if a developer manually creates workspace-level `AGENTS.md` files, there is no command to regenerate them when `forge.yaml` changes (new bindings, new stack entries, renamed project). The root `AGENTS.md` has `forge.agents.generate`; nested files have no equivalent.

**Problem 3 — Existing hand-written AGENTS.md are not validated.** Transplant projects (RFC-0546) may bring their own `AGENTS.md` files. `forge.doctor` does not check them for completeness or consistency with forge conventions. There is no mechanism to suggest improvements to these files.

## Decision

`forge.agents.generate` extends to generate nested `AGENTS.md` files for every workspace directory (a directory containing `package.json`) in the project. The command auto-detects the workspace type (app, package, or service) by content inspection and selects the appropriate type-specific template. `forge.upgrade` generates nested `AGENTS.md` for workspace directories that lack one. `forge.doctor` reports existing hand-written `AGENTS.md` files as info diagnostics with improvement suggestions. `forge-bootstrap` proposes improvements to existing hand-written `AGENTS.md` during onboarding, with operator confirmation.

## Architectural fit

**RFC-0548 (Core behavioral layer).** This RFC extends the behavioral layer concept from root-only to nested. The root `AGENTS.md` already includes a behavioral layer with intent-to-skill routing. Nested `AGENTS.md` files complement it with workspace-type-specific guidance.

**RFC-0544 (forge.create composition).** `forge.create` already auto-runs `forge.agents.generate` after `forge.init`. This RFC extends that auto-run to cover nested files — no new step is added to the composition.

**RFC-0554 (Silent upgrade trigger).** `forge.upgrade` already syncs skills and updates `forge.syncedVersion`. This RFC extends it to also generate missing nested `AGENTS.md` files, consistent with the additive-only upgrade philosophy.

**RFC-0079 (superseded).** RFC-0079 generated app-level `AGENTS.md` from templates in the warpgogol monorepo's `site-kernel-codegen`. This RFC addresses the forge-consumer side: `forge.agents.generate` in `packages/forge` generates nested `AGENTS.md` for any workspace type, not just apps.

## Design

### Workspace discovery

`forge.agents.generate` scans the project root for workspace directories. A workspace directory is any directory containing a `package.json` file. The scan is recursive but skips `node_modules/`, `.git/`, `dist/`, `.turbo/`, `.cache/`, and `.agents/`.

### Workspace type auto-detection

The command auto-detects the workspace type by content inspection:

| Detection rule                                  | Type      |
| ----------------------------------------------- | --------- |
| `astro.config.*` exists in the directory        | `app`     |
| `Dockerfile` or `service.config.yaml` exists    | `service` |
| `package.json` exists without the above markers | `package` |

If multiple markers match, `app` takes precedence over `service`, which takes precedence over `package`. If no markers match, the directory is skipped (not a workspace).

### Generated file header

Every generated nested `AGENTS.md` starts with the same generated marker as the root file:

```markdown
<!-- GENERATED BY forge.agents.generate — DO NOT EDIT -->
<!-- Re-run: pnpm exec forge agents generate -->
```

### Edit guard for existing files

The same edit guard that protects hand-written root `AGENTS.md` applies to nested files:

- File does not exist → generate it.
- File exists with generated marker → overwrite (regenerate).
- File exists without generated marker → skip (hand-written, not touched).

### forge.upgrade integration

`forge.upgrade` calls the nested `AGENTS.md` generation logic after syncing skills. It generates files only for workspace directories that lack an `AGENTS.md`. Existing hand-written files are skipped. Existing generated files are regenerated.

### forge.doctor integration

`forge.doctor` checks for:

- **Missing nested AGENTS.md** — workspace directories without `AGENTS.md` (info diagnostic, suggests running `forge agents generate`).
- **Stale generated AGENTS.md** — generated files whose content differs from what `forge.agents.generate` would produce (warning diagnostic, suggests regeneration).
- **Hand-written AGENTS.md improvement opportunities** — existing hand-written files analyzed for common forge conventions (generated marker presence, reference to root `AGENTS.md`, workspace-type-appropriate sections). Reported as info diagnostics with specific suggestions.

### forge-bootstrap integration

During transplant onboarding (step 6), `forge-bootstrap` checks existing hand-written `AGENTS.md` files in the transplanted project. If improvement opportunities are found, the skill proposes them to the operator in human language. Improvements are applied only with operator confirmation.

### CLI surface

```sh
# Generate root + nested AGENTS.md (existing behavior + new)
pnpm exec forge agents generate

# Upgrade syncs skills + generates missing nested AGENTS.md
pnpm exec forge upgrade

# Doctor checks nested AGENTS.md state
pnpm exec forge doctor
```

No new flags are added. The command discovers workspaces automatically.

### TypeScript contracts

```ts
interface WorkspaceDir {
  path: string;          // relative path from project root
  type: "app" | "package" | "service";
  hasAgentsMd: boolean;
  isGenerated: boolean;  // has generated marker
}

interface AgentsGenerateResult {
  command: "forge.agents.generate";
  status: "pass" | "fail";
  configPath: string;
  generated: string[];    // all generated files (root + nested)
  skipped: string[];      // hand-written files skipped
  errors: string[];
}
```

### File system responsibilities

| Path | Role |
| --- | --- |
| `AGENTS.md` | Root file — generated (existing behavior, unchanged) |
| `apps/<name>/AGENTS.md` | Nested workspace file — generated if missing, regenerated if generated, skipped if hand-written |
| `packages/<name>/AGENTS.md` | Same as above |
| `services/<name>/AGENTS.md` | Same as above |
| Any dir with `package.json` | Discovered as workspace, type auto-detected |

### Output format

```json
{
  "command": "forge.agents.generate",
  "status": "pass",
  "configPath": "forge.yaml",
  "generated": ["AGENTS.md", "apps/my-app/AGENTS.md", "packages/my-lib/AGENTS.md"],
  "skipped": ["services/api/AGENTS.md (hand-written)"],
  "errors": []
}
```

### Failure modes

- **No workspace directories found** — command generates only root `AGENTS.md` (existing behavior). Not an error.
- **`package.json` unreadable** — directory is skipped with a warning in `errors`.
- **Type auto-detection fails (no markers)** — directory is skipped, not treated as a workspace.
- **Hand-written file exists** — skipped, reported in `skipped` array. Not an error.
- **Generated file is stale** — overwritten silently (regeneration). Not an error.

## Rollout

**New projects.** `forge.create` auto-runs `forge.agents.generate` which now generates both root and nested `AGENTS.md`. New projects get nested files from day one — no migration needed.

**Existing forge-consumer projects.** `forge.upgrade` generates missing nested `AGENTS.md` on the next upgrade run. Projects with hand-written workspace `AGENTS.md` are not touched.

**Transplant projects.** `forge-bootstrap` checks existing hand-written `AGENTS.md` during onboarding and proposes improvements with operator confirmation.

**Warpgogol monorepo.** Not affected — the monorepo's root `AGENTS.md` is hand-written (no generated marker) and is skipped by the edit guard. The monorepo's nested `AGENTS.md` files are also hand-written and skipped.

**No deprecation.** This RFC does not deprecate or supersede any existing command. It extends `forge.agents.generate`, `forge.upgrade`, and `forge.doctor` with additional behavior.

## Alternatives considered

**Generate AGENTS.md for all declared workspace.dirs in stack profiles.** Rejected because `workspace.dirs` includes non-workspace directories like `docs/` and `scripts/` that do not benefit from `AGENTS.md`. Workspace discovery by `package.json` presence is more precise.

**Declare workspace types in stack profiles (`firstWorkspace.type: app`).** Rejected because it requires updating all profiles and does not cover workspaces created after scaffolding (e.g., transplant projects adding `apps/<name>/`). Auto-detection by content is more flexible and works retroactively.

**Minimal stub instead of fully generated content.** Rejected because a stub that is immediately extended by hand loses the regenerability property. Fully generated files with type-specific templates provide more value to agents and can be regenerated when `forge.yaml` changes.

**Modify existing hand-written AGENTS.md with generated blocks (markers).** Rejected because inserting generated blocks into hand-written files is fragile and can break the file's structure. The edit guard (skip hand-written, propose improvements via doctor/bootstrap) is safer and respects operator ownership.

**RFC fixes specific template content for app/package/service.** Rejected because the template content is an implementation detail that should evolve without RFC amendments. The RFC defines the mechanism (discovery, detection, generation, skip, regenerate); the templates are refined in code.

## Risks

**Risk: Type auto-detection misclassifies a workspace.** A directory with an `astro.config.*` that is actually a library, or a directory with a `Dockerfile` that is actually a build tool. Mitigation: the precedence rules (app > service > package) and the fact that misclassification only affects which template is used, not whether a file is generated. The generated content is still useful even if the type is slightly wrong.

**Risk: Generated nested AGENTS.md becomes stale after forge.yaml changes.** Mitigation: `forge.doctor` detects stale generated files and reports them. `forge.upgrade` regenerates them. The generated marker enables drift detection.

**Risk: Agents ignore the generated marker and edit nested files by hand.** Mitigation: the marker is prominent and includes the re-run command. `forge.doctor` detects the loss of the marker (file was generated, now hand-edited) and reports it.

**Risk: forge-bootstrap improvement proposals are noisy or unwanted.** Mitigation: proposals are opt-in (operator confirmation required). The skill presents them in human language, not as CLI commands. The operator can decline all proposals.

**Risk: Performance — scanning all directories for `package.json` in large projects.** Mitigation: the scan skips `node_modules/`, `.git/`, `dist/`, `.turbo/`, `.cache/`. In typical forge-consumer projects (few workspaces), the scan is fast. For very large monorepos, the scan is still O(n) in directory count, which is acceptable for a non-pipeline command.

## Acceptance criteria

- [ ] `forge.agents.generate` discovers workspace directories (containing `package.json`) and generates nested `AGENTS.md` for each, with the generated marker
- [ ] Workspace type auto-detection correctly classifies app (astro.config), service (Dockerfile/service.config.yaml), and package (package.json only) workspaces
- [ ] `forge.agents.generate` skips existing hand-written `AGENTS.md` (no generated marker) and reports them in the `skipped` array
- [ ] `forge.agents.generate` regenerates existing generated `AGENTS.md` (with generated marker) when content differs
- [ ] `forge.upgrade` generates missing nested `AGENTS.md` for workspace directories without touching hand-written files
- [ ] `forge.doctor` reports missing nested `AGENTS.md`, stale generated files, and hand-written improvement opportunities as diagnostics
- [ ] `forge-bootstrap` proposes improvements to existing hand-written `AGENTS.md` during transplant onboarding, with operator confirmation
- [ ] `--json` output includes `generated` and `skipped` arrays covering both root and nested files
- [ ] `rfc.validate` passes on this file before merging
