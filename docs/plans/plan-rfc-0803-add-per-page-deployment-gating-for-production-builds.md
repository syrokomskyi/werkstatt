### Step 3. Validator: create `deployment.gate.validate` command

**Goal:** Create the validator that checks non-gated pages do not reference gated pages (GATE-01: navigation, GATE-02: block props, GATE-03: parentPageId).

**Agent actions:**

- Create `packages/werkstatt-site/src/checks/deployment-gate.ts`
- Implement `DeploymentGateViolation` interface with `rule: "GATE-01" | "GATE-02" | "GATE-03"`, `sourcePageId`, `gatedPageId`, `referenceType`, `message`
- Implement `runDeploymentGateValidate(input, context)`:
  - Load `system.md` pages[] and build `gatedPageIds` via `collectGatedPageIds()`
  - If `gatedPageIds` is empty, return pass with no violations
  - GATE-01: Read navigation files (`navigation.md`, `labels.md`) and check if any non-gated page references a gated pageId in nav targets, `navIds`, `legalIds`, `transparencyIds`
  - GATE-02: Iterate all page content entries, inspect block props for `section-cta` with `kind: internal` targeting a gated `pageId`
  - GATE-03: Iterate all `system.md` pages[] entries and check if a non-gated page has `parentPageId` pointing to a gated pageId
  - Return violations array with `exitCode: 1` if any found
- Register in `packages/werkstatt-site/src/checks/command-tables/04-content-quality.ts`:
  ```ts
  {
    name: "deployment.gate.validate",
    description: "Validate that non-gated pages do not reference gated pages.",
    scope: "app",
    flags: {},
    supportsAllSites: true,
    reads: ["<app>/src/content/system.md", "<app>/src/content/pages/**/*.md", "<app>/src/content/navigation.md", "<app>/src/content/labels.md"],
    modulePaths: ["checks/deployment-gate.ts"],
    execute: runDeploymentGateValidate,
  },
  ```
- Verify: `pnpm --filter @warpgogol/werkstatt-site run build:check`

**Validation:**

- `pnpm --filter @warpgogol/werkstatt-site run build:check` passes
- `pnpm exec werkstatt run deployment.gate.validate --site warpgogol-com` (trivially passes — no gated pages yet)

**Completion criterion:** `deployment.gate.validate` command is registered, executable, and passes trivially when no gated pages exist.

### Step 5. Semantic loader: add `gatedPageIds` filter to `loadSemanticSiteModel()`

**Goal:** Add an optional `gatedPageIds` parameter to `loadSemanticSiteModel()` so callers that need to exclude gated pages (llms.generate, semantic-parity, page-markdown, content-regression, agent-knowledge-compute) can opt in, while callers that should still process all pages (page-blocks-validate, material-metadata-write) are unaffected.

**Agent actions:**

- Read `packages/werkstatt-site/src/content/semantic-loader.ts`
- Add `gatedPageIds?: Set<string>` to `SemanticLoaderOptions` interface (line 60-64)
- In `loadSemanticSiteModel()`, destructure `gatedPageIds` from options
- In the `for (const page of pages)` loop (line 728), after the `semanticType` check and before `resolvePageOutput`, add: `if (gatedPageIds?.has(page.pageId as string)) continue;`
- Update callers that should filter gated pages in production:
  - `checks/llms.ts` — compute `gatedPageIds` from manifest and pass to `loadSemanticSiteModel()`
  - `checks/semantic-parity.ts` — same, so validation matches llms.generate output
  - `checks/page-markdown.ts` — same, markdown twins should exclude gated pages
  - `checks/content-regression.ts` — same, regression snapshots should exclude gated pages
  - `checks/agent/agent-knowledge-compute.ts` — same, agent knowledge should exclude gated pages
- Callers that should NOT filter (unchanged):
  - `checks/page-blocks-validate.ts` — validates block structure, gated pages still need validation
  - `codegen/material-metadata-write.ts` — fallback org metadata, not page-specific
- In each filtering caller, compute `gatedPageIds` via `collectGatedPageIds(manifest.pages)` using the manifest already loaded by `loadSystemManifest()` in the same function. `collectGatedPageIds()` returns an empty set in dev mode (`process.env.NODE_ENV !== "production"`) — callers do not need their own env check.
- Verify: `pnpm --filter @warpgogol/werkstatt-site run build:check`

**Validation:**

- `pnpm --filter @warpgogol/werkstatt-site run build:check` passes

**Completion criterion:** `loadSemanticSiteModel()` accepts optional `gatedPageIds`, filtering callers pass it, non-filtering callers are unchanged, and `build:check` passes.

## 5. Risks and mitigation

| Risk (from RFC) | Mitigation (plan step) |
| --- | --- |
| Stale gate — operator forgets to remove `production: false` | Step 3: validator reports gated pages as informational notices in build output |
| SEO impact for previously-live pages | Out of scope — RFC nonGoals explicitly excludes automatic `retiredRoutes` entries |
| Agent misinterpretation — confusing gating with feature flags | Step 7: AGENTS.md update clarifies gating is build-time only |
| False positives in reference safety | Step 3: GATE-01/02/03 are hard errors with no escape hatch |
| Build pipeline complexity | Step 2: filtering happens in `getRouteRegistry()` — single source of route topology; downstream consumers use filtered registry without conditional logic |
| LLMs.txt not filtered (semantic model doesn't use route registry) | Step 5: `gatedPageIds` parameter added to `loadSemanticSiteModel()`; filtering callers pass it, non-filtering callers unchanged |

## 6. Escalation triggers

- If implementation reveals an invariant conflict with DNA-9 or DNA-13, run `pnpm exec werkstatt run rfc.supersede.propose --id RFC-0803 --reason "..." --invariant "DNA-N"` instead of working around it (RFC-0334).
- If `loadSemanticSiteModel()` cannot be filtered without modifying the semantic loader itself, escalate to a follow-up RFC rather than modifying the semantic model architecture.
