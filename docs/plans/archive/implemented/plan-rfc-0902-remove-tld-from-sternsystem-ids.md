### Step 1. Add `KNOWN_TLDS` and `hasTldSuffix()` to `naming-policy.ts`

**Goal:** Create the reusable TLD-suffix detection function and TLD set.

**Agent actions:**

- Add `KNOWN_TLDS` as a `ReadonlySet<string>` containing: `com`, `org`, `net`, `de`, `at`, `ch`, `it`, `fr`, `es`, `nl`, `be`, `pl`, `se`, `no`, `dk`, `fi`, `pt`, `cz`, `sk`, `hu`, `ro`, `bg`, `hr`, `si`, `lt`, `lv`, `ee`, `ie`, `lu`, `mt`, `cy`, `gr`, `uk`, `us`, `ca`, `au`, `nz`, `io`, `co`, `ai`, `dev`, `app`, `eu`, `info`, `biz`, `me`, `tv`, `gg`, `to`, `xyz`, `site`, `online`, `store`, `shop`, `blog`, `cloud`
- Add `hasTldSuffix(id: string): boolean` — splits by `-`, checks if last segment is in `KNOWN_TLDS`, returns false for single-segment IDs
- Update `STERNSYSTEM_ID_POLICY.examples`: replace `warpgogol-com` with `warpgogol`
- Update `STERNSYSTEM_ID_POLICY.counterExamples`: add `warpgogol-com`, `nicaragua-projekt-org`
- Update `MISSION_ID_POLICY.examples`: replace `warpgogol-com-m000001` with `warpgogol-m000001`
- Update `RELEASE_ID_POLICY.examples`: replace `warpgogol-com-r000001` with `warpgogol-r000001`

**Validation:**

- `pnpm --filter @warpgogol/werkstatt run build:check`

**Completion criterion:** `KNOWN_TLDS` and `hasTldSuffix()` exported from `naming-policy.ts`; all `*POLICY.examples` use `warpgogol` prefix (not `warpgogol-com`); typecheck passes.

### Step 2. Add `STERN-ID-TLD` rule to `sternsystem-validate.ts`

**Goal:** Integrate the TLD check into the existing validation loop.

**Agent actions:**

- Import `hasTldSuffix` from `../schemas/naming-policy.ts`
- In the `for (const entry of systems)` loop (after the `apps-collision` check, before bundle contract check), add:
  ```ts
  if (hasTldSuffix(entry.id)) {
    violations.push({
      systemId: entry.id,
      rule: "STERN-ID-TLD",
      message: `Sternsystem ID '${entry.id}' ends in a TLD suffix — use the business ID without domain TLD (e.g. 'warpgogol' not 'warpgogol-com')`,
    });
  }
  ```

**Validation:**

- `pnpm --filter @warpgogol/werkstatt run build:check`

**Completion criterion:** `sternsystem.validate` emits `STERN-ID-TLD` violation for any system whose ID ends in a known TLD; typecheck passes.

**Human review:** no

### Step 3. Add TLD check to `sternsystem-register.ts`

**Goal:** Reject TLD-suffixed IDs at registration time before any files are written.

**Agent actions:**

- Import `hasTldSuffix` from `../schemas/naming-policy.ts`
- After the `if (!id)` check (line 152), add:
  ```ts
  if (hasTldSuffix(id)) {
    throw new Error(
      `[sternsystem.register] id '${id}' ends in a TLD suffix — use the business ID without domain TLD (e.g. 'warpgogol' not 'warpgogol-com')`,
    );
  }
  ```
- This check runs before `--amend` and non-amend paths, covering both registration and amend.

**Validation:**

- `pnpm --filter @warpgogol/werkstatt run build:check`

**Completion criterion:** `sternsystem.register` throws before writing any files when `--id` has a TLD suffix; `--amend` also throws; typecheck passes.

**Human review:** no

## 5. Risks and mitigation

| Risk (from RFC) | Mitigation (plan step) |
| --------------- | ---------------------- |
| False positives (business name ends in TLD-like segment) | Step 1: `KNOWN_TLDS` is conservative and adjustable; operator can remove a TLD if legitimate |
| Destructive migration data loss (Bordbuch, missions, releases) | Step 7: operator backs up content before deletion; Bordbuch/release history is explicitly accepted as lost |
| External mirror orphan (GitHub repo) | Step 7: operator manually deletes or renames GitHub repo |
| Service config drift | Step 7: all downstream service configs listed and updated in the same migration pass |

## 6. Escalation triggers

- If implementation reveals an invariant conflict with DNA-44 or DNA-45 that cannot be resolved by tightening the existing text, run `pnpm exec werkstatt run rfc.supersede.propose --id RFC-0902 --reason "..." --invariant "DNA-44"` instead of working around it.
- If the `KNOWN_TLDS` set proves too aggressive (blocking legitimate IDs), do not weaken the `STERN-ID-TLD` rule — instead, remove the specific TLD from the set and document the exception in the RFC's Risks section.
