### Step 1. Add `checklistItems[]` to archetype and manifest schemas

**Goal:** Add the `checklistItems[]` prop with `ChecklistItem` shape and `ChecklistRuleType` enum to both the archetype YAML and the UI section manifest YAML.

**Agent actions:**

- Edit `packages/ontology/archetypes/sections/send-message.yaml`:
  - Add `checklistItems` to `propsSchema.shape` as a Zod array of objects with fields: `id` (string), `label` (string), `rule` (enum: min-length, contact-details, url-presence, keyword-match), `value` (number, optional), `keywords` (array of strings, optional)

- Edit `packages/ui/src/sections/send-message/send-message-section.manifest.yaml`:
  - Add `checklistItems` to `propsSchema.properties` as a JSON Schema array with matching item shape
  - Bump `version` from `1.2.0` to `1.3.0`
- Keep existing individual label props (`checklistTitle`, `checklistReadyLabel`, `checklistLengthLabel`, `checklistContactLabel`) — they serve as default fallback labels

**Validation:**

- `pnpm exec site-kernel run rfc.validate --id RFC-0757`
- `pnpm --filter @warpgogol/ontology build:check`

**Completion criterion:** Both YAML files have `checklistItems` in their `propsSchema` with the correct item shape; versions bumped to 1.3.0; typecheck passes.

### Step 3. Refactor `send-message-section.astro` template

**Goal:** Replace the 2 hardcoded checklist items with N dynamic items rendered from `checklistItems[]`, with fallback to default 2 items when prop is absent.

**Agent actions:**

- In the Astro frontmatter, construct the effective checklist items:
  - If `props.checklistItems` is present (including empty array), use it directly
  - If `props.checklistItems` is absent, construct default 2 items from `checklistLengthLabel`, `checklistContactLabel`, and `minMessageLength`
- Replace the hardcoded `<li>` elements with a `.map()` over the effective items array
- Each item renders with `data-send-message-checklist-item="{item.id}"` attribute
- Each item's label text goes in `<span data-send-message-checklist-text="{item.id}">`
- Conditionally render the entire checklist container only when `checklistItems` is not an empty array
- Keep the checklist header (title + pending/ready icons) as-is

**Validation:**

- `pnpm --filter @warpgogol/ui build:check`

**Completion criterion:** Template renders N items from `checklistItems[]` prop; falls back to default 2 items when prop is absent; hides checklist container when `checklistItems: []`; no hardcoded `length`/`contact` item attributes in the template.

**Human review:** no

### Step 4. Refactor `send-message-section.client.ts` with `evaluateRule()` dispatcher

**Goal:** Replace the hardcoded `updateChecklist()` function with a generic `evaluateRule()` dispatcher that handles all 4 rule types and iterates over `checklistItems[]`.

**Agent actions:**

- Add `URL_REGEX` constant for `url-presence` rule type
- Add `evaluateRule(rule, message, item)` function with switch over 4 rule types: `min-length`, `contact-details`, `url-presence`, `keyword-match`
- Refactor `updateChecklist()` to iterate over checklist items from the form's data attributes (serialized `checklistItems[]` via `data-checklist-items` JSON attribute on the form)
- For `min-length` items, update the label text with remaining character count on each input event
- For all other items, the label text is static (set by the template)
- Gate submit on all items being satisfied
- Handle unknown rule types: ignore the item and emit `console.warn`
- Keep the `hasContactDetails()` function for `contact-details` rule type (existing regex patterns)
- Keep the referrer field handling unchanged

**Validation:**

- `pnpm --filter @warpgogol/ui build:check`

**Completion criterion:** Client script has `evaluateRule()` function with 4 rule type cases; submit gating works for N items; `min-length` items show remaining character count; unknown rule types are ignored with `console.warn`.

**Human review:** no

## 5. Risks and mitigation

| Risk (from RFC) | Mitigation (plan step) |
| --- | --- |
| Closed rule set extensibility | Step 1, 4: `keyword-match` with `keywords[]` covers many cases; new rule types via follow-up RFC |
| Checklist bypass (client-side only) | Step 4: server-side validation (RFC-0572 regex) remains unchanged — checklist is UX gate, not security |
| Agent misinterpretation of individual label props | Step 7: `AGENTS.md` update clarifies `checklistItems[]` is the generalizable mechanism |
| Visual regression from N-item template | Step 3, 5: generic CSS class + `data-send-message-checklist-item` attribute; 2 default items render identically |
