### Step 2. Add `runRfcNextId` handler

**Goal:** Implement the read-only handler that scans `docs/rfcs/` recursively and returns the next free RFC number.

**Agent actions:**

- Add `runRfcNextId` function to `packages/forge/os/rfc/handlers/list-create.ts`
- Import `listRfcFiles` from `../frontmatter-io.ts` (already imported in this file)
- The handler:
  - Gets `workspaceRoot` from context
  - Builds `rfcDirPath = path.join(workspaceRoot, RFC_DIR)`
  - Calls `listRfcFiles(rfcDirPath)` (recursive scan)
  - Extracts numeric prefix from each filename via `path.basename(f).match(/^rfc-(\d{4})/)`
  - Computes `maxId = max(all numbers)`, `nextNumber = maxId + 1`
  - If no files found: `nextId: "RFC-0001"`, `nextNumber: 1`, `maxExistingId: "none"`, `scannedFiles: 0`
  - Returns `ForgeCommandResult<RfcNextIdResult>`
- Export `runRfcNextId` from `packages/forge/os/rfc/handlers.ts` (add to the existing re-export from `./handlers/list-create.ts`)

**Validation:**

- `pnpm --filter @wgogol/forge build:check` passes

**Completion criterion:** `runRfcNextId` is exported from `handlers.ts` and returns the correct shape

**Human review:** no

### Step 5. Add V-31 validation rule

**Goal:** Detect duplicate filename numbers and filename/id mismatches across the full RFC tree.

**Agent actions:**

- In `packages/forge/os/rfc/handlers/validate-rules.ts`, add V-31 at the end of `validateSingleRfc` (after V-30)
- The check needs access to all parsed files. The `allParsed` map (keyed by RFC id) is already passed as a parameter. However, V-31 needs filename-level data. Two approaches:
  - **Option A (recommended):** Add a new parameter `allParsedByFile: Map<string, { fileName: string; parsed: ParsedRfc }>` to `validateSingleRfc`. The caller in `validate.ts` already builds this map (line 59). This is the cleanest approach — the data already exists.
  - **Option B:** Build the filename-number map inside `validateSingleRfc` from `allParsed` entries. This works but re-derives data the caller already has.
- Use Option A: add `allParsedByFile` parameter to `validateSingleRfc` and pass it from `validate.ts`
- V-31 logic (runs once per file, but the duplicate check needs cross-file state):
  - **Filename/id mismatch:** Extract the numeric prefix from `fileName` via `path.basename(fileName).match(/^rfc-(\d{4})/)`. Extract the numeric part of `rfcId` via `parseInt(rfcId.replace(/^RFC-/, ""), 10)`. If they differ, add violation: `Filename number <filenum> does not match frontmatter id <rfcId>`.
  - **Duplicate filename number:** This requires cross-file state. Add a `seenFilenameNumbers: Map<number, string>` parameter to `validateSingleRfc` (similar to the existing `seenIds` pattern). The caller initializes an empty map. For each file, extract the filename number. If it's already in the map, add violation: `Duplicate filename number <num> — also in <other-file>`. Otherwise, set it.
- Update the call site in `validate.ts` to pass `allParsedByFile` and `seenFilenameNumbers`

**Validation:**

- `pnpm --filter @wgogol/forge build:check` passes
- `pnpm exec werkstatt run rfc.validate --json` passes (no existing mismatches or duplicates)

**Completion criterion:** V-31 is implemented and `rfc.validate` passes on the existing tree

**Human review:** no

## 6. Escalation triggers

- If V-31 reveals existing filename/id mismatches that were not caught by the pre-implementation scan, do not fix them in-place — investigate the root cause and determine whether a separate remediation RFC is needed.
- If adding `allParsedByFile` as a parameter to `validateSingleRfc` reveals a deeper architectural issue with the validation function's signature, consider refactoring in a separate RFC rather than expanding the parameter list further.
