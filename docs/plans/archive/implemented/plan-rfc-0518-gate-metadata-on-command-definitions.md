## 5. Risks and mitigation

| Risk (from RFC) | Mitigation (plan step) |
| --------------- | ---------------------- |
| Metadata drift — `gate` field describes behavior but does not enforce it | Step 6 verifies drift detection via `ecosystem.manifest.validate`; RFC-0519's `gate.catalog.validate` will cross-check (out of scope for this RFC) |
| Incomplete population — only ~10 commands have `gate` initially | Step 2-4 populate exactly the initial set from the RFC; remaining commands backfilled incrementally |
| Phase mismatch — declared phase might not match pipeline placement | Out of scope for RFC-0518; RFC-0519 GATE-CAT-04 cross-checks |
| Ecosystem manifest schema — additive change to commands array | Step 5 adds `gate?` as optional; schema version stays at 2; Step 6 verifies no drift |
| Orphaned gate metadata — command has gate but no pipeline | Out of scope; RFC-0519 handles this |

## 6. Escalation triggers

- If implementation reveals that `KernelRegisteredCommandInfo` does not inherit `gate` from `KernelCommandMetadata` (type structure issue), stop and create a superseding RFC — this would indicate a structural problem with the command registration type hierarchy.
- If `ecosystem.manifest.validate` cannot detect `gate` field drift (because the manifest comparison is field-by-field rather than whole-file), investigate the comparison logic in `manifest-commands.ts` before proceeding.
