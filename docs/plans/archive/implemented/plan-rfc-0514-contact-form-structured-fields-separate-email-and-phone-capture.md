**Goal:** Add `emailField` (required) and `phoneField` (optional) to the send-message section manifest; remove `contactRequirementMessage` from required props.

**Agent actions:**

  - Add `phoneField` to `propsSchema.properties` as an optional object with the same sub-properties

### Step 3. Update client script to read and validate structured fields

**Goal:** Read `email`/`phone` from structured inputs, validate, include in payload; remove regex-based `hasContactDetails`.

**Agent actions:**

**Validation:**

- `pnpm --filter @gogol/ui run build:check` — verify client script compiles
- Manual test: form submission sends `email` and `phone` as top-level fields

**Completion criterion:** Client script reads structured fields, validates email format, includes them in payload; regex code is removed; `hasContactDetails` is gone.

### Step 4. Update server API to accept top-level email/phone

**Goal:** Accept `email`/`phone` as top-level fields in `SendMessageBody`; remove regex extraction; pass through to `IntegrationEvent.contact`.

**Agent actions:**

- Edit `packages/ui/src/sections/send-message/send-message-section.api.ts`:
  - Update `SendMessageBody` type to include `email?: string` and `phone?: string`
  - Remove `EMAIL_REGEX`, `PHONE_REGEX`, and `hasContactDetails` function
  - Read `email` and `phone` directly from the request body
  - Validate email format when provided (simple format check, not regex extraction from message)
  - Return `400` with `error: "missing-email"` when `emailField.required` is true and no email is provided
  - Return `400` with `error: "invalid-email"` when email fails format validation
  - Return `400` with `error: "missing-phone"` when `phoneField.required` is true and no phone is provided
  - Pass `email` and `phone` directly to `IntegrationEvent.contact` (no extraction from message body)

**Validation:**

- `pnpm --filter @gogol/ui run build:check` — verify API route compiles
- Manual test: API receives `email`/`phone` as top-level fields and maps them to `IntegrationEvent.contact`

**Completion criterion:** API accepts top-level `email`/`phone`; regex extraction code is removed; `IntegrationEvent.contact` is populated from structured fields; error responses match the RFC's failure modes.

**Human review:** no

## 5. Risks and mitigation

| Risk (from RFC) | Mitigation (plan step) |
| --------------- | ---------------------- |
| Increased form complexity | Step 2: email is the only required structured field; phone is optional — rendered conditionally |
| Client-side validation bypass | Step 3: client validates email format; Step 4: server validates email format independently |
| Migrator failure on edge-case configurations | Step 6: migrator is idempotent (RFC-0479); Step 5: `contact.form.validate` catches missing `emailField` after migration |
| Cross-locale rendering divergence | Step 5: `contact.form.validate` enforces `emailField` consistency across locales; `phoneField` divergence is by design |

## 6. Escalation triggers

- If implementation reveals an invariant conflict with DNA-17 (Uni manifest contract), run `pnpm exec site-kernel run rfc.supersede.propose --id RFC-0514 --reason "..." --invariant "DNA-17"` instead of working around it.
- If the migrator cannot handle a site's send-message block configuration, do not patch the migrator to special-case it — raise the issue and let the operator fix the content in the workpiece (RFC-0479 error handling).
