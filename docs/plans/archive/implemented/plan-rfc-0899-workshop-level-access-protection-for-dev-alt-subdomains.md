## 3. Step sequence

### Step 1. Middleware implementation in werkstatt-shared

**Goal:** Create the access protection middleware with Host check, Basic Auth, constant-time compare, and X-Robots-Tag headers.

**Agent actions:**

- Create `packages/werkstatt-shared/src/share/middleware/access-protection.ts`:
  - Import `defineMiddleware` from `astro:middleware`
  - Export `accessProtectionMiddleware` (a `defineMiddleware` handler)
  - Import `env` from `cloudflare:workers` (NOT `context.locals.runtime.env` — Astro v6 removed `locals.runtime.env`, per `packages/werkstatt-shared/src/share/env.d.ts:62`)
  - Check `Host` header: if `host.startsWith("dev.")` or `host.startsWith("alt.")` → require auth; otherwise pass through
  - If `env.ACCESS_PIN` is unset → pass through but still set `X-Robots-Tag: noindex, nofollow, noai, noimageai` on the response
  - If PIN is set → check `Authorization` header for `Basic <base64(access:PIN)>` using constant-time comparison BEFORE calling `next()`
  - If auth fails → return 401 with `WWW-Authenticate: Basic realm="Staging Access"` and `X-Robots-Tag` headers
  - If auth succeeds → call `next()`, set `X-Robots-Tag` on the response
  - Use `btoa()` (Workers runtime), NOT `Buffer` or `crypto.timingSafeEqual`
  - Include `MODULE_CONTRACT` and `CHANGE_SUMMARY` comment blocks
- Add subpath export `./share/middleware/access-protection` to `packages/werkstatt-shared/package.json`
- Run `pnpm --filter @warpgogol/werkstatt-shared build:check`

**Validation:**

- `pnpm --filter @warpgogol/werkstatt-shared build:check` passes
- `accessProtectionMiddleware` is exported and typed correctly

**Completion criterion:** Middleware file exists, builds, and is exported via subpath export.

**Human review:** no

### Step 4. Command implementation: leitstand.access.protect/unprotect/status

**Goal:** Implement three workshop-level commands for PIN management.

**Agent actions:**

- Create `packages/werkstatt/src/leitstand/access-commands.ts`:
  - `runAccessProtect(input, context)`: resolves system config, validates/generates PIN, runs `wrangler secret put ACCESS_PIN` for dev and alt Workers (best-effort per channel), writes `accessPin` to `system-state.yaml`, returns `AccessProtectResult`
  - `runAccessUnprotect(input, context)`: runs `wrangler secret delete ACCESS_PIN` for dev and alt Workers (idempotent — secret-not-set is success), clears `accessPin` from `system-state.yaml`, returns `AccessUnprotectResult`
  - `runAccessStatus(input, context)`: reads `accessPin` from `system-state.yaml`, reports per-channel protection status, returns `AccessStatusResult`
  - Use `readSystemConfigSmart` for deployment channel/worker resolution
  - Use `readSystemState`/`writeSystemState` for `accessPin` field
  - Use `spawn("npx", ["--yes", "wrangler", "secret", "put", "ACCESS_PIN"])` pattern (matching `service-deploy-helpers.ts`)
  - **Pipe PIN to stdin**: `child.stdin.write(pin + "\n"); child.stdin.end()` — `wrangler secret put` reads the value from stdin
  - **Temp wrangler.jsonc**: create a temporary `wrangler.jsonc` with `{ "name": "<workerName>", "compatibility_date": "2024-09-23" }` in a temp directory, run wrangler from there, clean up after. This is needed because `wrangler secret put` reads the worker name from `wrangler.toml`/`wrangler.jsonc` in CWD, and we're running from the werkstatt repo root, not the site's deployment directory.
  - PIN validation: `/^\d{4}$/`; auto-generate random 4-digit PIN if `--pin` omitted
  - Best-effort: if dev fails, alt is still attempted; per-channel status reported
  - `wrangler secret delete` failure (secret not set) → exitCode 0 with warning (idempotent)
- Update `packages/werkstatt/src/leitstand/leitstand.module.ts`:
  - Import and register 3 new commands with `--site` (required), `--system` (alias) flags
  - `leitstand.access.protect` also has `--pin` (optional string)
  - `writes` and `reads` fields per command
- Update `packages/werkstatt/src/leitstand/index.ts`:
  - Re-export `runAccessProtect`, `runAccessUnprotect`, `runAccessStatus`
- Run `pnpm --filter @warpgogol/werkstatt build:check`

**Validation:**

- `pnpm --filter @warpgogol/werkstatt build:check` passes
- Commands are registered (verified by typecheck)

**Completion criterion:** Three command handlers implemented, registered in module, typecheck passes.

## 5. Risks and mitigation

| Risk (from RFC) | Mitigation (plan step) |
| --- | --- |
| PIN guessing (10K combinations, ~2.8h brute force) | Step 1 — middleware returns 401 for incorrect PIN; Cloudflare rate limiting can be added later |
| PIN leakage in URLs (Basic Auth limitation) | Acceptable for staging environments — documented in RFC |
| Middleware performance (Host header check O(1)) | Step 1 — simple string comparison, no measurable impact |
| Secret management (wrangler auth required) | Step 4 — error message includes "Run 'wrangler login' first" hint |
| PIN in system-state.yaml (visible in git) | Acceptable — 4-digit staging code, not high-security password. Documented in RFC. |

## 6. Escalation triggers

- If implementation reveals that `wrangler secret put` cannot be called programmatically via `spawn` in the kernel context, run `pnpm exec werkstatt run rfc.supersede.propose --id RFC-0899 --reason "wrangler secret put not callable from kernel" --invariant "DNA-73"` instead of working around it.
- If `cloudflare:workers` module import is not available in the test environment, mock it via vitest `vi.mock("cloudflare:workers", ...)` with a configurable `env` object.
- If the middleware chain order causes type errors in the integration test (e.g. `accessProtectionMiddleware` has incompatible type), investigate the `defineMiddleware` return type compatibility before changing the chain order.
