## 3. Step sequence

### Step 1. PBP entity contracts (TypeScript interface + Zod schema)

**Goal:** Define the `client-testimonial` PBP entity type and Zod schema, register them in the schema registry.

**Agent actions:**

- Create `packages/werkstatt-site/src/domain/pbp/entities/client-testimonial.ts`:
  - Export `CLIENT_TESTIMONIAL_SCHEMA_ID = pbpSchemaId("client-testimonial")`
  - Export `PbpClientTestimonial` interface extending `PbpEntity` with fields: `type: "client-testimonial"`, `name`, `quote`, `authorName`, `authorRole?`, `authorOrganization?`, `evidenceRef?`
  - Follow the pattern of `entities/claim.ts` and `entities/evidence-source.ts`
- Create `packages/werkstatt-site/src/domain/pbp/schemas/client-testimonial.ts`:
  - Export `clientTestimonialSchema = pbpEntitySchema.extend({ type: z.literal("client-testimonial"), name, quote, authorName, authorRole?, authorOrganization?, evidenceRef? }).strict()`
  - Import `pbpEntitySchema` and `nonEmptyString` from existing schema modules
  - Do NOT narrow `status` — inherit full `pbpEntityStatusSchema` from `pbpEntitySchema`
  - Do NOT add `slug` field — `id` from envelope is the sole identifier
- Edit `packages/werkstatt-site/src/domain/pbp/schemas/index.ts`:
  - Import `clientTestimonialSchema` as `_clientTestimonial`
  - Add `[pbpSchemaId("client-testimonial")]: _clientTestimonial` to `pbpSchemaById`
  - Add `_clientTestimonial` to `pbpEntityDiscriminatedUnion` array
- Edit `packages/werkstatt-site/src/domain/pbp/index.ts`:
  - Add barrel export for `PbpClientTestimonial` and `CLIENT_TESTIMONIAL_SCHEMA_ID`

**Validation:**

- `pnpm --filter @warpgogol/werkstatt-site run build:check` — typecheck passes
- `pnpm --filter @warpgogol/werkstatt-site run test` — existing tests still pass

**Completion criterion:** `clientTestimonialSchema` is registered in `pbpSchemaById` and `pbpEntityDiscriminatedUnion`; `PbpClientTestimonial` is exported from the package barrel; typecheck passes.

### Step 4. Section manifest and component

**Goal:** Create the `gratitude-section` UI component with manifest, Astro template, and CSS styles.

**Agent actions:**

- Create `packages/werkstatt-site/src/domain/ui/sections/gratitude/gratitude-section.manifest.yaml`:
  - `id: gratitude-section`
  - `uniName: gratitude-section`
  - `layer: section`
  - `semanticId: gratitude`
  - `archetype: gratitude`
  - `cosmicName: Gonggong`
  - `role: client-gratitude`
  - `version: 1.0.0`
  - `intent: [build-trust, differentiation]`
  - `industryFit: []`
  - `contentSchemaKey: gratitude-section`
  - `contentTypesPath: ./gratitude-section.types.generated.ts`
  - `propsSchemaCompose: [section-visual, section-header]`
  - `propsSchema:` with `type: object`, `additionalProperties: false`, `required: [header]`, `properties:` with optional `tag` field
  - Follow the pattern of `faq-list-section.manifest.yaml`
- Create `packages/werkstatt-site/src/domain/ui/sections/gratitude/gratitude-section.astro`:
  - Import `getCollection` from `astro:content`
  - Load published `client-testimonial` entities via `getCollection("business-profile")`
  - Filter by `type === "client-testimonial"` and `status === "published"`
  - If no testimonials found for active locale, render nothing (empty state — no DOM element)
  - Render each testimonial as a card with class `gratitude-card` containing:
    - Decorative quote mark
    - Quote text (italic)
    - Author name (bold)
    - Author role + organization (small, only if filled)
    - Optional link "Zum Nachweis →" to `/{lang}/nachweise/{slug}` when `evidenceRef` is set, where `slug` is resolved from the referenced evidence-source entity (look up the evidence-source by `id === evidenceRef` and use its `slug` field for the URL). If the evidence-source has no `slug` or is not found, omit the link.
  - Use `--ds-*` design tokens for styling
  - **Consent note:** Content authoring of a `client-testimonial` entity implies the client has consented to public display of their name, role, organization, and quote. The `consent` PBP entity workflow (RFC-0706) handles consent records separately — no `consentRef` field is needed on the testimonial entity.
- Create `packages/werkstatt-site/src/domain/ui/sections/gratitude/gratitude-section.css`:
  - Card grid layout (2 columns on desktop, 1 column on mobile)
  - Glass-effect or subtle card styling using `--ds-*` tokens
  - Quote typography styles

**Validation:**

- `pnpm --filter @warpgogol/werkstatt-site run build:check` — typecheck passes

**Completion criterion:** Manifest, Astro component, and CSS files exist; `props.types.generate` produces the generated types file without errors; component renders nothing when no published testimonials exist.

## 5. Risks and mitigation

| Risk (from RFC) | Mitigation (plan step) |
| --- | --- |
| Agent misinterpretation — confusing client-testimonial with evidence-source | Step 1: `type: z.literal("client-testimonial")` makes the entity type distinct; Step 4: section component filters by `type === "client-testimonial"` only |
| Content maintenance — locale mirroring | Step 6: create content per locale; `pbp.content.validate` enforces mirroring; empty-state rule handles partial coverage |
| Performance — O(n) getCollection at build time | Step 4: build-time only, acceptable for static generation; no client-side fetching |
| Anti-fabrication — agents fabricating testimonials | Step 6: human review point; content sourced from existing PDF evidence documents on Nachweise page; agents must not fabricate |

## 6. Escalation triggers

- If implementation reveals an invariant conflict with DNA-5 or DNA-17, run `pnpm exec werkstatt run rfc.supersede.propose --id RFC-0900 --reason "..." --invariant "DNA-N"` instead of working around it.
- If `Gonggong` is already assigned to another section at implementation time (e.g. another RFC was implemented in parallel), select a different unused planet name from `PlanetCatalog` and update the RFC via a follow-up amendment.
