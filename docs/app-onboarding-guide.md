# App Onboarding Guide

How to add a new deployable site to the warpgogol-4 monorepo.

> **Canonical rule:** new sites are **generated via `onboarding.scaffold`** (package `@warpgogol/site-kernel-onboarding`). Never hand-craft an app and never copy an existing app folder. Per-client divergence lives in content (`src/content/system.md` and the semantic domains), not in bespoke app code. See the onboarding paragraph in the root `AGENTS.md` and [RFC-0029](rfcs/RFC-0029-greenfield-rebuild-and-client-onboarding-playbook.md).

This document was rewritten for the RFC-0047 thin-app content surface. The earlier eight-wave hand-authoring flow (`src/configure/`, `src/content/components/`, `src/content/schemas/`, `src/semantic/`, `tokens-override.css`, manually-written `astro.config.mjs`/`tsconfig.json`/`package.json`) is **retired** — those surfaces are now either forbidden by `app.layout.validate`/`content.surface.validate` or generated by the build-prepare pipeline (RFC-0078).

---

## The onboarding flow (RFC-0075 phase chain)

1. Follow `.agents/workflows/00-prepare.md` and the RFC-0075 phase chain.
2. Treat `onboarding/.input/**` as **read-only**. `onboarding/.input/00-brief.md` must pass `brief.validate` before any phase starts.
3. Write all agent artifacts under `onboarding/.output/<NN-phase>/`.
4. Run `onboarding.scaffold` **only** inside the scaffold phase — it generates an RFC-compliant `apps/<id>/`.
5. Author the site by editing **content** (`apps/<id>/src/content/**`), not engineering files.
6. Gate readiness: `sites-check.run --site <id>` and `app.contract.full --site <id>`.

```sh
rtk pnpm exec werkstatt run brief.validate
rtk pnpm exec werkstatt run onboarding.scaffold --site <id>   # scaffold phase only
rtk pnpm exec werkstatt run sites-check.run --site <id>
rtk pnpm exec werkstatt run app.contract.full --site <id>
```

## What a current app looks like (RFC-0047)

An app is a thin composition shell. Author-facing content lives entirely in the semantic content domains; engineering files are generated.

```
apps/<id>/
  astro.config.mjs          # generated (RFC-0078)
  tsconfig.json             # generated (RFC-0078)
  package.json              # generated (RFC-0078)
  wrangler.jsonc            # generated — Cloudflare Workers deploy (RFC-0149)
  postcss.config.cjs
  tools/                    # generated kernel wiring (kernel.wire, RFC-0078)
  public/                   # build-only artifacts (sitemap, llms.txt, robots, …)
  src/
    content/                # ← the ONLY hand-authored surface (RFC-0047)
      system.md             #    site-wide config: identity, i18n, biome, shell, integrations, feature policy
      pages/{lang}/**.md    #    block-declarative pages
      prose/{lang}/**.md    #    long-form copy
      business/{lang}/**.md #    business records (org, team, offers, processors, …)
      navigation/{lang}/**.md
      site/{lang}/**.md     #    global UI labels / config
    content.config.ts       # generated
    middleware.ts           # generated (i18n redirect)
    env.d.ts, env.schema.generated.mjs, entitlements.generated.json   # generated
    pages/                  # generated thin Astro routes
    scripts/                # generated orchestrator
    styles/                 # generated global + biome CSS
```

**Forbidden in apps** (enforced by `app.layout.validate` / `content.surface.validate`): `src/configure/`, `src/semantic/`, `src/content/components/`, `src/content/schemas/`, `src/content/features/`, `src/components/`, `src/assets/images/`, `src/styles/tokens-override.css`, and any per-feature CSS outside `src/styles/`. Design tokens come from the app's biome in `system.md` + `@warpgogol/tokens` — never a per-app override file.

## Where things come from

| Concern | Source of truth |
| --- | --- |
| Brand tokens / palette | App biome in `system.md` → `@warpgogol/tokens` + `packages/ontology/biomes/*` |
| Sections & shell components | `@warpgogol/ui` (imported; never re-authored per app) |
| Business data | `src/content/business/**` validated against `@warpgogol/business` schemas |
| Feature visibility / behavior | `policy:` in RFC-0047 content domains — see [RFC-0183](rfcs/RFC-0183-content-layer-feature-policy-without-features-directory.md). No `src/configure/feature-graph.ts`, no `featureFlag:`. |
| Routes / config / middleware / env | Generated by `APPS_BUILD_PREPARE_PIPELINE` (RFC-0078) |
| Shared utilities (i18n, ids, base schemas) | `@warpgogol/share` — check it before writing app-local helpers (`packages/share/AGENTS.md`) |
| Deploy | Single Cloudflare Workers project (RFC-0149); images via `<ResponsiveImage>` + `cloudflare-runtime` provider (RFC-0152) |

## Promoting custom UI to `@warpgogol/ui`

If a site needs a section/component generic enough to share, add it to `packages/ui/src/{sections,components}/<name>/` with a colocated `<name>.manifest.yaml` (the Mirror Quintet — enforced by `manifest.contract.validate` + `mirror.quintet.validate`), then rebuild the registry:

```sh
rtk pnpm exec werkstatt run uni.registry.build
rtk pnpm exec werkstatt run uni.registry.validate
```

Apps consume it via the package export (`@warpgogol/ui/sections/<name>`), never via app-local component files.

## Quick-reference: key commands

| Command | Scope | Description |
| --- | --- | --- |
| `onboarding.scaffold` | workspace | Generate a new RFC-compliant `apps/<id>/` (scaffold phase only) |
| `brief.validate` | workspace | Gate `onboarding/.input/00-brief.md` before phases start |
| `sites-check.run` | app | Full author + postbuild check pipeline for an app |
| `app.contract.full` | app | Composite readiness gate (DNA-35) |
| `content.surface.validate` | app | Enforce the CMS-friendly thin content surface (RFC-0047) |
| `feature.policy.validate` | app | Validate `policy:` shape; reject retired feature surfaces (RFC-0183) |
| `uni.registry.build` / `uni.registry.validate` | workspace | Rebuild / verify `uni.registry.json` from manifests |
| `config.template.sync` | workspace | Propagate upgraded dependency versions into onboarding templates (RFC-0137) |
