Problem. The funnel validator carries a hardcoded VALID_EVENT_NAMES set that drifted — it's missing contact.phone_click, passport-view, star-map-navigate, and all donation events. Funnel steps referencing any of these are falsely rejected. Both funnel and experiment validators read system.yaml, a file that no longer exists after the RFC-0047 system.md migration. Their cross-reference checks silently no-op.

Solution. Deepen: one OntologyCatalogValidator module that owns the readdir → parseYaml → validate → cross-reference pipeline. Each catalog (events, funnels, experiments) contributes a small entry-validator. The module imports EVENT_NAMES from @warpgogol/growth and reads system config via loadSystemManifest — like growth-adapter.ts already does.

locality: catalog drift eliminated — one import locality: system.yaml → system.md fixed once leverage: three validators behind one interface delete 3 × boilerplate readdir/parse blocks

Problem. The adapter id list lives in adapter.ts; the module-specifier map lives in provider.astro. Adding an adapter requires editing both and keeping them in sync by hand. The validator in growth-adapter.ts imports KNOWN_ADAPTER_IDS but can't verify the provider's specifier map matches.

Solution. Deepen: one registry module that owns both the id list and the specifier map. adapter.ts, provider.astro, and the validator all import from it. The seam stays at the GrowthAdapter interface; the registry is behind it.

Problem. The vendor object (adapter + options) is defined twice — once in config.ts as GrowthVendorConfigSchema, once in ontology/growth.ts inside systemGrowthSchema. They're structurally identical today, but nothing enforces parity. A field added to one is silently absent from the other.

Solution. Ontology owns the canonical vendor schema; config.ts imports and composes it into GrowthConfigSchema. One shape, one place to change it.

locality: vendor schema drift eliminated leverage: one schema, two consumers delete 1 duplicated zod object
