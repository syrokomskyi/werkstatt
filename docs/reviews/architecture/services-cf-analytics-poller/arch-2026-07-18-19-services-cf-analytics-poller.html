Problem: runPollCycle calls fetch() directly via the inline graphqlRequest function. There is no seam — the Cloudflare API endpoint, auth header, and response shaping are fused into the cycle orchestration. The cycle cannot be exercised without real network.
Solution: Extract a CloudflareAnalyticsClient module that owns endpoint, token, query execution, and response shaping. runPollCycle accepts the client as a parameter. A FetchImpl type at the client's seam enables fake injection — mirroring fleet-probe-runner's FetchImpl/TlsImpl pattern.
leverage: one adapter, N tests locality: CF API knowledge in one module depth: cycle interface shrinks parity: matches fleet-probe-runner

Problem: runPollCycle is 60 lines doing five distinct things: config loading, zone loading, window computation, per-zone GraphQL + transform, and metric dispatch. Watermark seam is half-built — readWatermark is dead, write-ahead is incomplete

Strong in-process

imports readWatermark ✓

After — complete or delete
Option A: complete the seam

Problem: readWatermark is imported in loop.ts but never called. The README claims "persist before flush to prevent double-push," but the write-ahead pattern is incomplete — the watermark is written and never read, so double-push is not actually prevented. The WATERMARK_PATH module constant is computed at load time and then silently re-derived inside both functions.
Solution: Either complete the seam (read the watermark at cycle start, skip already-processed windows) or delete the entire module. The settledWindow approach (now−10m, now−5m) is already idempotent for overlapping windows, so deletion may be the honest choice. The deletion test: removing watermark.ts concentrates nothing — the complexity was never wired.
locality: double-push logic in one place or gone depth: no shallow dead exports honesty: README matches code

Problem: Both entrypoints construct a pusher with identical resource attributes (serviceName: "cf-analytics-poller", layer: "delivery", environment: "production"). If the resource identity changes, two call sites must be updated in sync.
Solution: Extract a createPollerPusher() factory that encapsulates the resource attributes. Both run-once.ts and runLoop call it. Small win — the deletion test is weak here, but it prevents resource-attribute drift.
locality: resource identity in one place leverage: one factory, two callers

Top recommendation

Candidate 1 — No Cloudflare adapter seam. Extracting a CloudflareAnalyticsClient module is the highest-leverage deepening because it unlocks testability of the entire poll cycle — the one thing this service currently lacks. The pattern already exists in the sibling fleet-probe-runner (FetchImpl / TlsImpl injection in probe.ts), so the ecosystem has a proven shape to follow. Once the adapter seam exists, Candidate 2 (separating orchestration from I/O) becomes a natural follow-up, and Candidates 3–4 are independent cleanups that can proceed in parallel.

Candidate 3 (watermark) is the strongest independent cleanup — the dead readWatermark import and the incomplete write-ahead pattern are a honesty bug that should be resolved regardless of whether the adapter refactor proceeds.
