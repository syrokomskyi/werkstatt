Problem

Three functions are exported but only proxyMatomoRequest is consumed by worker.ts — the other two are exported "for testability" but no tests exist.

Solution

Make mapProxyPath, buildForwardHeaders, and UpstreamTarget private to the module. Test the full proxy pipeline through proxyMatomoRequest with a stubbed fetch.

Wins

  • ▸ Locality: all proxy behavior concentrates behind one seam
  • ▸ Leverage: one interface, one test surface, one consumer
  • ▸ Depth: same implementation, smaller interface
  • ▸ Testability: tests cross the same seam as the worker

Problem

resolveMatomoOrigin throws at request time — a misconfigured MATOMO_CLOUD_HOST causes a 500 on the first visitor request, not a deploy-time failure.

Solution

Add a validateProxyEnv(env) function that the worker calls on the first request (cached per isolate) or in a health-check endpoint. Concentrate all env validation in one seam so operators get early, diagnostic failure instead of silent 500s.

Wins

  • ▸ Locality: env validation concentrates in one module, not scattered across request handlers
  • ▸ Leverage: one validation seam serves both health checks and request handlers
  • ▸ Depth: hides host normalization + validation + caching behind one call

Collapse the dead header denylist into the allowlist

Worth exploring in-process

Layers 1–3 are dead code. Layer 4 already excludes everything else. A reader must understand all 4 to realize only 1 matters.

After

buildForwardHeaders implementation
FORWARDED_HEADERS set (3 entries)
one loop, one check, one outcome
behind the seam
no denylist, no prefix patterns
no DROPPED_REQUEST_HEADERS constant
no drop:Cookie marker comment needed

Problem

Three filtering layers (explicit denylist, cf-* drop, x-* drop) are redundant — the allowlist in the final if already excludes everything except accept, accept-language, and content-type. The denylist looks load-bearing but changes nothing.

Solution

Delete DROPPED_REQUEST_HEADERS, the cf-* check, and the x-* check. Keep only the allowlist. The drop:Cookie marker comment — which exists solely to placate the string-scanning validator — becomes unnecessary.

Wins

  • ▸ Locality: header policy lives in one place, not three redundant layers
  • ▸ Depth: removes false complexity that makes the module look shallower than it is
  • ▸ Leverage: one allowlist is easier to audit than three denylists + one allowlist
ADR callout: The drop:Cookie comment marker exists to satisfy matomo.proxy.validate's source.includes("Cookie") check. Removing the denylist also requires updating the validator (see candidate 4).

Replace string-scanning proxy validation with behavioral checks

Problem

The validator uses source.includes() to detect forbidden patterns. It cannot distinguish the drop:Cookie comment from actual cookie forwarding. The drop: marker is a workaround that makes the validator look like it's checking behavior — it's checking text.

Solution

Replace string scanning with either AST-level checks (using the existing astro-parse.ts utility adapted for Worker source) or request-fixture tests that exercise proxyMatomoRequest with crafted requests and assert no cookies are forwarded or set.

Wins

  • ▸ Locality: validation rules concentrate in one behavioral check, not scattered string matches
  • ▸ Leverage: one fixture suite validates path, headers, cache, and privacy policy simultaneously
  • ▸ Depth: validator understands code structure instead of surface text
  • ▸ Removes: the drop: marker workaround and its cognitive load

Top recommendation

Narrow the proxy module interface

This is the highest-leverage change because it unlocks the others. Making mapProxyPath, buildForwardHeaders, and UpstreamTarget private to proxy.ts deepens the module immediately — same implementation, smaller interface. It also creates the natural test seam for request-fixture tests (candidate 4's behavioral validation) and makes the dead denylist (candidate 3) a private cleanup with no interface impact.

The proxy is 112 lines with 3 exports and zero tests. Collapsing to 1 export and adding fixture tests through that seam is a single focused change that increases depth, locality, and leverage simultaneously.
