# Agentic Internet Readiness — Multi-Layer Roadmap for warpgogol-com

> **Status:** Exploration — prepared for RFC drafting
> **Date:** 2026-08-10
> **Source:** Cloudflare blog post "Agentic Internet" + operator elaboration
> **Scope:** All sites created via Werkstatt; first target: `warpgogol-com` (mission `m000047`)
> **Target site state:** `missions/warpgogol-com-m000047/workpiece/`

---

## 1. The Four Layers

The Cloudflare article defines four layers of agent readiness. Here's how warpgogol-com maps today:

| Layer | Concept | Status | Details |
| --- | --- | --- | --- |
| **Readable** | Compact, structured content (Markdown over HTML) | ✅ Strong | `llms.txt`, `llms-full.txt`, Markdown twins, JSON-LD, knowledge envelopes |
| **Discoverable** | AEO — agents can find the site and its capabilities | ✅ Strong | `robots.txt`, `sitemap.xml`, `.well-known/agent.json`, `api-catalog`, `server-card.json`, `agent.openapi.json` |
| **Callable** | WebMCP / OpenAPI — agents can call explicit tools | ⚠️ Infrastructure ready, **actions empty** | Full Agent Gate + MCP handler exists, but `actions: []` — no capability YAMLs |
| **Payable** | Agents can pay for content/APIs (x402) | ❌ Not implemented | No payment protocol integration; future concern |

---

## 2. Layer-by-Layer Assessment

### 2.1 Readable — ✅ Already strong

**What exists:**

- `llms.txt` (14 KB) + `llms-full.txt` (42 KB) — generated by `llms.generate` (RFC-0050, RFC-0184)
- Markdown twins for key pages: `/preis.md`, `/leistungen.md`, `/kontakt.md`, `/notausgang.md`, etc.
- Sitemap includes markdown twin alternate links (RFC-0788)
- JSON-LD via PBP semantic profile (`buildPbpSemanticProfile`):
  - `Organization` (with `schemaType` override support, RFC-0242)
  - `WebSite`, `WebPage`, `BreadcrumbList`
  - `Service` nodes (org-level + industry-specific, RFC-0492/0498)
  - `FAQPage` (RFC-0506 suppression on ratgeber depth-1)
  - `Person` nodes (founders, board, team, AI agents)
  - `Offer` + `PriceSpecification` (RFC-0147, RFC-0745 multi-currency)
  - `Article`/`BlogPosting` (RFC-0167, RFC-0506)
  - `ItemList` for initiatives, services, collections (RFC-0490)
- Knowledge envelopes: `/api/agent/v1/company.json`, `/api/agent/v1/people.json` — structured per-language JSON with `freshness` metadata
- `Content-Signal` directive in `robots.txt` (RFC-0784): `text/html, text/markdown, application/ld+json, text/plain`
- Content negotiation for Markdown (RFC-0785): Cloudflare Worker serves `.md` twins via `Accept: text/markdown`

**Gaps (minor):**

- No `Offer` knowledge envelope in `/api/agent/v1/` — pricing data exists in PBP/JSON-LD but not as a standalone agent-readable JSON file. An `offer.json` knowledge envelope would let agents fetch pricing without parsing HTML or JSON-LD.
- `llms.txt` organization name is empty (`# ` on line 1) — the `organization.name` field in the semantic model is not populated. This is a content data issue, not a code gap.

**What makes sense:**

- Add an `offer` knowledge envelope (`agent.knowledge.generate` already supports arbitrary domains — the `company` and `people` domains prove the pattern). This would give agents a dedicated `/api/agent/v1/offer.json` with per-language pricing, first-year cost, and TCO — the most common agent question for a B2B service site.
- Fix the empty organization name in `system.md` or PBP entity data (content fix, not code).

| `llms.txt` | `/llms.txt` | RFC-0050, RFC-0184, RFC-0789 | ✅ Generated, includes 4 agent discovery links |


The `server-card.json` declares:

**Gaps:**

- The OpenAPI spec has only `knowledge.*.get` paths — no action paths because `actions: []`.
- The `api-catalog` links to the MCP endpoint, but an agent discovering it would find `tools/list` returns only knowledge tools, no action tools.
- No `.well-known/agent-card.json` (the article mentions this as a higher-level agent identity card, distinct from the MCP server card). This is a minor gap — `agent.json` already serves this role.

**What makes sense:**

- Discoverable is essentially complete. The main improvement is filling the Callable layer so that the discovery artifacts point to real, callable tools rather than empty arrays.

### 2.3 Callable — ⚠️ Infrastructure ready, actions empty

This is the **highest-impact gap**. The entire server-side pipeline is built, tested, and deployed — but no capability YAML files exist, so `actions: []` everywhere.

**What exists (infrastructure):**

| Component | Location | RFC | Role |
| --- | --- | --- | --- |
| Agent Gate runtime | `packages/werkstatt/src/agent-gate/` | RFC-0290 | HTTP + MCP JSON-RPC handler |
| MCP handler | `packages/werkstatt/src/agent-gate/mcp/handler.ts` | RFC-0290 | `tools/list`, `tools/call`, `initialize` |
| Action pipeline | `packages/werkstatt/src/agent-gate/action-pipeline.ts` | RFC-0290 | Composable validation steps |
| Schema validator | `packages/werkstatt/src/agent-gate/actions.ts` | RFC-0288 | Closed JSON-Schema subset validation |
| Rate limiter | `packages/werkstatt/src/agent-gate/limits.ts` | RFC-0291 | Per-IP fixed window |
| Astro adapter | `packages/werkstatt/src/agent-gate/astro.ts` | RFC-0290 | QStash dispatch, fetch-based knowledge reads |
| Capability catalog schema | `packages/werkstatt-site/src/domain/ontology/schemas/capability.ts` | RFC-0288 | Zod schema for `CapabilityRecord` |
| Capability resolver | `packages/werkstatt-site/src/domain/share/agent/capability.ts` | RFC-0288 | `resolveActiveCapabilities` — gates by entitlements, sections, disabled list |
| Manifest builder | `packages/werkstatt-site/src/domain/share/agent/manifest.ts` | RFC-0286 | `buildAgentSurfaceManifest` — assembles knowledge + actions |
| OpenAPI projection | `packages/werkstatt-site/src/domain/share/agent/openapi.ts` | RFC-0289 | `formatAgentOpenApi` — projects manifest to OpenAPI 3.1 |

| Generate/validate commands | `packages/werkstatt-site/src/checks/agent/` | RFC-0286..0291, 0783 | `agent.manifest.generate`, `agent.openapi.generate`, `agent.api-catalog.generate`, `agent.mcp-card.generate`, `agent.capability.validate` |
| Pipeline wiring | `packages/werkstatt-site/src/checks/command-tables/` | RFC-0787 | Generators wired into `build.prepare` + `build.check` |
| Unit tests | `packages/werkstatt/src/agent-gate/tests/` | — | `gate.test.ts` (MCP), `actions.test.ts` (validation) |
| `agent.actions` entitlement | `system.md` line 38 | RFC-0288 | ✅ Already enabled for warpgogol-com |
| `send-message` section archetype | `packages/werkstatt-site/src/domain/ontology/archetypes/sections/send-message.yaml` | — | ✅ Renders on `/kontakt/` and `/verantwortungsvolle-empfehlungen/` |

**What is missing:**

- **No `capabilities/` directory** — `packages/werkstatt-site/src/domain/ontology/capabilities/` does not exist. The `loadCapabilityCatalog` function in `agent-capability.ts` reads from this directory but finds no YAML files.
- **`lead.submit` exists only as a test fixture** — `gate.test.ts` defines `LEAD_SUBMIT: CapabilityRecord` inline, but there is no `lead.submit.yaml` in the catalog.
- **`agent.json` actions is empty** — `"actions": []` because `resolveActiveCapabilities` returns `[]` when the catalog is empty.
- **OpenAPI has no action paths** — only `knowledge.company.get` and `knowledge.people.get`.
- **MCP `tools/list` returns only knowledge tools** — no `action.lead.submit` tool.

**The dispatch pipeline is also ready:**

The Agent Gate's `astro.ts` adapter wires `ports.dispatch.send` to QStash (RFC-0181):
```ts
dispatch: {
  async send(event) {
    const publishRequest = buildQstashPublish(event, {
      token: UPSTASH_QSTASH_TOKEN ?? "",
      callbackUrl: `${manifest.baseUrl}/api/integration-route`,
    });
    const res = await fetch(publishRequest);
    if (!res.ok) throw new Error(`QStash publish responded ${res.status}`);
    return { accepted: true, eventId: event.eventId };
  },
}
```

This means a validated `lead.submit` action would:
1. Be validated against the capability's JSON Schema (message: string, minLength 10, maxLength 4000)
2. Be rate-limited (per-IP, per-minute)
3. Be normalized into an `IntegrationEvent` with `kind: "lead"`, `source: "agent"`
4. Be published to QStash for reliable delivery
5. Arrive at `/api/integration-route` — the same substrate the human `send-message` form uses

**What makes sense (RFC-0798):**

Create the first real capability: `lead.submit`. This requires:

1. **`packages/werkstatt-site/src/domain/ontology/capabilities/lead.submit.yaml`** — the capability definition (id, version, kind, title, description, input schema, output schema, integration config, requires, humanEquivalent, limits)
2. **Wire the Agent Gate route** — ensure `/api/agent/actions/lead.submit` and `/api/agent/mcp` are served by the Astro API routes (the `astro.ts` adapter exists but needs to be imported in the site's `src/pages/api/`)
3. **Verify the build pipeline** — `agent.manifest.generate` should now produce non-empty `actions[]`, and `agent.openapi.generate` should include `POST /api/agent/actions/lead.submit`

The `lead.submit` capability should match the test fixture shape:
```yaml
id: lead.submit
version: 1
kind: action
title:
  de: "Anfrage senden"
  en: "Submit an inquiry"
description:
  de: "Übermittelt eine Anfrage."
  en: "Delivers an inquiry."
input:
  type: object
  required: [message]
  additionalProperties: false
  properties:
    message:
      type: string
      minLength: 10
      maxLength: 4000
    name:
      type: string
      maxLength: 200
    email:
      type: string
      format: email
      maxLength: 200
    phone:
      type: string
      maxLength: 100
output:
  type: object
  additionalProperties: false
  properties:
    accepted:
      type: boolean
    eventId:
      type: string
integration:
  eventKind: lead
  source: agent
requires:
  entitlements: []
  sections: [send-message]
humanEquivalent:
  sectionType: send-message
limits:
  perMinutePerIp: 10
  maxPayloadBytes: 16384
```

**What also makes sense (RFC-0799, browser-side WebMCP):**

The article describes `document.modelContext.registerTool` as a browser-side API for agents to discover and call tools directly from the page context. This is experimental (Chrome origin trial) and acts as a progressive enhancement on top of the server-side MCP endpoint.

For warpgogol-com, this would mean:
1. A small `<script>` on `/kontakt/` that registers `lead.submit` via `document.modelContext.registerTool`
2. The tool's handler would `fetch('/api/agent/actions/lead.submit', ...)` — the same endpoint the server-side MCP uses
3. No new backend logic — just a thin browser adapter

This is lower priority than the server-side capability but worth a separate RFC to define the pattern.

### 2.4 Payable — ❌ Not implemented

**What exists:**

- No x402 protocol integration
- No micropayment layer
- No agent payment negotiation

**What the article describes:**

The "Payable" layer enables agents to pay for content or API access using protocols like x402 (HTTP 402 Payment Required + crypto micropayments). This is relevant for:
- Paywalled content (not applicable to warpgogol-com — all content is free)
- API rate limit bypass via payment (potentially applicable — agents could pay for higher rate limits)
- Premium agent-only endpoints (future — e.g., structured project evidence access)

**What makes sense:**

This is a **future concern** for warpgogol-com. The site's business model is subscription-based (human-facing), not pay-per-API-call. The Payable layer becomes relevant when:
1. Agents need to access premium content (e.g., detailed project case studies behind a paywall)
2. The site offers tiered API access (free tier with rate limits, paid tier without)
3. Agents negotiate service contracts (e.g., "create a website for this client" — the agent pays for the setup)

For now, the right move is to **document the architectural placeholder** — ensure the Agent Gate's response pipeline can include a `402 Payment Required` response in the future, and that the capability schema can express payment requirements — without implementing the payment protocol itself.

**RFC placeholder:** RFC-0800 (future) — "Add payable capability metadata and 402 response support to the Agent Gate"

## 3. Proposed RFC Roadmap

| RFC | Layer | Title | Priority | Effort |
| --- | --- | --- | --- | --- |
| RFC-0798 | Callable | Add `lead.submit` as the first real capability in the closed catalog | **High** | Medium — new YAML file + route wiring + pipeline verification |
| RFC-0799 | Callable | Add browser-side WebMCP (`document.modelContext.registerTool`) as progressive enhancement | Medium | Small — thin client script, no backend changes |
| RFC-0800 | Payable | Add payable capability metadata and 402 response support to the Agent Gate | Low | Medium — schema extension + response pipeline + payment protocol adapter |
| (content fix) | Readable | Fix empty organization name in `llms.txt` / `system.md` | **High** | Trivial — content data fix |
| (content task) | Readable | Add `offer` knowledge envelope for pricing data | Medium | Small — new domain in `agent.knowledge.generate` |

### Dependency graph

```
RFC-0798 (lead.submit capability)
  ├── enables: non-empty OpenAPI, MCP tools/list, agent.json actions
  ├── unblocks: RFC-0799 (WebMCP registers the same tool)
  └── prerequisite: RFC-0800 (payable adds payment to existing capabilities)
```

### Priority rationale

1. **RFC-0798 first** — it activates the entire Callable layer. Every discovery artifact already points to the MCP endpoint and OpenAPI spec; making them non-empty is the single highest-leverage change.
2. **Content fixes** (org name, offer envelope) — trivial, immediate agent experience improvement.
3. **RFC-0799** — progressive enhancement, only relevant once the server-side tool exists.
4. **RFC-0800** — future concern, not actionable until the business model requires it.

## 4. What an AI agent experience looks like after RFC-0798

### Discovery flow

1. Agent fetches `https://warpgogol.com/llms.txt`
2. Sees agent discovery links → fetches `/.well-known/agent.json`
3. Reads the manifest: knowledge domains (`company`, `people`), actions (`lead.submit`), interfaces (OpenAPI, MCP)
4. Fetches `/.well-known/agent.openapi.json` — sees `POST /api/agent/actions/lead.submit` with full schema
5. Alternatively fetches `/.well-known/mcp/server-card.json` — sees MCP endpoint at `/api/agent/mcp`

### Knowledge flow

1. Agent calls `GET /api/agent/v1/company.json` — gets structured company data with per-language payloads
2. Agent calls `GET /api/agent/v1/people.json` — gets team/founder data
3. (Future) Agent calls `GET /api/agent/v1/offer.json` — gets pricing data

### Action flow (MCP)

1. Agent sends `POST /api/agent/mcp` with `{"method": "tools/list"}`
2. Receives: `knowledge.company.get`, `knowledge.people.get`, `action.lead.submit`
3. Agent sends `POST /api/agent/mcp` with:
   ```json
   {
     "method": "tools/call",
     "params": {
       "name": "action.lead.submit",
       "arguments": {
         "message": "Mein Kunde braucht eine Website für seine Tischlerei...",
         "name": "AI Agent",
         "email": "agent@example.com"
       }
     }
   }
   ```
4. Agent Gate validates schema, checks rate limit, builds `IntegrationEvent`, publishes to QStash
5. Agent receives: `{"content": [{"type": "text", "text": "{\"accepted\":true,\"eventId\":\"...\"}"}]}`

### Action flow (HTTP)

1. Agent sends `POST /api/agent/actions/lead.submit` with JSON body
2. Same validation → same QStash dispatch → same response shape

## 5. Trust and abuse controls (already implemented)

The article emphasizes "Trust instead of 'bots are bad'". The Werkstatt Agent Gate already implements:

| Control | Location | RFC |
| --- | --- | --- |
| Per-IP rate limiting | `limits.ts` (fixed window, per-capability, per-IP) | RFC-0291 |
| Payload size cap | `action-pipeline.ts:checkPayloadSize` | RFC-0291 |
| Schema validation (closed subset) | `actions.ts:validateAgainstCapabilitySchema` | RFC-0288 |
| Agent identity passthrough | `action-pipeline.ts:buildAndDispatchEvent` (`_agentIdentity`) | RFC-0290 |
| Idempotency ledger | `qstash.ts:restRedisLedger` (Upstash Redis SET NX) | RFC-0181 |
| Reliable delivery | QStash publish with dedup + retries | RFC-0181 |
| Crawler blocklist | `robots.txt` (nikto, nmap, sqlmap) | RFC-0052 |
| AI policy declaration | `ai.txt` + `system.md` (allow with usage rights) | RFC-0051 |

**Gap:** No agent identity verification (e.g., signed agent credentials, Cloudflare AI Bot verification). The `_agentIdentity` field is passthrough — it trusts whatever the agent sends. A future RFC could add verification.

---

## 6. Summary

The Werkstatt platform has built a **production-grade agent surface** that covers the Readable and Discoverable layers completely, and has the full server-side infrastructure for the Callable layer — but the Callable layer is empty because no capability YAML files have been authored.

**The single highest-impact action is RFC-0798: create `lead.submit` as the first real capability.** This activates the entire pipeline: OpenAPI gets action paths, MCP `tools/list` returns action tools, `agent.json` gets non-empty actions, and AI agents can submit inquiries on behalf of human users through a validated, rate-limited, identity-tagged, reliably-delivered channel.

The Payable layer is a future concern that depends on business model evolution, not technology readiness.
