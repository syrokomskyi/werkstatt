# ADR-0013: Harden generated timestamp validator and ownership map

## Context

RFC-0602 introduced `generated.timestamp.validate` to detect volatile timestamp patterns (`new Date()`, `Date.now()`, `process.env.BUILD_TIMESTAMP`) in generator source modules. The validator runs in the `build.check` pipeline (`packages/os/site-kernel-checks/src/pipelines/build-check.ts`) and scans modules listed in `GENERATOR_OWNERSHIP_MAP` (`packages/os/site-kernel-checks/src/generator-ownership.ts`).

Three gaps were discovered during mission `warpgogol-com-m000022` close failure:

1. **Warning-only mode** — the pipeline step calls `generated.timestamp.validate` without `--mode fail`, so the default `"warning"` mode produces warnings instead of errors. Volatile timestamps in `entitlements.ts` and `open-source-page.ts` were not caught as hard failures and caused a dirty workpiece cycle that blocked `mission.close`.
2. **Stale allowlist entry** — `packages/os/site-kernel-codegen/src/open-source-page.ts` remains in `TIMESTAMP_ALLOWLIST` in `generated-timestamp-validate.ts` even though all volatile timestamp patterns (`serialNumber: crypto.randomUUID()`, `timestamp: new Date().toISOString()`) were removed from the file.
3. **Missing ownership registration** — `src/freshness.generated.yaml` (generated by `content.freshness.validate` in `packages/os/site-kernel-checks/src/content-freshness.ts`) is not registered in `GENERATOR_OWNERSHIP_MAP`. This means the timestamp validator never scans `content-freshness.ts`, `ownership.sync.validate` may flag the file as unowned, and `generated.files.validate` does not check its existence.

## Decision

Harden the generated timestamp validator and ownership map with three targeted fixes in `packages/os/site-kernel-checks`.

- Switch `generated.timestamp.validate` to `--mode fail` in the `SITES_BUILD_CHECK_PIPELINE` so volatile timestamps in generator source are hard errors, not warnings.
- Remove the stale `TIMESTAMP_ALLOWLIST` entry for `packages/os/site-kernel-codegen/src/open-source-page.ts`.
- Register `src/freshness.generated.yaml` in `GENERATOR_OWNERSHIP_MAP` with `command: "content.freshness.validate"` and `module: "packages/os/site-kernel-checks/src/content-freshness.ts"`.

## Justification

The warning-only mode was the original RFC-0602 default to allow gradual migration. All known volatile timestamps in generator source files have now been removed (commit `8cdd438`). Switching to fail mode is safe — no current generator source triggers TS-TIME-01. Keeping warning mode risks reintroducing volatile timestamps silently, as happened with `entitlements.ts` and `open-source-page.ts`.

The stale allowlist entry for `open-source-page.ts` is dead code — the file no longer contains any volatile timestamp pattern. Leaving it creates false confidence that the file is exempt when it should simply pass the scan like any other generator module.

The missing `freshness.generated.yaml` registration is a gap in RFC-0087's single-owner invariant. The file is generated by `content.freshness.validate` but has no ownership entry, so the timestamp validator cannot catch volatile timestamps in its generator, and `ownership.sync.validate` may flag it as an unowned file on disk.

Alternatives considered:

- Keep warning mode and rely on manual review — rejected because the mission close failure proved manual review did not catch the issue.
- Add a separate lint for ownership map completeness — rejected as over-engineering; the existing `GENERATOR_OWNERSHIP_MAP` is the single registry and adding the missing entry is sufficient.

## Consequences

- Positive: volatile timestamps in generator source are now hard build failures, preventing dirty workpiece cycles before they block `mission.close`.
- Positive: `freshness.generated.yaml` is now covered by ownership validation, timestamp scanning, and generated-files validation.
- Positive: the allowlist is clean — no stale entries that mask removed code.
- Negative: any future generator that legitimately needs a timestamp (e.g. signing proofs) must be added to `TIMESTAMP_ALLOWLIST` with a justification, same as before.
- Technical debt: the timestamp validator still scans only the `module` file listed in `GENERATOR_OWNERSHIP_MAP`, not files imported by that module. A generator that delegates timestamp generation to a helper file (as `entitlements.ts` delegated to `share/src/entitlement.ts`) would not be caught. This is postponed to a future enhancement.

## Evolution

Revisit if a generator legitimately requires a volatile timestamp — add it to `TIMESTAMP_ALLOWLIST` with a justification entry. If the transitive-import scanning gap becomes a source of missed violations, enhance `scanModuleForTimestamps` to trace imports from the registered module file. This ADR is implemented alongside the mission close fix for `warpgogol-com-m000022`.
