# Engineering: Passport Signing & Keys

> RFC-0028 / DNA-31..34

---

## Architecture overview

The Cosmic Passport pipeline consists of three artifacts written to `dist/.well-known/`:

| File                   | Description                                    |
| ---------------------- | ---------------------------------------------- |
| `cosmic-passport.json` | Signed build provenance + Nebula Score summary |
| `nebula-score.json`    | Full Nebula Score pillar breakdown             |
| `cosmic-star-map.svg`  | Deterministic architecture diagram             |

All three are generated by the `passport.emit` command during CI. The passport JSON is signed with an Ed25519 Verifiable Credential (W3C VC Data Model, `Ed25519Signature2020`).

---

## Command pipeline

```
nebula.score.compute   →  computes NebulaScore from Lighthouse/Axe/DNA results
star-map.render        →  generates deterministic SVG from system manifest + UI registry
passport.emit          →  signs and writes all three artifacts
passport.verify        →  verifies signature and system hash post-deploy
pulsar.heartbeat       →  POSTs a heartbeat to heartbeatUrl (optional)
```

Run all commands via:

```bash
rtk pnpm kernel nebula.score.compute --appDir apps/<app>
rtk pnpm kernel star-map.render --appDir apps/<app>
rtk pnpm kernel passport.emit --appDir apps/<app>
rtk pnpm kernel passport.verify --appDir apps/<app>
```

## Nebula Score pillars

The composite score (0–100) is a weighted sum of four pillars:

| Pillar                   | Weight | Source                             |
| ------------------------ | ------ | ---------------------------------- |
| Performance              | 30 %   | Lighthouse performance score × 100 |
| Accessibility            | 30 %   | Axe violations → scaled 0-100      |
| Content Health           | 20 %   | Content check pipeline pass rate   |
| Architectural Compliance | 20 %   | DNA check pipeline pass rate       |

Weights are defined in `packages/nebula/src/weights.ts` (version `NEBULA_WEIGHTS_VERSION`). The module asserts at load time that weights sum to exactly 1.0.

## Ed25519 key management

### Key file location

Each app stores its public key at:

```
apps/<app>/public/.well-known/cosmic-passport-key.json
```

This file is committed to the repository. It contains an array of keys; each entry has:

```json
{
  "id": "<appId>#v1",
  "type": "Ed25519VerificationKey2020",
  "controller": "https://<domain>/.well-known/cosmic-passport-key.json",
  "publicKeyMultibase": "z<base58btc-encoded-key>",
  "active": true,
  "addedAt": "<ISO-8601>"
}
```

### Private key storage

The private key is **never written to disk** — only the public key enters version control. The private key is stored as a GitHub Actions secret (`PASSPORT_PRIVATE_KEY`) and passed to `passport.emit` via the `--privateKey` flag or `PASSPORT_PRIVATE_KEY` environment variable.

### Key rotation

```bash
rtk pnpm kernel passport.key.rotate --appDir apps/<app>
```

1. Generates a new Ed25519 keypair.
2. Prints the new private key to stdout (**save it immediately**).
3. Adds the new public key as the active entry in `cosmic-passport-key.json`.
4. Marks the previous key as `"active": false` (retained for historical verification).
5. Bumps the `keyVersion` in the file.

Update the `PASSPORT_PRIVATE_KEY` GitHub Actions secret with the printed value before merging the public key file update.

## Verifiable Credential structure

The signed VC embedded in `cosmic-passport.json` follows the W3C VC Data Model:

```json
{
  "@context": [
    "https://www.w3.org/2018/credentials/v1",
    "https://w3id.org/security/suites/ed25519-2020/v1"
  ],
  "type": ["VerifiableCredential", "WarpgogolPassportCredential"],
  "issuer": "https://<domain>/.well-known/cosmic-passport-key.json",
  "issuanceDate": "<ISO-8601>",
  "credentialSubject": {
    "appId": "<appId>",
    "systemHash": "<sha256-of-system.yaml>",
    "commitSha": "<git-commit-sha>",
    "issuedAt": "<ISO-8601>"
  },
  "proof": {
    "type": "Ed25519Signature2020",
    "created": "<ISO-8601>",
    "verificationMethod": "<appId>#<keyVersion>",
    "proofPurpose": "assertionMethod",
    "proofValue": "z<base58btc-signature>"
  }
}
```

The `credentialBytes()` function in `packages/passport/src/sign.ts` produces a **deterministic, sorted-key JSON** serialization for signing — no timestamps or random values enter the signed payload.

## Star Map determinism

The `cosmic-star-map.svg` is byte-stable for identical inputs:

- Node positions use a **mulberry32 PRNG** seeded from `djb2(appId)`.
- No `Date.now()` or random values appear in deterministic SVG fields.
- The only non-deterministic field is the metadata comment, which uses manifest data.

This means `git diff` on the SVG artifact is meaningful — any position change indicates a genuine change to the component graph.

## Security notes

- Private keys never leave the CI environment.
- The `rotateKey()` function cannot be used to read or export existing private keys.
- The `verifyCredential()` function is safe to run in any environment — it only needs the public key.
- The VC proof covers `appId`, `systemHash`, and `commitSha` — sufficient to detect tampering with build outputs or provenance claims.
- `heartbeatUrl` should be rate-limited on the server side to prevent abuse.

## Agent surface (RFC-0291)

The same passport keypair also signs the **Agent Surface** artifacts (`agent.json`, knowledge envelopes, OpenAPI document). The signing command `agent.surface.sign` (RFC-0308) uses `PASSPORT_SIGNING_KEY` and `cosmic-passport-key.json` identically to the passport VC flow — no separate key or rotation procedure exists for the agent surface.

**Key rotation blast radius:** when the passport key is rotated via `passport.key.rotate`, the new key automatically covers agent surface artifacts on the next `agent.surface.sign` run. Third parties verify agent surface signatures with `agent.manifest.verify` (RFC-0291), which reads the same `cosmic-passport-key.json` public key file.

**Post-deploy verification:** `pnpm exec site-kernel run agent.manifest.verify --site <site> --url https://<origin>` fetches `/.well-known/agent.json` + the passport key from the live origin and verifies the signature, contentHash, and ref-reachability — mirroring `passport.verify` for the agent surface.
