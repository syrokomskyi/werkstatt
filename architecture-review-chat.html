Problem. The chat-widget section is a shallow pass-through for 202 lines of delivery logic — QStash verification, Redis idempotency, channel fan-out, CRM routing, email sending — that belongs behind the integration port.

Solution. Move the delivery callback into @warpgogol/share/integration as a createDeliveryHandler(secrets, extraAdapters) factory. The section's API route becomes a 5-line adapter that calls it. The manifest's api: block shrinks to the inbound route only.

Wins

  • • Locality: delivery logic concentrates in the integration module
  • • Leverage: one delivery handler, N source sections call it
  • • Interface shrinks: section owns render + click-to-load only
  • • Tests hit one interface: createDeliveryHandler testable without Astro
  • • Delete 362 lines from the section directory

2. Make the chat adapter self-describing — eliminate hardcoded adapter maps

Strong ports & adapters
packages/chat/src/port.ts (ChatWidgetAdapter interface)
packages/chat-adapter-uchat/src/index.ts
packages/os/site-kernel-checks/src/chat.ts (REQUIRED_OPTIONS)
packages/os/site-kernel-checks/src/consent.ts (CHAT_VENDOR_ORIGINS)
packages/ui/src/sections/chat-widget/chat-widget-section.client.ts (ADAPTER_LOADERS)

Before

uchat adapter
id, load(), open()
adapter facts live elsewhere
chat.ts: REQUIRED_OPTIONS["uchat"] = [["widgetId","scriptUrl"]]
consent.ts: CHAT_VENDOR_ORIGINS["uchat"] = ["uchat.com.au"]
client.ts: ADAPTER_LOADERS["uchat"] = () => import(...)
4 files must stay in sync manually

After

uchat adapter
id, load(), open()
requiredOptions: [["widgetId","scriptUrl"]]
vendorOrigins: ["uchat.com.au"]
adapter owns its own facts
chat.ts: reads adapter.requiredOptions
consent.ts: reads adapter.vendorOrigins
client.ts: static import map (code-split)
1 source of truth per fact

Problem. Adapter-specific knowledge — required options and vendor origins — leaks across seams into the validator (chat.ts) and the consent check (consent.ts). Adding a new adapter means manually syncing 4 files outside the adapter package.

Solution. Extend ChatWidgetAdapter with optional requiredOptions?: string[][] and vendorOrigins?: readonly string[]. The validator and consent check read from a registry built from adapter metadata. The adapter is the single source of truth for its own facts.

Wins

  • • Locality: adapter facts concentrate in the adapter
  • • Leverage: one interface, N validators read from it
  • • Delete 2 hardcoded maps (REQUIRED_OPTIONS, CHAT_VENDOR_ORIGINS)
  • • Adding an adapter = 1 package + 1 catalog entry (was 4 files)
ADR note: The static ADAPTER_LOADERS map in chat-widget-section.client.ts must stay in the host — Vite needs static import() specifiers for code-splitting. This candidate moves metadata (required options, origins) into the adapter, not the import specifiers. The loader map is a separate sync point addressed by making ChatAdapterLoaders typed as Record<ChatAdapterId, ...> so TypeScript catches missing entries at compile time.

3. Delete the hand-written ChatWidgetConfig interface — let the Zod schema be the single source of truth

Worth exploring in-process
packages/chat/src/port.ts (ChatWidgetConfig interface)
packages/chat/src/config.ts (ChatWidgetConfigSchema, ChatWidgetConfigParsed)

Before

ChatWidgetConfig
hand-written interface (port.ts)
appId, locale, adapter, options
drift risk — two identical shapes
ChatWidgetConfigSchema
Zod schema (config.ts)
appId, locale, adapter, options
ChatWidgetConfigParsed = z.infer<schema>

After

ChatWidgetConfigSchema
Zod schema (config.ts)
appId, locale, adapter, options
single source of truth
ChatWidgetConfig = z.infer<schema>
port.ts re-exports the type

Problem. ChatWidgetConfig in port.ts is a hand-written interface structurally identical to the Zod schema in config.ts. Two identical shapes maintained separately — a field added to one but not the other silently drifts.

Solution. Delete ChatWidgetConfig from port.ts. Export type ChatWidgetConfig = z.infer<typeof ChatWidgetConfigSchema> from config.ts and re-export from the port. The schema is the single source of truth.

Wins

  • • Delete one duplicated interface
  • • Locality: config shape lives in one module
  • • No drift between hand-written type and schema
  • • Deletion test: complexity concentrates, not moves

Top recommendation

Candidate 1 — Extract the delivery callback

Strong

The chat-widget section is a god-module: it owns a first-party launcher UI and 362 lines of integration delivery logic (QStash verification, Redis dedup, channel fan-out, CRM routing, email, billing routing) that belongs behind the integration port. Extracting the delivery callback into a createDeliveryHandler() factory deepens the integration module and shrinks the section's interface to what it should own: render a launcher, wire click-to-load. This is the highest-leverage deepening because it concentrates 202 lines of delivery orchestration into one testable interface and removes 3 API routes + 20 secrets from the section's manifest.
